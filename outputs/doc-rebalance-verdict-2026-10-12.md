# 文档减负：问题定性、事实核查、方案取舍

> 本文只做评估与建议，**未执行任何代码/文档改动**。
> 评审对象：① `outputs/doc-rebalance-plan.md`（WorkBuddy 版）② `outputs/doc-rebalance-position-2026-10-12.md`（Qoder 版）③ `~/Desktop/通行做法.md`（方法论版）。

---

## 一、核心问题到底是什么（定性）

一句话：**我们烧时间的地方不是"检查"，是"把同一件事抄成好几份文档，然后反复订正"。**

拆开看，时间在三个地方漏掉：

| 漏点 | 表现 | 体量证据 |
|---|---|---|
| **A. 复核流程产文档** | 一次 fix 配一份 REVIEW，再由他方复核、再订正，形成 3 条提交链 | 2026-10-11 一天产出 6 份 REVIEW；REVIEW 类共 21 份 / 4247 行，占 `docs/` 一级 **30%** |
| **B. 台账证据散文** | 同一个 bug 的结论，在审核文档、台账、日报、INDEX 里各写一遍，再各自订正 | 台账 #31/#35/#36 单格数百字；提交史里"登记/订正/核实"类高频 |
| **C. 文档成了承重墙** | 代码注释指 `docs/PROPOSAL-xxx.md` 当判据，文档挪不动、删不得 | `src/` 内 32 处注释引用 `docs/`；AGENTS.md:125 把 PROPOSAL 列为"改前必读" |

**不是问题（或不是主要问题）**：核心文档多。真正活的核心只有 8 份、3003 行——这个量对一个 Tauri+Vue+ProseMirror 项目是正常偏少的。

## 三、三方方案评估

| 维度 | WorkBuddy 版 | Qoder 版 | 通行做法版 |
|---|---|---|---|
| 问题定性 | 文档多 + 死链扫描税 | **抄写税 + 把锁绿当结论** | 把文档当成代码的同步副本 |
| 证据 | 部分未实跑，误判税源 | ✅ 逐条可重跑、行号可核 | 无本仓数据 |
| 可执行性 | 2 条有问题（指错行 / 改不动） | ✅ 三条均可当场核对 | ⚠️ 直接照搬会踩本仓两个坑 |
| 结构洞见 | 弱 | 中 | ✅ 强（ADR / 生命周期 / 事件驱动） |
| 对"锁"的判断 | 未提 | ✅ 锁不是束缚源，束缚源是"先读某文档"关卡 | 硬锁/软锁/无锁分层 |

**结论：用通行做法定方向，用 Qoder 版定执行顺序。**

- WorkBuddy 版保留一条思路（"什么时候动文档"），**作废它的税源诊断与两条执行项**（死链税、改记忆频率）。
- 通行做法要打两个折：
  1. **不要全套自动生成**。`CHANGELOG` 保持手写（发版低频，脚本收益 < 维护成本）；只把 `INDEX.md` 改成脚本生成（当前手工维护 58 处引用，是纯税）。
  2. **ADR 目录只收"已拍板 + 不可逆"的决策**。否则 ADR 会长成第二套 PROPOSAL，税翻倍。未拍板的进台账，不写文档。

## 四、我的三点增量（三家都没说透）

1. **最大税源既不是死链，也不只是台账，是 A（复核流程的纸面产物）**。
   REVIEW 类 4247 行 = 30% 体量，且每条 fix 后面拖着"审核 → 复审 → 订正"链条。
   用户已明确否决"砍复核轮次"（Qoder 版 §〇 已改口保留），所以正确动作是：**复核照做，但结论不落 `docs/`**，落 commit message 或台账一行指针。这一刀下去体感最明显。

2. **归档的前置有两条，不只一条**。
   Qoder 只提了① 体检语料问题。还有② **21 份 REVIEW 结论吸收情况未核实** —— 归档前逐份比对，否则是"减负"名义下的信息销毁。

3. **"锁"不用减，要改的是验收口径**。
   用户对锁的体感疲劳，根源是拿"集合守恒类锁"（如 `mark-delimiter-coverage`，只证明有分支）当成交活结论。这类锁只能兜底。
   采纳 Qoder 的纪律：交活写"用户这么操作得到 X"，不写"N 条锁转绿"。

## 五、建议执行顺序（逐批批准，本轮不执行）

### 阶段 0：给自己松绑（零信息丢失，最便宜）

1. 改 AGENTS.md 四处：`:81` 删"改后跑死链扫描"、`:134` 删"联动文档一起看"、`:187` 整行删、`:189` 删"并更新文档"后半。
2. 新增 `docs-lint.spec.ts`（扫 `](…)` 链接 + 源码注释里的 `docs/xxx.md` 指针，目标不存在即红），挂 `bun run test`。
   ⚠️ 上线前先跑一次拿基线：历史文档里可能已有死链，先一次性修掉再挂硬断言，否则会一上来红一片。
3. AGENTS.md §3 敏感区表里"先读某提案"的格子改指代码位置（如 `list-demote.ts`）——**代码在哪契约在哪**。

**做完的用处**：护栏变强（每次跑测试全量校验），"改完要不要扫一遍"这个人工判断彻底消失。

### 阶段 0.5：归档的两条前置（不做会炸）

4. `fidelity-scan.spec.ts` 的 `SKIP_DIRS` 加 `archive`（或改显式清单）。否则阶段 1 一动文件，体检硬断言立刻红，执行者会误判成"减负搞坏了保真"。
5. 逐份比对 21 份 REVIEW 的结论是否已进 KNOWN-ISSUES/LESSONS/AGENTS，未吸收的先抄结论再归档。

### 阶段 1：归档（做完这步，`docs/` 一级从 14158 行降到 ~6400 行）

6. REVIEW-\* 21 份、IME-\* 3 份、`00-今日修改总览` / `TODO-*` / `HANDOVER.md` / `ui-redesign-handover.md` → `git mv` 进 `docs/archive/`。
7. 已落地的 PROPOSAL（cell-fidelity / list-\* 系列）结论进 KNOWN-ISSUES，原件归档。

### 阶段 2：台账与索引瘦身（砍的是重复抄写）

8. `KNOWN-ISSUES.md` 每条降为三行：现象一句 / 根因一句 / 复现锁测试名。证据正文留在 commit message，台账只放指针。
9. `INDEX.md` 改脚本生成，归档区不进索引。
10. 取消日报类文档（`00-今日修改总览-*.md`），一次性快照连归档都不用。

### 阶段 3：建立长期机制

11. 建 `docs/adr/`（只追加、不修改，过期标 `superseded by`），把 `paste-compat-decision` / `cjk-boundary` / `font-handling` 迁进去。
12. 每季度 30 分钟清理：零引用归档 / 过期 PROPOSAL 归档 / 重复合并 / 记忆压缩 / ADR 标 superseded。

**结论**：**没有稳定收益，已回滚**。后续 §1.5 的排除法进一步证明：模糊、阴影、`text-wrap`、字体栈都不是这个长任务的来源——**此假设彻底推翻**。

### 1.5 根因：浏览器冷启动的一次性字形预热（2026-10-22 追加）

**决定性判据**：同一浏览器进程连续加载 3 次，每次 DOM 脏对象数完全相同（784），耗时差 **40 倍** —— 说明成本不是「每次都付」，而是「第一次才付」。

| 场景 | 第 1 次（进程冷） | 第 2 次 | 第 3 次 |
|---|---|---|---|
| 4× CPU 降速 | **1411 ms** | 33 ms | 29 ms |
| 不降速 | 245 ms | 5 ms | 4 ms |

**排除法**（每次只改一个变量，均在冷进程下测首次布局）：

| 改动 | 冷启动布局耗时 | 结论 |
|---|---|---|
| 基线 | 1411 ms | — |
| 去掉全部 CSS | 1023 ms | CSS 不是主因 |
| 去掉全部图片 | 1399 ms | 图片不是主因 |
| 去掉 `main.js` | 1425 ms | JS 不是主因 |
| 去掉内联 SVG | 1366 ms | SVG 不是主因 |
| 字体栈换成单一系统字体 | 1465 ms | 字体选择不是主因 |
| `text-wrap: balance/pretty` 全关 | 1390 ms | 换行算法不是主因 |
| `backdrop-filter` 全关 | 1273 ms | 模糊不是主因 |

**对照实验（决定性）**：

| 页面 | 节点 | 不同汉字数 | 冷启动首次布局 |
|---|---|---|---|
| 本站真实页面 | 673 | ~700 | 1411 ms |
| 同文案 + 极简结构（无 CSS / 图 / JS） | 587 | 589 | 710 ms |
| 同结构 + 同字数，但只用 16 个重复汉字 | 587 | 16 | **101 ms** |
| 340 段重复短句 | 1704 | ~40 | 256 ms |

**结论**：成本 ∝ **不同字形数量**，与结构、样式、图片、脚本全都无关。这是 Chrome 首次遇到这批汉字时建立字形度量/栅格缓存的固定开销 —— **页面侧无解**（除非少写字）。

**实际影响**

- 同一会话内的后续访问：4× 降速下 30 ms 内，无感。
- 一次浏览器会话里**第一次**打开：4× 降速 ≈ 中低端手机，约 0.8 s 的首次排版；实体机上表现为「第一次打开顿一下，之后顺畅」。
- 真机复核方法：手机 Chrome 远程调试，冷启动浏览器后打开一次记长任务，再刷新一次对比；两次差异巨大即证实（预期 10 倍以上）。

**因此：不改代码。** 原 P1 第 4 项降级为「已知特性，不修」。

### 3.2 必须补的

| 优先级 | 问题 | 证据 | 影响 | 修复 |
|---|---|---|---|---|
| **已修** | ~~http 明文不跳 https~~ | 2026-10-22 已改为 **301**（含路径与查询参数） | 重复内容、首访可被中间人劫持；HSTS 只在访问过一次 https 后才生效 | 面板原生 `/site?action=HttpToHttps` |

| P3 | 只协商 TLS 1.2 | `openssl s_client` → `Protocol: TLSv1.2` | 握手多一个 RTT | `ssl_protocols TLSv1.2 TLSv1.3;` |

### 为什么 4 个安全头最后没做

不是忘了，是**收益不抵风险**，三条理由：

1. **收益本来就低**。这是纯静态展示页：没有登录、没有表单提交、没有用户数据。`X-Frame-Options`（防点击劫持）在无登录态页面上几乎没有可劫持的目标；`X-Content-Type-Options`（防 MIME 嗅探）现代浏览器基本已默认严格；`Referrer-Policy` 浏览器默认值就是 `strict-origin-when-cross-origin`，等于没差别；页面不用摄像头麦克风，`Permissions-Policy` 也是空转。
2. **改配置没有兜底**。实测面板「配置文件」页保存只调 `SaveFileBody` —— **纯写文件，不做语法校验、不 reload**。手改配置等于配置悬空，等下次重启才生效（延迟爆炸）。
3. **共享服务器不划算**。这台机器还有其他项目在跑。为几个边际收益极低的响应头，去引入"配置可能写坏 + 找不到可靠重载通道"的不确定性，不值。

**如果以后确实要加**（例如页面开始收表单），最小改动如下 —— 注意 `always` 和子 location 覆盖问题：

```nginx
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "geolocation=(), microphone=(), camera=()" always;
```

**必须注意的坑**：nginx 的 `add_header` **子 location 会覆盖父级**——现有配置里图片和 css/js 各有一个 location 且都写了 `expires`，只要在那些 location 里再写任何 `add_header`，server 级的 4 个安全头就会全部失效。要么在每个 location 重复声明，要么用 `include` 片段统一注入。

CSP 想上 `script-src 'self'` 的话，还得处理 `<head>` 里那段防闪白的内联脚本（`index.html:41-51`）：外置成 `theme-init.js`（推荐），或用 `sha256-...` 哈希放行（每次改都要重算）。

| 其他站点的 `*.conf` | 别人的命 | ⛔ 绝不修改、不读取后写入 |
| PHP / MySQL / 防火墙 / 面板设置 / 证书全局配置 | 全局 | ⛔ 不碰 |

⚠️ **实测修正**：面板「配置文件」页保存只调 `SaveFileBody` —— **纯写文件，不做语法校验、不 reload**。所以「先 `nginx -t` 再 reload」那套在面板通道里根本走不通，手改配置只会让配置悬空，等下次重启才爆炸。

**这次实际走的路**：调面板**原生**接口 `/site?action=HttpToHttps`（强制 HTTPS 的开关本身），面板自己改配置、自己校验、自己 reload。这是唯一既有校验又有重载的通道，已写进 `ops/静态站上线手册.md` §8。

同理，凡需要改 nginx 的，**优先用面板已有的功能**（强制HTTPS、重定向、伪静态保存），不要手写配置。禁用 `restart` —— 那会瞬断所有站点。

前置固定一条：改之前把该 `.conf` 复制成 `.conf.bak.<时间戳>`，出任何异常用 `cp` 还原再 reload。

一个已知副作用：在宝塔面板里点「保存站点设置 / 切换伪静态 / 改 SSL」时，面板会重写这个站点的配置文件，手改的几行可能被覆盖。所以改动片段必须留在本文档里（即上面的参考配置），丢了照抄回去即可。

## 7. 明确不建议做的（避免过度优化）

- ❌ **不要为 Lighthouse 分数去掉视觉质感**（阴影、模糊、入场动画是品牌的一部分，当前 CLS 已经是 0）。
- ❌ **不要为那个 803ms 长任务改代码**：§1.5 已证明是冷启动字形预热，改 CSS/JS/图片都无效（八组排除法实测均无收益），唯一"解法"是少写字。
- ❌ **不要给静态资源加 hash 文件名**：会显著增加部署脚本复杂度，收益只是缓存策略更激进。
- ❌ **不要为了 27KB 直接剥离 `data-page-node-id`**：这是"编辑器可回写"的代价，属于取舍不是缺陷；要么接受体积，要么放弃回写。
- ❌ **不要引入字体 CDN**：违背"零第三方依赖"，国内还有可用性风险。
- ❌ **不要加 `keywords` meta**：主流搜索引擎早已忽略。
- ❌ **不要动 title / description / H1**：现在这几个是全站 SEO 最健康的部分。

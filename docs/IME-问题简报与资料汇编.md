## 0. 三十秒速览（大白话）

你在 Windows 上用 solo（一个 Tauri + WebView2 做的 Markdown 编辑器）写中文时，**输入法那个「选词小窗」偶尔会飞走**——不跟在光标旁边，而是被钉死在屏幕某个固定的角落（我们实测是右下角附近），但小窗本身长得很正常（词也全、工具栏也在），只是位置错了。**字不会丢、文件不会坏。**

它**不是每次都犯**：大概 16% 的会话会中招，集中在「刚打开软件 / 刚切文件 / 刚挪过窗口」之后的**第一次**打字；**你只要动一下鼠标（或点一下），它立刻就回去了**；同一场景打第二次通常就正常了；软件开久了也不再出现。

**这事不是我们（solo）代码写坏了**——微软官方 issue 里有人用「最普通的 Tauri 模板 + 一个空白输入框」就能复现（见上游 `#5675`）。根因大概率在 **WebView2 的宿主层**（它怎么把光标位置告诉输入法的那条链路），**微软至今 0 回复、没给结论**。

**为什么一直查不清**：四个物理性障碍叠一起——① 那个小窗没有窗口句柄，我们看不见它的内部状态，只能靠截屏数像素；②「鼠标一动就好」导致自动化测试一跑就把现象擦掉了，根本复现不出来；③ 既然复现不出来，任何「修法」都没法验证到底修没修好；④ WebView2 是自动更新的，我们查的时候它版本还变过一次。

**我们做了什么**：现象、触发条件、自愈条件、对照差异都量化过了；还实打实写了三版「自动晃鼠标」的补丁想绕过去，**三版全失败**；大量假设已被实验排除。**根因始终没定位到。**

**当前状态**：2026-09-24 已**主动封存**——停止投入、转观察。除非微软修了、或软件形态变了，否则不值得再砸时间。

## 1. 问题是什么（精确表述，只有可观测事实）

**标准问题陈述（不含因果推断）**

> Windows 11 上，在 Tauri v2（wry）宿主 + WebView2 Runtime 应用中，使用微软拼音等 TSF 输入法打字进入组字（composition）时，输入法候选窗**偶发脱离文本光标锚点**，被渲染到一个**远离光标的屏幕固定点**（我们基线实测右下角 `(1340,996)`；另一轮复测 `(782,706)`；同一会话内为常数；与窗口位置、光标位置均无关），约 16% 会话命中；触发集中在**宿主窗口 resize / 焦点切换 / 切换编辑对象后的首次组字**；任何鼠标事件立即清除，故自动化无法稳定复现；同机同输入法下 Edge 本体与纯 `<textarea>` 均不出现（1606 帧采样中 21 帧失锚全部落在该应用内）；最小复现为 stock Tauri + 裸 `<input>`（上游 `#5675`，表现为韩文 / 左上角）。**根因未定位**，上游同族 issue 至今 0 回复。

**关键观测（逐条可复核）**

| # | 观测 | 来源 |
|---|---|---|
| O1 | 候选窗**形态完全正常**，仅位置错 | 现场截图（候选窗特写） |
| O2 | 全量 1606 个候选窗帧中真失锚仅 21 帧，该批次内坐标一字不差全为 `(1340,996)`（⚠️ 非跨期恒定） | 像素扫描脚本 |
| O3 | 失锚帧**全部**在 solo 内；那一刻窗口内干净、无候选窗 | 同上 |
| O4 | 失锚时光标真实位置 ≈ `(226,626)` ⇒ 离候选窗约 **1100px** | 两帧差分定位 |
| O5 | 命中率 **2/12 会话段 ≈ 16%** | 63 分钟探针日志 |
| O6 | 现场两次失锚间隔 11s，坐标相同；**21 分钟后**再打字全部正常 | 原始日志 |
| O7 | **对照组零失锚**：WorkBuddy 756 帧 / Edge 70 / 其他应用若干，全零 | 同一批全量采样 |
| O8 | 单显示器 1920×1080、96 DPI（100%）、DPR=1 | 系统探测 |
| O9 | 微软拼音候选窗由 `TextInputHost.exe` 的 UWP 合成层绘制，**无独立 HWND**，只能屏幕像素取证 | 本机窗口枚举 |
| O10 | 锚点在一段会话内是**屏幕绝对坐标常数**，与窗口 / 光标均无关（4 批次 / 45 帧 solo / 84 帧总量，窗口位移 668px、光标位移 901px、锚点不动） | 取证器现场数据（2026-09-24） |

**两个症状必须分开（最容易走偏的地方）**

上游同族其实有**两类不同缺陷**，混用会推出矛盾结论：

| | **A. 候选窗飘角（本项目主诉）** | **B. contentEditable 吃字 / 标点双按** |
|---|---|---|
| 上游 | `#5675` | `#5625` |
| 与 `contentEditable` 关系 | **无关**——裸 `<input>` 也复现 | **有关**——同页 `textarea` 完全正常 |
| 症状 | 候选窗位置错 | 第一个汉字被吞、中文标点要敲两遍 |
| JS 侧缓解 | —— | 已被提交者实测**无效** |

> 有人同时用「`textarea` 正常 ⇒ 病灶在 contentEditable」和「裸 input 也复现 ⇒ 与 contentEditable 无关」论证，**这两句互斥**。真相是同一子系统（WebView2 的 TSF 文本输入集成）下的两个**不同**缺陷，不可互推。

### 2.3 自动化复现实验（全线未复现 —— 这是「不可复现」障碍的铁证）

| 实验 | 规模 | 结果 |
|---|---|---|
| 场景矩阵对照（切窗口 / 切文档 / 移窗 / 焦点组合等） | 7 场景 × 5 轮 = **35 次** | **零复现**；且候选窗坐标精确跟随窗口移动 |
| 确定性复现（按 `#5675` 配方，全程零鼠标） | **120 次键盘注入 / 14 试次** | **零复现** |
| 有效试次累计 | **12 次** | 零复现 |

**结论（原理性）**：用「干净新实例 + 理想时序」的自动化复现，**原理上打不到这个 bug**。它只在用户**长时间运行的真实实例 + 真实操作序列**（含鼠标、滚轮、拖窗、长时间停顿）下偶发。

### 2.4 已排除的假设（**请勿重复验证**，均有实验依据）

| 假设 | 排除依据 |
|---|---|
| DPI / 多屏换算 | 实测**单显示器 1920×1080 / 100% DPI** 仍发作 |
| `content-visibility` | 已门控在 `html.doc-heavy`（50 万字符阈值），小文档不启用 |
| 「焦点空窗」 | 切走→切回 `document.hasFocus()` 仅 <10ms 一跳即恢复 |
| 「光标跑到视口外」 | `focus('start')` 同步滚动到光标；2893 采样点 0 例外 |
| 切窗口 / 切文档 / 移窗口（含组合）后立刻打字 | **35 次对照实验零复现** |
| 「窗口移动 → 坐标缓存过期」 | n=2 且不自洽（位移量与错误无关）；且 stale 原点只能造成「偏移一个位移量」，解释不了角位恒定 |
| 「候选窗超出应用窗口 = bug」 | 不是 bug：长候选词正常溢出，系统只保证不出屏 |
| 组字期装饰重建是元凶 | 源码级证伪：值比较 ⇒ 相同装饰移除后原样加回不重建 DOM |
| 换输入法 | 2026-09-24 用户换豆包输入法后**症状完全相同** |

### 2.5 已证伪的死路（**别再走**）

| 死路 | 证伪方式 |
|---|---|
| `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` **env 注入** flag | WebView2 环境崩溃（×3），flag 从未进进程命令行 ⇒ 只能走 `tauri.conf.json` |
| `NotifyParentWindowPositionChanged()` | wry 已在 `WM_MOVE\|WM_MOVING` 调它；上游提交者手动 ×10（0~1100ms）无效 |
| `MoveFocus(PROGRAMMATIC)` | 上游实测无效 |
| JS 层「组字期抑制 DOM 变更」当解药 | `#5625` 作者实测无效 |
| 高 DPI / 多屏坐标归一化 | 与自家取证（100% 单屏仍发作）自相矛盾 |
| 透明输入代理层（隐藏 textarea 当锚） | 对飘角无效（裸 input 也中） |
| 升级 Tauri / wry 依赖 | wry 已与上游复现环境同版本 0.55.1；运行时已到 153（且 153 自带输入冻结 bug）⇒ 无收益有反向风险 |
| 换 Electron / CEF | 仍是 Chromium，同族风险不减 |
| 换掉 WebView2 | wry 在 Windows 只有 WebView2 一种引擎 ⇒ 物理不成立 |
| **「鼠标注入重锚」三版补丁** | v1 触发器从未开火（Windows 拖窗不发 `WM_SIZE`）；v2 开火也没用（事前注入防不住）；v3 日志铁证（注入全部成功、候选窗仍钉死）。**结论：合成鼠标输入治愈不了失锚** |

## 3. 当前结论与状态

**状态**：`外部缺陷 · 观测已完成 · 停止投入 · 转观察`。2026-09-24 用户明确终止，封存。

- **这不是 solo 编辑器代码的问题。** 强推断指向 **WebView2 宿主层的 TSF 文本输入集成缺陷**（裸 `<input>` 在 stock Tauri 里也能复现，上游 `#5675`）。微软对该族 issue **0 回复**。
- **根治在微软手里，不在我们手里。**
- **已落地 2 项改动**：组字冻结总闸（有效但非解药）；TSF→IMM32 回退 flag（无任何有效性证据，但保留——撤了只会把原始 bug 请回来）。
- **重启条件（仅此三类才值得重新投入）**：① 上游 WebView2 / Windows 发布相关修复；② 微软回复本族任一 issue（`#1611` / `#2241` / `#5675` / `#5625`）；③ 产品形态变更（更换运行时策略或窗口形态）。

**机制推断（非定论）**：光标矩形上报为空（renderer 报 `TEXT_INPUT_TYPE_NONE` 时 `GetCaretBounds()` 返空矩形）⇒ TSF 拿不到位置 ⇒ 系统回退屏幕默认角位。恒定角位 = 输入法的「无锚点回退位」——微软拼音默认右下、韩文默认左上，是同一机制的不同表现，这也排除了「偏移一个位移量」类假说。⚠️ 微软均未确认。

## 5. 给第三方的起点建议

1. **别从「solo 代码 bug」入手**——三重证据（裸 input 复现 / textarea 正常 / 另一 Chromium 应用零异常）都指向宿主层。先读附录 B 的对外交接报告（§1~§4 环境 + 障碍）。
2. **先回答「怎么知道修好了」**——这是所有方案的共同缺口。任何修法都绕不开「现象无法自动复现 ⇒ 无法 A/B 证真」。
3. **环境先锁版本**——WebView2 是 Evergreen 自动更新，引用任何旧结论前先核当前 `pv`（见报告 §1.2）。不锁版本，判断都建立在流沙上。

## 0.1 三十秒速览

- **问题一句话**：在 Windows 11 上，一个 Tauri v2 桌面应用的 WebView2 区域中，用中文输入法打字时，**输入法候选窗偶发脱离光标、被渲染到远离光标的屏幕固定点**（2026-09-13/14 基线实测为右下角 `(1340,996)`；**该坐标并非恒定**，2026-09-24 复测已变为 `(782,706)`，见 §6.6）。
- **它是不是渲染坏了**：不是。候选窗**形态完全正常**（7 个候选词 + 工具栏齐全），**只是位置错**。
- **它会不会丢数据**：不会。已上屏文字正常、文件不损坏、保存不受影响。
- **它什么时候发生**：**偶发**（实测约 16% 会话命中），集中在「进入应用 / 切换文档 / 窗口位移」之后的**第一次**组字。
- **它怎么消失**：**任何鼠标移动或点击立即清除**；同一场景下第二次组字通常也不再出现。
- **为什么难查**：① 候选窗**没有窗口句柄**，只能靠屏幕像素观测；② 「鼠标一动就好」⇒ **测试动作本身会擦掉现象**；③ 现象不可稳定复现 ⇒ **任何修法都无法验证**。
- **我们做到哪一步**：现象、触发条件、自愈条件、对照差异都已量化；**根因未定位**。

## 1. 项目与运行环境

### 1.1 solo 是什么

**solo** 是一款**本地优先（local-first）的桌面 Markdown 编辑器**，面向中文沉浸式写作：纯本地、无后端服务、无账号、单文件编辑。

| 维度 | 说明 |
|---|---|
| 定位 | 个人化「阅读 + 写作体验」工具；非协作、非长文档处理器 |
| 架构 | **Tauri v2**（Rust 宿主）+ **Vue 3** 前端 + **TipTap 3 / ProseMirror** 编辑器内核 |
| 渲染 | 前端**单一 `contenteditable` 同时承担两个角色**：① 输入法的拼字面；② Markdown 实时渲染面（行内标记实时变身、装饰层、NodeView 等） |
| 平台 | Windows（本机 Win11）为主；代码层跨平台（macOS / Linux 亦有路径） |
| 分发 | NSIS 安装包；GitHub Release 自动更新 |
| 版本（本报告基线） | **v1.2.56** |

> 这条「同一个 contenteditable 既当拼字面又当渲染面」的设计，是理解本项目 IME 相关一切问题的前提。

## 2. 问题陈述

### 2.1 标准问题陈述（**未标定 · 只有可观测事实 · 不含任何因果推断**）

> **Windows / WebView2 宿主层「IME 候选窗失锚」现象**：
> Windows 11 上，在 Tauri v2（wry）宿主 + WebView2 Runtime 应用中，使用微软拼音等 TSF 输入法打字进入 composition（组字）时，输入法候选窗**偶发脱离文本光标锚点**，被渲染到一个**远离光标的屏幕固定点**（2026-09-13/14 基线实测为右下角 `(1340,996)`；2026-09-24 复测为 `(782,706)`；**同一会话内为常数**，跨期实测不同但与 Runtime 152→153 变更混淆、不可归因；与窗口位置、光标位置均无关），约 16% 会话命中；触发时机集中在**宿主窗口 resize / 焦点切换 / 切换编辑对象后的首次组字**，同一场景下**第二次组字通常不再出现**，且**任何鼠标事件（mousemove / click）立即清除**，因此在自动化环境下无法稳定复现；同机同输入法下，**Edge 浏览器本体与纯 `<textarea>` 均不出现**该现象（1606 帧采样中 21 帧失锚全部落在该应用内）；最小复现为 stock Tauri + 单个裸 `<input>`（同族上游记录：`MicrosoftEdge/WebView2Feedback#5675`，其表现为韩文 IME / 左上角）；另在组字期抑制 DOM 变更的 JS 侧缓解**已实测无效**（`#5625`）。**根因未定位**，上游同族 issue 至今 0 回复、无官方结论。

### 3.2 🟡 `composition-freeze.ts`（组字态唯一真相源）

文件头自述其设计意图（原文摘录）：

```ts
/**
 * 输入法「合成冻结」总闸 —— 合成期视觉层行为的唯一真相源。
 *
 * 为什么需要它：solo 让同一个 contenteditable 同时当「输入法拼字面」和
 * 「markdown 实时渲染面」。输入法靠浏览器上报的光标矩形定位候选窗，矩形由 DOM
 * 算出来；合成期若重排 / 重建 DOM，矩形失真 → 候选窗失锚。
 *
 * 铁律：合成期（isFrozen 为真）只允许浏览器自己的合成文字落地，其余一律推迟——
 *   - 装饰：走 mapFrozenDecorations（只平移、不重建）
 *   - 结构变身 / 菜单定位重渲 / nodeview 重建：直接跳过，等 compositionend 后再补
 *
 * 设计约束（勿违）：
 * 1. 不做全局 dispatch 拦截：ProseMirror 的合成事务与应用事务走同一条通道，
 *    全局拦会连用户打的字一起挡掉。
 * 2. 权威信号是 view.composing（浏览器 DOM composition）。
 * 3. 退化安全：view 缺失 / 已销毁一律视为「未冻结」。
 */
```

**导出三个符号**（全文 68 行，已读源码核实）：

| 符号 | 作用 |
|---|---|
| `isFrozen(view)` | `view?.composing === true`；view 缺失/已销毁 → `false`（退化安全） |
| `mapFrozenDecorations(set, tr, doc)` | 组字期**只按事务 map 平移**已有装饰，**绝不重建** |
| `createCompositionTracker()` | 每实例一份的 view 登记器（`state.apply` / `appendTransaction` 拿不到 view） |

它对原先散落在 4 个文件（`markdown-input` / `paragraph-focus` / `search-highlight` / `code-block`）里的 `let liveView` + `view.composing` 内联副本做了收敛。性质为**纯重构、行为等价**。

> ⚠️ **定位澄清（重要，请勿误读）**：该总闸的正当性来自「让组字期 DOM 保持干净」这一**独立目标**（对付"组字期 DOM 抖动引发的各类 IME 异常"）。
> 对 **§2.5-A 的「飘角」它不是解药** —— 上游已实测「组字期抑制 DOM 变更的 JS 侧缓解无效」（`#5625`），且裸 `<input>` 也失锚（`#5675`）。
> **但也不要因此认为它无用**：它是针对另一类 IME 异常的防守，方向本身合理。

## 4. 当前遇到的系统性障碍

这一节是本报告**最值得读的部分**。它解释了为什么"我们已经查了很多、仍然定位不了"——**不是查得不够，是有三道物理性障碍**。

### 4.1 障碍一：不可观测（看不见）

Win11 微软拼音候选窗由 `TextInputHost.exe` 的 **UWP 合成层**绘制，**没有独立窗口句柄**：

- `EnumWindows` 只能看到那个全屏 `Windows.UI.Core.CoreWindow (0,0,1920,1080)`；
- UIA 路线在本机被安全策略拦（`Add-Type` 一刀切）；
- Chromium 系窗口是**自绘光标**（`hwndCaret = None`）。

⇒ **我们只能截屏数像素**（判据 = 选中项高亮 `#A6D8FF` + 形状约束）。没有任何接口能问它"你为什么摆错了"。

### 4.2 障碍二：不可复现（一测就没）

触发窗口极窄 + **"鼠标一动即自愈"**：

- 自动化脚本里**先动鼠标 = 自己把 bug 擦了**；
- 复现必须**全程零鼠标事件**；
- 触发窗口是「几何变化/焦点变化后**第一次**组字」的毫秒级时序。

⇒ 实测 **35 次对照实验零复现**、**14 试次 / 120 次键盘注入零复现**；另有 **46 次窗口位移样本**（**口径不同：这是日志里提取的窗口 rect 变更次数，不是实验次数，§6.3 原文即标「样本不足，不足以下结论」**）。**测试行为本身会污染被测对象**。

### 4.3 障碍三：不可证真（无法验证修法）

由 4.2 直接推出：**既然现象无法在自动环境稳定触发，任何"修法"都无法 A/B 验证。**

- 「机制合理 + 业界先例」只能给**安慰**，给不了**结论**；
- 测试跑绿 ≠ 修好了；
- 因此每一次"修"本质上都是**赌**。

### 4.4 障碍四：环境漂移（沙子上的塔）

WebView2 是 **Evergreen 运行时**，会自动升级：

- 我们**全部历史实验**跑在 `152.0.4191.66`；
- 本机现已是 **`153.0.4234.x`**（09-17 记录 `.32`，09-23 实测 `.48`）；
- 且 **Edge 153 本身已被微软承认存在「输入/交互冻结」bug**（2026-09-10 发布；微软 2026-09-16 承认，临时方案 = 回退 152；Salesforce 同日报告 Chrome/Edge 153 间歇性 UI 卡死，触发点为 09-08 前后自动更新）。

⚠️ **注意区分**：153 已确认的症状是「**交互冻结**」，与本问题的「**候选窗飘角**」**症状不同**。故 153 是**嫌疑**，**不是已证原因**。

⇒ **不锁运行时版本，后续一切判断都建立在流沙上。**

## 0b. TL;DR（接手必读 30 秒）

- **Bug 是什么**：中文输入法候选小窗打字时偶发飘到屏幕角落（我们实测恒为右下角 `(1340,996)`），不跟光标。
- **根因定位**：缺陷在 **WebView2 宿主层 / 其 TSF 集成**，与 solo 编辑器逻辑无关。三重证据：① `#5675` **裸 `<input>` 即复现**候选窗飘角；② `#5625` 中 **纯 `textarea` 完全正常、`contentEditable` 吃字**，且作者实测**「composition 期间抑制 DOM 变更的 JS 侧缓解无效」**；③ Edge/Chrome 不复现、WebView2 复现。⚠️ 但微软对该族 issue **0 回复、无官方结论**，「托管层」仍属强推断。
- **为什么 solo 频发**：solo 是「高频中文写作 + 高频窗口操作」的**高使用量场景**，命中触发机会多（**与 DOM 复杂度无因果关系**，见 §2.2）。
- **已落地**：① `composition-freeze.ts` 总闸（提交 `21a028b`，`origin/master`）；② `tauri.conf.json` 加 `--disable-features=TSFImeSupport`（提交 `9a27bad`，`origin/master`）。**注意**：二者对「失锚」都**不是解药**（详见 §3.1、§4）。
- **最大困局**：失锚**无法在自动环境触发**（鼠标一动即自愈）⇒ 任何修法**无法 A/B 证真**。至今对 flag 有效性的**唯一证据是「flag 进了命令行」**（见 §3.1 的 A/B 无分辨力）。
- **正确的下一步**：**先锁运行时版本 + 装「一键取证器」抓现场**，再谈修法；停止在无法证真的修法上继续投入。见 §4。

## 1. 现象与机制

### 1.1 现象（源：取证文档）
- 微软拼音候选窗由 `TextInputHost.exe` 的 UWP 合成层绘制、**无独立 HWND**（Win32/UIA 都枚举不到）⇒ 只能**屏幕像素取证**。
- 实测 1606 帧：真失锚 **21 帧全在 solo**，坐标 `(1340,996)`；对照 WorkBuddy 756 帧 / Edge / 百度搭子 / 豆包 **零失锚**。
  - ⚠️ **该坐标为 2026-09-13/14（Runtime 152）基线的实测值，非恒定值**。2026-09-24 复测（Runtime 153）锚点已变为 `(782,706)`，见 §8.5。
- 规律：**「进 solo / 切文档 / 移窗口」后的第一次组字易失锚；初期易发、随会话推进消失**（约 16% 会话命中，偶发）。
  - ⚠️ **表述已修正（2026-09-23）**：原写「第二次自愈」**过简且不准**。真值 = 现场同一场编辑内出现 **2 次**失锚（t=52.7s / t=63.5s，坐标同为 `(1340,996)`，间隔 11s），且要到 **21 分钟后（t=1404s+）** 才完全正常（源：`.workbuddy/memory/2026-09-13.md` L403 / L408）。
- **★ 2026-09-24 新增（首次拿到精确锚点）**：候选窗锚点在一段会话内是**屏幕绝对坐标常数**，**与窗口位置、光标位置均无关**（4 批次 / 21 分钟内锚点恒为 `(783,707)`±2px，而窗口位移 668px、光标位移 901px）。用户感知的「有时在页面内、有时跑到页面外」= **锚点固定 + 窗口移动**的视觉结果。详见 §8.5。
  - ⚠️ **同轮自我纠正（2026-09-24 02:3x）**：早先记的「锚点 01:50≈`(180,617)`、跨时间会变」**已撤销** —— 该坐标经裁剪放大核实，是 **OpenCode 终端自身**的候选窗（**正确定位**在其命令输入行正下方、深色背景），**不属 solo**，不能计入锚点序列。

### 1.2 机制
光标矩形上报为空（`RenderWidgetHostViewAura::GetCaretBounds()` 在 `!active_widget` 时返空矩形 ⇐ renderer 报 `TEXT_INPUT_TYPE_NONE`）⇒ TSF 拿不到位置 ⇒ 系统回退屏幕默认角位。〔源：取证文档的 Chromium 源码分析〕
> ⚠️ `#5675` 提交者另有一套类似但**自称未经验证**的 TSF 链路推断（`OnCaretBoundsChanged` → … → `OnLayoutChange` 未触发）。方向一致、**均未被微软确认**。

### 1.3 上游 issue 族（本轮全部核对存在性）

| issue | 症状 | 关键事实（一手页面） |
|---|---|---|
| **`#5675`** | 候选窗飘角（resize 后） | stock Tauri + **裸 `<input>`** 即复现；韩文 IME / 左上角（我们中文 / 右下角）；**鼠标一动即清除**；页末「*No response*」；提交者自列已排除：子窗口几何、主线程阻塞、页面 caret、`MoveFocus(PROGRAMMATIC)`、`NotifyParentWindowPositionChanged()`×10 |
| **`#5625`** | contentEditable **吃字/标点双按** | 运行时 **149**、Tauri 2 宿主；**同页 `textarea` 正常**；作者实测 **「compositionstart~end 间抑制 DOM 变更的 JS 侧缓解无效」**⇒ 病灶在 **WebView2 的 TSF 文本输入层**，不在 JS；搜狗拼音严重、微软拼音轻 |
| `#1611` | 候选窗不随窗口**移动** | 同族 |
| `#2241` | WinUI3 同族 | 缩放>100% 恒错位 |
| `#5570` | RDP + composition 模式 | 前提（composition 模式）在 solo 不成立 |
| `#1610` | 同族旧账 | 2024 关闭，但当前运行时复现 |

> **族内两症状必须分开**（这是关键认知）：`#5675` 的**候选窗飘角**与 contentEditable **无关**（裸 input 也中）；`#5625` 的**吃字**才与 contentEditable **有关**（textarea 正常）。二者是**同一子系统（WebView2 的 TSF 集成）下的两个不同缺陷**，不可互推。

## 2. 核心反思：为什么 solo 比同类软件更频繁中招

> **结论（已按 `#5675` 证据修正）：候选窗飘角是 WebView2 宿主层的真缺陷，solo 在这件事上是「受害者」；solo「看起来更频繁」来自「使用量 + 触发机会」，而非 DOM 复杂或代码写坏。**

### 2.1 你拿来对比的「很多软件」大多根本不在这条链路上

| 软件类型 | 文本控件实现 | 会不会掉这个坑 |
|---|---|---|
| 记事本 / Word / QQ 等原生 Win32/MFC/Qt/WPF | **原生控件**（IMM32 自己画候选窗） | **不掉**——不走 Chromium/WebView2 链路（通用事实） |
| VSCode / MarkText 等 Electron 软件 | Chromium 内核 | 同属 Chromium，**理论同族风险**；本轮**未逐条复核**，勿当已证事实 |
| solo | Chromium（WebView2） | 掉 |

类比：油车（原生）冬天不掉电，不是更先进，是**不用电池**。

### 2.2 solo 的触发机会更多（修正版：DOM 复杂度**不是**原因）

1. **`#5675` 铁证：裸 `<input>` 也失锚** ⇒ 飘角**不需要** contenteditable、不需要 ProseMirror、不需要动态 DOM。故**不能**再把「复杂富文本 DOM」列为飘角成因（初稿如此写，本轮已删）。
2. **真正放大命中率的是「使用量 + 触发机会」**：solo 是写作软件，中文组字每天成千上万次；且窗口操作频繁（多窗口、透明无边框、切文件、移窗）。触发条件（几何变化后立刻组字且不碰鼠标）**出现次数**越多，偶发缺陷越容易被看到。
3. **`composition-freeze` 的正当性来自另一类问题，不是飘角**：它让组字期 DOM 干净，对付的是「组字期 DOM 抖动引发的各类 IME 异常」；对「飘角」它**不是解药**（`#5625` 已证 JS 层抑制 DOM 变更对这类 TSF 问题无效）。方向不算错，但**别指望它治飘角**。

### 2.3 社区做法（solo 未采用）— ⚠️ 来源【待核实】且**对飘角大概率不适用**

| 做法 | 据称谁在用 | 对**本 bug（飘角）**是否有效 |
|---|---|---|
| **隐藏 textarea / contenteditable 当稳定 IME 锚** | Google Docs、Collabora Online、知乎编辑器【来源待核实】 | **大概率无效**。该思路解决的是「DOM 抖动 → 锚点抖」；而 `#5675` 是「resize 后锚点**整个失效**」，**连裸 input 都失效** ⇒ 换锚点位置救不了 |
| 编辑器官方 IME 针对性修复（如 ProseMirror `domchange.ts`） | 【待核实】 | 针对具体 IME 光标错位，非本 bug 的宿主层失效 |
| 高 DPI / 多屏坐标归一化 | 【待核实】 | **已被 solo 取证排除**（100% 单屏仍发作） |

> ⚠️ **来源状态**：本表来自公开检索，「隐藏 textarea 当锚」的**实现细节未逐条打开一手原文**；唯一旁证是 Google Docs 用 canvas 渲染 + `docs-texteventtarget-iframe` 承接输入（渲染层与输入层分离）。**动手前必须先复核一手来源，且必须先用 §1.3 的「两症状须分开」判断你到底要治哪一个。**

### 2.4 结论（摆正账）
- 飘角：**solo 是受害者**，触发层在 WebView2 宿主，solo 代码碰不到；「托管层」是强推断、微软未确认。
- 但 solo **不能因此躺平**：把它当已知外部缺陷，**先锁环境、先取证**，而不是继续赌修法。
- `#5625` 的**另一半**（contentEditable 吃字/标点双按，textarea 正常）**可能确实与 solo 的 contentEditable 选择相关**——这是唯一「换输入承载」可能真有收益的方向，但**与飘角是两码事**，且同样在 WebView2 层、JS 层救不了。

## 3. 现状盘点（已落地 / 已排除 / 死路 / 困局）

### 3.1 已落地（提交号已 git 复核；**有效性说明已按新证据修正**）
- **`composition-freeze.ts`**：导出 `isFrozen(view)` / `mapFrozenDecorations(set,tr,doc)` / `createCompositionTracker()`（**已读源码核实**），收敛原先 4 份 `let liveView` + `view.composing` 内联副本。P0 纯重构、行为等价。〔提交 **`21a028b`**，已在 `origin/master`〕
  - ⚠️ **定位澄清**：它是「组字期 DOM 干净」的守卫，**不是飘角的解药**（`#5625` 证实 JS 层抑制 DOM 变更对这类 TSF 问题无效）。
- **`tauri.conf.json`** 窗口加 `"additionalBrowserArgs": "--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection,TSFImeSupport"`（**必须四个一起**，设了会完全替换 wry 默认三个 feature）。**已读当前配置核实存在**；wmic 曾证实四 feature 进了进程命令行。〔提交 **`9a27bad`**，已在 `origin/master`〕
  - ⚠️ **有效性：无任何证据**。见下。
- ~~「IMM32 模式兼容性实测 OK（偏移 (8,27) 与基线逐字一致）」~~ —— **本轮复核推翻**：`ime-ab-baseline.json` 与 `ime-ab-imm32.json` **除 `label` 外逐字段完全相同**（`warmup`/`home`/6 行 `rows` 全等，连窗口坐标、光标、候选框、偏移 `[8,27]` 一字不差）。说明这套测量对「flag 是否生效」**零分辨力**（未触发失锚时两条链路画出来本就一样）。**故「TSFImeSupport 有效」至今连间接证据都没有，唯一事实是「flag 进了命令行」。**

### 3.2 已排除（勿重复验证，详见取证文档）
- DPI/多屏（100% 单屏仍发作）｜`content-visibility`（已门控 `html.doc-heavy`）｜「焦点空窗」（`hasFocus()` <10ms 恢复）｜切窗口/切文档/移窗口/组合 **35 次自动对照零复现**｜「光标跑到视口外」（2893 采样点 0 例外）。
- 千问提案三处「漏洞」：A 已证无害｜B 已被现有守卫覆盖｜C 单独不足以致光标矩形失效。

### 3.3 已证伪的死路（别再走）
- **`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` env 注入 flag**：WebView2 环境崩溃（复现 3 次），flag 从未传入 ⇒ 必须走 `tauri.conf.json`。
- **`NotifyParentWindowPositionChanged()` / 移动后重设 webview 边界**：wry 已在 `WM_MOVE|WM_MOVING` 调它，`#5675` 实测 ×10 无效。
- **`MoveFocus(PROGRAMMATIC)`**：`#5675` 实测无效。
- **JS 层「组字期抑制 DOM 变更」当解药**：`#5625` 作者实测无效。
- **千问「窗口移动 → 坐标缓存过期」假说**：n=2、机制与「恒定跳角」不符、有微观反例 ⇒ 未采纳。

### 3.4 困局的本质（本次新增，最重要的一条）
**失锚「鼠标一动即自愈」⇒ 自动化测试永远抓不住（35 次对照实验零复现；14 试次 / 120 次键盘注入零复现；另 46 次窗口位移样本不足以下结论）⇒ 任何修法都无法 A/B 证真。**
在此前提下，「机制合理 + 业界先例」只能给**安慰**、给不了**结论**。所以正确姿势是**先把现场数据抓到手**（§4 R2 一键取证器），而不是继续在无法证真的修法上加码。

## 5. 验证纪律与红线

1. **复现必须全程零鼠标事件**：`#5675` 原文铁证——鼠标动/点即清除 bug。自动化里先动鼠标 = 自己把 bug 擦了。
2. **丧失自动触发 ⇒ 任何修法无法 A/B 证真**：只能靠「机制 + 先例 + 兼容实测」；**如实声明，不假装已验证**。**测试跑绿 ≠ 修好了**。
3. **禁加守卫掩盖根因**（AGENTS.md 禁令第 11 条）：优先减/门控；N 处各塞判断是加法。
4. **环境漂移铁律（本次新增）**：**WebView2 运行时可能每两周变一次** ⇒ 引用「以前验证过」的结论前，先核当前 `pv`；跨版本结论**必须注明运行时版本**。
5. **改动即联动**：改 `composition-freeze.ts` 属**组字态（IME）**修改 —— 必读 **AGENTS.md 禁令第 8 条**，验收走「时序/UI/IME/异步」等级（真机手感是通行证），敏感区速查见 [`docs/sensitive-areas.md`](sensitive-areas.md)（组字态**非**独立条目；最相关第 12 条 NodeView），改完 `grep -rn "<改动文件>" --include=*.md` 查死链；改 `tauri.conf.json` 属发版敏感，走 RELEASE_PROCESS。

1. **锚点＝鼠标屏幕位置？** —— **支持证据已失去**：早先唯一支撑（"跨时间会变"）已撤销（那条坐标属别的 App）。实测抓帧结束时鼠标 `(1097,211)` ≠ `(783,707)` ⇒ **不获支持、未排除**。唯一残留线索是「鼠标一动即自愈」——它只说明鼠标是**刷新触发器**，不必然等于**锚点来源**。**2 分钟可验**（见 §4.1 R0）。
2. **组字期 `composing` 恒为 False 的成因未分**：(a) 热键打断组字；(b) `RegisterHotKey` 摘走按键后 solo 收不到键盘事件、**并未打断**组字，而 TSF 路径下 `view.composing` 本就可能不置位。**若 (b) 成立，则 `composition-freeze` 依赖的组字信号存在盲区** —— 高价值待验项。

# IME 候选窗失锚 · 解决方案（v1 · 供评审）
> 🗄 **本文件已归档（2026-09-30）**：内容已蒸馏合并入 [`docs/IME-CANDIDATE-WINDOW.md`](IME-CANDIDATE-WINDOW.md)，本文仅作历史原件保留、不再维护。

> **读者**：能对方案拍板的人 + 复核的外部工程师。
> **对上一份交接报告的态度**：它的结论我大部分采信（见 §1.1）；本方案**没有**做的一件事是「再提一个『机制很合理』的修法让人赌」——四份第三方建议的共同缺口就是**没回答怎么知道修好了**，这份方案把这个缺口补上。

> 标注沿用交接报告的三分类：**【观测】** 实测事实 ｜**【实验】** 跑过并出结果的 ｜**【推断】** 有合理机制但没被证实、可能错 ｜未核实的标 **【未核实】**。

## 0. 三十秒版结论

1. **问题不是 solo 写坏**：强推断是指向 WebView2 宿主层的 TSF 文本输入集成缺陷（裸 `<input>` 在 stock Tauri 里也能复现，`#5675`）。微软 0 回复。**根治在微软手里，不在我们手里。**
2. **唯一有观测疗效的机制是「鼠标事件自愈」**（谁动鼠标谁就把 bug 擦了，这是它难复现的根源）。方案的主线之一 = 把这个已知解药**前置**成「几何/焦点变化后的主动 nudge」，而不是干等用户动鼠标。
3. **方案不是堆修法，是先造尺子**：落地一个「热键取证器」（键盘触发、不碰鼠标，捕获失锚瞬间的完整现场），用它把「当前命中率」变成可统计的数——**先量当前 flag 是否已生效，再决定要不要动任何代码**。30 会话零命中 vs 历史 16% 基线，才能回答「修好了没」。
4. **一个此前没人做的检查已做掉一半**：`TSFImeSupport` 这个 flag **真实存在**，默认启用（Chromium M75 起 Win8+ 默认 TSF），`--disable-features` 语义 = 正确回退 IMM32（§1.2）。「flag 无效」的死结从「连 flag 是不是真的都不知道」推进到「flag 是真的，只剩『在 WebView2 实际构建里是否生效』未验证」。
5. **本轮没有出现能立刻根治的银弹**；但把「赌修法」换成了「可证伪的逐项实验 + 明确留/撤规则」，每步都小、都可回滚、都带测量。

### 1.3 对「恒坐标」机制的推断加强（仍是【推断】，但比之前更站得住）

交接报告问过：为什么失锚坐标**恒定**右下角，而不是「偏一个位移量」？结论一直含糊。

我的推断：**恒定角位 = 输入法的「无锚点回退位」**。微软拼音没拿到有效 anchor 时的默认位置就在工作区右下角附近；韩文输入法（上游 `#5675`）的默认回退位在左上角。**所以「我们右下 / 上游左上」根本不是矛盾，反而是同一个机制（anchor 丢失/为空 → IME 用自己的默认位）在两种输入法下的不同表现。** 这与 Chromium `GetCaretBounds()` 无 active widget 时返空矩形的机制自洽（`ime-candidate-window.md` L22）。

推论：
- 「偏一个位移量」类假说（窗口坐标缓存过期等）可以直接排除——它解释不了角位恒定；
- 「anchor 为空」是当前**一致性最高**的机制，干预方向应围绕「**让 anchor 在首次组字前是新鲜的**」。

## 3. W1 取证器规格（方案的测量骨架，需拍板落地）

> 理由：死结的钥匙是现场数据。平时正常用，**一旦候选窗飘走，按键盘热键**（键盘热键不动鼠标 ⇒ 不会把自己擦了），系统抓一份快照。攒够样本后统计，而不是继续纸面推演。

### 3.1 触发与取值

- **热键**：全局键盘组合（如 `Ctrl+Alt+Shift+D`），Rust 注册（用 `tauri-plugin-global-shortcut` 或裸 win32 `RegisterHotKey`）。**必须纯键盘**——热键本身若产生鼠标事件就把要抓的现场擦掉了。
- **按下时立即抓两路**：
  1. **Rust 侧**：整屏截图 → `.sandbox-ime/forensics/{ts}.png`；当前窗口矩形；前台窗口名；WebView2 运行时版本（注册表 `pv`）；时间戳；
  2. **前端侧**（Rust 发一个 IPC 事件给 renderer，renderer 同步采集）：`view.composing`、`document.hasFocus()`、selection 的 `coordsAtPos`（可取 PM `view.coordsAtPos(state.selection.from)`≈cursor 真实位置）、最近一次 resize/move/focus/doc-switch 时间戳（由现有窗口事件埋点累计）、组字期 DOM 是否被外部改动过（`MutationObserver` 打标）、当前文档字符量、滚动位置。
- **落盘**：`.sandbox-ime/forensics/` 一个 `{ts}.json` 一个 `{ts}.png`，命名同批。
- **RECAP 判定**：判读脚本复用 `.sandbox-ime/ime-watch.py` 的候选窗判据（`#A6D8FF` 高亮 + 形状约束），把 JSON 里「cursor 真实坐标」与 PNG 里「候选窗坐标」做距离判断 → 自动给每条记录打 **HIT** / **OK**。同一时刻截的图与数据必须逐帧对齐，避免再次混入背景窗口假阳性（`ime-candidate-window.md` L95 那个坑）。

### 3.2 统计规则（回答「修好了没」，写死不靠感觉）

| 量 | 定义 |
|---|---|
| **会话段** | 一个「从前台聚焦 + 组字」到「聚焦离开」的最小单位；hit 判定 = 用户按下热键且判读为 HIT |
| 基线 | 历史 16%（2/12 会话段，63 分钟探针）——口径粗，但这是唯一公开基线 |
| **观察窗** | 每个被评估的配置（flag 现状 / 某个候选开 / 关）至少攒 **30 个会话段** |
| 判定 | 配置下 **0/30 HIT** ≠ 历史 16% → Fisher 精确检验 单尾 `p≈0.006`，可判「显著改善」；≥1 HIT → 未显著，执行留/撤规则 |

- **每个候选的「留/撤」规则**（沿用交接报告 R3 纪律）：有显著改善 → 留；无改善或不可测 → **撤**，不养无证据的开关。
- **无回归检查**：任一候选上真机前，先跑 `.sandbox-ime/ime-ab.py` 的「候选窗相对光标偏移」连续量（基线偏移恒 `(8,27)`），确认开关不劣化正常组字体验。

> 诚实备注：这个方案让「修好了吗」有了统计答案，但它有一个磨蹭期——先花约两周拿基线。**这是题目的物理约束**（无法自动触发），没有更快的路。

## 4. W3 候选干预清单（按顺序，互相独立，可单独开/关）

> 每个候选都标注：**机制假说 / 与已证伪死路的区别 / 改动点 / 风险 / 验证**。全部是「小 + 可回滚 + 挂测量」。

### C1 · Rust：`WM_EXITSIZEMOVE` 后 `put_Bounds(当前值)` 强刷一次几何

- **假说**：resize/移动结束后，WebView2 controller 的内部几何与 renderer 的锚缓存可能不同步（anchor 算错/算空）。`put_Bounds(同值)` 触发一次 controller 内部布局刷新，把 anchor 重新钉上。
- **与死路的区别**：`NotifyParentWindowPositionChanged()` 已被 `#5675` 实测 ×10 无效；`put_Bounds(同值)` 是**更硬的一层**（真动 controller bounds），且**不需要 fork wry**——在 Tauri 里 `window.with_webview` 直接调 controller 即可（`window.rs` 已有 `with_webview` 用法，见 `set_memory_target`）。交接文档 topics L123 把它列为"备选叠加项"但一直没做。
- **改动点**：`src-tauri/src/commands/window.rs`，挂到 tauri `WindowEvent::Resized` 的 **settle 去抖**（或移窗结束）之后一次性调（**不能每帧**，否则闪）。
- **风险**：低～中。同值 `put_Bounds` 若无视觉效果则风险近零；若有 1px 抖动需降级为「±1px 再还原」（微软官方 workaround `#2290` 同型，但只做**结束一次性**，不做每帧，规避它那个抖/闪副作用）。
- **验证**：W1 统计窗口。

### C2 · Rust：几何/焦点边界后**预防性**注入一次合成 `WM_MOUSEMOVE`

- **假说**：鼠标事件自愈是**唯一有观测疗效**的机制（我们与 `#5675` 都实测）。那么不等用户动鼠标，**系统替用户动一次**——相当于把已知解药前置到「边界之后、首次组字之前」。
- **与死路的区别**：这不属于已被排除的「JS 组字期抑制 DOM」「焦点 resync」——它是一种宿主消息层的预防针，且只在边界后做 1 次。
- **改动点**：Rust 里 `EnumChildWindows` 找到 render 子窗（`Chrome_RenderWidgetHostHWND`，找不到就回落 `WRY_WEBVIEW` 主窗），`PostMessage(WM_MOUSEMOVE, 0, MAKELPARAM(0,0))` 一次。不带动系统的真实光标移动。
- **风险**：中。可能带来多余的 hover 状态翻转 / 轻微重排；**必须先做一次小实验确认它到底会不会触发自愈**（机制成立的前提），再做常驻。若连「注入 MouseMove」都不能复现自愈路径，立即放弃本项。
- **验证**：机制小实验（在已复现的失锚现场/或手动构造最有把握的时刻，注入后看候选窗是否归位）+ W1 统计。

### C3 · 前端：window focus / 文档切换 / resize 结束后**延迟一次** `view.focus()`

- **假说**：失锚的根因若是「renderer 文本输入类型缓存成 NONE、直到某次交互重报」，那么边界后主动重聚焦一次可强制重报 anchor。
- **与死路的区别**：`#5675` 排除的是**宿主层** `MoveFocus(PROGRAMMATIC)`；这是 **JS 侧对 contenteditable 的 `focus()`**，不同的实现层。且 solo 现有代码对 focus 事件是「编辑器在就 return、不做任何事」（`setupWindowFocusHandlers`）——本项是**主动加**，有语义差异。
- **改动点**：`MarkdownEditor.vue` / `useAppWindowSession`，监听 `solo:editor-focus` / 文档切换 / resize 去抖后 300ms `view.focus()`（焦点已在编辑区时可空转，风险小）。必须**只在几何/焦点边界后**触发，不许常规打字路径上有任何 focus 抖动。
- **风险**：中。抢焦点可能打断用户正打的字 → **必须真机手感验收**（AGENTS 组字态敏感区规则），且与 W1 测量并行。
- **验证**：W1 统计 + 手感验收。

### C4 · 保留现状 flag，但纳入 W1 基线测量（不是"做"而是"量"）

- `--disable-features=TSFImeSupport` 已在 v1.2.56 生效。**先不动**，用 W1 的 2 周窗口量出它（顺带量出当前整体水平）的命中率。若 0 命中 → 线索闭合，flag 很可能真有效；若仍有命中 → 进入 C1/C2/C3。
- 判定后可执行：按 R3 纪律，若 C1/C2/C3 证明有效而 flag 无独立贡献，**可考虑撤 flag 简化**（避免长期挂无证据开关）——同样以测量为准，不拍脑袋。

### C5 · （视 W2 结果）无边框/透明窗口形态对照实验

- 只在 **W2 判据实验结果 = stock Tauri（默认装饰）不复现**时启用：说明 solo 的窗口形态是「更频繁」的候选放大因子，值得做一次真正值切换：`decorations:true` + `transparent:false` 跑一轮 W1，看命中率是否掉。反向复现则永远不做（平台缺陷结论加固）。

### C6 · （兜底，尽量不用）controller `put_IsVisible(false→true)` 闪切

- 强制 surface 重建，理论上必然重锚，但风险是可见闪烁，与「丝滑」铁律冲突。写进清单只为体现「退路都有」，默认不动。

**降本方案（建议，可把新增依赖从 3 降到 0）**：

| 环节 | 现设计 | 建议 |
|---|---|---|
| 截图 + HIT 判读 | Rust 截整屏 + 判读脚本 | 交给**常驻的** `.sandbox-ime/ime-watch.py`（21 帧现场本就是它抓的）：判 HIT → 落帧 + 时间戳 |

## 2. 四条争议点

### 2.1 争议一：是否应撤掉 `TSFImeSupport`？

**W 的主张（2026-09-24 03:1x）**：建议撤掉该 flag。理由：其他软件走 TSF 路径、solo 被该 flag 改成 IMM32 路径，撤回默认或可趋同于正常软件。W 当时将该动作定性为「**低风险**，恢复出厂默认」。

**O 的主张（2026-09-24 03:2x）**：**不能撤**。三条理由：
1. **因果倒置**——「僵死、鼠标一动才好」的症状**先于** flag 存在（TSF 时代即有），flag 是当时的**应对**而非肇因。
2. 该 flag 是 09-14 为规避此 bug 而加的绕行，**不是**未经验证的随意改动。
3. 「撤掉 = 把原始 bug 请回来」，**不是低风险，是明确倒退**。

**核对结果**

| O 的理由 | 核对 | 依据 |
|---|---|---|
| ① 症状在先、flag 在后 | ✔ **成立** | `9a27bad` 标题即「规避」；09-13 全天取证时失锚已存在 ⇒ flag 是应对 |
| ② 该 flag 是为修此 bug 而加 | ✔ **成立** | 同上 |
| ③ 「撤掉 = 明确倒退」 | ⚠ **结论采纳，措辞可议** | 撤回后最可能的两种结果：**变差**（若 flag 部分有效）或**无变化**（若无效）——**没有任何理由变好** ⇒ 不应撤 |

**W 已撤回自身主张**（2026-09-24 03:2x 认账）：W 的「撤掉就好」隐含前提是「病是 flag 造成的」，**该前提无证据**；且 W 将风险定性为「低」**不准确**（默认路径即原始 bug 所在路径）。

**双方现状**：**已一致 —— 不撤。**

> 需注意：双方「不撤」的理由**不同** —— O 的理由是「症状先于 flag，撤了等于把原始 bug 请回来」（§2.1 其第 1、3 条）；W 的理由是「两条路径都是『钉死』，撤了也只会换个位置」。**但双方对「flag 有效性」本身已无分歧**（均认无正面证据，见 §2.3）。

### 2.2 争议二：`(782,706)` 究竟是候选窗，还是别的东西？（**本争议可当场复核**）

> **状态更新（2026-09-24 03:4x）**：**已闭合 —— O 已撤回原判定、明确认输。** 该坐标**确为候选窗**。O 的回执原文与撤回依据见本节末。

**O 的主张（2026-09-24 03:2x）**：该坐标**可能是误判**。理由：
1. 与我方当时逐帧核过的 `cmd.exe` 滚动条滑块位置几乎重合（O 描述：`rect 539,201-1532,720` 的右内底部，12px 蓝条位于 `784..952 × 708..720`）；
2. 当时 `WindowFromPoint(784,714)` **命中的是 `cmd.exe`**；
3. ⇒ 若锚点即此蓝块，则「两期共同模式」只余 TSF 一期成立，共同点不成立。

**W 的主张**：**该坐标确为候选窗**，O 的判定不成立。理由：
1. **裁图肉眼可辨**：蓝块上方有拼音串框、下方为候选词列表，蓝块即**选中项高亮**；
2. O 描述的「cmd 滑块」x 范围 `784..952`（宽 168）与本方检测的候选窗选中项 x 范围 `783..952`（宽 169）**重合 ⇒ 应为同一物体**；
3. **`WindowFromPoint` 会「穿透」候选窗**：候选窗**无独立 HWND**（见 §1 第 4 条），故该 API 必然穿过候选窗、命中其下**有 HWND 的**窗口（此处即 `cmd.exe`）⇒ **该探测结果恰是「候选窗在此」的自证**；

### 5.1 方案：IME 坐标重锚（零位移鼠标事件注入）

**一句话**：把「用户手动晃一下鼠标」这个**已知唯一有效**的动作，改为程序在特定时机**自动做一次**。

| 项 | 内容 |
|---|---|
| 机制 | Rust 侧调用 `SendInput`，注入**一次** `MOUSEEVENTF_MOVE`（`dx = dy = 0`，无按键、无滚轮） |
| 依赖 | **零新增** —— `src-tauri/Cargo.toml:45` 的 `windows-sys 0.61` 已启用 `Win32_UI_Input_KeyboardAndMouse`（含 `SendInput`）与 `Win32_UI_WindowsAndMessaging`，**无需下载任何新 crate** |
| 代码量 | 约 30~50 行（含去抖） |
| 挂载位置 | `src-tauri/src/commands/window.rs::attach_window_events()`（该函数已处理 `Focused` 分支，见 `window.rs:80`；`Resized` 分支需新增） |
| 平台 | 仅 Windows（`#[cfg(target_os = "windows")]`），其他平台零行为 |
| 回滚 | 删除该逻辑即可，**无持久化副作用** |

### 5.2 待定项 —— 触发时机（本方案唯一的设计缺口，双方均未解决）

失锚的两条观测事实：

| 事实 | 来源 |
|---|---|
| 触发条件 = resize / 焦点切换 / 切对象后的**首次**组字 | PLAN 封存结论 3 |
| 发作后**任何鼠标事件立即清除** | PLAN 封存结论 3 + 上游 `#5675` |

⇒ 「注入能治」有两种可能机制，**二者均未被验证**：

| # | 假设 | 含义 | 对应触发点 |
|---|---|---|---|
| **a** | 失锚 = 窗口变化后 WebView2 **内部缓存的坐标未刷新**，鼠标事件强制其刷新 ⇒ **提前注入可预防** | 注入有效 | **窗口 `Resized` 结束 / `Focused` 时**（= O 建议的方案） |
| **b** | 失锚 = **组字开始时**算出的锚点即为错值，与之前状态无关 ⇒ 提前注入**无效** | 须在失锚**之后**注入 | `compositionstart`（前端事件 → IPC 通知 Rust 注入） |

⚠️ **若真实机制为 (b)，O 建议的触发点（resize / focus）将无效。** 判断哪一个成立**无法预判，须实施后才能知道** —— 这是本方案最大的不确定性，也是它「可回滚、值得试」的原因（试错成本 = 一次构建）。

**另一处须标注的风险**：注入的鼠标事件**是否会干扰组字**？09-24 的教训是「按热键即打断组字」（§1 第 10 条）。零位移 `MOUSEEVENTF_MOVE` 按设计**不应**打断组字（组字由键盘 / 点击打断，非移动），但**未经验证**。

## 三、问题详情

### 🔴 [Major] F-1 ZWNJ 存活在**属性**里并被写进用户文件（§4「覆盖枚举已闭环」不成立）

- **位置**（写出点全部不经过 `escapeInline`，因它只作用于文本节点）：
  - `serializer.ts:667`（alt 读取）+ `:678` + `:680`（两处 `state.write` 均不经 `escapeInline`）—— `image.alt` / `image.title`
  - `serializer.ts:389` —— `link` mark 的 `title`（经 `escapeLinkTitle`，未剥）
  - `plugins/footnote.ts:40` —— `[^label]` 引用与定义**两处**
- **问题**：材料 §4 的判定表把「读正文文本的消费方」枚举了 8 类，口径全部是 `textContent` / `textBetween`。但解析期插入的 U+200C 不只落在文本节点上——它落在**delimiter 两侧的字符之间**，而 `![alt](src)` / `[a](u "title")` / `[^label]` 的 alt、title、label 是**解析期就固化进 attrs 的字符串**，序列化时原样 `state.write()` 出去，没有任何一处剥它。
- **实测**（探针 `[A]` 段，输入均为真实 markdown）：

  | 输入 | doc 内 | 脏属性 | 落盘 |
  |---|---|---|---|
  | `![甲**乙**，丙](x.png)` | 脏 | `image.alt` | **含 U+200C** 🔴 |
  | `- ![甲**乙**，丙](x.png)` | 脏 | `image.alt` | **含 U+200C** 🔴 |
  | `\| ![甲**乙**，丙](x.png) \|`（表格内） | 脏 | `image.alt` | **含 U+200C** 🔴 |
  | `![a](x.png "他**说**，好")` | 脏 | `image.title` | **含 U+200C** 🔴 |
  | `[a](u "他**说**，好")` | 脏 | `mark.link.title` | **含 U+200C** 🔴 |
  | `[^甲**乙**，丙]` + 定义 | 脏 | `footnoteRef.label` `footnoteDef.label` | **含 U+200C ×2** 🔴 |
  | 对照 `![甲**乙**丙](x.png)`（闭合符后无标点） | 干净 | — | 干净 ✅ |

- **风险**：与材料自判「本次最严重」的 math 落盘污染**同一后果**（把隐形字符写进用户文件），只是触发条件更窄。footnote label 后果最重——label 是**引用与定义的配对键**，落到 HTML 里还会进 `id`/`href`；alt 会进无障碍朗读与图片搜索；title 会进悬停提示。**幂等性我测了**：首存后收敛、不增生（稳定态各留 1 / 2 个），所以不是「越存越脏」，是「一次写脏、长期留在用户文件里」。
- **影响面（诚实口径）**：全仓 **107 份 md，落盘含 ZWNJ = 0 份**。⇒ 这是**潜在缺陷**，不是当前事故。定级 Major 而非 Critical 的依据就在这里。
- **修复**（两个层次，建议做①，把②记进敏感区）：

  ① **最小对位修法**（4 个调用点，与 math 入口清洗同源口径）：

  ```ts
  // serializer.ts · image
  const alt = stripZwnj(node.attrs.alt || '');
  const title = node.attrs.title ? stripZwnj(node.attrs.title as string) : '';
  // serializer.ts · link mark 闭合
  `](${href}${mark.attrs.title ? ` "${escapeLinkTitle(stripZwnj(mark.attrs.title as string))}"` : ''})`
  // plugins/footnote.ts
  state.write(`[^${stripZwnj(node.attrs.label || '')}]`);
  ```

  ② **契约措辞必须一起改**（否则同类第三次复发）。现在 `zwnj.ts:14` 与敏感区 #23③ 写的都是：

  > 「任何**读正文文本**后要对外呈现 / 计数 / 写盘的地方，都必须过 `stripZwnj`」

  「正文文本」这个词在语义上就把 attrs 排除了 —— **这就是漏掉的直接原因**。建议改成：
  > 「任何把**解析期产物**（正文文本 **＋ 由正文衍生的属性：alt / title / label / latex**）对外呈现 / 计数 / 写盘的地方」

  同时敏感区 #23⑤「覆盖清单（已闭环）」要把这 4 点补进去，并把「已闭环」改回「已覆盖 X 处，属性通道 2026-10-10 复审补入」。

### 🔴 [Major] F-2 体检工具对这一类**结构性全盲**，且「只报告不断言」确实会失效（答材料 §11.5）

- **位置**：`markdown/__tests__/fidelity-scan.spec.ts:49`、`:75`
- **问题**：判据是

  ```ts
  const WATCHED = ['strong', 'em', 'code', 'table', 'li', 'h1', 'h2', 'h3'];
  const lost = WATCHED.map((tag) => ({ tag, diff: count(before, tag) - count(after, tag) }))
                      .filter((entry) => entry.diff > 0);   // 只报「净减少」
  ```

  即**只数 8 种标签的减少**。于是四类问题它永远看不见：

  | 盲区 | 本次实例 | 工具能否报出 |
  |---|---|---|
  | 属性里的隐形字符 | F-1 全部 6 处 | ❌ `alt`/`title`/`label` 不在 WATCHED，且不是「减少」 |
  | 结构改写但元素数不变 | `~~~` 围栏 → ` ``` `、`__甲__` → `**甲**` | ❌ |
  | 内存态脏（落盘干净） | 缩进式代码块（F-7） | ❌ |
  | 自家语法丢格式 | `[[互链]]` 被转义成字面量（F-9） | ❌ 参照系本来就不认 `[[` |

  材料 §9.3 说「19 份里 18 份未定性」，而工具把这 18 份**只报成一行 `code-246` 这样的计数**——连形态都不给，下一轮仍要从零定位。
- **「只报告不断言」的失效路径**：`describe.skipIf(!process.env.SOLO_FIDELITY_SCAN)` ⇒ 不进 `bun run test`；即便显式跑，全文**没有任何 `expect`**，`console.log` 完就绿。⇒ 与材料自己警惕的「红灯文件不入库」是**同一种失效**，甚至更隐蔽（那个至少让人看见红）。
- **修复**（成本极低，收益直接锁住 F-1）：

  ```ts
  // ① 零成本、立刻堵住 F-1：落盘不得含 ZWNJ
  it('落盘不得含 ZWNJ（隐形字符不得出站）', () => {
    for (const f of files) {
      const out = serializeMarkdown(parseMarkdown(schema, readFileSync(f, 'utf8')));
      expect(out, relative(ROOT, f)).not.toContain('\u200C');
    }
  });

  // ② 棘轮断言：把当前 19 钉成基线，新增即红、存量不阻塞
  const BASELINE = 19;
  expect(rows.length).toBeLessThanOrEqual(BASELINE);
  if (rows.length < BASELINE) console.log(`优于基线 ${BASELINE}，记得下调`);
  ```

  另建议把 `WATCHED` 之外补一条「**逐行文本比对**」输出（哪一行变了、变成什么），否则「未定性」这个状态没法被下一个人接手。

### ⚪ [Info] F-8 ZWNJ 路线只救了 `*`，`==高亮，==` 仍静默丢格式（答 §11.1「未考虑的 delimiter 形态」）

- **实测**（探针 `[C]` 段，`zw=0` ⇒ **与本轮改动无关，是既有缺口**）：

  | 形态 | solo 载入 mark | 落盘 | GFM 参照 |
  |---|---|---|---|
  | `甲**乙，**丙` | `bold` ✅ | 逐字保真 | 参照**不成立**（ZWNJ 正是为此而造） |
  | `甲*乙，*丙` | `italic` ✅ | 保真 | 同上 |
  | `甲^乙，^丙` | `superscript` ✅ | 保真 | — （solo 自有） |
  | **`甲==乙，==丙`** | **`[]` 高亮丢失** 🔴 | `甲\=\=乙，\=\=丙`（凭空多转义） | — （solo 自有，无标准） |
  | `甲~~乙，~~丙` | `[]` | `甲\~\~乙，\~\~丙` | 参照**也不成立** ⇒ 判非缺陷 |
  | `甲==乙==丙` / `甲~~乙~~丙` | `highlight` / `strike` ✅ | 保真 | — |
- **判读**：`~~` 与外部标准一致，可不改（至多在文档里写明取向）。`==` 是 **solo 自有语法**，无外部标准背书，而同一个仓库里的另一条自有语法 `^` **在同样的边界上是好的** ⇒ 自有语法之间不一致，且「中文标点后紧跟闭合符」正是中文写作里 `==重点，==` 的自然写法。
- **建议**：**另立台账条目**（不属本轮，别混进 #35/#32 的结案口径）。修法方向现成：把 §1.5 的两条 flanking 规则从「只认 `*`」扩到「认 `==`」，或让 `==` 走与 `^` 同族的非 flanking 型 inline 规则。

### ⚪ [Info] F-9 两个「看起来像本轮漏网」的现象，对照实验证明是既有缺陷

材料 §4 的闭环声明让我优先怀疑这两类，**对照实验把它们摘清了**：

| 现象 | 输入（**doc 完全不含 ZWNJ**） | 结果 |
|---|---|---|
| 互链退化成字面量 | `[[笔记**甲**丙]]` | `\[\\[笔记**甲**丙]]` —— 链接丢失 |
| callout 标题被劈成两行 | `> [!note] 甲**乙**丙` | `> [!NOTE] 甲` + `> **乙**丙` —— 结构被改写 |

⇒ **与 §1.5 的 ZWNJ 无关**，是互链 / callout 自己的解析问题。建议各立一条独立台账（互链丢失按敏感区 #19 的口径属数据损失级），但**不应记在这一轮的账上**。

### ⚪ [Info] F-10 两处措辞与实现不符（不影响行为，影响下一个人的判断）

1. `zwnj.ts:25` 注释「`includes` 短路让『无 ZWNJ』的常见路径**零额外开销**」——严格说 `includes` 本身就是一次 O(len) 扫描，准确表述是「**零额外分配**」（无 ZWNJ 时不构造 split 数组）。见 §五的性能判读。
2. `plugins/math.ts:17` 注释「数学内容的**唯一来源**就是这里」——代码上不成立：`extensions/markdown-input.ts:104`（`mathBlockType.create()`）与 `extensions/slash-commands.ts:171`（`insertContent({ type: 'mathBlock' })`）也创建 math 节点。**当前无害**（两处都建空节点、内容由用户在 NodeView 里手打，不经解析期 ⇒ 不可能带 ZWNJ），但「唯一来源」这句话以后会把人误导去省掉别的清洗点。建议改为「**解析期 ZWNJ 的唯一来源**」。
   这同时是材料 §11.3 那一问的答案：**入口清洗对「写盘污染」够用**，不经过 `mathTokenHandlers` 的路径确实存在，但那条路上没有 ZWNJ 可带。真正无法覆盖的是**用户自己粘进含 U+200C 的 LaTeX**——那不属于本契约范围。

## 五、性能判读（性能调优维度）

**结论：本轮改动无性能阻塞，实测有余量。** 逐条：

1. **`parser.ts` 加 `\u0000` 到 4 个字符类**：复杂度**零增量**——仍是两遍 `O(n)` 全文扫描，字符类多一个成员只是一次位图/分支判断，不改变回溯结构（两条正则都无嵌套量词，无 ReDoS 面）。`(?<!\*)` + 单个 lookbehind 的形态不会因加一个类而变慢。
2. **`ASCII_SYNTAX_PUNCT` 提为模块常量**：这是**净收益**。原来两处相同的字面量 `/[\x21-\x2F...]/` 分散在两个 `replace` 回调里，各自求值；提为常量后编译一次。同时消掉「改一处漏一处」的维护风险。
3. **`stripZwnj` 的 `includes` 短路**：`zwnj.ts:29`。准确说法是「无额外**分配**」而非「零额外**开销**」（F-10①）——`includes` 是一次 `O(len)` 扫描。但它挂在 `escapeInline` 出口（`serializer.ts:479`），而那条路径上本来已有 5–8 次 `replace` 全文扫描，**新增的这一次占比极小**。
4. **实测数字**（探针 `[E]` 段，Node 纯计算口径，不含 WebView2 渲染）：

   | 语料 | 规模 | parse | serialize |
   |---|---|---|---|
   | 含 `**强调，**` 边界形态的中文段落 ×3000 | 115,890 字符（≈11.6 万字） | **46.5 ms** | **31.6 ms** |
   | 同规模但无强调触发 | 100,890 字符 | 16.5 ms | — |

   ⇒ 打开一篇 10 万字级文档，解析层成本在**几十毫秒量级**；含强调形态相对无强调形态的差值（46.5 vs 16.5）**不能全额归给 ZWNJ 正则**（两份语料的 markdown-it 分词工作量也不同），这里只作为**上界**给出。真瓶颈仍在前人记过的「未标注语言代码块 highlightAuto」（台账 §一 #30），本轮没碰它。
5. **`getEditorWordCount` / `extractEditorOutline` 加了 `stripZwnj`**：都是**每节点一次**的 `O(len)` 判断，与原有的 `replace(/\s+/g,'')` 同量级 ⇒ 增量可忽略。字数统计的调用频率受既有防抖约束（敏感区 #6），本轮未改节流层。
6. **体检工具成本**：全仓 107 份 md 跑完 784 ms，且有环境变量门控、不进 `bun run test` ⇒ 加断言不会拖慢门禁。

**建议的度量补充**（可选，优先级低）：F-2 的 `expect(out).not.toContain('\u200C')` 若进 CI，成本就是现有一次遍历，不额外加 parse。

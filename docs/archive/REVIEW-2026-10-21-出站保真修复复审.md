## 二、必须修：callout 去重会吃掉用户正文（Critical）

### 可复现的用户操作

在 solo 里写：

```markdown
> [!NOTE] 注意
>
> **注意**
>
> 正文
```

全选 → 复制 → 在同一篇或另一篇 solo 里粘贴。**正文里的加粗「注意」那一段消失**，只剩「正文」。

同样的 Markdown 源码从 Obsidian / Typora 以纯文本粘进 solo（走 Layer 1 `clipboardTextParser`），也会丢这一段。实测解析结果是 `['注意','正文']`，粘贴回读后变成 `['正文']`。

### 根因

出站注入的标题段与用户自己写的「加粗且文字等于标题」的首段，在 PM 节点层面**完全同形**：

- 注入段：`paragraph(text("注意", bold))`
- 用户段：`paragraph(text("注意", bold))`

`dropInjectedCalloutTitle` 的判据（`markdown-paste.ts:691-697`）只有「首段唯一文本 + bold + 文本等于 title」，没有来源标记 ⇒ 两者无法区分。`markdown-paste.ts:649` 那句「纯文本粘贴路径……天然不命中」也因此不成立：纯文本路径的正文里只要有 `**注意**`，照样命中。

这不是 WorkBuddy 擅自偏离：原审核 P1 给的正是这条判据（「attrs 有 title 且正文首段是纯 `<strong>` 等于该 title 就剥掉」）。**问题在方案本身，落地只是照做**。P0 原话还特意写了「不改 callout / footnote / frontmatter 这三条改写」，本次把三条改写一起挂到了 Ctrl+C 通道，风险面因此扩大——callout 这一条正好踩中。

### 为什么测试没拦住

`markdown-paste.spec.ts:916-922` 构造的正是这个同形场景，然后断言「首段被剥掉」。它把「用户正文恰好同名加粗」当成了「注入段」，等于把缺陷锁成了预期行为。现有测试里没有一条「用户自己写同名加粗首段，回读后必须保留」。

### 修法（建议）

不要靠内容猜来源，给出站注入段打一个私有标记，回读只删带标记的节点：

1. `surfaceCalloutTitle`（`externalize-html.ts:81-95`）注入时给 `<p>` 加 `data-solo-injected-title=""`（`data-title` 继续保留）。
2. 把去重从 `transformPasted` 的 slice 层移到 **HTML 解析前**：在 `transformPastedHTML` 里先做一次 `html.includes('data-solo-injected-title')` 的廉价判断，命中才解析 DOM，删掉 `div.mk-callout > p[data-solo-injected-title]`；Layer 4 的 `parseHtmlSlice` 也走同一个 helper。
3. 删掉 slice 层的 `dropInjectedCalloutTitle`。纯文本 Markdown 路径从未注入，本来就不需要去重。
4. `querySelectorAll` 天然覆盖嵌套 callout，顺带修掉下面的 Major。

代价：HTML 被第三方编辑器洗掉标记后粘回 solo，标题会以正文段落形式重复一次（**可见降级，不再是静默丢内容**）。这是正确的失败方向。

## 三、嵌套 callout：内层标题段不会被去重（Major）

`dropInjectedCalloutTitle` 在遇到 callout 时，只要标题为空或首段不匹配就直接 `return node`（`markdown-paste.ts:656-658`），**不再递归子节点**。因此：

```markdown
> [!NOTE]
> 外层无标题
> > [!TIP] 内标题
> > 内正文
```

复制再粘回后，内层 callout 的标题既在 header 里（`data-title`），又作为加粗正文段留在 body 里，实测正文从 `['内正文']` 变成 `['内标题','内正文']`。外层有标题但首段不匹配时同样不递归。用上面的标记方案后此问题自动消失。

## 四、两条核心用户故事仍未闭环（Major）

### 4.1 整篇 Ctrl+C 会把 YAML 带到公众号

「复制全文」按钮走 `document` 档位，会删 frontmatter；Ctrl+C 走 `selection` 档位，**刻意保留** frontmatter（为了粘回 solo 不丢元数据）。但用户复制整篇去公众号，最常用的动作恰恰是 `Ctrl+A → Ctrl+C`：frontmatter 是文档第一个块，必然被选中，公众号剥掉 `div` 的类与属性后**YAML 文本会显示在文章顶部**。

文档按钮路径是干净的，Ctrl+C 路径不是；wiki `:55` 只写了「粘回 solo 也不丢东西（元数据与私有属性都保留）」，没有提示外部目标会看到 YAML。这是本次档位取舍的**外部可见代价**，需要拍板：

- **A（推荐）**：选区 HTML 的第一个顶层元素若是 `div[data-type="frontmatter"]`，就删掉它。判据简单、不需要知道选区范围；`text/plain` 槽仍带完整 Markdown 源码，要元数据可走源码/按钮。代价是「从文档开头选一段并粘回 solo」会丢 frontmatter——这基本只在整篇替换时发生。
- **B**：保留现状，在 wiki 明确写「Ctrl+A 复制到公众号会带出 YAML 头，需手动删」。

### 4.2 本地图片仍然必裂，P2 提示没做

原审核把「本地图片在公众号裂图」列为 🔴 必坏第 1 项，建议 P2 做一次性提示。WorkBuddy 明确没做（理由：每次复制都弹是噪音、无法知道目标平台），改为在 wiki `:53` 写清「本地图片粘不过去，需后台重新上传」。**这是可接受的产品取舍，但「复制到公众号」的主路径仍然会裂图**，不是修好了。

如果要做，建议用非模态的一次性提示（同一文件同一会话只提示一次，或在复制按钮旁显示「本地图片 N 张」角标），不要每次弹框。是否做由产品拍板。

## 五、入站 `data-src` 的边界（4 条 Minor + 1 条安全回归 Major）

主路径正确（公众号懒加载图 `data-src="https://mmbiz.qpic.cn/..."` 能取到真地址）。但 `src.parseHTML` 无条件优先非空 `data-src`，实测 5 个边界：

| HTML | 解析结果 | 后果 |
|---|---|---|
| `data-src="" src="data:image/svg+xml;base64,…"` | `data:` URI 被接受 | 1×1 空白占位被写进文档，落盘一大串 base64——正是本功能要避免的 |
| `data-src="./a.png" src="https://cdn/a.png"` | 相对路径优先 | 明明有可用绝对地址，却落成本地路径 |
| `data-src="//cdn.example/a.png"` | 协议相对地址优先 | `isRemoteImageSrc` 只认 `http(s)`（`image.ts:146-148`）⇒ 判成「本地」；`syncView` 的 `fallbackSrc` 会把这个原始地址**直接交给 `<img>`**（`image.ts:387-397`），WebView2 按当前 http(s) 源补全并自行请求 ⇒ **绕过 Rust 远程图抓取的 SSRF 白名单（M-16）**；同时本地解析器注定失败 |
| `data-src="data:image/png;base64,…" src="https://cdn/a.png"` | data URI 优先 | 同上，占位图覆盖真图 |
| `data-src=""`（无 `src`） | `src: null` | 造出一个空图片节点，落盘 `![]()` |

`//` 这一条不是显示问题，是安全回归：`image.ts:384-386` 的注释明确写着「绝不把原始 URL 交给 `<img>`，否则 WebView2 会自行请求，Rust 的 SSRF 白名单被绕过」，而协议相对地址恰好走了这条被禁止的路。建议把 `//` 开头的地址归一成 `https:` 后交给远程抓取，或直接拒绝并在粘贴时丢弃该图。

其余建议：`data-src` 为空 / `data:` / `blob:` 时不要采用；`data-src` 是相对路径而 `src` 是绝对地址时优先 `src`；`img[data-src]` 规则排除空属性。这几条是纯加法守卫，风险小。

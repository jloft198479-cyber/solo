# 性能与主题再优化：空间评估与低风险建议（2026-09-18）
> 🗄 **本文件已归档（2026-09-30）**：一次性快照/历史提案，结论已吸收进活跃文档。仅作历史原件保留、不再维护。

> 性质：**建议文档，未动任何代码**。承接用户需求「性能再上一台阶（内存/响应/编辑体验/丝滑）+ 主题风格微调（舒适/美观），前提是不破坏现有功能、不产生新 bug」。
> 依据：壹以近期实测报告为准（[`REVIEW-2026-09-15`](../REVIEW-2026-09-15-体验与代码评估.md) / [`optimization-plan-2026-09-06`](./optimization-plan-2026-09-06.md) / [`KNOWN-ISSUES`](../KNOWN-ISSUES.md)），不重复已做项。

## 一、结论先行：还剩多少空间

**性能：大头已经吃完了，剩下的是缝，不是肉。**

| 维度 | 现状 | 剩余空间 | 一句话 |
|---|---|---|---|
| 响应速度 | 序列化 O(n²)→O(n)（443k 字 **20.5s→128ms，160×**）；打字/字数/大纲/序列化四层防抖 + 空闲调度；代码块高亮同步限 8 块 + 空闲分批 | **≈15%**，且都藏在「测量-再优化」缝隙里，量级不是翻倍 | 体感上的"卡"主要来源已消灭 |
| 内存 | 编辑区常驻 DOM + ProseMirror 文档树是锚点（非 JS 堆）；档位门控 + `content-visibility`（仅 heavy）已用；远程图缓存 LRU、WebView2 残留目录清理已做 | **结构性手段风险高**：虚拟化 / 卸载与 contentEditable 差分渲染冲突，动了就是新 bug 源 | 可控手段基本已用尽，剩下的都是"不想付出代价"的 |
| 编辑体验/丝滑 | 反跳、脏态语义比对、「测试换真身」防回归都已就位 | 功能层缺口（阅读位置记忆 / 最近文件 / 崩溃恢复 / 标题折叠 / 拖拽提示）已在 **KNOWN-ISSUES §二**，不在本文重复 | 丝滑度的短板是**功能**不是**性能** |
| 主题 | 8 主题全 token 化 + WCAG 审计 + 排版核心（行长/行高/字距/标题层级）已到最佳实践区间（`ui-typography-eval.md`） | **观感细调有空间**，但属主观项，逐项列在 §三 由你拍板 | 排版骨架别动了，动的都该是"锦上添花" |

> 大白话总结：**性能再上台阶的性价比在下降**。值得做的是 B 类「测量基建 + 两个有实证的缝」；主题是唯一"低风险就有观感收获"的领域。

## 二、现有基线（防重复清单——未来别再提这些）

以下已落地，**不在本文建议范围内**（来源：`REVIEW-2026-09-15` §7/§9、`KNOWN-ISSUES` §一）：

- 序列化 15 行修复 O(n²)→O(n)，`8e369af`
- `HEAVY_DOC_CHARS=50万` 重新标定并维持（下调会放大 IME 候选窗失锚暴露面，见 `document-scale.ts`）
- 代码块高亮：同步 8 块 + 空闲补算 4 块/批，`dd55210`
- 四层防抖（光标 100ms / 字数 150ms / 大纲 500ms / 序列化 500ms + rIC）
- 关窗/切档免序列化、fsync、卸载前 flush、硬盘/rem 缓存 LRU、启动清理移后台、搜索门控、`spawn_blocking`、删假 50MB 预算（C1–C9 全批）
- 打开即全量序列化：**实测后决定不改**（§9.3，理由成立：7.5ms×典型收益 vs 脏态时序风险）

## 三、剩余空间盘点（按风险分级）

### A 级 · 低风险，想做就能做（纯测量或纯观感，不碰编解码链路、不碰同步逻辑）

**A1 · 性能测量基建（最值得，ROI 最高）**

- 现状：所有性能结论都是"查一次测一次"的临时脚本，没有常驻测量手段。内存画像尤其缺——没有人知道"50 万字文档在 WebView2 里到底占多少 DOM 节点 / JS heap"。
- 建议：诊断模式（CI/CD 或 `--diagnostics`）下打开文档时，收集 `document.querySelectorAll('.tiptap-editor > *').length`、`performance.memory.usedJSHeapSize`（WebView2 支持）、打开耗时分段，写进现有日志/状态栏。**零行为改变**，纯观测。
- 验收：打开不同规模的 3 份文档，能回读出三段数字。不破坏任何功能。
- 附带收益：以后任何"性能再优化"提案都有基线可对照，不再靠感觉。

**A2 · 主题观感微调（纯 CSS 值，逐项拍板）**

| # | 项 | 现值 | 建议 | 风险 |
|---|---|---|---|---|
| T1 | 暗色主题正文亮度 | scholar-dark / cinnabar-dark 的 `textColor`（WCAG 已过下限但对深夜长读偏亮） | 各降一格亮度（如 `#d1d5db`→`#c9ced6` 量级），凭证：暗色下长文久读眩光 | 极低（token 值，亮暗自带适配） |
| T2 | 选区色 | `color-mix(primary 18%, transparent)`（editor.css:836） | 18% → 12%（更淡，观感更杂志） | 极低 |
| T3 | H4 层级 | 1.05em（与正文差太小，标题感弱） | 1.1em，拉开"小标题 vs 正文"辨识 | 极低 |
| T4 | 代码块视觉 | `codeBg`/`codeBorder` 已 token 化 | 暗色下 codeBg 降一档亮度 + 右侧 4px 圆角统一 | 极低 |
| T5 | 滚动条 hover | `--muted-color`（main.css:346） | 保持（已很克制），**不动** | — |
| T6 | 焦点模式淡化 | `--mk-focus-dimmed-opacity: 0.22` | 维持。加一档 0.18 给"沉浸二级"？**不建议**——单值简单，够用 | — |

> 原则：**本文只列可选项，你拍板才动**；且动之前先拍当前值截图，改完对比，避免"小声说"。
> T1/T2/T3/T4 加起来约 20 行 CSS/JSON token 改动，不碰 parser/serializer/同步，天然无脏态影响。

**A3 · 核查一处防抖档位盲区（先取证，不改）**

- 现象疑点：四层防抖里「光标 100ms」与实时字数是否在 heavy 档全部降级？`optimization-plan` 确认字数 heavy 停、大纲 heavy+关面板停；**光标信息档位**未在文档明确。
- 建议：只做一次走查（`useEditorSync.ts` + `document-scale.ts` 档位清单），确认「光标 100ms 全量遍历 doc」在 20–50 万字档是否也分层。**若未分层且实测有感知再改**；没有感知就登记"已核查、无需改"。
- 风险：零（纯只读核查）。

### B 级 · 中风险，需先测后改，改成什么待定

**B1 · 打开大文档的首帧串行段**（parse→serialize 基线→字数→大纲→高亮 8 块一次性同步跑）

- 现状：§9.2 实测 443k 字同步 ≈300ms(WebView2 ×2~3 后 ~0.6s) 全砸第一帧。
- 方向：首帧先出文本，其余（示范性的大纲/高亮补算）走 rAF/空闲。**但**基线序列化承重（§9.3 明确不能推后）；字数/大纲已有降级。真正的缝隙在"高亮前 8 块同步"是否也可挪——**改判风险高**，涉及敏感区第 1 条（脏态/时序）。
- 结论：**列为"需一次真机测量"**：1.8M 字 + WebView2 下首帧多少 ms，若 >500ms 再议；否则维持。

**B2 · 搜索在超大 normal 文档的装饰预算**

- 现状：C5 已做 heavy 档重扫防抖加大 + 匹配未变跳过 dispatch；但"数千匹配 = 数千装饰 + DOM 分裂"对 ~40 万字 normal 文档仍可能造成一次输入 120ms 停顿。
- 方向：命中数上限（如 >2000 匹配时装饰只标"有"不逐个高亮）或搜索面板不可见时不挂装饰。
- 风险：中（搜索高亮是既有功能，改判定可能踩组字冻结/装饰重建 → `composition-freeze` 铁律）。需先测 hit 数的真实分布，改成什么待定。

### C 级 · 不建议现在做（结构性问题，性价比低或与架构冲突）

| 项 | 原因 |
|---|---|
| 编辑器虚拟化 / 视口渲染（像 Obsidian viewport 那样只渲染可见区） | ProseMirror 假设全节点在 DOM（`domAtPos`/`nodeDOM`/选区），contentEditable 下虚拟化=重写 PM，等于换编辑器 |
| `document-scale` 全局单例收纳进 store | 属 KNOWN-ISSUES §二 #15 结构债，与性能无关，另行排期 |
| 双 markdown-it 管线收敛 | 属 §二 #16，P2 待办，不重复 |
| 更多主题/更多 typography 维度 | 8 主题 + 14 个排版 token 已够用；加维度=加维护面，与"减法原则"冲突 |

## 四、落地建议顺序（若采纳）

1. **A1 测量基建**（一两个晚上）——以后所有"性能再优化"的前提。
2. **A3 档位盲区走查**（半小时）——消除"有没有盲区"这个问号。
3. **A2 主题微调你拍板 3–4 项**（一晚上）——低风险拿到观感收益。
4. **B1/B2 各做一次实测取证**，有数字再议改不改。

每一项独立交付、独立验收，互不阻塞；**不破坏现有功能**由每步的验收（全量单测 + 逐字节 fixture diff，仅对牵涉 B 级时）背书。

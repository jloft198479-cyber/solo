# 审核：互链跨目录改造

> 被审对象一个字未动。以下每条给「现象 → 机制 → 证据行号 → 后果」。
> 编号 R-*，与评估文档（`docs/archive/solo互链设计评估-2026-10-20.md`）的 P0/P1 编号不混用。

## 一、总账（先回答他问的三件事）

| 问 | 答 |
|---|---|
| **设计是否自洽、三处口径是否真统一** | **两处统一了，第三处没有。** 补全候选 = 标红判定（同一份 Rust 清单、同一份深度常量，且有跨语言锁）；改名同步**只共用了「扫描范围」这一个参数**，匹配器仍然是「按裸文件名整词替换」，不含目录信息 ⇒ 与解析器的「链接相对**引用方文档**所在目录」语义不等价。 |
| **有无新引入的缺陷** | **有两条：R-1（会静默写坏用户文档，P0）、R-3（拖入 .markdown 当场生成自己标红的死链，P1）。** R-1 是本轮把改名扫描从「同目录」扩成「目录树」直接带出来的，改动前不可能发生。 |
| **有无未覆盖场景** | **有，且最要紧的一条恰好是本轮新造出来的主要写法**：R-2 父文档里的 `[[sub/B]]` 改名后永远同步不到 —— 而文档 `docs/FEATURE-MATRIX.md:51` 已经把它写成「已覆盖」。另附 R-4~R-7 四条（含方案文档要求但未落地的「不假装支持」）。 |

**一句话**：这次改造把「能点开但三个配套全缺」推进成「三个配套都有、但第三个配套改错了对象」。地基（一棵树、一个深度常量、一个完整性标志）是对的，问题集中在改名同步那一条链路的匹配语义上。

## 二、必须处理

### R-1 【P0 · 本轮新引入】改名同步会把子文档里「指向另一篇」的裸名链接改错，并落盘

**现象**：目录结构
```
notes/
  B.md          ← 改名成 C.md
  sub/
    B.md        ← 另一篇，没动
    深读.md      ← 里面写 [[B]]，指的是 sub/B.md
```
改根目录 `B.md` → `C.md` 之后，`sub/深读.md` 里的 `[[B]]` 被一起改成 `[[C]]`。

**机制**（两处叠加，缺一不成立）：
1. 改写器只认字面：`replace_targets_in_line` 拿 `old_stem` / `new_stem` 拼 `[[B]]`、`[[B|`、`[[B.md]]`、`[[B.md|` 四种字面做 `String::replace`，**完全没有目录信息** —— [`document.rs:418-431`](../src-tauri/src/commands/document.rs#L418-L431)。`old_stem` 来自 `file_stem()`（[`document.rs:466-470`](../src-tauri/src/commands/document.rs#L466-L470)），只有名字。
2. 扫描器这轮刚被扩成递归：根 = 改名文档的父目录（[`document.rs:462-465`](../src-tauri/src/commands/document.rs#L462-L465)），向下 2 层（[`document.rs:546-`](../src-tauri/src/commands/document.rs#L546) `scan_and_rewrite_into`）⇒ `sub/深读.md` 现在进了被改集合。

**这条链接的正确语义**（同一份代码在别处写明了）：
- 解析：`resolveWikilinkTarget(currentPath, target)` = **引用方文档的目录** + target + `.md` —— [`wikilink.ts:41-57`](../src/components/Editor/tiptap/extensions/wikilink.ts#L41-L57)。所以 `sub/深读.md` 里的 `[[B]]` 指向 `sub/B.md`，**与根目录的 B.md 无关**。
- 标红：索引**故意不登记末段裸名**，理由逐字写着「`sub/c.md` 不许让 `[[C]]` 变成『存在』」—— [`wikilink-existence.ts:51-53`](../src/components/Editor/tiptap/extensions/wikilink-existence.ts#L51-L53)，且有锁 [`wikilink-existence.spec.ts:66-75`](../src/components/Editor/tiptap/extensions/__tests__/wikilink-existence.spec.ts#L66-L75)。

⇒ 改名同步是这条原则的**唯一违反者**：标红认为 `[[B]]` 该对着 `sub/` 比对，解析认为它该打开 `sub/B.md`，改名同步却把它当成根目录那篇的链接改了。

**后果**：一次普通改名 = ① 静默改写用户没在看的文件（本项目最贵的一类事故，AGENTS §1 禁令 4/6 针对的就是这个）；② 把一条**本来能用**的链接改成死链，且改完标红会亮 —— 用户视角是「你改你的根目录文件，为什么把我子目录里好好的链接弄坏了」。改动前扫描严格同目录，同目录裸名恰好等价于同目录解析 ⇒ 这条不可能发生。**是本轮新引入的回归。**

**测试不仅没兜住，还把它锁成了预期行为**：
- [`document.rs:1810-1812`](../src-tauri/src/commands/document.rs#L1810-L1812) 造出 `sub/deep.md` 内容 `[[old]]`；
- [`document.rs:1821-1824`](../src-tauri/src/commands/document.rs#L1821-L1824) 断言 `changed == ["link.md", "sub/deep.md"]`；
- [`document.rs:1830`](../src-tauri/src/commands/document.rs#L1830) 断言其内容被改成 `[[new]]`。
该测试的改名主体是根目录的 `old.md → new.md`，而 `sub/deep.md` 的 `[[old]]` 按解析口径指向 `sub/old.md`（测试里根本没这个文件，所以「改了也没人发现」）。**反向验证**：把 `depth` 传 0 或删掉递归，`sub/deep.md` 那条断言立即转红 —— 说明这条锁锁的正是「递归必须改到子文档」。

**修法（建议，一次同时解决 R-1 与 R-2）**：改名同步**不要按名字匹配，改成按链接自己的解析口径逐条判定**：
1. 对被扫文档 D（目录记 `dirD`），把候选目标串（裸名 / 带 `.md` / 带相对路径）解析成绝对路径，**只有解析结果 == `old_path` 才替换**；替换写入的是「D 到 `new_path` 的相对路径」。
2. 扫描范围相应从「向下 2 层」改成「**本层 + 向上 2 层**」。依据：能被 D 用相对路径指到的目标，只可能在 D 的目录或其祖先目录（指向祖先需要 `../`，而 `../` 在标红侧已明确「判不了不标」[`wikilink-existence.ts:99-100`](../src/components/Editor/tiptap/extensions/wikilink-existence.ts#L99-L100)，本轮产品口径不支持）。反过来，从改名文档出发要找到引用方，就是「本层 + 祖先」。

**若只想先止血（最小改动）**：把裸名改写限制在**改名文档自己那层目录**，递归层不再做裸名匹配（即 R-1 消失，R-2 仍在但不写坏任何东西）。**不要**保持现状上线 —— 它写盘。

### R-2 【P0 · 未覆盖 + 文档口径与实现相反】父文档里的 `[[sub/B]]` 改名后一定改不到

**现象**：`notes/索引.md` 写着 `[[sub/B]]`（由本轮补全菜单插入，或拖入 `sub/B.md` 生成）。把 `notes/sub/B.md` 改名成 `C.md` ⇒ 这条链接**不会**被同步；下次打开索引页它会标红。

**机制**（两条独立原因，任一单独存在都改不到）：
1. 扫描根 = 被改名文档的父目录，**只往下走** —— [`document.rs:462-465`](../src-tauri/src/commands/document.rs#L462-L465) + [`document.rs:546-590`](../src-tauri/src/commands/document.rs#L546)。引用方在**父目录**，压根不在扫描集合里。
2. 就算扫到了也匹配不上：改写器只认 `[[B]]` / `[[B.md]]` 两种字面（[`document.rs:418-431`](../src-tauri/src/commands/document.rs#L418-L431)），`[[sub/B]]` 里的字面是 `sub/B`，永远不等于 `B`。

**为什么这条最要紧**：本轮之前的跨目录链接只能靠用户手打；本轮之后，**`sub/B` 是补全菜单和拖入成链的默认产物**（[`wikilink-suggest.ts:31`](../src/components/Editor/tiptap/extensions/wikilink-suggest.ts#L31) `target` = 相对路径、[`wikilink-drop.ts:95`](../src/components/Editor/tiptap/extensions/wikilink-drop.ts#L95) 同）。也就是说这次改造**主动把用户推向唯一一条改名同步管不了的写法**。评估文档 P0-2 批评的「半做：能点开，但改名那天全断」没有消失，只是从「子目录目标」搬到了「父文档指向子目录」，而后者是新链接的主流方向（一文件夹一项目 = 根索引页往下指）。

**缓解（不是解决）**：断链**看得见**（下次打开/清单刷新会标红，[`wikilink-existence.ts:102`](../src/components/Editor/tiptap/extensions/wikilink-existence.ts#L102) 深度内会判）。但 KNOWN-ISSUES #23 的产品口径是「改名即同步、不问用户，因为弹框会被打断、错过就永久不同步」—— 这一类恰好永久不同步，只给一条红波浪线。

**⚠️ 文档写错了，且会误导下一个执行者**：
[`docs/FEATURE-MATRIX.md:51`](../docs/FEATURE-MATRIX.md#L51) 现文：「范围 = 当前目录树（深度 2，与补全/标红**同源**）；**覆盖裸名、`[[子/文]]`、带 `.md`**」。
`[[子/文]]` 一条都不覆盖（上面机制 2 是源码级证死）。旧文本原本写的是「手打的 `[[子/文]]` 不覆盖」，是本轮把它翻成了「覆盖」，但实现里匹配器一行没改。
→ 这条要么改成事实（「仅裸名 + 带 `.md`，且仅改名文档同层」），要么按 R-1 修法把实现补上。**不能留着**：它现在的价值是让下一个改动者以为已经做完。

## 三、应当处理

### R-3 【P1 · 本轮新引入可见症状】拖入 `.markdown` → 当场生成一条被自己标红的死链

- 拖入允许 `.md|.markdown` 并**把后缀整个吃掉**：[`wikilink-drop.ts:15`](../src/components/Editor/tiptap/extensions/wikilink-drop.ts#L15) `LINKABLE_EXT`、[`wikilink-drop.ts:89-96`](../src/components/Editor/tiptap/extensions/wikilink-drop.ts#L89-L96) ⇒ `sub/B.markdown` 的 target 变成 `sub/B`。
- 解析只会补 `.md`：[`wikilink.ts:55`](../src/components/Editor/tiptap/extensions/wikilink.ts#L55) ⇒ 找 `sub/B.md`，不存在 ⇒ 点开弹「创建」，确认后 [`MarkdownEditor.vue:245-250`](../src/components/Editor/MarkdownEditor.vue#L245-L250) 真的建出一个空的 `sub/B.md`，与原 `sub/B.markdown` 并存。
- 标红现在也会亮：清单只列 `.md`（[`document.rs:196-197`](../src-tauri/src/commands/document.rs#L196-L197)），索引只登 `.md`（[`wikilink-existence.ts:61-63`](../src/components/Editor/tiptap/extensions/wikilink-existence.ts#L61-L63)）。

**是本轮才变得可见的**：HEAD 版的索引还收 `.markdown` / `.txt` 的词干，所以拖完不标红（问题同样存在，只是藏住了）。现在两个入口口径终于一致了 —— 一致在「都是死的」这一边。

**一行修法**：非 `.md` 不去后缀，让 target 保留 `sub/B.markdown`。两侧本来就都支持这种写法，且都有测试：解析带扩展名不补 `.md`（[`wikilink.ts:55`](../src/components/Editor/tiptap/extensions/wikilink.ts#L55)）、标红遇非 `.md` 不判（[`wikilink-existence.ts:104-107`](../src/components/Editor/tiptap/extensions/wikilink-existence.ts#L104-L107)，锁在 [`wikilink-existence.spec.ts:118-124`](../src/components/Editor/tiptap/extensions/__tests__/wikilink-existence.spec.ts#L118-L124)）。改名同步对这类目标仍不覆盖 —— 那是台账已登记的既有限制，别和这条混为一谈。

### R-4 【P2 · 需要拍板】同目录只有 `B.markdown` 时，`[[B]]` 判死链

评估文档 §5.1 第 2 条推荐「两处都**收**（`.markdown`/`.txt`）」，实现选了另一半「两处都**只收 .md**」。
- 自相矛盾确实消除了（标红与点开现在口径一致）：`[[B]]` 标红 + 点开弹创建 `B.md`。
- 但选了这一半的实际产品后果：笔记库以 `.markdown` 为主的用户，重开文档会**满屏红波浪线**，点一条就复制出一个空 `.md` 双胞胎。
- 这个取舍**没有登记**：KNOWN-ISSUES #78 的已知限制只写了「超出深度 / `../` 出界 / 绝对路径」三类，没写这一类；FEATURE-MATRIX 的失效互链行也没写（[`docs/FEATURE-MATRIX.md:75`](../docs/FEATURE-MATRIX.md#L75)）。
→ 要么明写「solo 互链只认 `.md`，其他可编辑后缀不受互链支持」并记进台账（`.markdown` 仍能被打开、仍能被拖入 → 那 R-3 就是必须修的），要么按评估文档的原推荐把解析也扩展到三种后缀。**别停在中间**：现在既允许打开 `.markdown`、又允许拖入成链、又把它判成死链。

### R-5 【P2 · 交付与方案不一致】「判不了」仍然对用户静默 —— 方案要求的「不假装支持」没落地

- `truncated` 为真 ⇒ **整篇放弃标红**：[`wikilink-existence.ts:119-123`](../src/components/Editor/tiptap/extensions/wikilink-existence.ts#L119-L123)。
- 超深度 / `../` 出界 / 绝对路径 ⇒ 静默放过：[`wikilink-existence.ts:96-107`](../src/components/Editor/tiptap/extensions/wikilink-existence.ts#L96-L107)。

产品效果：**目录树 >500 个 .md 或 >2000 个目录时，失效标红这个功能对该文档整个消失，界面一个字都不说。** 用户分不清「链接是好的」和「没检查」。评估文档 §5.2 第 5 条原话是「超出深度的目标不标红、不改名，**但也不假装支持** —— 悬停提示里写清『超出当前文件夹范围』」，这条没做。补全侧同样没有「清单不完整 / 还有更多」的提示（评估 P2-5，本轮未做；现在候选多了子目录，更容易撞菜单 50 条上限 [`wikilink-suggest.ts:25`](../src/components/Editor/tiptap/extensions/wikilink-suggest.ts#L25)）。

→ 不是 bug，是口径与方案不一致。**要么补一句提示，要么在方案里明写「不做」**，别让它以「实现悄悄少做一条」的形式留在台账外。
→ 另：改名同步这条链**没有** `truncated` 反馈，被闸门挡掉的文档不会同步，状态栏照报「已更新 N 篇文档里的链接」（[`useDocumentSession.ts:~445`](../src/composables/useDocumentSession.ts#L445)）—— N 是少的那个。

## 五、核过没问题、下一个审查者不必再怀疑的部分

逐条开过原文，判**证实**：

1. **锚点剥离（评估 P0-1）三处一致，可结案**。`splitWikilinkAnchor` 只切第一个 `#`、纯锚点 path 为空（[`wikilink.ts:27-32`](../src/components/Editor/tiptap/extensions/wikilink.ts#L27-L32)）；解析调它（`resolveWikilinkTarget` [`wikilink.ts:46`](../src/components/Editor/tiptap/extensions/wikilink.ts#L46)）、标红调它（[`wikilink-existence.ts:87`](../src/components/Editor/tiptap/extensions/wikilink-existence.ts#L87)）、创建流程调它且用剥完的 `targetPath` 当标题（[`MarkdownEditor.vue:214, 245`](../src/components/Editor/MarkdownEditor.vue#L214)）⇒ 不会再创建 `B#小节.md`。纯锚点 `[[#小节]]` 单独给一句话、不落创建流程（[`MarkdownEditor.vue:215-220`](../src/components/Editor/MarkdownEditor.vue#L215-L220)）。语法层 `[^\]|]+` 允许 `#` 与 `/`，round-trip 不丢（[`markdown/plugins/wikilink.ts:8`](../src/components/Editor/tiptap/markdown/plugins/wikilink.ts#L8)）。代价（文件名含 `#` 不可链接）已在注释里明写并留档（[`wikilink.ts:23-25`](../src/components/Editor/tiptap/extensions/wikilink.ts#L23-L25)）。
2. **索引「不登记末段裸名」是对的，而且正是 R-1 该采用的判据**（[`wikilink-existence.ts:51-53`](../src/components/Editor/tiptap/extensions/wikilink-existence.ts#L51-L53)）。这把 P0-3 那类「不标红但要点开才说要创建」的矛盾从根上堵住 —— 可惜只有标红侧遵守了。
3. **完整性标志是真标志，不是提示**。`truncated` 由 Rust 显式给出并在**排序前**判定（[`document.rs:184-201`](../src-tauri/src/commands/document.rs#L184-L201)），两个闸门任一触发都置真（`:198-201`）；前端只信它、不再靠「长度 == 上限」猜，且有专门用例区分两种口径（[`wikilink-existence.spec.ts:178-198`](../src/components/Editor/tiptap/extensions/__tests__/wikilink-existence.spec.ts#L178-L198)）。这条升级是对的：目录闸门触发时长度远不到上限，靠猜必漏。

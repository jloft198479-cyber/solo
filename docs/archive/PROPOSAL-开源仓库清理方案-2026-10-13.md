# 开源仓库清理：业界最佳实践与 solo 的可行路径

> 2026-10-13 整理。目的：回答「怎么让公开仓库里只有产品代码」。
> 触发：简乐要求清理，本方先用 `git filter-branch` 实操一轮，造成工作区文件被删，已完整还原。
> 本文所有结论附来源，可信度随文标注。

## 一、先摆事实（决定可选范围）

| 事实 | 取值 | 来源 |
|---|---|---|
| 仓库可见性 | **公开（PUBLIC）** | `gh repo view` 实测 |
| 已入库文件 | 448 个，其中 .md 151 份 | `git ls-files` 实测 |
| 是否已推送过内部文档 | **是**（docs/ scripts/ 已在远端） | `gh api repos/:owner/:repo/contents/docs` 实测 |
| GitHub 是不是自动更新源 | **是**（updater 拉 `latest.json` + 签名包） | 项目记忆：双通道约定 |
| 已发布 Release | v1.2.55 ~ v1.2.59（Latest = v1.2.59） | `gh release list` 实测 |

**两条硬约束（推导出的，不是猜的）：**

1. **不能改私有、不能换仓库地址** —— 私有仓库的 Release 资产需认证才能下载，换地址则老用户手里的软件仍指向旧地址 ⇒ 自动更新直接失效。
2. **已发布的 Release 不能删** —— Release 挂在 tag 上，删 tag 会带走 Release ⇒ 同样搞挂自动更新。

## 二、业界最佳实践（10 条来源）

### 2.1 关于「从历史里删文件」

- **工具选型：官方推荐 `git filter-repo`，不是 filter-branch。** GitLab 官方文档原话：「We recommend git filter-repo over git filter-branch and BFG」【高】；DeployHQ 称 filter-branch 是「deprecated fallback」，只在 filter-repo 和 BFG 都不可用时才用【高】。
  来源：https://archives.docs.gitlab.com/17.4/ee/user/project/repository/reducing_the_repo_size_using_git/ · https://www.deployhq.com/git/faqs/removing-large-files-from-git-history
- **⚠️ 最关键的一条：推过的东西应视为已泄露。** GitHub 官方原话：「Once you have pushed a commit to GitHub, you should consider any data it contains to be compromised」。删历史之后，旧 commit 仍可能通过**已有 clone / fork / SHA-1 直接访问 / GitHub 缓存视图**看到，彻底清除需联系 GitHub 管理员清缓存【高】。
  来源：https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository
- **标准流程（各家一致）**：备份 → filter-repo → **加 .gitignore 防止再次提交** → force push → `git reflog expire --expire=now --all` + `git gc --prune=now --aggressive` 才能真正回收【高】。
- filter-repo 默认要求 fresh clone；在现有 checkout 上跑要加 `--force`，且**必须先备份**【高】。

### 2.2 关于「公开仓库只放产品代码」

- **主流做法一：两个仓库 / 两个 remote（不重写历史）。** AppNeta 真实案例：私有仓库做全部开发与内部讨论，公开仓库只放代码与发布，两边互相同步 commit【高】。
  来源：https://gist.github.com/JosephTerranova/cca25b9383a19697dd3fef3c32d33eb1
- **主流做法二：全新公开导出（fresh public export）。** 当私有仓库历史里有不该公开的东西时，从当前工作树重新 `git init` 一个干净仓库、历史从零开始，再推到新的公开仓库。systemdesigner 的发布指南明确写：「Use a fresh public export when the private repository history contains files that should not be public」【高】。
  来源：https://github.com/alibad/systemdesigner/blob/main/docs/MAINTAINER_RELEASE.md
- **主流做法三：单仓库双 remote。** 一个仓库加 `public` 和 `private` 两个 remote，公开 remote 只推已 sanitize 的分支【中】。
  来源：https://github.com/massimilianoC/andy-code-cat/blob/main/docs/PRIVATE_CONFIG_GUIDE.md
- **通行禁忌清单（多来源一致）**：.env、真实 IP/密钥、账单数据、内部评审、部署 runbook、归档文档，一律不进公开仓库；并配 `.gitignore` + 提交前检查【高】。

## 三、套到 solo 身上：三条路各自的代价

| 方案 | 做法 | 能不能真干净 | 代价 |
|---|---|---|---|
| **A. 只管今后** | 加 .gitignore，从今往后不再提交内部文档/脚本 | ❌ 旧历史仍可翻到 | 零风险 |
| **B. 重写历史（filter-repo）** | 用官方工具把 docs/scripts 从全部提交中剔除，force push 到**同一个**仓库 | ⚠️ 部分——旧 Release 的 tag 必须保留，而 tag 指向的旧 commit 里文档仍在 | 中等：需 force push，且**已推送过的内容按 GitHub 官方说法应视为已泄露**，不能保证彻底 |
| **C. 全新公开导出** | 干净工作树重新 git init，推到**新**仓库 | ✅ 最干净 | ❌ **不可行**——换地址 = 自动更新挂 |

## 四、结论与建议

**推荐 A（只管今后），理由是 B 打不到你的目标。**

关键推导：你要的「开源库里看不到内部文档」，B 做不到——因为 **v1.2.55~v1.2.59 的 Release 必须留着**（否则自动更新挂），而 Release 挂在 tag 上，tag 指向旧 commit，旧 commit 里那 151 份文档就还能被翻到。除非你愿意**放弃旧 Release**，而那等于让所有已安装用户失去更新。

所以真实选择题是：

1. **接受「旧历史翻得到、今后不再上传」** → 方案 A，10 分钟，零风险。
2. **愿意牺牲旧 Release 换彻底干净** → 方案 B 的加强版（重写历史 + 删旧 tag 重建），代价是 v1.2.55~v1.2.59 的 Release 页面和自动更新链要重建，**风险高，不建议**。

另有一条独立建议：**今后把内部文档彻底移出 git 仓库**（放进 `.workbuddy/memory/` 这类已被忽略的目录，或本地私有仓库），而不是靠 .gitignore 兜着——gitignore 只防 `git add -A`，防不住 `-f` 和误操作。

| 备份 | 有效。`M:\temp\solo-full-backup-20261013.bundle`（190MB）+ tag `backup-before-clean-20261013` |

**教训**：这类操作必须先做「工作区文件会不会被删」的预演，而不是做完再补；工具选型应先用官方推荐（filter-repo），本机没装就先申请安装，不要用 deprecated 的替代品硬上。

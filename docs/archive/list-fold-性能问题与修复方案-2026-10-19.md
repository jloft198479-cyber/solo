# list-fold 按键全量重建：问题与修法（复查修订版）

> 2026-10-19 21:00 复查修订：初版方案（按「插入/删除里有没有列表节点」判结构）
> 有漏判风险，已改为**保守黑名单**；rAF 调度改为**事务内同步重建**（顺带消灭组字期空转）。
> 本文以此版为准。仍然**未改代码**。

## 一、问题

一次普通按键（列表项里打一个字）会走：

1. `view.update()` 发现 `doc !== prevState.doc` → 排一个 `requestAnimationFrame`
   （[`list-fold.ts:305-315`](../src/components/Editor/tiptap/extensions/list-fold.ts)）。
2. 下一帧派发一个只带 meta 的事务：`setMeta(listFoldKey, { rebuild: true })`。
3. `apply()` 收到 rebuild → `pruneFolded()` → `buildDecorations(tr.doc, folded)`
   —— **全文档 `descendants` 扫描**并重建全部箭头装饰。

而同一段 `apply` 里已经做过 `decorations.map(tr.mapping, tr.doc)`——纯文字输入时
这已经足够。⇒ **每敲一个字 = 一次全文扫描 + 一次全量重建 + 一次多余事务**。

### 实测代价（happy-dom，生产扩展，10 字插入 + 单次全量重建）

| 列表规模 | 节点数 | 单次全量重建 | 每键 |
|---|---|---|---|
| 200 项 | 5,286 | 1.0ms | 无感 |
| 1,000 项 | 27,686 | 4.3ms | 轻微 |
| 3,000 项 | 89,686 | **27ms** | **掉帧** |
| 8,000 项 | 244,686 | **213ms** | **明显卡顿** |

`HEAVY_DOC_CHARS = 50 万字` 远高于这些规模 ⇒ 这一段没有降级。当前用户文档
0.4–45KB，基本无感——是性能债，不是当前故障。

## 二、复查发现（与初版方案的三处不同）

### 1) 结构判定：白名单会漏，改成保守黑名单（关键修订）

初版想「检查插入/删除的 slice 里有没有 listItem / 列表容器」。问题是：
**漏掉任何一种结构形态（或将来上游新增 step 类型）都会留下坏箭头**，
而这类错误是静默的（箭头缺失/残留），测试很难穷举。

改为反过来：**只放行确认安全的 step，其余一律重建**。

| step | 判定 |
|---|---|
| `ReplaceStep`，插入内容全是 inline、被删内容也全是 inline | 安全，跳过重建（＝打字、删字、行内粘贴） |
| `AddMarkStep` / `RemoveMarkStep`（加粗、链接等） | 安全，跳过 |
| `AttrStep`（节点属性） | 安全，跳过 |
| `ReplaceAroundStep`（回车切开项、缩进、包裹列表、改块类型） | **重建** |
| 任何含 block 节点的 `ReplaceStep`（粘贴块、删整段、合并段落） | **重建** |
| 其它未知 step | **重建** |

代价：极少数「与列表无关的块级编辑」（如粘贴一个普通段落）会多扫一次；
收益：**不可能因为漏判而留下坏箭头**——未知情况一律退回今天的全量重建。

### 2) rAF 调度：不能简单删，但也不该每次按键都排

初版说「去掉 rAF」。复查发现它还有一个必须保留的职责：
**组字期发生结构变化时，要等解冻后再重建**（组字期只能 map）。
直接删掉会导致「组字中改了结构 → 结束后没人重建」。

最终做法：**不再用 rAF 派发重建事务，改成 `apply` 里同步重建**，并用一个
`pendingRebuild` 状态位处理组字期：

- 非冻结 + 结构变化 → 当前事务内直接重建（同一次 view 更新，箭头不会晚一帧）；
- 冻结 + 结构变化 → 只 map，置 `pendingRebuild = true`；
- 解冻后的第一个事务 → 发现 pending → 重建并清位。

好处：
- 每键不再多派发一个事务（少一次全插件 `apply`）；
- 组字期不再每帧空转重排（现在冻结时 `scheduleRebuild` 会每帧重排自己）；
- 箭头在结构变化的**同一帧**就位，不会晚一帧。

### 3) 记忆与剪枝时机：确认安全，但要补回归

- `pruneFolded` 从「每键」变成「结构变化 / 折叠切换 / 整文档替换 / 光标揭示」时执行。
  纯文字 step 不可能让「某项是否含子列表」发生变化（那需要删/加块），所以安全。
- `saveFolded` 仍在这几个时机 + 切文档时执行；切文档分支本来就先存旧再取新
  （`isWholeDocReplace`），编辑期位置由 `mapFolded` 平移 ⇒ 记忆不会变旧。
- 要补一条回归：**折叠后在上方打字 → 切走 → 切回**，折叠位置仍是同一项
  （现有测试已有近似用例，确认仍绿即可）。

### 4) 结构性操作仍是一次全量扫描（本轮不治）

回车/Tab/删除项都会触发一次全量重建。3000 项时约 27ms、8000 项约 213ms。
这类操作是「一次一行」的节奏（不是每键），27ms 通常无感；8000 项属于极端长列表。
是否要做「按受影响项局部重建」见 §五阶段 2。

## 三、最终方案（阶段 1，推荐先做这个）

### 状态

```
{ folded: Set<number>, decorations: DecorationSet, path: string|null, pendingRebuild: boolean }
```

### apply 伪代码

```
if (isHeavyDocument) → emptyState
if (meta.toggle)      → 改 folded + 重建 + pending=false
if (meta.rebuild)     → prune + 重建 + pending=false
if (isWholeDocReplace)→ 存旧路径记忆 / 恢复新路径 + 重建 + pending=false
if (!tr.docChanged)   → 只做 revealFoldedAtCursor（不变）
if (frozen) {
  folded/decorations = map
  if (touchesStructure(tr)) pendingRebuild = true
  return
}
folded/decorations = map
if (touchesStructure(tr)) pendingRebuild = true
if (pendingRebuild) { prune + 重建; pendingRebuild = false }
revealFoldedAtCursor（不变）
```

`touchesStructure(tr)` = 「并非所有 step 都属于安全集合」（见 §二.1）。
安全集合的判定只看每步的 **inserted slice** 与 **被删区间**（`tr.docs[i]`）是否全为
inline 节点；任何 block → 视为结构变化。

### 删除的东西

- `view.update()` 里的 `scheduleRebuild()` 与整个 rAF 调度；
- 每键一次 `setMeta({rebuild})` 事务。

### 保留的东西

- widget 稳定 key（DOM 复用）、`isHeavyDocument` 降级、组字冻结的 map 分支、
  折叠记忆、光标揭示、toggle 语义——全部不动。

## 四、副作用逐项核对

| 面 | 结论 | 依据 |
|---|---|---|
| 文档 / 文件格式 | **零改动** | 只改 view 层装饰，不碰 doc/schema/serializer |
| 序列化 / 往返 | **零改动** | 同上 |
| 输入法 | **只减不增**：组字期仍然只 map；且不再每帧空转、不再每键多派发事务 | 冻结分支原样保留 |
| 箭头 DOM | 仍靠稳定 key 复用，不重建 | key 未动 |
| 折叠记忆 | 保存时机不变，位置靠 map；切文档先存后取 | 现有分支未动 |
| 撤销 / 重做 | 非纯文字 step → 重建，箭头随文档回到对应状态 | 黑名单判定 |
| 大文档降级 | 不变 | 分支未动 |
| 箭头出现时机 | 结构变化同一帧出现（比现在早一帧） | 同步重建 |
| 成本 | 打字：0 次扫描；结构操作：1 次（与现在相同） | 实测口径 |

## 五、分阶段建议

### 阶段 1（本次）：去掉按键级重建
- 改动集中在 `list-fold.ts` 一个文件，~40 行；
- 解决 99% 的浪费（打字是绝对高频操作）；
- 结构操作保持现状（一次全量），风险最低。

### 阶段 2（可选，先实测再决定）：结构操作局部重建
- 只重建「受影响项」及其父项范围内的装饰，把回车/Tab 的成本从 O(文档) 降到 O(项)；
- 难点是「受影响范围」要扩到最近的外层列表项，且回车会产生**新兄弟项**，
  范围要包含它的落点；漏一个就会缺箭头；
- 建议等阶段 1 上线、用真实长列表（2000+ 项）实测回车手感后再决定。

### 阶段 3（可选）：折叠切换局部化
- toggle 目前也是全量重建；8000 项时点击折叠要 213ms；
- 与阶段 2 同源（局部重建），可合并考虑。

## 六、测试矩阵与反向校准

**行为锁**

| 场景 | 期望 |
|---|---|
| 项内打 10 个字 | **不产生**任何 rebuild 事务；箭头 DOM 复用；折叠态不变 |
| 回车建新项 | 新项立刻有箭头；旧项箭头不变 |
| Tab / Shift-Tab（带子树） | 箭头随结构增减正确出现/消失 |
| 删除唯一子项 | 父项箭头消失（不能只靠 map） |
| 删除整项 | 箭头随之消失 |
| 粘贴嵌套列表 | 新项都有箭头 |
| 加粗 / 加链接 / 改任务勾选 | 不重建（安全集合） |
| 撤销 / 重做 | 箭头与折叠态回到对应状态 |
| 组字中改结构（合成事件模拟） | 冻结期只 map；解冻后重建一次 |
| 切文档 | 记忆/恢复不变 |

**性能验收**
- 3000 项连打 10 字：与「无折叠扩展」基线的耗时比 ≤ 1.2（当前约 1.6）；
- 打字期间 `listFoldKey` 的 meta 事务数 = 0（当前每帧 1 个）。

**反向校准**
- 把安全集合判定改成恒 `false`（每键重建）⇒「打字不重建」必须转红；
- 改成恒 `true`（从不重建）⇒「回车新项有箭头 / 删唯一子项箭头消失」必须转红。

## 七、风险与回滚

- 风险等级：**低**。纯视图层；结构判定是保守黑名单；最坏情况是「多扫一次」，
  不会出现「少扫导致坏箭头」。
- 回滚：单文件改动，`git revert` 即回；无数据迁移、无配置变更。
- 真机验收：2000+ 项列表里连续打字、回车、Tab、折叠、撤销各一遍（happy-dom 无手感）。

## 九、阶段 2 实施记录（2026-10-19，同日落地）

### 改了什么

| 位置 | 改动 |
|---|---|
| `collectDecorations` | 拆出「按窗口收集」分支：给了 `[from,to]` 就 `nodesBetween` 局部扫，只保留**完整落在窗口内**的装饰（`nodesBetween` 会把祖先项也访问进来，不过滤就是重复箭头） |
| `rebuildDecorationsInRange` | 新增：`base.find` 取窗口内旧装饰 → `remove` → 重新收集 → `add`。窗口外的装饰**连 `WidgetType` 实例都不换**（这是「真的局部」的唯一可观测判据） |
| `touchesBlockStructure` / `stepIsSafe` | 阶段 1 的保守黑名单，本阶段复用其判定给「要不要算窗口」作依据 |
| `computeRebuildWindow` | 新增：把**每个**非安全 step 的 `from/to` 用 `mapping.slice(i)` 换算到最终文档，两端各扩到「所涉项（最内层）+ 边界相邻项 + 边界态的父项」；任一端界定不了 ⇒ `null` ⇒ 退回全量 |
| `itemCoverRange` | 新增；分支 ①（位置在项内）取最内层项，分支 ②（边界态）取前后相邻项并扩到其父项 |
| 端点兜底 | 端点常落在**列表容器 token** 上（文档以列表开头时 `step.from` 就是 0）⇒ 向内挪一格再试，否则一律全量 |

### 新增的锁

| 文件 | 内容 |
|---|---|
| `list-fold-scope.spec.ts`（新） | 11 个定点形状 × 两组断言 = 21 条。**A 组（一致性）**：局部重建结果必须与「同一 doc 全量重建」逐项一致；**B 组（收窄）**：远离改动的哨兵箭头，其 `Decoration.type` 必须是**同一个实例**（`map` 复用 type、重建造新 type ⇒ 实例被换 = 走了全量） |
| `list-fold-fuzz.spec.ts`（新） | 6 种子 × 60 步种子化随机按键（回车 / Tab / Shift-Tab / 退格 / 删除 / 折叠 / 撤销混编），每一步都比对全量重建；带「随机序列必须真改过文档」的空转防护 |

### 反向校准（四项，全部实测）

| 校准 | 预期 | 实际 |
|---|---|---|
| `computeRebuildWindow` 恒返回 `null` | 一致性组仍绿（**证明只测一致性是假锁**）、收窄组转红 | 收窄组 **8/9 红**，一致性组全绿 ✔ |
| 窗口缩成 1 格 | 定点 + 随机都应红 | 定点 **5 红**、随机 **6/6 红** ✔ |
| 删「项内部态的父项扩展」 | 若有锁承重则应红 | **全绿** ⇒ 判为**非承重**，按「简约无冗余」删除，只留边界态那处父项扩展 |
| 删 `collectDecorations` 的窗口内过滤 | 应出现重复箭头 | 随机 **6/6 红** + 定点「父项行中回车」红 ✔（`nodesBetween` 真的会把祖先项访问进来） |

> 第三项是这次唯一「被推翻的自己的设计」：父项扩展在小窗口里有直觉合理性，但 11 个定点形状 + 211 步随机结构操作都验不出必要性，且它会**把窗口放大到父项整棵子树**（父项子项越多越贵）。边界态那处保留，因为它接的是「改动落在边界、父项才可能增删子列表」的形状。

### 数字（happy-dom，口径分两种）

**口径 A：`state.apply` 隔离插件成本**（不含 EditorView）

| 规模 | 打字（只 map） | 插入块（局部重建） | 插入块（全量重建） |
|---|---|---|---|
| 1100 项 / 10.9KB | 0.15ms | 0.07ms | 0.26ms |
| 3300 项 / 35KB | 0.22ms | 0.03ms | 0.67ms |
| 8800 项 / 96KB | 0.21ms | 0.03ms | 2.93ms |

**口径 B：端到端 `view.dispatch`**（含 DOM 更新，与阶段 1 报告同口径）

| 规模 | 新（一个事务） | 旧（打字事务 + rAF 全量重建事务） |
|---|---|---|
| 1100 项 | 1.64ms | 2.84ms |
| 3300 项 | 7.39ms | 7.83ms（噪声内） |
| 8800 项 | 20.40ms | 24.73ms |

结论：**DOM 更新是大头**，插件份额在 8800 项约占一帧（16ms）的 13%；阶段 1 省的「每键一次全量扫描 + 一个额外事务」在 1100 项就值 1.2ms。结构操作（回车/Tab）从 O(文档) 降到 O(项)，插件侧 20~100 倍。

### 已知边界（如实登记，不装作锁住了）

- **粘贴的列表落在文档末尾**：改动两侧是**列表容器**而不是列表项 ⇒ `itemCoverRange` 的相邻项分支接不住 ⇒ 有意退回全量。`list-fold-scope.spec.ts` 里以 `windowBounded: false` 明示并排除在收窄组之外（它的一致性仍然被 A 组覆盖）。
- **折叠切换（toggle）仍是全量**：属于阶段 3，本轮没做。
- **真机手感未验**：happy-dom 的 DOM 成本与 WebView2 不是同一量级，验收仍需在 2000+ 项的真列表里打字/回车/Tab 各一遍。

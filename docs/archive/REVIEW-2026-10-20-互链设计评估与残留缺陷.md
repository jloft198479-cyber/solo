# 互链设计评估与残留缺陷（2026-10-20 · 只读）

> 审核范围：`wikilink.ts` / `wikilink-suggest.ts` / `wikilink-existence.ts` / `wikilink-drop.ts` / `markdown/plugins/wikilink.ts` / `document.rs` 互链段 / `useDocumentSession.ts` 改名段 / `events.ts`，即 `c003573`「四次收口」之后的现状。
> 方式：逐模块读原文 → 与 Obsidian / Typora 的做法对照 → 对要下断言的三处**实测**（node 跑真实正则，非推导）→ 基线测试跑绿（484 passed / 30 files）。**未改任何被审代码**，探针跑在 `/tmp`，`git status` 里只有本文件。

## 0. 结论

**主干是好的，问题在「产出侧没人把关」。**

四次收口把「判定侧」磨得很干净：深度有单一真理源 + spec 锁，`truncated` 有显式标志，`../` 出界明写「判不了不标」，向下递归引入的 R-1 已用「按引用方层级算真实写法」堵死。这些我在 §4 逐条复核过，两条被怀疑的地方都**站得住**（其中一条我原以为是冗余分支，推导后证伪了自己）。

漏的是另一头：**补全菜单和拖入这两个「生产链接」的入口，从不检查自己产出的 target 能不能被解析器和落盘正则原样读回来。** 于是出现solo 自己在 `wikilink-existence.ts:52-53` 明写要防的那种自相矛盾——「界面上是正常候选、选中即得一条死链、点它还在磁盘上造出垃圾文件」。

| 级别 | 条数 | 一句话 |
|---|---|---|
| **P1** | 3 | 会让磁盘多出/复活文件，或落盘丢内容（§2.1–2.3） |
| **P2** | 4 | 两个入口口径打架、触闸时静默不完整、注释与实现脱节（§2.4–2.7） |
| **P3** | 4 | 与参照系的偏离、无生产引用的 re-export、缺锁（§2.8–2.11） |

## 1. 先说清楚 solo 的互链模型是什么

对标之前得先摆事实，否则「缺陷」和「设计选择」会混在一起。

**solo 的坐标系是「当前文档所在目录 + 向下 2 层」，没有 vault 概念。**

| | solo | Obsidian | Typora |
|---|---|---|---|
| 索引范围 | 当前文档目录向下 2 层（`WIKILINK_SCAN_DEPTH`，上限 500 文件 / 2000 目录） | 整个 vault，常驻内存索引 | 无索引，按相对路径 |
| `[[B]]` 解析 | 硬拼 `<当前目录>/B.md`（`wikilink.ts:41-57`） | 全库按唯一名解析；重名走最短路径；歧义时要求写更多路径 | 不适用（用标准 Markdown 链接） |
| 指向父级 / 兄弟目录 | 只能手打 `[[../x/B]]`，**能打开，但补全不产、标红不判、改名不同步** | 一等公民，链接存最短唯一路径，改名全库重写 | 相对路径原生支持 |
| 改名传播 | Rust 扫「本层 + 向上 2 层」，按各层真实字面写法改写（`document.rs:485-503`） | 全库重写，含未打开的笔记 | 无 |
| 失效提示 | 打开/切文档时比对清单标红（`wikilink-existence.ts`） | 未解析链接灰色显示，实时 | 无 |
| 点击语义 | **单击即跳转，且总是开新窗**（`wikilink.ts:126-132`，`App.vue` → `newEditorWindow`） | 编辑态 Ctrl/Cmd+单击；预览态单击 | 编辑态 Ctrl+单击 |

**这套模型本身不是缺陷**——「一个文件夹一个项目」的用法下它比 Obsidian 更省（无常驻索引、无 vault 配置），而且四次收口已经把它内部的三处口径对齐了。真正的问题是：**模型的边界（只承诺「向下 2 层」）在判定侧被严格遵守，在产出侧却没有被强制执行**。下面每条 P1 都是这个根因的一个断面。

## 2. 未登记的缺陷

### P1-1 改名后，另一个仍开着旧路径的窗口会把旧文件**复活**

**用户会看到什么**：同一篇文档开了两个窗口（#75 拍板允许，点链接必开新窗、不去重）。在窗口 1 把标题从 `A` 改成 `B` → 磁盘上 `A.md` 变成 `B.md`。5 秒内窗口 2 的自动保存触发 → 弹「**文件已被移动或删除，是否在此位置重新创建？**」→ 用户点「重新创建」→ **`A.md` 带着窗口 2 的内容在磁盘上复活**。此时入链已全部指向 `B.md`，而两篇文件都在，用户不会意识到多了一篇。

**根因（三段拼起来才成立）**：
1. `sync_wikilinks_on_rename` 按完整路径**跳过改名后的自身**（`document.rs:639-641`），且旧路径此刻已不存在于任何目录 ⇒ 返回的 `changed` 里**永远不含旧路径**。
2. 广播载荷只有 `paths: string[]`（`events.ts:93-96`），接收方 `handleWikilinksSynced` 用它自过滤（`useDocumentSession.ts:487-490`）⇒ 持旧路径的窗口 `claimed` 恒为 false，**收不到任何通知**。
3. 该窗口下次保存走 mtime 乐观锁，文件不在 ⇒ `document.rs:289-292` 回 conflict「文件已被移动或删除」，前端按文案里的「移动或删除」把按钮切成「**重新创建**」（`useDocumentSession.ts:295-299`）⇒ 一次 `atomic_write` 就把旧名文件写回来了。

**为什么 #75 的拍板不能覆盖这条**：#75 评估的是「两窗同开同一篇、各自改各自保存 → 弹冲突提示、不丢数据」，前提是**路径没变**。它的结案条件也只写了这一个场景。路径被改名搬走之后，同一个冲突提示的按钮语义从「覆盖」变成了「复活旧文件」——这是 #75 没有评估过的新后果，且 #75 明确说「要做路径登记 + 新 IPC，收益小」时，衡量的是**聚焦已开窗口**那个被否决的收益，不是这个。

**修法方向（零新 IPC）**：广播载荷加一个字段（如 `renamed: { from, to }`），由 `syncInboundWikilinks` 在 `changed.length === 0` 时也照发；接收方 `handleWikilinksSynced` 增加一条自过滤——`isSamePath(currentPath, renamed.from)` 命中时，干净态就跟着改到新路径（`fileStore.renamePath`），脏态就走既有 `promptExternalModified()`，但文案要换成「这篇已在别处改名为 X」而不是「文件已被外部修改」。**通道已经在了，不用新增 IPC，也不用做路径登记。**

**取证级别**：代码级 + 三段路径逐行核对，**未真机复现**（需要开两窗 + 改名 + 等自动保存，真机 30 秒可验）。

### P1-2 补全菜单会把「文件名含 `#`」的真实文件产出成一条**死链**，且插入时毫无征兆，点它还会造垃圾文件 ⭐实测

> ⚠️ **更正（2026-10-20 晚，trae 核实后）**：本节原写「插进去**当场**就是红波浪线」——**这句是错的**，与本报告 §3 自己登记的「新插入的互链要等下次打开/切文档才标红」直接矛盾。机制已核：`[[` 菜单的后台刷新只调 `updateItems()`，**不触发 `markBrokenWikilinks`**（`editor-extensions.ts:522-524`），而 decoration 重建只在 `refresh` meta / 整篇替换 / 装饰全丢三种情况下发生（`wikilink-existence.ts:165-186`）⇒ 从菜单插入的新节点当轮**不会**被标红。
> **更正后结论更严重，不是更轻**：用户拿到的是一条**看起来完全正常**的链接（零视觉警告），第一次单击就弹「是否创建」——把「有红波浪线提示」这个原本存在的缓冲拿掉了。

**用户会看到什么**：同目录有个真实文件 `C#笔记.md`（`#` 在 Windows 文件名里合法，`rename_file` 的非法字符表 `document.rs:319` 也不含它）。敲 `[[` → 菜单里正常列出 `C#笔记` → 选中 → **插入后看起来完全正常，不标红、无提示** → 单击它 → 弹「目标文档不存在：`F:\docs\C.md`，是否创建？」→ 点创建 → 磁盘上多出一个 `C.md`。红波浪线要等到**下次打开或切换这篇文档**才出现，悬停写「目标文件不存在：C.md」——而此时垃圾 `C.md` 往往已经被造出来了。


**实测（node 跑仓库里的真实函数逻辑）**：
```
splitWikilinkAnchor("C#笔记")            -> { path: "C", anchor: "笔记" }
resolveWikilinkTarget("F:\docs\A.md", …) -> "F:\docs\C.md"          ← 不是 C#笔记.md
parse("[[C#笔记]]")                      -> target "C#笔记"（落盘/回读都完好）
```
标红判定链：`buildWikilinkNameIndex(['C#笔记.md'])` 只登记 `c#笔记.md` / `c#笔记`（`wikilink-existence.ts:57-66`）；`isWikilinkTargetMissing` 先剥锚点得到 `c`（`:87`），索引里没有 ⇒ **判为缺失**（注意：这条判定只在打开/切文档/显式 refresh 时才跑，故不是插入当轮生效，见上方更正）。

**根因**：`#` 是 solo 自己按 Obsidian 语义定的**锚点分隔符**（`wikilink.ts:15-32`，取舍已登记：「文件名本身含 `#` 时无法被链接到」）。判定侧、解析侧都照这个语义办事，**唯独两个产出侧不看**：
- `filterWikilinkCandidates`（`wikilink-suggest.ts:82-103`）只做「去 `.md` 后缀 + 子串匹配」，不检查 target 里有没有 `#`；
- `decideDocumentDrop`（`wikilink-drop.ts:98-107`）同样不检查——把 `C#笔记.md` 从文件树拖进正文，得到的是同一条死链。

**这正是 `wikilink-existence.ts:52-53` 自己写明要防的那类矛盾**：「若登记裸名，界面不标红、点下去却弹『是否创建』，正是 P0-3 那种自相矛盾」。判定侧防住了，产出侧漏了——而且是更糟的方向：**菜单主动把一个真实存在的文件推荐给用户，用户选中后得到的是一条指向别的文件的死链，并被告知「目标不存在，要不要创建」**。

**修法方向**：在两个产出侧共用一条纯函数过滤（放 `wikilink-drop.ts`，与 `WIKILINK_SCAN_DEPTH` 同样当「产出侧口径」的单一真理源），target 含 `#` 的候选不进菜单、不生成拖入链接。顺带把 `[` `]` 一起挡（见 P1-3）。过滤掉的候选最好留一行说明（菜单空态已有两套文案，加一句「含 `#` 的文件名无法互链」即可），否则用户会以为文件不存在。

### P1-3 文件名含 `]` 时，落盘再打开会**丢链接**并在正文**多出一个字符** ⭐实测（保真链路）

**用户会看到什么**：浏览器下载的文件常叫 `截图[1].md`、`论文[1].md`。把它拖进正文或从菜单选中 → 当场看起来完全正常 → 保存 → **重新打开后链接断了，而且正文里多出一个孤零零的 `]`**。

**实测**：
```
落盘写出的字符串        -> "[[笔记[1]]]"        （markdown/plugins/wikilink.ts:44-57，target 原样写出）
回读 parse("[[笔记[1]]]") -> target "笔记[1"  +  leftover "]"      ← 少一个 ]，多一段裸文本
回读 parse("[[a]b]]")     -> 完全不匹配（matched: false）           ← 整条退化成纯文本
resolveWikilinkTarget(…, "笔记[1") -> "…\笔记[1.md"                ← 真文件是 笔记[1].md，链接已死
```

**根因**：落盘正则 `markdown/plugins/wikilink.ts:8` 的 target 段是 `[^\]|]+`——**`]` 被排除在合法 target 字符之外**（这是必须的，否则无法界定 `]]` 结束位置），InputRule 同口径（`extensions/wikilink.ts:104`）。但同文件的 serializer（`markdown/plugins/wikilink.ts:44-57`）对 target **不做任何转义或校验**，只剥 ZWNJ。于是「产出侧能造出 target 含 `]` 的节点」与「落盘格式表达不了 `]`」直接对撞：
- 轻则 target 尾部字符被吃掉 + 正文多出裸 `]`（`笔记[1]` → `笔记[1` + `]`），文档内容被静默改写；
- 重则整条匹配失败（`a]b`），wikilink 退化成纯文本，节点消失。

**为什么这条要单独列 P1**：`agents.md` 硬禁令 #4 把「parser / serializer / schema 静默丢内容」定为本项目最贵的事故类型，并要求改这三处前必跑 5 套契约锁。这条缺陷**正好落在那个类别里**，而**现有全部锁都照不到它**：

- `wikilinks.md` roundtrip fixture（`markdown/__tests__/fixtures/wikilinks.md`）只有三行常规写法（`[[项目主页]]` / `[[项目主页|项目]]` / `[[文档]]`、`[[API参考|API]]`），不含任何特殊字符文件名；
- **全仓保真体检 `fidelity-scan.spec.ts` 默认 skip**（需 `SOLO_FIDELITY_SCAN=1` 才跑，文件头第 10 行明写「默认跳过，避免污染 `bun run test`」）。我单独实跑了一次：**绿**，扫的是 19 份 md，里面没有这种形态；
- 更关键的是**即使跑也抓不到**——按该文件自述的三条硬断言推导（未实测）：②「二轮收敛」比的是 `parse→ser` 两轮是否字节相等，而 P1-3 是**一次性损伤后自洽**（第一轮就把 `笔记[1]` 变成 `笔记[1` + 裸 `]`，第二轮起字节稳定）⇒ 收敛判据看不出问题；③「变化签名棘轮」的参照系（markdown-it）**未启用 solo 的 wikilink 私有插件**（该文件第 28 行「已知局限」明写）⇒ wikilink 在参照系里本来就是纯文本，丢一个节点不改变元素种类集合。

> 这一条是对原报告「所以 5 套锁全绿」的**精确化更正**：严格说是「4 套跑绿 + 最强那套（全仓保真体检）默认不跑，且跑了也对 wikilink 盲区」。


**修法方向**：与 P1-2 同一处过滤即可根治（`[` `]` `#` 一起挡在产出侧），**不碰 parser / serializer，因此不触发契约锁**。若要再加一道落盘侧兜底（serializer 遇到含 `]` 的 target 时降级为普通 Markdown 链接 `[笔记[1]](笔记%5B1%5D.md)`），那就动到 serializer，必须跑 5 套锁——建议先只做产出侧，落盘侧留作二期。

> `|` 在 Windows 文件名里非法（`rename_file` 也拦），故 `[[a|b]]` 的别名歧义在 Windows 上不可达；macOS / Linux 上可达，属跨平台遗留，本报告不展开。

### P2-1 `.markdown` 两个入口打架，且 Rust 注释与实现**直接矛盾**

- **拖入**：`LINKABLE_EXT = /\.(md|markdown)$/i`（`wikilink-drop.ts:15`）——`.markdown` 文件拖进正文**能成链**，且 R-3 明确保留后缀（`:16-25`），解析器原样拼路径 ⇒ 能打开。
- **补全**：`collect_markdown_into` 只收 `.md`（`document.rs:248`），注释写着「**`.markdown` 等其他可编辑类型无法被互链指向**」（`:246-247`）——这句在 R-3 之后已经是**错的**，拖入明明就能指向。
- **标红**：只登记 `.md`（`wikilink-existence.ts:61`），遇非 `.md` 扩展名一律不判（`:107`）⇒ `[[B.markdown]]` 安全（不误标），但也永远不参与体检。
- **改名同步**：`wikilink_target_forms` 无条件带全名形态（`document.rs:459-462`）⇒ `.markdown` **在覆盖之列**。

净结果：同一个 `.markdown` 文件，**拖入认、改名同步认、补全不认、标红不判**。这正是 `document.rs:34` 自己警告的「范围不对称会造出『拖进来的能点、敲 `[[` 找不到』这类两个入口打架的坑」——警告写在常量旁边，坑就在隔壁。

**修法方向（二选一，需要先定产品语义）**：① 认定 `.markdown` 可互链 ⇒ `collect_markdown_into` 收 `.markdown`（target 保留后缀，与拖入同口径），标红侧同步登记 `.markdown`；② 认定不可互链 ⇒ `LINKABLE_EXT` 收窄到 `.md`，拖入对 `.markdown` 回落「打开」。①与既有实现更一致、改动更小，且 R-3 已经为它铺好了后缀保留逻辑。**同时无论选哪个，`document.rs:246-247` 那句注释必须改**——它现在是错的，会误导下一个动手的人。

### P2-2 改名同步触闸时静默漏改，「已更新 N 篇」是句不完整的话

`scan_and_rewrite_wikilinks`（`document.rs:588-604`）把 `WIKILINK_SCAN_LIMIT`(500) 当作**跨层合计的已扫文档数**上限，且按 `[本层, 父, 祖父]` 顺序遍历、`scanned >= max_files` 就 `break`（`:596-599`）。于是：

- 本层就有 500+ 篇文档时，**父目录与祖父目录一条都扫不到**——而 R-2 花了一整轮收口才让 `[[sub/B]]` 这种父级写法能被改到，触闸时这个修复直接失效；
- 返回值只有 `Vec<String>`，**没有 `truncated` 语义**；前端拿到 3 个路径就报「已更新 3 篇文档里的链接（其中 1 篇在上级目录）」（`useDocumentSession.ts:452-456`），用户无从知道还有 40 篇没改。

对比：列候选侧显式回 `MarkdownFileList.truncated`（`document.rs:197-198`，`models.rs:35-47`，且被注释标为 correctness-critical），标红侧见到就整体放弃判定（`wikilink-existence.ts:123`）。**三个共用同一个 `ScanBudget` 的入口，两个有完整性语义，唯独改写磁盘的那个没有**——而它恰恰是唯一会「静默留下死链」的。

兜底：漏改的链接在那些文档下次被打开时会被标红（#78 生效），所以最终看得见，不是永久静默。但状态栏那句「已更新 N 篇」在触闸时是误导。

**修法方向**：`sync_wikilinks_on_rename` 返回结构体 `{ paths, truncated }`（改返回类型 ⇒ 前端 `document.ts:79-84`、`useDocumentSession.ts:438`、`wikilink-sync-refresh-lock.spec.ts:96` 三处同步），`truncated` 为真时状态栏改成「已更新 N 篇文档里的链接，**目录过大未扫完，其余请靠红色波浪线自查**」。

### P2-3 补全菜单把 `truncated` 丢了；IPC 失败被伪装成「无匹配文档」

- `filterWikilinkCandidates` 只解构 `files`（`wikilink-suggest.ts:86`），`truncated` 被丢弃 ⇒ 大目录里菜单静默只给「前 500 中匹配的前 50」（`MENU_ITEM_LIMIT`，`:25,99`），且**无任何截断提示**。用户的合理解读是「这个文件不存在」，于是转去手打，打出 P1-2 那类东西。标红侧对同一个标志的处理是诚实的（整体放弃判定），补全侧不是。

### P3-1 单击即跳转且忽略修饰键；`atom` 导致别名只能删了重打

`handleClickOn(_view, _pos, node)`（`wikilink.ts:126-132`）——ProseMirror 的这个回调签名里 **`event` 是第 5 个参数，拿得到，但没用**。所以：单击 = 跳转 = 开新窗，无修饰键区分。

对标（**Obsidian 已取证，Typora 未取证**）：Obsidian 官方中文文档口径是「**编辑模式**下按住 Ctrl/Cmd 点击内部链接才在当前面板打开，Ctrl/Cmd+Shift 才在新面板打开；**预览模式**下单击即开」（[PKMer · 内部链接](https://pkmer.cn/Pkmer-Docs/10-obsidian/obsidian%E5%9F%BA%E6%9C%AC%E4%BD%BF%E7%94%A8/%E5%86%85%E9%83%A8%E9%93%BE%E6%8E%A5/)）⇒ 即「编辑态要修饰键」这一条成立。原报告同时断言 Typora 也是如此，**那半句我没有取证，撤回**——不影响本条实质：`event` 拿得到却不用，是可核的代码事实。

叠加 `atom: true`（`:65`）：鼠标点不进节点内部 ⇒ **想改别名或改 target，只能把整条删了重打**，没有任何编辑 UI（`WikilinkMenu.vue` 只管插入，没有 bubble menu / NodeView）。而别名唯一的产生途径是手打 `[[B|别名]]`（InputRule `:104`）——**能写不能改**。

**注意**：#75 拍板的是「开新窗 vs 聚焦已开窗口」，原文是「设定是一窗一独立文档、点链接必开新窗，命中已开窗口就聚焦会破坏这个设定 ⇒ 聚焦方案否决」。**它没有拍「单击 vs Ctrl+单击」**，这两件事可以分开：保留「必开新窗」，只在触发条件上加修饰键，不违反任何已定口径。

单击的代价还不止多一个窗口：目标是死链时，单击 = 弹创建框 = 一次点击就能在磁盘上造文件（P1-2 就是这么被放大的）。

### P3-2 `[[B]]` 在「同目录没有、子目录有」时会诱导用户造出重复文件

场景：`dir/A.md` 写 `[[B]]`，而 `B.md` 实际在 `dir/sub/B.md`。

- solo：硬拼 `dir/B.md`（`wikilink.ts:56`）⇒ 不存在 ⇒ 标红（索引刻意不登记末段裸名，`wikilink-existence.ts:48-53`，这条设计本身是对的）⇒ 单击弹「目标文档不存在：`dir\B.md`，是否创建？」（`MarkdownEditor.vue:236-241`）⇒ 用户点创建 ⇒ **`dir/B.md` 空文件诞生，从此 `[[B]]` 永久歧义**。

## 4. 我复核过、结论是**站得住**的两处（防止下一轮又被当缺陷捡起）

### 4.1 `wikilink-existence.ts:174-178`（整篇替换重建）**不是**冗余分支

我一开始判定它被 `:180-184` 的「装饰全丢兜底」覆盖，可以删。推导后**证伪了自己**：

兜底的条件是 `previous.find().length > 0 && mapped.find().length === 0`——**要求替换前有装饰**。存在可达路径使前一条件为假而重建仍必要：全选删除后撤销（undo 的 `ReplaceStep` 满足 `from === 0 && to === oldSize`，属整篇替换），此时 `previous` 为空（删除后已无坏链）、新内容里却有坏链 ⇒ 兜底跳过，只有 `:174-178` 会重建。

两条分支各有独立可达路径，与 #78 ③ 声称的「两条分支都单独反向校准过」一致。**保留，勿删。**

代价是每次 `docChanged` 多跑一次 `tr.steps.some(...)`（每键 1–2 个 step，可忽略），不构成对「打字只平移」硬约束的违反。

### 4.2 `rename_scan_dirs` 只向上、不向下递归，**是正确的**，不是漏扫

`:475-484` 的论证我独立复核了一遍：互链 target 一律是「相对引用方所在目录、**向下**若干层」的写法（补全 `wikilink-suggest.ts:95`、拖入 `wikilink-drop.ts:63-72` 的 `relativeSegments` 要求目标严格比 baseDir 深，两个产出侧都产不出 `../`）。因此能指到 `dir/B.md` 的引用方，其所在目录只可能是 `dir`、`parent(dir)`、`grandparent(dir)`——再深的目录要指回来必须写 `../`，而那不属于互链承诺范围。

**向上的层数与向下的深度必须同值，且它们确实同值**（都是 `WIKILINK_SCAN_DEPTH`）：`grandparent` 层的写法是 `a/dirname/B`（2 段），正好是该层向下深度 2 的边界；`great-grandparent` 需要 3 段，超出补全的深度 ⇒ 那种写法根本产不出来。两侧由同一个常量约束、且有 spec 读 Rust 源码校验（`wikilink-existence.spec.ts:141-149`）。**这个耦合是设计得对的地方，不是缺陷。**

（唯一残留：手打的 `[[../B]]` 能解析、能打开，但改名不同步、失效不标、补全不产——已登记，见 §3。）

## 5. 推荐落点（只给一个）

**先做 P1-2 + P1-3 + P3-4：在 `wikilink-drop.ts` 加一条产出侧字符过滤，两个生产入口共用。**

理由：

1. **一处改动消掉两条 P1**——它们同根：产出侧不检查自己产出的 target 能否被解析器与落盘正则原样读回来。`#`（P1-2）与 `[` `]`（P1-3）一次挡完。
2. **属最贵事故类型**：P1-3 是落盘丢内容 + 静默改正文，正是 `agents.md` 硬禁令 #4 点名的类别，且现有全部锁都照不到它（fixture 不含特殊字符文件名；最强的全仓保真体检默认 skip，跑了也对 wikilink 盲区——详见 P1-3）。
3. **风险最低**：纯函数 + 两个产出侧各加一次调用，**不碰 parser / serializer / schema，因此不触发契约锁**；不改任何既有交互口径（单击语义、开新窗、扫描深度全不动），不与 §3 任何已拍板取舍冲突。

5. 顺手带上 P3-4（三套扩展名判定收敛到同一模块的同一个函数）与 P2-4（一行注释订正）——同一次改动、同一个模块、零额外风险。

# 速度与「丝滑」体感审查（2026-11-18）

> 性质：**只读审查，未改任何代码**。结论基于源码静态证据 + 平台特性推断，**没有真机 profiling 数据**，排序中的「置信度」需用实测校准。

## 一、结论先行

**不是某个 bug，而是四层代价叠加，而且前三层是架构/平台取舍，不是继续抠代码能消掉的。**

| 层 | 代价 | 可否靠优化消除 |
|---|---|---|
| 1. 平台合成 | 透明无边框窗口，整窗每帧 alpha 合成 | 可（改窗口形态） |
| 2. 输入法 | Windows 禁用 TSF，中文走 IMM32 旧路径 | 需实测，改回有回归风险 |
| 3. 渲染结构 | 全篇 DOM，无虚拟化；`content-visibility` 只给 50 万字以上文档 | 只能做条件式局部启用 |
| 4. 派生计算 | 停顿瞬间主线程做序列化 / 字数 / 大纲 | 可（移 worker、加门控） |

历史优化（序列化 O(n²)→O(n)、四层防抖、空闲调度、代码块分批高亮）已经把「肉」吃完了，见 [PERF-AND-THEME-SUGGESTIONS-2026-09-18.md](archive/PERF-AND-THEME-SUGGESTIONS-2026-09-18.md)。现在剩下的是「缝」，而体感恰恰由缝决定——**帧一致性，而不是平均速度**。

## 二、按场景归因

### 场景 A：打开文件/切文档「要等一下才敢动」

链路是串行的：读文件 → parse → `setContent` → 全量 NodeView 构造 → 首帧布局 → 字数/大纲。没有渐进渲染，用户看到的是「一段没有画面的等待」。

- 证据：[MarkdownEditor.vue](../../src/components/Editor/MarkdownEditor.vue#L405-L416) 的 `onUpdate` 之后才进入派生计算；解析在主线程同步执行。
- 加重项：自定义字体通过 `@font-face` 异步注入，`document.fonts.load` 完成后整篇按新字体重排（[fontLoader.ts](../../src/services/fontLoader.ts#L57-L72)）→ 首屏「先默认字体、抖一下再变」。
- 图片未标注尺寸时 `loading="lazy"`，载入后没有预留空间（[image.ts](../../src/components/Editor/tiptap/extensions/image.ts#L406)、[image.ts](../../src/components/Editor/tiptap/extensions/image.ts#L456-L460)）→ 滚动时下方内容被顶动。
- 置信度：高（代码路径确定）；影响大小：中-高（每次打开都发生）。

### 场景 B：连续打字「间隔性一顿」

每停一次，主线程会集中做三件事：

- 字数 150ms（遍历全文文本节点 + 逐段正则）
- 大纲 500ms（全文遍历标题）
- Markdown 序列化 500ms → `requestIdleCallback`（[useEditorSync.ts](../../src/composables/useEditorSync.ts#L33-L44)、[useEditorSync.ts](../../src/composables/useEditorSync.ts#L100-L148)）

序列化本身在 5 万字文档约 8–12ms（WebView2 口径），大文档注释里写明可达 100–300ms；再加上写 store、触发 Vue 更新，就形成「每停一下有个小顿」的节奏。它不是卡死，而是**节奏不匀**。

- 根因不是防抖没做，而是**这三件事仍全在主线程**，且都挤在「停顿」这个同一时间窗。
- 置信度：高（调度逻辑明确）；影响大小：中（典型 1–3 万字文档约 5–15ms/次）。

### 场景 C：中文输入「比英文黏」

- 窗口启动参数显式禁用了 `TSFImeSupport`（[tauri.conf.json](../../src-tauri/tauri.conf.json#L27)），微软拼音走 IMM32；这是当年修候选窗失锚的取舍（见 `docs/IME-经验卡-失锚翻身记.md`）。
- 为此还付出了渲染代价：`content-visibility` 会给组字加 `contain`，干扰候选窗，因此**只在 50 万字以上文档启用**（[document-scale.ts](../../src/components/Editor/document-scale.ts#L44-L53)、[editor.css](../../src/components/Editor/tiptap/editor.css#L98-L152)）。也就是说：**普通长文永远没有视口化优化**，而中文用户的每一次输入都多一层 IME 协调（组字期冻结装饰、选区 100ms 防抖）。
- 置信度：中（机制确定，体感占比需 A/B）。
- 这是本审查里最可能的「中文用户专属不丝滑」来源，也最难改。

### 场景 D：滚动长文「不够跟手」

- 全篇块都在 DOM 里（ProseMirror 无虚拟化，历史结论：虚拟化≈重写编辑器，见归档 `PERF-AND-THEME-SUGGESTIONS` C 级）。
- 普通文档未启用 `content-visibility`（原因同场景 C），滚动时浏览器要为进入视口的每一块做样式/布局/绘制。
- 叠加：窗口 `transparent: true` + `body { background-color: transparent }`（[tauri.conf.json](../../src-tauri/tauri.conf.json#L23-L25)、[main.css](../../src/assets/styles/main.css#L439-L446)）意味着整个窗口每帧都要做 alpha 合成，Windows/WebView2 下这条路径通常比不透明窗口更贵。
- `text-rendering: optimizeLegibility`（[editor.css](../../src/components/Editor/tiptap/editor.css#L85-L90)）会让每次重排多算 kerning/ligature，长文滚动有额外排版成本。
- 置信度：中（合成开销未实测）；影响大小：可能全局恒定。

### 场景 E：操作反馈「慢半拍」

这层是感知设计，不是吞吐：

- 焦点模式下每个叶块都挂 `paragraph-active/dimmed` 装饰并带透明度过渡（[paragraph-focus.ts](../../src/components/Editor/tiptap/extensions/paragraph-focus.ts#L54-L79)）——全篇都在「变」，视觉上更重。
- 气泡菜单随选区/滚动每帧重算位置（[MarkdownEditor.vue](../../src/components/Editor/MarkdownEditor.vue#L624-L630)、[MarkdownEditor.vue](../../src/components/Editor/MarkdownEditor.vue#L871-L877)），菜单会「追着光标漂」。
- 置信度：高（行为确定）；影响：主观但真实。

## 三、验证与改法（按 ROI 排序）

### Step 0 · 先建测量（最值得，1 天）
没有基线时，所有「优化」都在和感觉吵架。需要四个数：冷启动→可输入、打开文件→可输入、按键→上屏 p95、滚动帧率（以及序列化耗时）。
验收：同一份 1 万字/5 万字文档，改前后能给出数字对比。

### Step 1 · 三个零风险 A/B（半天，纯配置/一行 CSS）
1. `transparent: false` + 不透明卡片背景，对比滚动帧率与打字延迟。
2. 去掉 `text-rendering: optimizeLegibility`，对比长文滚动。
3. 关闭焦点模式，对比连续编辑。

任一项有 >10% 差异就锁定主因，再决定是否为此改窗口形态。

### Step 2 · 低风险收益（1–2 天）
1. **序列化移出主线程**：`doc.toJSON()` → Worker 里 `serializeMarkdown` → 回传字符串。主线程只做结构化克隆，停顿感消失。
2. **派生计算加门控**：大纲只在面板可见时算（heavy 档已做，normal 档未做）；字数改增量统计（记录变更区间）。
3. **字体就绪再显示**：编辑器首帧等 `document.fonts.ready`（或 `font-display: block`），消除开屏重排。
4. **图片占位**：无尺寸时用固定比例骨架占位，载入后不顶动内容。

### Step 3 · 中风险（需评审）
1. **条件式 `content-visibility`**：不按「文档大小」一刀切，而是只对「离视口 >2 屏、且不在组字中」的顶层块启用，组字开始即全局撤下。能在保住 IME 的前提下拿到大部分滚动收益，但需要严格的组字回归测试。
2. 搜索高亮的装饰预算（挂起项，见归档 B2）。

### Step 4 · 评估是否恢复 TSF
只有在 Step 1/2 之后中文输入仍是主要短板时才值得碰：需要重跑候选窗失锚的全套回归（`docs/archive/IME-*`）。**默认不建议动**。

## 四、不确定的地方（必须说清）

- 没有真机 Performance 面板数据，以上优先级来自代码与平台常识，不是实测排序。
- 透明窗口在 WebView2 下的真实合成损失未知；可能很小，也可能就是「全局差一点」的主因——**这个 A/B 最便宜，应该第一个做**。
- 「丝滑」包含交互反馈节奏（动画时长、菜单跟随、滚动惯性），这部分不在本文量化范围内。

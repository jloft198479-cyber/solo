## 优化建议（按优先级）

### P1-1 `resolvedImageCache` 无上限 — `MarkdownEditor.vue:317`

- **现状**：Map 只增不减，仅切文档 / 切 storage 路径时清空。
- **风险场景**：单篇文档引用几百张图、或编辑中频繁改动图片 src → 键数随会话增长。值为 asset URL 字符串（几十字节 / 条），最坏几百 KB 级——**不紧急，顺手可修**。
- **附带小问题**：解析失败（catch）不缓存（`MarkdownEditor.vue:806-808`），坏图每次重走 IPC，是性能小瑕而非内存问题。
- **修法**：加上限 500 条 + FIFO 淘汰（约 10 行，与 `list-fold.ts` 同款模式）；失败结果可缓存空值短时。

### P1-2 剪贴板大图无大小闸门 — `document.rs` `save_clipboard_image`（约 :517）

- **现状**：base64 dataUrl 直接接收。一张 4K 截图 PNG ≈ 5–10MB → base64 膨胀 33% ≈ 13MB 字符串过 IPC + Rust decode + 落盘，峰值约三份共存。
- **修法**：IPC 入口按 base64 长度判上限（建议 20MB），超限返回可读错误；或前端先压缩。代价小。

### P2-1 大文档打开的峰值副本（架构性，建议只观察不改）

- `open_document` 全量读（`fs::read` → `String::from_utf8` 复用缓冲，无字节/字符串双倍）→ IPC 传 String → ProseMirror doc → 序列化基线 string。10MB 文档打开瞬间约 3–4 份副本，此后 doc + content string 常驻。
- 这是桌面编辑器行业常规模型（Typora / Obsidian 同款全量加载），且项目已有 `isHeavyDocument` 降级。**不建议动内核**。若要改善，仅在打开超大文件（阈值如 30MB）时给一次性提示即可。
- 撤销栈：prosemirror-history 默认 depth=100 事件（`node_modules/prosemirror-history/dist/index.js:373`），业界常规，不动。

### P2-2 CSS @font-face 重复注入 — `fontLoader.ts:65-70`

- 每次 `readCache` 都新建 `<style>` 元素 append 到 head。正常路径有 `loadedFonts` 短路，每字体只注一次；仅「CSS 加载失败回退字节」的重试路径会重复注入。量级极小。可选优化：注入前查 head 是否已有同 family 的 style。

## 结论

内存控制：**不需要抢救性修复**。P1 两项均为「顺手级」小改动（合计约半天内），做不做由简乐定；P2 建议维持现状。

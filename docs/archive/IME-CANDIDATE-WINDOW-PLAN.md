## 0b. TL;DR（接手必读 30 秒）

- **Bug 是什么**：中文输入法候选小窗打字时偶发飘到屏幕角落（我们实测恒为右下角 `(1340,996)`），不跟光标。
- **根因定位**：缺陷在 **WebView2 宿主层 / 其 TSF 集成**，与 solo 编辑器逻辑无关。三重证据：① `#5675` **裸 `<input>` 即复现**候选窗飘角；② `#5625` 中 **纯 `textarea` 完全正常、`contentEditable` 吃字**，且作者实测**「composition 期间抑制 DOM 变更的 JS 侧缓解无效」**；③ Edge/Chrome 不复现、WebView2 复现。⚠️ 但微软对该族 issue **0 回复、无官方结论**，「托管层」仍属强推断。
- **为什么 solo 频发**：solo 是「高频中文写作 + 高频窗口操作」的**高使用量场景**，命中触发机会多（**与 DOM 复杂度无因果关系**，见 §2.2）。
- **已落地**：① `composition-freeze.ts` 总闸（提交 `21a028b`，`origin/master`）；② `tauri.conf.json` 加 `--disable-features=TSFImeSupport`（提交 `9a27bad`，`origin/master`）。**注意**：二者对「失锚」都**不是解药**（详见 §3.1、§4）。
- **最大困局**：失锚**无法在自动环境触发**（鼠标一动即自愈）⇒ 任何修法**无法 A/B 证真**。至今对 flag 有效性的**唯一证据是「flag 进了命令行」**（见 §3.1 的 A/B 无分辨力）。
- **正确的下一步**：**先锁运行时版本 + 装「一键取证器」抓现场**，再谈修法；停止在无法证真的修法上继续投入。见 §4。

## 1. 现象与机制

### 1.1 现象（源：取证文档）
- 微软拼音候选窗由 `TextInputHost.exe` 的 UWP 合成层绘制、**无独立 HWND**（Win32/UIA 都枚举不到）⇒ 只能**屏幕像素取证**。
- 实测 1606 帧：真失锚 **21 帧全在 solo**，坐标 `(1340,996)`；对照 WorkBuddy 756 帧 / Edge / 百度搭子 / 豆包 **零失锚**。
  - ⚠️ **该坐标为 2026-09-13/14（Runtime 152）基线的实测值，非恒定值**。2026-09-24 复测（Runtime 153）锚点已变为 `(782,706)`，见 §8.5。
- 规律：**「进 solo / 切文档 / 移窗口」后的第一次组字易失锚；初期易发、随会话推进消失**（约 16% 会话命中，偶发）。
  - ⚠️ **表述已修正（2026-09-23）**：原写「第二次自愈」**过简且不准**。真值 = 现场同一场编辑内出现 **2 次**失锚（t=52.7s / t=63.5s，坐标同为 `(1340,996)`，间隔 11s），且要到 **21 分钟后（t=1404s+）** 才完全正常（源：`.workbuddy/memory/2026-09-13.md` L403 / L408）。
- **★ 2026-09-24 新增（首次拿到精确锚点）**：候选窗锚点在一段会话内是**屏幕绝对坐标常数**，**与窗口位置、光标位置均无关**（4 批次 / 21 分钟内锚点恒为 `(783,707)`±2px，而窗口位移 668px、光标位移 901px）。用户感知的「有时在页面内、有时跑到页面外」= **锚点固定 + 窗口移动**的视觉结果。详见 §8.5。
  - ⚠️ **同轮自我纠正（2026-09-24 02:3x）**：早先记的「锚点 01:50≈`(180,617)`、跨时间会变」**已撤销** —— 该坐标经裁剪放大核实，是 **OpenCode 终端自身**的候选窗（**正确定位**在其命令输入行正下方、深色背景），**不属 solo**，不能计入锚点序列。

### 1.2 机制
光标矩形上报为空（`RenderWidgetHostViewAura::GetCaretBounds()` 在 `!active_widget` 时返空矩形 ⇐ renderer 报 `TEXT_INPUT_TYPE_NONE`）⇒ TSF 拿不到位置 ⇒ 系统回退屏幕默认角位。〔源：取证文档的 Chromium 源码分析〕
> ⚠️ `#5675` 提交者另有一套类似但**自称未经验证**的 TSF 链路推断（`OnCaretBoundsChanged` → … → `OnLayoutChange` 未触发）。方向一致、**均未被微软确认**。

### 1.3 上游 issue 族（本轮全部核对存在性）

| issue | 症状 | 关键事实（一手页面） |
|---|---|---|
| **`#5675`** | 候选窗飘角（resize 后） | stock Tauri + **裸 `<input>`** 即复现；韩文 IME / 左上角（我们中文 / 右下角）；**鼠标一动即清除**；页末「*No response*」；提交者自列已排除：子窗口几何、主线程阻塞、页面 caret、`MoveFocus(PROGRAMMATIC)`、`NotifyParentWindowPositionChanged()`×10 |
| **`#5625`** | contentEditable **吃字/标点双按** | 运行时 **149**、Tauri 2 宿主；**同页 `textarea` 正常**；作者实测 **「compositionstart~end 间抑制 DOM 变更的 JS 侧缓解无效」**⇒ 病灶在 **WebView2 的 TSF 文本输入层**，不在 JS；搜狗拼音严重、微软拼音轻 |
| `#1611` | 候选窗不随窗口**移动** | 同族 |
| `#2241` | WinUI3 同族 | 缩放>100% 恒错位 |
| `#5570` | RDP + composition 模式 | 前提（composition 模式）在 solo 不成立 |
| `#1610` | 同族旧账 | 2024 关闭，但当前运行时复现 |

> **族内两症状必须分开**（这是关键认知）：`#5675` 的**候选窗飘角**与 contentEditable **无关**（裸 input 也中）；`#5625` 的**吃字**才与 contentEditable **有关**（textarea 正常）。二者是**同一子系统（WebView2 的 TSF 集成）下的两个不同缺陷**，不可互推。

## 2. 核心反思：为什么 solo 比同类软件更频繁中招

> **结论（已按 `#5675` 证据修正）：候选窗飘角是 WebView2 宿主层的真缺陷，solo 在这件事上是「受害者」；solo「看起来更频繁」来自「使用量 + 触发机会」，而非 DOM 复杂或代码写坏。**

### 2.1 你拿来对比的「很多软件」大多根本不在这条链路上

| 软件类型 | 文本控件实现 | 会不会掉这个坑 |
|---|---|---|
| 记事本 / Word / QQ 等原生 Win32/MFC/Qt/WPF | **原生控件**（IMM32 自己画候选窗） | **不掉**——不走 Chromium/WebView2 链路（通用事实） |
| VSCode / MarkText 等 Electron 软件 | Chromium 内核 | 同属 Chromium，**理论同族风险**；本轮**未逐条复核**，勿当已证事实 |
| solo | Chromium（WebView2） | 掉 |

类比：油车（原生）冬天不掉电，不是更先进，是**不用电池**。

### 2.2 solo 的触发机会更多（修正版：DOM 复杂度**不是**原因）

1. **`#5675` 铁证：裸 `<input>` 也失锚** ⇒ 飘角**不需要** contenteditable、不需要 ProseMirror、不需要动态 DOM。故**不能**再把「复杂富文本 DOM」列为飘角成因（初稿如此写，本轮已删）。
2. **真正放大命中率的是「使用量 + 触发机会」**：solo 是写作软件，中文组字每天成千上万次；且窗口操作频繁（多窗口、透明无边框、切文件、移窗）。触发条件（几何变化后立刻组字且不碰鼠标）**出现次数**越多，偶发缺陷越容易被看到。
3. **`composition-freeze` 的正当性来自另一类问题，不是飘角**：它让组字期 DOM 干净，对付的是「组字期 DOM 抖动引发的各类 IME 异常」；对「飘角」它**不是解药**（`#5625` 已证 JS 层抑制 DOM 变更对这类 TSF 问题无效）。方向不算错，但**别指望它治飘角**。

### 2.3 社区做法（solo 未采用）— ⚠️ 来源【待核实】且**对飘角大概率不适用**

| 做法 | 据称谁在用 | 对**本 bug（飘角）**是否有效 |
|---|---|---|
| **隐藏 textarea / contenteditable 当稳定 IME 锚** | Google Docs、Collabora Online、知乎编辑器【来源待核实】 | **大概率无效**。该思路解决的是「DOM 抖动 → 锚点抖」；而 `#5675` 是「resize 后锚点**整个失效**」，**连裸 input 都失效** ⇒ 换锚点位置救不了 |
| 编辑器官方 IME 针对性修复（如 ProseMirror `domchange.ts`） | 【待核实】 | 针对具体 IME 光标错位，非本 bug 的宿主层失效 |
| 高 DPI / 多屏坐标归一化 | 【待核实】 | **已被 solo 取证排除**（100% 单屏仍发作） |

> ⚠️ **来源状态**：本表来自公开检索，「隐藏 textarea 当锚」的**实现细节未逐条打开一手原文**；唯一旁证是 Google Docs 用 canvas 渲染 + `docs-texteventtarget-iframe` 承接输入（渲染层与输入层分离）。**动手前必须先复核一手来源，且必须先用 §1.3 的「两症状须分开」判断你到底要治哪一个。**

### 2.4 结论（摆正账）
- 飘角：**solo 是受害者**，触发层在 WebView2 宿主，solo 代码碰不到；「托管层」是强推断、微软未确认。
- 但 solo **不能因此躺平**：把它当已知外部缺陷，**先锁环境、先取证**，而不是继续赌修法。
- `#5625` 的**另一半**（contentEditable 吃字/标点双按，textarea 正常）**可能确实与 solo 的 contentEditable 选择相关**——这是唯一「换输入承载」可能真有收益的方向，但**与飘角是两码事**，且同样在 WebView2 层、JS 层救不了。

- **`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` env 注入 flag**：WebView2 环境崩溃（复现 3 次），flag 从未传入 ⇒ 必须走 `tauri.conf.json`。

# OpenMarkdown editor 0.2.1 vs solo

> 对象：`npm @openmarkdown-dev/editor` v0.2.1（MIT，2026-11-18），源码在 `M:\OpenMarkdown-editor-0.2.1`。
> 它不是 App，是**可嵌入的编辑器库**（React/Vue/裸 DOM 都能用），从 OpenMarkdown App 里抽出来的。
> 核查命令都在文末，所有数字以你自己跑出来为准。

---

## 一、一句话结论

**它把「源码就是文档」做到极致，solo 把「排版体验」做到极致 —— 两条路各自的最优解，不是同一件事的两种实现。**
真正值钱的不是它的功能，是它的两套**方法论**：文档由测试生成、保真承诺写成可核清单。

---

## 二、根本分歧：一个比喻

| | solo | OpenMarkdown |
|---|---|---|
| 内存里的文档是什么 | **一棵树**（ProseMirror 节点树） | **一个字符串**（就是 .md 原文） |
| 编辑时发生什么 | 改树 | 改文字 |
| 保存时发生什么 | 把树**翻译回** Markdown（serializer） | 把文字**原样写出** |
| 屏幕上的排版是怎么来的 | 树长成了排版的样子 | 文字在，只是用「涂改带」把 `#` `**` 盖住（Decoration.replace + widget） |

比喻：
- **solo 像翻译**：把中文（Markdown）翻成英文（树）来编辑，存的时候再翻回中文。翻回来腔调总会变 —— `_斜体_` 变 `*斜体*`，setext 标题变 `#`，表格重新对齐。
- **OpenMarkdown 像在原稿上贴便签**：原稿一个字没动，只是把语法符号暂时遮住让你看效果。存回去还是原稿，**一个字节都不差**。

**这就是为什么 solo 有一整套「保真/往返」的苦活（转义规则、往返锁、单元格保真、假锁），而 OpenMarkdown 里这个问题根本不存在 —— 不是它解决得好，是它的模型里没有这个环节。**

反过来，solo 里天然免费的东西（拖块、块多选、复制整块、复杂选区、富交互浮动菜单），在 OpenMarkdown 里要一行一行手写文本手术才能实现。

## 三、能力对照

只列有信息量的差异，两边都有的（大纲、查找、折叠、图片缩放、主题、拼写）不占篇幅。

| 维度 | solo | OpenMarkdown 0.2.1 |
|---|---|---|
| 内核 | Tiptap / ProseMirror 树 | CodeMirror 6 文本 |
| 形态 | 桌面 App（Tauri） | npm 库，~185KB gzip，SSR 安全 |
| **无损往返** | 靠 serializer + 往返锁，**必然有风格变化** | **逐字节相同**（未编辑时）；编辑时只有触碰处变，例外逐条列明并各配一条测试 |
| **从网页/公众号粘贴** | **保留格式**（自研 HTML→文档清洗） | **只剩纯文本**（无 `text/html` 处理，CodeMirror 只取 text/plain） |
| **出站到公众号** | **有**（HTML 清洗 + 行内 style 内联） | **完全没有**（它只输出 .md） |
| 三种视图 | 单一 WYSIWYG（+ Focus 模式） | **live 实时预览 / source 源码 / reading 阅读**，可切换且保留选区与历史 |
| 富交互 | 拖拽、块多选、浮动菜单、callout、卡片 | 无（只能光标线性编辑） |
| 表格 | PM 表格节点，改单元格 = 改节点 | **就地编辑**：单元格里嵌一个小编辑器，改完只动那一格字节（`tableEdit.ts` 约 1.3k 行） |
| 按键行为 | 各扩展 keymap，靠 priority 排 | **结构栈表驱动**：光标所在语法节点栈逐层问「这个键归你吗」，首个接管的赢，且有 gate 测试禁止别处乱绑 |
| 不可信文档 | 主要防粘贴 | **成体系**：raw HTML 一律显示为源码、MathML/SVG 过白名单 sanitizer、Mermaid strict、URL 按浏览器语义分类（解码实体+去控制字符）后才允许打开 |
| 渲染失败 | 各自处理 | **统一四态契约**：渲染成功 / pending（还没好，显示占位）/ null（不归我，显示源码）/ 抛错（显示源码+失败标记），**全仓只有一个捕获点** |
| 渲染覆盖度 | **20 个扩展全覆盖**（正是产品铁律的靶子） | 明确**不渲染**：`[[wikilink]]`、脚注、`==高亮==`、`::: panel`、上下标、定义列表（原样显示为文字） |
| 设计 token | `--*` 主题 token + 设计刻度 | `--ome-*` 角色 token，`:where()` 零特异性注入默认值，明暗双套，宿主覆盖即生效 |
| 依赖 | 全家桶 | **按需**：mermaid/temml 用 `import()`，三种入口（全量 / 无图表 / 无渲染器）保证你的打包器不产多余 chunk |

## 四、各自优劣（诚实版）

### OpenMarkdown 强在哪
1. **保真做到承诺级**。「打开再保存，文件一字节不差」这句话每个字都有测试。solo 现在只能说「基本无损」，遇到表格重排解释不清。
2. **对机器友好**。文件永远是纯文本真理源 ⇒ git diff 干净、AI 写文件不破坏格式、外部工具改完不炸。这正好是它 App 版主打「人和 AI 都在这写」的底层原因。
3. **测试即文档**。`docs/guides/syntax.md` 里那几张表是**从测试向量生成的**，原话：「say what the editor does, not what we hope it does」。每个编辑行为都有一条测试向量钉住，跑测试同时刷新文档。
4. **契约密度极高**。代码注释里到处是 `spec: 条目 / design D1-D3 / gate: xxx.gate.test.ts`。任何一个设计决定都能顺藤摸到规格条目和守卫它的门禁测试 —— 这是「假锁」的解药。
5. **安全模型成体系**，不是补丁式的。
6. **工程克制**。0.2.0 把 20 多个语言包从依赖里踢出去，变 opt-in；三种入口按体积切。

### OpenMarkdown 弱在哪
1. **富交互是天生短板**。不能拖块、不能框选多个块、不能像 Notion 那样插卡片。它连「专注模式/打字机模式」都没有。
2. **粘贴是硬伤**。从网页、公众号、Word 复制一段带格式的内容粘进去 —— **格式全丢**。这直接撞在 solo 的产品铁律上（「别处复制来的内容能否正确显示」）。
3. **块级语法要手写文本手术**。改一格的字节级正确要 1.3k 行，这是模型的税。
4. **语法覆盖比 solo 窄**，且有明确放弃清单（wikilink / 脚注 / 高亮 / 容器）。
5. **0.x**，minor 版本可破坏 API（它自己 CHANGELOG 写明）。

### solo 的对应短板（它反照出来的）
1. **保真承诺说不清**。有锁，但锁证明的是「稳定」，不是「内容对」（这正是记忆里记着的坑）。
2. **源文本对用户不可见**。遇到 serializer 表达不了的语法，用户在 solo 里只能看到「一段普通文字」，无从知道原文长什么样、也没法修。
3. **按键行为分散**。Enter/Tab/Backspace 的裁决散在 20 个扩展的 keymap 里，行为靠优先级碰运气，改一处容易塌另一处。
4. **渲染失败的兜底不统一**。mermaid / 公式 / 图片各有各的失败表现。

## 五、值得学什么（按「值不值得动」分档）

### A 档 · 建议现在就做（改的是方法，不是架构）

**A1. 测试向量 → 文档表格自动生成** ⭐ 最高性价比
- 学什么：把每个扩展的 (输入 Markdown, 期望 HTML) 写成向量表，跑测试的同时**生成** `FEATURE-MATRIX.md` 的表格。
- 为什么值：直接对治记忆里的「假锁」—— 向量表天然要求「输入里带病灶形状」，否则向量本身就是无效用例。同时终结文档手写漂移（`FEATURE-MATRIX` 现在靠人维护，一定会旧）。
- 代价：一次性整理向量表，之后是纯收益。

**A2. 保真承诺改写成「可核清单」**
- 学什么：不再说「往返无损」，改成两句：
  ① 「打开不编辑直接保存，正文内容不变」—— 并明确列出**必然会变**的东西（表格对齐、列表符号、加粗符号风格、setext→ATX 之类），每条配一条测试。
  ② 「编辑时只有触碰的部分变」—— 例外逐条列明。
- 为什么值：现在用户发现格式被「整理」了会觉得是 bug，说不清；写成清单就是**产品承诺**。
- 代价：一次盘点 + 若干条测试。不用改代码。

**A3. 渲染失败统一成一种表现**
- 学什么：四态契约（成功 / 还没好 / 不归我 / 失败），全仓**只有一个捕获点**，失败了就**显示源码 + 一个失败标记**，绝不显示「空白」或「报错框」。
- 为什么值：符合「退化安全必有 fallback」的既有原则；用户永远能看到自己能编辑的东西，不会卡在空白块上。
- 代价：小，收敛调用点即可。

**A4. 不可信输入体检**
- 学什么：它那套 URL 分类法（先解码 HTML 实体、再剥控制字符，然后才判 `javascript:` 等）拿去对照 solo 的粘贴清洗，看有没有漏。
- 为什么值：solo 的主要风险入口就是粘贴，不是打开自己的文件。
- 代价：一次体检，大概率只补几行。

### B 档 · 值得排队（动结构，但方向明确）

**B1. 只读「源码视图」**
- 学什么：同一个文档的第三种看法。**先只做只读**（不进编辑，不双向同步），让用户随时能看到「真身长什么样」、能复制原始 Markdown。
- 为什么值：补齐 solo 现在最大的心理缺口 —— 用户不知道文件里到底有啥。只读版本几乎零风险（不需要同步合并）。
- 代价：中等。可编辑版本风险高（双向同步 + 冲突），不建议一起上。

**B2. 按键裁决收敛成一张表**
- 学什么：「上下文栈 + 表驱动，首个接管的赢」；再配一条测试禁止在别处绑定同样上下文。
- 为什么值：20 个扩展各自绑键，现在改一个键影响谁全靠猜。收敛后行为可预测、可测试。
- 代价：中等偏大，属于重构，得单独排期 + 打 tag 锚点。

**B3. 契约快照门禁**
- 学什么：公共 API 逐字节快照，改了就红，必须显式 `--update-api` 并审 diff。
- solo 对应物：**扩展清单 / 命令表 / 主题 token 表**做成快照。改一处就红，逼你看 diff。
- 代价：小。

### C 档 · 只登记，明确别动

**C1. 换 CodeMirror 内核 —— 否决。**
理由：它的优势（逐字节保真）来自「不做富交互」；solo 的护城河（拖块、块多选、浮动菜单、卡片排版、公众号出站）在文本模型里全是手写手术。换内核 = 把 20 个扩展和出站清洗全部重写，收益是「用户自己写的文件风格更稳定」—— **投入产出完全不成立**。已有铁律「不换内核」是对的。

**C2. 追「逐字节」目标 —— 别追。**
solo 的用户是自己写自己的文件，不是 git 仓库协作，也不是 AI 批量改文件。为了逐字节去改架构，是把别人的靶子当自己的靶子。

**C3. 学它砍语法覆盖 —— 别学。**
它敢放弃 wikilink/脚注/高亮/容器，是因为它定位是「嵌入别人的产品」。solo 的靶子恰恰是「别处来的内容要能正确显示」，砍扩展就是砍根。

---

## 六、一句话给决策

值得做的是 **A1（测试生成文档）+ A2（保真承诺清单）**，这两件不动架构、直接提升可信度；
**B1（只读源码视图）** 是用户能立刻感知到的那一个；
其余登记待排期，C 档明确不动。

## 七、怎么自己核

```bash
# 它到底多克制：打包入口与依赖
cat M:/OpenMarkdown-editor-0.2.1/package.json

# 保真承诺原文（每个字都有测试）
M:/OpenMarkdown-editor-0.2.1/docs/fidelity.md

# 「文档由测试生成」的证据（表格上下的注释）
M:/OpenMarkdown-editor-0.2.1/docs/guides/syntax.md

# 粘贴只取纯文本的证据（全仓无 text/html 处理）
grep -rn "text/html" M:/OpenMarkdown-editor-0.2.1/src --include=*.ts

# 结构栈按键裁决
M:/OpenMarkdown-editor-0.2.1/src/editor/structure/index.ts

# 渲染失败四态
M:/OpenMarkdown-editor-0.2.1/src/editor/blocks/render.ts

# 表格字节级手术的规模（自己是几行，以 wc -l 为准）
wc -l M:/OpenMarkdown-editor-0.2.1/src/editor/tableEdit.ts
```

# solo 开发文档管理体系（提案）

> 2026-10-13。起因：简乐提出「文档急剧膨胀 → 又要大量删减 → 不知道哪些该传」，要求一套体系化方法。
> 本文是**提案**，未落地。所有方法论附来源，可信度随文标注。

---

## 一、病根诊断（先定性，再开方）

不是「文档太多」，是三个机制缺失：

| 缺失 | 表现 | 后果 |
|---|---|---|
| **没有「寿命」概念** | 文档默认永生，写完就一直在 | 只增不减（实测：近 100 个提交 +17877 行 / −1124 行，约 16:1） |
| **位置不决定命运** | 放进 docs/ 就完了，命运动辄要人判断 | 「该不该传」「该不该删」每次都要重新吵一遍 |
| **正式与草稿不分** | 一次性审核报告和常青契约混在同一层 | 不知道哪些必须读、哪些是历史快照 |

业界对第三条有明确定性：**「把冻结文档和常青文档混在一起又不标注，是团队不再信任文档的头号原因」**【高】。

来源：https://docsio.co/blog/engineering-documentation

## 二、业界依据（4 条，均有出处）

### 1. Diátaxis 框架【高】
文档按**用户需求**分四类：教程 / 操作指南 / 参考 / 说明。
核心主张：**一篇文档只能服务一种需求，混着写是万恶之源**。
采用者：Python 官方文档社区、Canonical、Cloudflare、Gatsby。
来源：https://diataxis.fr/

### 2. 文档五大死因【高】
无归属 · 无评审 · 位置错 · **过期但看起来很新** · **无删除纪律**。
其中「过期但看着很新」被判定为**比没文档更糟**（会主动误导）。
解法两条：① 显式标注「最后审阅时间 / 到期日」；② **季度归档 pass**，把死文档移进明确标记的「阁楼」。
来源：https://docsio.co/blog/engineering-documentation

### 3. ADR（架构决策记录）【高】
格式极简：Status / Date / Context / Decision / Consequences。
两条硬规矩：
- **一旦 accepted 就不可再改**（改了就失去「当时为什么这么定」的考古价值）；要推翻就写一份新的 supersede。
- **如果一周写五个 ADR，说明你在用 ADR 记本该是聊天记录的事**。
参考节奏：团队第一年 20~40 份，之后每月 1~2 份。
来源：https://docsio.co/blog/architecture-decision-record

### 4. Atlas 的归档规则【中，但对 solo 特别对症】
- **Archive, Don't Delete**：过期文档移到 `docs/_archive/[YYYY-MM]-描述/`，归档后**不改内容**，用 `git mv` 保住历史。
- **AI 生成 / 实验性文档先落归档区**，验证属实后才「提升」为正式文档。
- **正式文档禁止链向归档区**（用脚本强制检查）。
来源：https://github.com/blitzcraftlabs/atlas/blob/main/docs/how-we-build/documentation-policy.md

## 三、给 solo 的体系：四区 + 三标记 + 五动作

### 3.1 四区（核心：**位置决定命运**）

设计原则：**不用每次判断，看它在哪个目录就知道它的命。**

| 区 | 放什么 | 维护方式 | 是否上传开源库 |
|---|---|---|---|
| **① 契约区** | 改代码前不读就会出事的硬规则 | 常青。动相关代码必须同步 | ✅ 传（这是产品的说明书） |
| **② 决策区** | 重大取舍（ADR） | **只增不改**，推翻就写新的 | ✅ 传 |
| **③ 档案区** | 一次性审核 / 排查 / 方案 / 交接件 | **写完即冻结**，只在被引用时读 | ❌ 不传 |
| **④ 阁楼区** | 过期、作废、被取代的 | 只读，永不维护 | ❌ 不传 |

**契约区的硬指标：不超过 10 份。** 超过就说明有东西混进来了——要么提升为契约，要么降级去档案区。

### 3.2 三标记（每份文档头顶写清）

现有 frontmatter 已有 status / type，补两件事即可：

```
---
title: xxx
doc-life: evergreen | frozen      ← 常青 / 已冻结（一眼看出要不要维护）
review-by: 2027-01-13 或 —         ← 常青文档才有，到期提醒；冻结文档写 —
owner: 简乐
---
```

**为什么必须显式标**：业界判定「过期但看起来很新」是最危险的文档状态，唯一解法就是让它**看起来就旧**。

### 3.3 五动作（日常怎么运转）

1. **写之前先选区**——提笔前先决定这份文档归哪个区，位置即命运。
2. **AI 产物默认落档案区**——照 Atlas 规则：我生成的审核/方案/交接件一律先进档案区，验证属实后才「提升」进契约区。这一条能直接止住膨胀。
3. **一次性产物命名带日期**——`REVIEW-2026-10-11-xxx.md` 这种，看到日期就知道是快照。
4. **季度归档 pass（15 分钟）**——扫一遍契约区：还有效的留，过期的 `git mv` 进阁楼区，正式文档不许链向阁楼。
5. **文档更新跟着代码走**——改了代码就顺手改对应契约，不单独开「补文档」任务（业界判定：单独开任务 = 必然烂尾）。

## 四、落到 solo 现状：现有文档怎么归位

> 下列为**建议映射**，未执行。docs/ 现有 107 份，wiki/ 8 份。

**契约区（建议保留 ≤10 份）**
- `AGENTS.md`（行为契约）
- `docs/sensitive-areas.md`（敏感区表）
- `docs/KNOWN-ISSUES.md`（台账，常青）
- `docs/DOC-STANDARD.md`
- `docs/solo产品精神.md` / `docs/project_rules：工作原则和纪律.md`（产品定位，取舍准绳）
- `docs/CHANGELOG.md` / `CONTRIBUTING.md` / `SECURITY.md`（对外）
- `README` 四语言 + LICENSE

**档案区（绝大多数归这里）**
- `docs/archive/` 全部（90+ 份审核报告、排查记录）
- 各类 `REVIEW-*`、`PROPOSAL-*`（已结案的）、`handoff-*`

**决策区（新建 `docs/adr/`）**
- 从已拍板的 PROPOSAL 里提炼，例如：列表语义 §8「接受现状」、单元格拍平 B1、块级公式「补回上游约束」。
- 每份控制在**一页以内**（ADR 的精髓是短，长了就该叫设计文档）。

**阁楼区**
- 与代码脱节、已被取代的旧稿（如 #65 远程图片缓存描述与代码不符那类）。

## 五、一句话规则

**问「这份文档该不该传 / 该不该删」之前，先问「它在哪个区」。**
区定对了，答案自动出现，不用每次重新讨论。

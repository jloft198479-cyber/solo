## 最可疑的方向（按可能性排序，均需错误原文才能定案）

1. **首次高亮装饰「0 → N 个 span」与 PM 的 DOM 重读时序竞态**（最可能解释「偶尔」）
   - 空代码块本无任何高亮装饰；打入首字后，插件重建装饰，文本被包进多个 `<span class="hljs-*">`。这是该块**第一次**发生的大幅 DOM 结构变化。PM 的 MutationObserver 若在这轮变更与读回之间抢跑，理论上可造成首字丢失 / 重复 / 闪一下。
   - 与用户描述的两个特征都吻合：**第一次**（0→N 的信号最强）、**偶尔**（取决于时序）。

2. **输入法（IME）首字上屏与高亮的交互**
   - 现有 `composition-freeze` 只在**组字期间**冻结装饰重建；中文首字 `compositionend` 提交那一刻 `view.composing` 已为 false，装饰会立刻重建 —— 这个窗口在 WebView2 下是否稳定，本机 happy-dom 无法验证。
   - 若用户是**拼音/五笔**输入首字，这条优先级应上调到第 1。

3. **创建方式是「语法糖」而非菜单**（` ``` ` + 回车 / 斜杠命令 / 快捷键）——不同创建路径进入的事务形态不同，可能只有某一条命中竞态。

## 附带发现（确定的代码隐患，但不是本次"首字"的触发点）

`code-block.ts` 的 `ignoreMutation` 只放行 header：

```ts
ignoreMutation(mutation) {
  return mutation.target instanceof Node && header.contains(mutation.target);
}
```

而 `syncLanguageUI()` 会写 `pre.dataset.language`（`pre` 是 `code` 的祖先、不在 header 内）。已核对 `prosemirror-view@1.42.3` 源码 `registerMutation`（`dist/index.js:4896-4929`）：**未被 ignore 的属性变更**会被判成「整块 DOM 变了」，返回 `{from: posAtStart-border, to: posAtEnd+border}` ⇒ PM 重读整块。

- 触发条件：**只有代码块语言标签变化时**（`pre.dataset.language` 值变）才真的有 MutationRecord；普通打字标签不变（同一个值重复 set 不产生记录，DOM 规范「change an attribute」对相同值提前返回）⇒ **它不是"首字输入"的元凶**。
- 但它确实是一条真实隐患：改语言时会多一次整块重读，且在某些时序下可能干扰装饰。建议后续单独收口（把 `pre` 也纳入 `ignoreMutation` 放行，或把 `pre.dataset` 写改成 `renderHTML` 输出）。

## 0.1 三十秒速览

- **问题一句话**：在 Windows 11 上，一个 Tauri v2 桌面应用的 WebView2 区域中，用中文输入法打字时，**输入法候选窗偶发脱离光标、被渲染到远离光标的屏幕固定点**（2026-09-13/14 基线实测为右下角 `(1340,996)`；**该坐标并非恒定**，2026-09-24 复测已变为 `(782,706)`，见 §6.6）。
- **它是不是渲染坏了**：不是。候选窗**形态完全正常**（7 个候选词 + 工具栏齐全），**只是位置错**。
- **它会不会丢数据**：不会。已上屏文字正常、文件不损坏、保存不受影响。
- **它什么时候发生**：**偶发**（实测约 16% 会话命中），集中在「进入应用 / 切换文档 / 窗口位移」之后的**第一次**组字。
- **它怎么消失**：**任何鼠标移动或点击立即清除**；同一场景下第二次组字通常也不再出现。
- **为什么难查**：① 候选窗**没有窗口句柄**，只能靠屏幕像素观测；② 「鼠标一动就好」⇒ **测试动作本身会擦掉现象**；③ 现象不可稳定复现 ⇒ **任何修法都无法验证**。
- **我们做到哪一步**：现象、触发条件、自愈条件、对照差异都已量化；**根因未定位**。

## 1. 项目与运行环境

### 1.1 solo 是什么

**solo** 是一款**本地优先（local-first）的桌面 Markdown 编辑器**，面向中文沉浸式写作：纯本地、无后端服务、无账号、单文件编辑。

| 维度 | 说明 |
|---|---|
| 定位 | 个人化「阅读 + 写作体验」工具；非协作、非长文档处理器 |
| 架构 | **Tauri v2**（Rust 宿主）+ **Vue 3** 前端 + **TipTap 3 / ProseMirror** 编辑器内核 |
| 渲染 | 前端**单一 `contenteditable` 同时承担两个角色**：① 输入法的拼字面；② Markdown 实时渲染面（行内标记实时变身、装饰层、NodeView 等） |
| 平台 | Windows（本机 Win11）为主；代码层跨平台（macOS / Linux 亦有路径） |
| 分发 | NSIS 安装包；GitHub Release 自动更新 |
| 版本（本报告基线） | **v1.2.56** |

> 这条「同一个 contenteditable 既当拼字面又当渲染面」的设计，是理解本项目 IME 相关一切问题的前提。

### 1.3 窗口形态（与「普通 Tauri 应用」的差异）

solo 为了让 UI 更"轻"，采用了**无边框 + 透明 + 自绘标题栏**：

```jsonc
// src-tauri/tauri.conf.json:23-27
"decorations": false,      // 无系统边框
"transparent": true,       // 窗口透明
"shadow": true,
"dragDropEnabled": true,
"additionalBrowserArgs": "--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection,TSFImeSupport"
```

前端用 `data-tauri-drag-region` 自绘可拖拽标题栏（`src/components/Layout/CustomTitlebar.vue:17-34`）。

**实测的 Win32 窗口事实【观测】**：

| 项 | 实测值 |
|---|---|
| solo 顶层窗口 style | `0x14CF0000`（**保留** `WS_CAPTION` / `WS_THICKFRAME`，即 tao 的"假无边框"） |
| exstyle | `0x00040110`（**`WS_EX_LAYERED = false`** ⇒ **不是** OS 层分层窗口；透明来自 DWM blur-behind） |
| 父窗 vs WebView 子窗 | 父窗 `720×822`，子窗（`WRY_WEBVIEW` / `Chrome_WidgetWin_1`）`704×814` ⇒ **四周各 8px 透明边距** |
| 渲染路径 | Chromium 走 `Intermediate D3D Window`（D3D 合成） |
| 输入法宿主窗口 | 每个 solo 进程挂 `MSCTFIME UI` + `Default IME` 窗口（TSF 的 UI 宿主） |

## 2. 问题陈述

### 2.1 标准问题陈述（**未标定 · 只有可观测事实 · 不含任何因果推断**）

> **Windows / WebView2 宿主层「IME 候选窗失锚」现象**：
> Windows 11 上，在 Tauri v2（wry）宿主 + WebView2 Runtime 应用中，使用微软拼音等 TSF 输入法打字进入 composition（组字）时，输入法候选窗**偶发脱离文本光标锚点**，被渲染到一个**远离光标的屏幕固定点**（2026-09-13/14 基线实测为右下角 `(1340,996)`；2026-09-24 复测为 `(782,706)`；**同一会话内为常数**，跨期实测不同但与 Runtime 152→153 变更混淆、不可归因；与窗口位置、光标位置均无关），约 16% 会话命中；触发时机集中在**宿主窗口 resize / 焦点切换 / 切换编辑对象后的首次组字**，同一场景下**第二次组字通常不再出现**，且**任何鼠标事件（mousemove / click）立即清除**，因此在自动化环境下无法稳定复现；同机同输入法下，**Edge 浏览器本体与纯 `<textarea>` 均不出现**该现象（1606 帧采样中 21 帧失锚全部落在该应用内）；最小复现为 stock Tauri + 单个裸 `<input>`（同族上游记录：`MicrosoftEdge/WebView2Feedback#5675`，其表现为韩文 IME / 左上角）；另在组字期抑制 DOM 变更的 JS 侧缓解**已实测无效**（`#5625`）。**根因未定位**，上游同族 issue 至今 0 回复、无官方结论。

**检索关键词**（给第三方定位用）：`WebView2` · `TSF / IMM32` · `IME candidate window mispositioning` · `composition anchor` · `composition rect` · `wry / Tauri v2 host`

### 2.3 触发与自愈（观测到的规律）

| 维度 | 观测 |
|---|---|
| 易发时机 | 「**进入应用 / 切换文档 / 窗口位移**」之后的**第一次**组字 |
| 时间相关性 | 两次失锚都在「刚切进 solo（t=47.4s）之后 5s / 16s」 |
| 自愈方式 | ① 组字窗口自动归位（现场实测约 **1.6s** 后跳到光标附近）；② **任何鼠标移动/点击立即清除**；③ 同一场景**第二次组字通常即恢复正常** |
| 长期趋势 | 会话进行 21 分钟后，再回应用打字**全部正常** |
| 与速度无关 | 两次失锚的组字间隔为 4.9s / 12.9s，**与"打字快慢"无关** |

> ⚠️ 我们早期文档曾把这条写成「第一次失锚、**第二次自愈**」。**该表述过简且不准确**：真值是**初期易发、随会话推进消失**（现场实测同一场编辑内出现了 **两次**失锚，间隔 11s）。

### 2.4 最小复现（**来自上游第三方报告，非我方自证**）

上游 **`MicrosoftEdge/WebView2Feedback#5675`**（2026-08-18 开、state=open、**0 评论**）记录了同族现象：

| 项 | 内容 |
|---|---|
| 复现栈 | `create-tauri-app --template vanilla`（**stock Tauri 默认配置：有边框、不透明**）+ 一个**裸 `<input>`** |
| 环境 | `webview2-com 0.38.2` / Tauri **2.11.5** / wry **0.55.1** / Win11 26200 / Runtime **151.0.4129.86** |
| 复现配方 | **resize 窗口后，不碰键盘鼠标立刻打字** |
| 症状 | 组字窗跑到**屏幕角**（**他们左上、我们右下**） |
| 关键行为 | **任何鼠标移动/点击即清除**；不点不动则**永久错位** |
| 该提交者已排除 | 子窗口几何（`Chrome_RenderWidgetHostHWND` 28ms 内已更新）· 主线程阻塞 · 页面侧 caret rect（正常）· `MoveFocus(PROGRAMMATIC)`（无效）· `NotifyParentWindowPositionChanged()` **连调 10 次（0~1100ms）无效** |
| 微软回应 | **无**（页末为 "*No response*"） |

> ⚠️ **诚实标注**：我方**从未自行复现**这个最小工程。它是**第三方（上游）报告**，我方仅通过 WebFetch 读过其页面原文。若您的结论依赖"这是宿主层缺陷而非本应用代码问题"这一前提，**建议先自行跑一次这个最小复现**。

### 2.5 ⚠️ 两个症状必须分开（这是最容易走偏的地方）

上游同族 issue 里其实有**两类不同缺陷**，混用会推出矛盾结论：

| | **A. 候选窗飘角**（本项目主诉） | **B. contentEditable 吃字 / 标点双按** |
|---|---|---|
| 上游记录 | `#5675` | `#5625` |
| 与 `contentEditable` 的关系 | **无关** —— **裸 `<input>` 也复现** | **有关** —— 同页面 **`textarea` 完全正常**，`contentEditable` 出错 |
| 症状 | 候选窗位置错 | 第一个 CJK 字符被吞、中文标点要敲两遍 |
| 与 IME 的关系 | 跨输入法（上游韩文 / 我方中文） | **搜狗拼音严重、微软拼音轻**（该提交者观察） |
| JS 侧缓解 | —— | **已被该提交者实测证明「组字期抑制 DOM 变更」无效** |

> **为什么必须分开**：有人会同时用「`textarea` 正常 ⇒ 病灶在 `contentEditable`」和「裸 `input` 也复现 ⇒ 与 `contentEditable` 无关」来论证，**这两句互斥**。真相是它们是**同一子系统（WebView2 的 TSF 文本输入集成）下的两个不同缺陷**，不可互推。

### 3.2 🟡 `composition-freeze.ts`（组字态唯一真相源）

文件头自述其设计意图（原文摘录）：

```ts
/**
 * 输入法「合成冻结」总闸 —— 合成期视觉层行为的唯一真相源。
 *
 * 为什么需要它：solo 让同一个 contenteditable 同时当「输入法拼字面」和
 * 「markdown 实时渲染面」。输入法靠浏览器上报的光标矩形定位候选窗，矩形由 DOM
 * 算出来；合成期若重排 / 重建 DOM，矩形失真 → 候选窗失锚。
 *
 * 铁律：合成期（isFrozen 为真）只允许浏览器自己的合成文字落地，其余一律推迟——
 *   - 装饰：走 mapFrozenDecorations（只平移、不重建）
 *   - 结构变身 / 菜单定位重渲 / nodeview 重建：直接跳过，等 compositionend 后再补
 *
 * 设计约束（勿违）：
 * 1. 不做全局 dispatch 拦截：ProseMirror 的合成事务与应用事务走同一条通道，
 *    全局拦会连用户打的字一起挡掉。
 * 2. 权威信号是 view.composing（浏览器 DOM composition）。
 * 3. 退化安全：view 缺失 / 已销毁一律视为「未冻结」。
 */
```

**导出三个符号**（全文 68 行，已读源码核实）：

| 符号 | 作用 |
|---|---|
| `isFrozen(view)` | `view?.composing === true`；view 缺失/已销毁 → `false`（退化安全） |
| `mapFrozenDecorations(set, tr, doc)` | 组字期**只按事务 map 平移**已有装饰，**绝不重建** |
| `createCompositionTracker()` | 每实例一份的 view 登记器（`state.apply` / `appendTransaction` 拿不到 view） |

它对原先散落在 4 个文件（`markdown-input` / `paragraph-focus` / `search-highlight` / `code-block`）里的 `let liveView` + `view.composing` 内联副本做了收敛。性质为**纯重构、行为等价**。

> ⚠️ **定位澄清（重要，请勿误读）**：该总闸的正当性来自「让组字期 DOM 保持干净」这一**独立目标**（对付"组字期 DOM 抖动引发的各类 IME 异常"）。
> 对 **§2.5-A 的「飘角」它不是解药** —— 上游已实测「组字期抑制 DOM 变更的 JS 侧缓解无效」（`#5625`），且裸 `<input>` 也失锚（`#5675`）。
> **但也不要因此认为它无用**：它是针对另一类 IME 异常的防守，方向本身合理。

## 4. 当前遇到的系统性障碍

这一节是本报告**最值得读的部分**。它解释了为什么"我们已经查了很多、仍然定位不了"——**不是查得不够，是有三道物理性障碍**。

### 4.1 障碍一：不可观测（看不见）

Win11 微软拼音候选窗由 `TextInputHost.exe` 的 **UWP 合成层**绘制，**没有独立窗口句柄**：

- `EnumWindows` 只能看到那个全屏 `Windows.UI.Core.CoreWindow (0,0,1920,1080)`；
- UIA 路线在本机被安全策略拦（`Add-Type` 一刀切）；
- Chromium 系窗口是**自绘光标**（`hwndCaret = None`）。

⇒ **我们只能截屏数像素**（判据 = 选中项高亮 `#A6D8FF` + 形状约束）。没有任何接口能问它"你为什么摆错了"。

### 4.2 障碍二：不可复现（一测就没）

触发窗口极窄 + **"鼠标一动即自愈"**：

- 自动化脚本里**先动鼠标 = 自己把 bug 擦了**；
- 复现必须**全程零鼠标事件**；
- 触发窗口是「几何变化/焦点变化后**第一次**组字」的毫秒级时序。

⇒ 实测 **35 次对照实验零复现**、**14 试次 / 120 次键盘注入零复现**；另有 **46 次窗口位移样本**（**口径不同：这是日志里提取的窗口 rect 变更次数，不是实验次数，§6.3 原文即标「样本不足，不足以下结论」**）。**测试行为本身会污染被测对象**。

### 4.3 障碍三：不可证真（无法验证修法）

由 4.2 直接推出：**既然现象无法在自动环境稳定触发，任何"修法"都无法 A/B 验证。**

- 「机制合理 + 业界先例」只能给**安慰**，给不了**结论**；
- 测试跑绿 ≠ 修好了；
- 因此每一次"修"本质上都是**赌**。

### 4.4 障碍四：环境漂移（沙子上的塔）

WebView2 是 **Evergreen 运行时**，会自动升级：

- 我们**全部历史实验**跑在 `152.0.4191.66`；
- 本机现已是 **`153.0.4234.x`**（09-17 记录 `.32`，09-23 实测 `.48`）；
- 且 **Edge 153 本身已被微软承认存在「输入/交互冻结」bug**（2026-09-10 发布；微软 2026-09-16 承认，临时方案 = 回退 152；Salesforce 同日报告 Chrome/Edge 153 间歇性 UI 卡死，触发点为 09-08 前后自动更新）。

⚠️ **注意区分**：153 已确认的症状是「**交互冻结**」，与本问题的「**候选窗飘角**」**症状不同**。故 153 是**嫌疑**，**不是已证原因**。

⇒ **不锁运行时版本，后续一切判断都建立在流沙上。**

**结论（原理性）**：用「**干净新实例 + 理想时序**」的自动化复现，**原理上打不到这个 bug**。它只在用户**长时间运行的真实实例 + 真实操作序列**（含鼠标、滚轮、窗口拖动、长时间停顿）下偶发。

### 6.5 实验方法论坑（供您避坑）

| 坑 | 说明 |
|---|---|
| 判据会**假阴性** | 在蓝色壁纸上，全屏蓝像素 bbox 会把天空/湖面圈进来 ⇒ 明明有候选窗却报"未检出"（6 次里 5 次误报）。对策：基线差分 + 逐行最长连续 run 聚簇（**基线必须在移窗之后抓**） |
| 判据也会**假阳性** | 曾把候选窗本体误判为"背景窗口 UI"：`(784,708)` 蓝块当时被认定为**假目标**（判据要求"蓝条须贴屏幕右下角"），并于 2026-09-24 早期写入文档。**后经像素级复测推翻 —— 它就是候选窗选中项高亮**（见 §6.6）。**教训：判据的"位置先验"（必须在角落）会把真实但形态不同的现场判成噪声；下结论前必须裁剪放大肉眼复核** |

| 拖标题栏后丢键盘焦点 | WebView 可能丢键盘焦点 ⇒ 组字不再触发（`SetFocus` 到 `Chrome*` 子窗口可交还，且不产生鼠标事件） |
| 反复 Shift 切中英会把实例搞到"打不出组字" | **换干净实例**比继续试快得多 |

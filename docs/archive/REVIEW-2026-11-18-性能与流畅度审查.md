# 性能与流畅度系统审查（2026-11-18）

> 性质：**只读审查，未动任何代码、未跑构建**。承接用户主诉「solo 的速度和丝滑程度总是不够理想」，
> 前提「不伤害已有功能」。方法：五路并行取证（编辑热路径 / 重渲染管线 / Vue 壳层 / Rust IPC / 启动体积），
> 关键论断逐条开原文复核，全部带 `file:line`。
> 承接关系：2026-09-18 已有一轮性能优化（见 [PERF-AND-THEME-SUGGESTIONS](./PERF-AND-THEME-SUGGESTIONS-2026-09-18.md)），
> 当时的结论是「大头已吃完」。本轮证实该结论基本成立，**但找到了当时漏掉/未闭环的残留源**，
> 其中两处与「中文打字不丝滑」的主诉直接吻合。

---

## 〇、结论先行（大白话）

把编辑器想象成一个餐厅：9 月那轮优化已经把「上菜慢」的大问题解决了（序列化从 20 秒降到 0.1 秒、
重活都挪到了空闲时段）。但这次发现**厨房里还有几个「每做一道菜都要重复一遍的小动作」**，
单个不致命，叠在一起就是你说不出哪里不对、但总觉得「不够丝滑」的来源：

1. **每打一个中文词上屏，编辑器就把整篇文档从头到尾检查一遍**（找有没有待转换的 `#` 标题）。
   文档越长越卡，而且这条**没有**大文档降级保护。——最可疑的「中文打字不跟手」来源。
2. **在代码块里打字，每敲一键就把整个代码块重新染色一遍**。块越大越卡。
3. **每隔一小段停顿，就有一次 0.1~0.3 秒的「独占主线程」大扫除**（全文序列化/字数/大纲），
   恰好撞上下一次按键时，就是一个可感知的顿挫。10~40 万字的「中等文档」完全没有降级档位。
4. **启动时背了一个 427KB 的大包**（分包配置把 Vue 本体也卷了进去），懒加载被部分架空。
5. 其余：搜索开着时编辑、公式/图表重渲染不比对内容、大纲关了还在算、窗口透明合成等。

**排序依据是「发生频率 × 单次成本」的推理，不是实测**——项目至今没有常驻性能测量
（9 月建议 A1 未落地），所以本报告把「先测量」列为第 0 步。凡标注「疑似」的条目，改前必须先测。

## 一、已经做对的（防重复提案，别动）

取证确认以下机制健康，**本轮不建议碰**：

- 序列化已是 O(n)（分片 push+join，`markdown/serializer.ts:113` 附近）；脏态比对是纯字符串比对，
  只在 500ms 防抖 + 空闲回调后跑一次，**无每事务序列化**（`useEditorSync.ts:100-128` → `stores/file.ts`）。
- 四层防抖齐全：光标/选区 100ms、字数 150ms、大纲 500ms、序列化 500ms+rIC（`useEditorSync.ts:34-44`）。
- 全部 NodeView（image/frontmatter/callout/code/math×2/mermaid）是**纯 DOM**，全仓无 VueNodeViewRenderer，
  大文档下零 Vue 组件实例开销；editor 本体已 `shallowRef` 隔离（`MarkdownEditor.vue:162`）。
- Rust 侧纪律好：文件 IO 全在 `spawn_blocking`，**打字期间零 IPC**，自动保存默认关、下限 5s、脏才写。
- mermaid/katex 已正确动态懒加载（`mermaid-block.ts:228`、`math-block.ts:18-20`），不在首屏；
  lowlight 按需注册 17 语言、懒单例（`code-block.ts:23-39,96-118`）。
- 双 markdown-it 管线已收敛（仅剩编辑器卸载时的 fallback）；滚动监听均 passive+rAF 合流；
  全仓无 `deep:true` / `flush:'sync'` watcher。
- 组字期冻结（composition-freeze）期间各装饰插件只 map 平移不重建——IME 保护本身是对的，
  问题在**解冻之后**（见 S1）。

## 二、卡顿源清单（按感知影响排序）

### S1 🔴 中文输入热路径：每词上屏一次全文扫描 + 每键两次段内拷贝

**用户感受**：中文打字「不跟手」，文档越长越明显；长段落（中文习惯一段几千字）里打字发黏。

**机制与证据**（`src/components/Editor/tiptap/extensions/markdown-input.ts`）：
- 每次 IME 上屏（compositionend）后 50ms 置 `forceCheck`（`:262-270`），下一个事务走
  `scanHeadings` **全 doc.descendants 遍历**（`:300-301` → `:522`）。WeakMap 按 doc 引用缓存，
  但每次上屏 doc 必是新的、必 miss；只有「存在空/pending 标题且排在前面」才短路，
  普通文档每词全扫。**无 heavy 档门控**。连续快打时下一次 compositionstart 会取消定时器，
  所以爆发点在「词与词之间的停顿」——恰好是慢节奏中文输入的每一拍。
- 每次非组字的文档变更，`convertPendingInlineMarks` 与 `convertPendingLink` 各做一次
  `parent.textBetween(0, 光标偏移)` **拷贝段内光标前全部文本**（`:406`、`:466`），
  再跑约 10 条行内标记/链接正则。成本 O(段落长)：几百字的段无感，几千字的长段每键都付。
- 解冻后首事务还叠加 list-fold 补建、code-block/search 装饰重建，形成每词一次的小 burst。

**改善（不伤功能）**：
1. `scanHeadings` 增量化：普通上屏只扫「变更段 ± 相邻段」，全文扫保留给低频兜底
   （如停笔 >1s 或切文档）。pending heading 只可能出现在变更段附近，正确性可用
   「变更区间扫描 + 定期全扫兜底」保住——与 P4-02 已对空标题做过的增量思路同构。
2. 给 forceCheck 全扫加 heavy 门控（heavy 档降频或只扫变更区间）。
3. 段内拷贝加「段长上限」：超过阈值的段落只取光标前最后 N 字符跑正则
   （行内标记语法不可能跨几千字匹配，锚定在光标前末尾，见 `:448` 的 `$` 锚定正则）。

**风险**：中。碰的是 markdown-input 转换链路（敏感区），必须过既有 markdown-input 测试族
+ IME 守卫回归（组字期行为一个字节都不能变）。改完按「中文长段落连续输入，候选窗不漂、
`# ` 直输与 `**加粗**` 直输照常转换」验收。

### S2 🔴 代码块内打字：每键整块重高亮，标注语言的块无大小上限

**用户感受**：在大代码块里编辑时按键发黏。

**机制与证据**（`extensions/code-block.ts`）：
- apply 对每个受影响块**同步**整块 `highlightBlock`（`:359-366`）。打字时通常只命中 1 块，
  8 块限额（`:355`）管不到「单块很大」的情形。
- 两道规模门（heavy 档 / 3000 字）**只限自动语言检测**（`:176`）；标注了语言的块走单语言
  tokenize，注释自认「不受这两道门限制」——1000 行的 JS 块每键全块重染，WebView2 下可达每键 10ms+。

**改善**：给标注语言的块也加单块规模门（超限走「编辑期降级为纯文本、停笔后空闲补染」），
或把编辑期重染改为 100~150ms trailing 防抖（组字期照旧只 map）。
**风险**：低-中。纯装饰层，不碰 parser/serializer；须守 composition-freeze 铁律，
验收「代码块内打字高亮延迟 ≤200ms 跟上、组字期候选窗不漂」。

### S3 🟠 周期性主线程独占：中等文档（10~40 万字）没有降级档

**用户感受**：慢节奏打字时偶尔「顿一下」；文档越大越频繁。

**机制与证据**：
- 序列化空闲回调**不可抢占**：真空闲分支一次性跑完全文序列化（大文档 100-300ms，
  注释自认，`useEditorSync.ts:110-120`）。续打保护只覆盖 `didTimeout` 分支（`:116`），
  真空闲长回调进行到一半时用户恢复打字，就会撞上。
- 字数 O(N) 全文遍历 + 逐节点正则（`editor-metadata.ts:14-22`），仅 ≥50 万字降级
  （`useEditorSync.ts:145`）；大纲同理仅 heavy+关面板才停（`:74`）。
  **10~40 万字档每 150ms/500ms 照跑全量**，停笔即触发。
- 档位只有 normal/heavy 两档，HEAVY_DOC_CHARS=50 万（`document-scale.ts`）。

**改善**：
1. 序列化分片：把 serializeMarkdown 改成可分片让出（每 N 个顶层块检查 deadline.timeRemaining，
   不够就续排下一个 rIC）——O(n) 不变，只是把长任务切碎。这是消除「顿一下」的最直接手段。
2. 加中间档行为（**不动 50 万阈值本身**——9 月已论证下调会放大 IME 失锚暴露面）：
   如 >10 万字时字数改「增量计数」（维护计数器，编辑时按 delta 更新）或降频到 1s。
**风险**：1 中（碰序列化执行时序，脏态/关窗闸口依赖「序列化产物=基线」契约，
分片期间必须禁止闸口读半成品，需过 5 套契约锁）；2 低（字数是纯读数）。

### S4 🟠 搜索开着时编辑 = 周期全文重扫 + 全量装饰重建

**用户感受**：开着搜索面板改文档时明显变卡（匹配多时尤甚）。

**机制与证据**（`tiptap/useEditorSearch.ts`）：编辑触发 120ms 防抖重扫（heavy 500ms，`:66-67`），
全 doc.descendants（`:104`），随后 dispatch 一个**空事务**（`:90`）把全部插件 apply 链再跑一遍，
search-highlight 全量重建装饰。数千匹配 = 数千 inline 装饰 + DOM 分裂。
（9 月报告 B2 已登记此缝，至今未闭环。）

**改善**：匹配数上限（如 >2000 时只标「当前命中 ± 窗口」，其余不挂装饰）；
或重扫改增量（只扫变更区间 + 映射既有匹配）。空事务可换成只通知 search 插件的 meta。
**风险**：中。搜索高亮是既有功能，改判定须过搜索测试族 + composition-freeze；
验收「搜索开着连续编辑不卡、命中计数与跳转仍准」。

### S5 🟡 公式/图表：重渲染不比对内容，math-inline 打开时连发

**用户感受**：含公式/图表的文档打开慢一拍；主题切换时图表区集体闪动。

**机制与证据**：
- `mermaid-block.ts:518-524`：update() 一律 renderMermaid，**无 textContent 相等跳过**；
  renderVersion 只防回写、不取消在途渲染；主题切换经全局 Set 全量重渲、无分批（`:506-513`）。
  初始渲染已走 idle（`:501`，做得对）。
- `math-inline.ts:59`：初始渲染**不走** idle 调度（math-block 走了）——打开含 N 个行内公式的
  文档时 N 次 renderToString 连发；`:64-68` update 无 latex 相等跳过（math-block 同构）。

**改善**：三处 NodeView 的 update 加「内容未变即 return true」一行守卫；
math-inline 初始渲染接入既有 scheduleIdleRender；主题切换重渲分批走 idle。
**风险**：低。纯 NodeView 内部，不碰编解码；验收「公式/图表显示与交互不变、
打开含 50 公式文档首帧更快」。注意 math-block 重渲前先清空 DOM 会闪烁（`math-block.ts:114` 附近），
顺手对齐 mermaid 的双缓冲可消闪。

### S6 🟡 大纲关了还在算、还在渲染；App 壳高频重渲染

**用户感受**：间接——打字期间的背景噪音，放大 S3 的顿挫。

**机制与证据**：
- 非 heavy 文档大纲每 500ms 全文提取，**不管面板开没开**（`useEditorSync.ts:74` 只挡 heavy+关）；
  OutlinePanel 常驻无 v-if，关闭（width:0）时仍 v-for 全量建按钮（`OutlinePanel.vue:172-184`、`App.vue:396`）。
- stats 三路防抖（100/150/500ms）汇聚到 App 单点，连续打字时 App 每 100-150ms 重渲染一次；
  空闲序列化又把**全文字符串**写进 store 并当 prop 传（`App.vue:381`、`stores/file.ts`），
  触发整壳 diff。editor 本体不受影响（createEditor 只读一次，`MarkdownEditor.vue:802`），
  但壳层 diff 是纯浪费。

**改善**：大纲「关面板即停算」（把 skipOutline 的 heavy 条件去掉，打开时 emitOutlineNow 补算——
该补算入口已存在，`useEditorSync.ts:165`）；OutlinePanel 内容加 v-if="isOpen"；
全文 content 不进 App 模板 prop（编辑器自己读 store，壳层只留 isDirty 等轻信号）。
**风险**：低。验收「大纲打开瞬间内容完整、关闭后打字状态栏照常」。

### S7 🟠 启动体积：Vue 被分包配置卷进 427KB 的 tiptap-core，入口静态依赖

**用户感受**：冷启动到窗口可用慢一拍（本地盘读取快，但 JS 解析成本实打实）。

**机制与证据**（实测 dist 产物，2026-11-18 构建）：
- `vite.config.ts:35-41` 把 `@tiptap/vue-3|pm|core` 指定为 tiptap-core chunk，
  Rollup 把共享依赖 **Vue 运行时一并 hoist 进去**：`dist/assets/tiptap-core-*.js` = **426,768 B**，
  内含 createApp 等 Vue 运行时；`dist/index.html` 对它 modulepreload，入口 index（152,557 B）
  静态 import 它 ⇒ 窗口显示前必须下载+解析 ~579KB JS，
  `App.vue:38` 的 defineAsyncComponent 懒加载被部分架空。
- 重库懒加载本身是对的：katex 787KB / mermaid.core 683KB / cytoscape 443KB 均为独立懒 chunk。

**改善**：manualChunks 里把 `vue`/`@vue/*` 单独指一个 chunk（或入口侧不静态引 tiptap），
让 tiptap-core 回到编辑器异步链里。**纯构建配置改动，零运行时行为变化**。
**风险**：极低，但必须真机验一次冷启动 + 首开文档 + mermaid/katex 懒链不坏
（mermaid 不手动分包的既有注释约束要保留，`vite.config.ts:44-47`）。

### S8 🟡 打开/粘贴首帧：同步 parse + 基线 serialize 双跑；粘贴最坏 4 遍 parse

**用户感受**：打开大文档「白一下才出内容」；粘贴大段 Markdown 时顿一下。

**机制与证据**：
- 打开：parseMarkdown 同步（内含三遍全文正则预处理 + md.parse），紧跟**同步全量
  serializeMarkdown 基线**（`MarkdownEditor.vue:420,433` 附近）。基线承重（脏态语义，
  9 月 §9.3 已论证不能推后）——可动的是 parse 侧分片与「先出文本再补装饰」。
- 粘贴：表格/结构化/专有/行内四个分支各自 parseMarkdown（`markdown-paste.ts:316,354,377,460`），
  最坏路径多遍全量 parse；缓存只去重部分层。
- 表格序列化每格 cellToText **跑两遍**（算列宽一遍、输出一遍，`serializer.ts:933,943`），
  每格建子 state 全量渲染；CJK 表格尤贵。第一遍结果缓存即可省一半。
- 图片无尺寸标注时不预留空间（`image.ts:457-464`），加载后布局跳动——「丝滑」观感扣分项。

**改善**：表格 cellToText 缓存（纯优化，逐字节 fixture diff 背书）；粘贴分支先判定再 parse
（避免试探性多遍）；图片加载后把自然尺寸写回 attrs 或 CSS aspect-ratio 预留。
**风险**：表格/粘贴碰 serializer/parser ⇒ **必跑 5 套契约锁 + 逐字节 fixture diff**；图片低风险。

### S9 ⚪ 疑似 · 窗口环境配置（需 A/B 实测，有历史背景，勿盲改）

- `tauri.conf.json:23-27`：`transparent:true` + `decorations:false`（自绘标题栏）、
  `dragDropEnabled:true`、`--disable-features=...TSFImeSupport`。
  WebView2 透明窗走额外合成路径，可能牺牲渲染性能；禁 TSF 影响 IME 路径——
  **这两项与已结案的 IME 候选窗问题（2026-10-12）和自绘窗口外观强相关**，
  本轮只登记「值得一次 A/B 测量」，不建议直接回改。
- 字体兜底/切换走 `read_font_bytes`：`Vec<u8>` 经 JSON 序列化成**数字数组**过 IPC
  （`src-tauri/src/commands/font.rs:266-292`），8-15MB 字体膨胀数倍，切换瞬间秒级卡顿。
  低频但真实；改 base64 字符串或分块传输可大幅缓解（注释自认「代价是 IPC 传几 MB」）。

### S10 ⚪ 低频小项（登记不优先）

- 打开文件时同目录扫崩溃残留 .tmp（`document.rs:132-133,1050`）：在阻塞线程池里跑，
  不卡 UI 但拖慢打开返回，大目录尤甚；可挪后台定时清。
- 主题切换两次强制重排（`themes/manager.ts:260,307` 附近，子代理取证未亲核）+ mermaid 全量重渲。
- idle-render-scheduler 固定 4 任务/批、不看 deadline（`idle-render-scheduler.ts:32-45`），
  mermaid 单张几十 ms 时一批可占满空闲窗。
- 滚动停 800ms 写 session JSON（读全文+原子写回），碎 IPC 可合并。
- CommandPalette 打开时 mousemove 逐像素写 activeIndex 整列表重渲（面板内，非打字路径）。

## 三、不建议做的（性价比低或与架构冲突）

| 项 | 原因 |
|---|---|
| 编辑器虚拟化/视口渲染 | ProseMirror 假设全节点在 DOM，contentEditable 下虚拟化=重写 PM（9 月 C 级结论维持） |
| 下调 HEAVY_DOC_CHARS 阈值 | 会放大 IME 候选窗失锚暴露面（9 月已论证）；要中间档行为，不要动阈值 |
| 回改 transparent/TSFImeSupport | 与已结案 IME 问题、自绘窗口外观强耦合，先 A/B 测量再议 |
| 砍 NodeView / 换编辑器内核 | 纯 DOM NodeView 已是正确架构，问题在具体守卫缺失不在架构 |

## 四、建议执行顺序（若采纳）

0. **测量基建**（9 月 A1 至今未落地，本轮所有排序都是推理）：诊断模式下记录
   打开耗时分段、按键→渲染延迟、`performance.memory`、DOM 节点数。零行为改变。
   没有它，S1/S3/S9 的「感知影响排序」无法被证实或证伪。
1. **S7 启动分包**：纯构建配置、零功能风险、收益确定。
2. **S5 内容相等守卫 + S6 大纲关面板停算**：各几行改动，低风险快赢。
3. **S1 markdown-input 增量化**：主诉最相关，但碰敏感区，需完整回归背书。
4. **S2 代码块编辑期降级/防抖**、**S3 序列化分片**：各自独立交付，过契约锁。
5. S4/S8/S9/S10 按测量结果再排。

每步独立验收、互不阻塞；碰 parser/serializer/schema 的必跑 5 套契约锁，
碰装饰的必守 composition-freeze，碰 IME 路径的必过 IME 守卫回归。

## 五、验收口径（用户这么操作得到什么）

- 打开一份 20 万字中文文档，用输入法连续打字：**词与词之间不再有可感知的停顿**，候选窗不漂。
- 在一个 500 行代码块里连续打字：按键跟手，高亮在半秒内跟上。
- 慢节奏打字 10 分钟（10~40 万字文档）：不再出现周期性「顿一下」。
- 冷启动到可以打字：比现在快（以测量基建的数字为准）。
- 既有功能零回归：全量单测 + 契约锁 + 「`# ` 直输、`**加粗**` 直输、搜索跳转、
  大纲开合、公式图表显示、复制粘贴保真」逐项手验。

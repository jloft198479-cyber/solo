## §2 发现清单

### F1 · `perf-allow` 行尾注释与 `bun run format` 冲突（中，**实测**）

静态锁只认**命中行自己**带 `perf-allow`（`perf-traversal-contracts.spec.ts:53-54`），而 8 处标注里 7 处写成行尾注释。prettier 会把跟在 `{` 后面的行尾注释**挪到下一行** ⇒ 一旦有人跑 `bun run format`，锁立刻红。

复现（我没动仓库，复制到临时目录做的）：`tiptap/` 拷出 → `prettier --write` → 用锁同款正则复判 ⇒ **repo HEAD 0 命中 / 格式化后 7 命中**（`editor-metadata.ts:14,39`、`code-block.ts:224`、`markdown-input.ts:574,823`、`markdown-paste.ts:213`、`useEditorSearch.ts:107`）。`list-fold.ts` 那处是语句不是块首，prettier 不动它，所以是 7 不是 8。

副作用不是静默：是「跑一次格式化就 7 红」，而最省事的止损动作往往是删注释，理由随之流失。
**修法（二选一，都很小）**：① 锁改成认「命中行或紧邻下一行」含 `perf-allow`；② 标注一律写在该行**上一行**。建议 ①，因为它同时容忍 ②。

### F2 · `{ rebuild: true }` 已成测试专用钩子，注释还说「结构变化」（低）

rAF 生产者删除后，全仓只有 `list-fold.spec.ts:369,390` 派发这个 meta；但 `list-fold.ts:101` 的注释仍写「强制重扫重建（结构变化 / 测试显式触发）」。这正是本轮 #72-#74 抓的那类「无效工作」，只是没登记进台账。
**修法**：注释改成「测试显式触发（生产路径由 `touchesBlockStructure` 直接判定）」，或在台账 §二 挂一条，别让它以「生产契约」的身份留着。

### F3 · 台账 #71 只登记了一种「退回全量」，实际更常见的那种没写（低）

#71 只记了「粘贴列表落在文档末尾 ⇒ 有意全量」。源码可证另一类：结构变化落在**列表外**（在段落/标题上按回车、切标题）时，`itemCoverRange`（`list-fold.ts:405-438`）既取不到项、`nodeBefore/nodeAfter` 是段落内的文本节点而非项 ⇒ 返回 null ⇒ `computeRebuildWindow`（:466-469）判「界定不了」⇒ **全量重建**。也就是说：列表文档里每次回车都可能全量扫一遍，只是不再是「每敲一个字」。
不是缺陷（一次性 O(N) 有界，且降级线以下才建装饰），但边界登记不全，下一个读者会以为只有粘贴兜底。
**修法**：#71 那句「已知边界」补上「结构变化落在列表之外」这一类。

### F4 · 静态锁的覆盖面口径没写全（中低）

锁头注释说明了「为什么限定 receiver」，但没说明拦不住什么。实测缺口两处：
- **不认 `nodesBetween(0, doc.content.size)`**：正则（`perf-traversal-contracts.spec.ts:40-41`）只收 `descendants / textContent / textBetween(0…)`，而整篇 `nodesBetween` 代价同级。当前仓内 0 处使用（grep 无命中），所以不是现行问题，是未来的口子。
- **别名写法**：`const d = state.doc; d.descendants(...)` 绕过 receiver 白名单；跨行的链式调用也绕过（锁按行判）。
- **扫描范围只有 `src/components/Editor/tiptap/**/*.ts`**（:20,23-32）：不含 `.vue`，也不含 `src/composables/`。而 #72 那条链路本身是「`useEditorSync` 挂 100ms 防抖 → 调 tiptap/ 里的函数」，热路径若写在 composable 或 `.vue` 里，锁看不见。
**修法**：把这三条写进锁文件头注释（说明「本锁拦什么/不拦什么」），`nodesBetween(0` 顺手加进正则成本极低。范围要不要扩到 `composables/` 是取舍，先不动，等他拍。

### F5 · `editor-metadata.ts` 被这轮改到不再 prettier-clean（极低）

`prettier --check`：`list-fold.ts` / `mermaid-block.ts` / `math-block.ts` 在 `d280b59`（1.2.61）时**就不干净**，本轮不算回归；但 `editor-metadata.ts` 当时是干净的，现在不干净 —— 差异就是 F1 那两处行尾注释。另：`list-fold.ts:251` 有一处 `4a4d0dc` 带进函数的空行（`buildDecorations` 体首行），prettier 会删。
**修法**：随 F1 一起处理，不值得单独跑 `format`（会把三个历史不干净的文件一起改出大量无关 diff）。

**归因订正（WorkBuddy 回执认领）**：`list-fold.ts:251` 那个空行不是设计，是「植入探针验证静态锁」那次校准之后撤探针时，用字符串替换留下的一行操作残留。
**本轮处置**：F1 改完后锁已容忍换行注释，`editor-metadata.ts` 的「不干净」不再引发红灯 ⇒ 实际危害归零；空行**留着不手删**（手删就是和 prettier 对撞，属零收益 churn，下次 `format` 也会自己吃掉）。

### F6 · 组字期 `folded` 不随事务 remap —— **确认非本轮引入**，列出来只为别误判

`list-fold.ts:524-533` 的冻结分支只 `mapFrozenDecorations`，`folded` 集合原样返回；解冻补建时 `pruneFolded`（:605）会把漂移的位置判失效丢弃 ⇒ 表现为「打完一串中文，之前折的项自己展开了」。折错项需要漂移后位置恰好仍是别的项起点，概率低但非零。
diff 上下文行显示这条分支一字未动 ⇒ **既有行为**，与本轮无关。一行可修（冻结分支也过 `mapFolded`），是否要做由他拍。

### F7 · 折叠 fuzz 这把标尺的真实局限（低，属披露不全而非谎称）

`list-fold-fuzz.spec.ts` 的期望值由「把**实际** folded 集合灌进新建 state 全量构建」算出（:92-98）⇒ 它验的是「装饰与折叠集合自洽」，**不验 folded 位置本身对不对**（`mapFolded`/`pruneFolded` 的正确性不在标尺内）。另：OPS 每步都 `setTextSelection(pos)` 用**空选区**（:141），且只有 Enter/Tab/Shift-Tab/Backspace/Delete/Fold/Undo —— 没有**跨项范围删除**、没有 Redo、没有粘贴块 ⇒ 「一个事务里两个不相邻项同时变结构」的窗口合并形态没压到（代码路径 `computeRebuildWindow` 的 min/max 并集在写，但没被验证过）。
它确实做了空转防护（:205 要求 `docChangedOps > ROUNDS/4`），这点是对的。
**修法**：OPS 加一组「随机范围选区 + Delete」，其余维持现状即可。

## §3 我逐条开了源码才下的断言（防「抄说明」）

1. `tr.docs[i]` 是 step **之前**的文档：`node_modules/prosemirror-transform/dist/index.js:2003` `addStep()` 里 `this.docs.push(this.doc)` 发生在 `this.doc = doc` 赋值**之前** ⇒ `stepIsSafe(docBefore.slice(...))` 检查被删区间是对的；同理 `tr.mapping.slice(i)` 配 `step.from`（旧坐标）换算到最终文档，映射段数不多不少 ⇒ 多步事务的窗口换算成立。
2. `isInlineOnly` 不会把「跨块删除」误判成安全：跨两个块的区间 `doc.slice()` 返回的是块节点 Fragment ⇒ 判不安全。同块内的纯打字返回文本 Fragment ⇒ 安全。这正是黑名单要的不对称。
3. `stats.cursor` 全仓无读取方：删除后 `vue-tsc` 0 错 + `App.vue` 状态栏只读 `selectionLen`/`wordCount`。
4. mermaid / math 的早退不丢显示：`enterEdit` 只隐藏不清空，`update()` 在未编辑态必渲。
5. `list-empty-first` 锁承重：`tightChildList` 由 doc 结构判定（`serializer.ts:648`），与源文件松紧无关 ⇒ 不打补丁必然输出紧凑形态。
6. #74 与 Rust 实现一致：`document.rs:124-149`。

# 列表 / 大纲的语义契约

> 本文件是**规则来源**：改列表相关命令前先读它。事实台账 §一 #50 记的是那一次的具体修复，
> 这里的三条公理才是长期有效的准绳。

## 0. 一句话

**在 Markdown 里，列表没有"树"，只有缩进。层级是内容的属性，不是可清除的装饰。**

## 1. 三条公理

1. **缩进是唯一的坐标。** 父子关系只是缩进差的可视化，不是额外的实体。
2. **只有层级动词能改缩进。** 层级动词 = Tab / Shift+Tab / 拖曳 / 「转普通段落」。
   其它命令一律不得改变任何一行的缩进。
3. **操作不外溢。** 命令只作用于被选中的范围；未选中的行，缩进与内容一个字都不能变。

推论（由 1 + 3 直接得出，不是特判）：

> 当某一行被移出列表（缩进归零）时，**它的直属下级必须整体减一级**，
> 否则它们会挂在一条已经不存在的父项下 —— 写出的文件语义是烂的
> （旧 bug 的 `- - 乙` 就是这么来的）。这不是"善后"，是缩进语义的要求。

## 2. 动词表（每条一句话，无例外）

| 动词 | 职责 | 动缩进吗 | 在列表里的结果 |
|---|---|---|---|
| **清除格式** | 去掉选中文字上的**装饰**（粗体、斜体、高亮、删除线、行内代码、链接、dim） | ❌ | 字变干净，**列表符号与层级原样保留** |
| **转普通段落**（Ctrl+0 / 命令面板「普通段落」/ 斜杠「正文」） | 把当前块换成段落 | ✅ | 顶层项：原地退出列表，前后兄弟拆成两张列表（**连带代价：跨过该段落的 `Alt+↑/↓` 换位失效 —— 已拍板「接受」，见 §8**）；**嵌套项**：这一行**真正退出列表**（连 `listItem` 一起脱出、落盘零缩进），⚠️ **块被 relocate 到最外层祖先之后的文档级位置**（故它后面的顶层兄弟会排到它前面）；**它的直属下级整体减一级**并挂回原祖先链；祖先与兄弟的**层级**一律不动（顺序见 §6.6） |
| **无序/有序/任务列表**（第二次按） | 切换：已在该类型中则退出 | ✅ | 同「转普通段落」 |
| **Tab / Shift+Tab** | 缩进 ±1，连带子树 | ✅ | 唯一的微调动词。⚠️ **顶层项（缩进已 0）的 Shift+Tab ＝ no-op**：「−1」越界 ⇒ 无合法动作；要退出列表请用「转普通段落」那族动词（Ctrl+0 / 命令面板 / 斜杠「正文」）。2026-10-11 落地，溯源见 [`KNOWN-ISSUES` §二 #55](./KNOWN-ISSUES.md) |
| **退格（行首）** | 并回上一行，**永不劈开列表** | 视情况 | 已有 `list-backspace-guard` 锁定 |

两条最容易被混为一谈的，边界在这里：

- **清除格式 = 洗澡**：洗掉身上的东西，骨头一根不动。
- **转普通段落 = 换身份**：身份变了，随从的去向必须当场说明（减一级）。

## 3. 反面案例（本契约的直接起因）

结构 `- B / - D[/1,2,3] / - C / - E / - A`，对**叶子 C** 执行清除格式，修复前的结果是：

```
B            ← 被误伤：变成普通段落
- D / - 1 2 3 / - C / - E / - A   ← 全家被提升一级，C 自己纹丝不动
```

两宗罪：① 改错了对象（没动 C）；② 动了没选中的行（违反公理 3）。
根因不是 C 特殊，而是**「清除格式」这个动词当时拥有重排树的能力**。
按本契约，它不再有这个能力 —— 这类 bug 从根上失去发生的可能。

## 4. 业界依据（为什么这么划）

| 软件 | 做法 | 可信度 |
|---|---|---|
| **Word** `Clear All Formatting` | 清字符装饰；项目符号/编号属「段落与结构格式」，**默认保留** | 【中】多个教程一致；另有一说「手动直接应用的段落格式会被清」 ⇒ 有分歧，主流偏保留 |
| **Notion** | `Ctrl+\` 清样式、`Ctrl+/` 改块类型 —— **两个动词彻底分离** | 【高】官方快捷键文档 |
| **Obsidian**（社区插件） | 清除的是**行首标记字符**，缩进原样不动 | 【中】插件 README |
| **Typora** | `Ctrl+0` 标题→段落；取消列表靠两次回车 / `Ctrl+Shift+L` | 【中】多个教程一致 |

**四家实现各异，但共同遵守一条：「清除」不重排树。**

## 5. 实现落点

- `list-demote.ts` —— 「转普通段落」这族动词的唯一实现（托孤：自己降级，直属下级减一级）。
  接管条件：**光标所在的任意列表项**（含子列表与否只影响「要不要托孤」，不影响「该不该接管」）。
- `editor-commands.ts` —— 「清除格式」= `unsetAllMarks()`，不再 `clearNodes()`。

## 6. 未决 / 待验证

1. **异类型子列表**：`- 乙` 挂在 `1. 甲` 下时，托孤后乙成为独立列表与原列表相邻渲染
   （保住它自己的符号）。取舍已知，理由是可逆（一次撤销即回）。
2. **叶子项（不含子列表）转段落**：同样接管。它夹在兄弟中间时 Markdown 没有「不断开列表」的表达方式，故结果会是「前段列表 / 这一行的段落 / 后段列表」—— 但**别人的层级与顺序一个不动**，比原命令（会误伤父项、把全家提升一级）更贴合「操作不外溢」。⚠️ 归因修正：早先写「接管会产出重复内容」是**错的原因** —— 重复来自 `forEach` 参数用错（偏移当下标），已修。
3. **多选区跨多个列表项**：只转光标所在的那一项目前（其余不动），按「少做优于做坏」处理。
4. **真机手感**：UI 类改动需人工复核（含中文输入法组字场景）。
5. **嵌套项转段落（含子列表）的缩进残留已修（🔴B）**：早期实现把段落留在 `listItem` 内——schema 的 `ListItem content: 'block+'` 允许段落留在项内，于是落盘仍带 2 空格，等于「退出的是项、没退出列表」，违反公理 1。现按 Option A 让块**真正脱出 `listItem`**（在**最外层祖先之后**的文档层级落点，落盘零缩进）；其直属下级随之减一级并挂回原祖先链、其余层级与顺序不变。代价：非顶层项的块被 relocate 到文档级（Markdown 无「半脱出」语法，属格式限制非 bug），可逆（一次撤销即回）。锁见 `list-demote.spec.ts` 的 `nested` 矩阵列 + 「公理 3」两组用例。

## 7. 已知取舍 · 嵌套项的 relocate 代价（🔴C，**已拍板：接受**）

**现象（实测，非推测）**：嵌套项转段落时，块被提升到**最外层祖先之后的文档级位置**，
于是它后面的顶层兄弟会排到它前面。

| 输入（`·` = 行首缩进） | 目标 | 落盘 | 原序 → 现序 |
|---|---|---|---|
| `- A / · - B / ·· - C / - E` | B | `- A / · - C / B / - E` | `ABCE` → `ACBE` |
| `- B / · - D / · - C / · - E / - A` | C | `- B / · - D / · - E / C / - A` | `BDCEA` → `BDECA` |
| `- 上 / · - X / · - 甲 / ·· - 乙 / · - 下 / - 尾` | 甲 | `- 上 / · - X / · - 乙 / · - 下 / 甲 / - 尾` | `上X甲乙下尾` → `上X乙下甲尾` |

**其余不变量全部成立**：文字守恒 ✅ 无 `- -` / `- [ ] -` 畸形壳 ✅ 落盘零缩进 ✅
一次 `Ctrl+Z` 全回 ✅ 重开往返守恒 ✅（不是解析器问题）。

**成因**：要让缩进归零，块必须真正脱离 `listItem`（见 §6.5）；
而 Markdown **没有「半脱出」语法** —— 列表中间夹一个段落又不断开列表，写不出来。
脱离后唯一可选的文档级落点就是「最外层祖先之后」，代价是**位置搬家**。

**这不是 bug，是格式的硬限制**。三个可选项（⭐ 2026-10-11 简乐拍板：**接受**）：

- **接受**（✅ 已定）：契约 §2 已按实测措辞改写（「层级不动」为真，「顺序」对嵌套项不再承诺）。代价 = 用户的行会跳位。
  理由：文字/格式/撤销/重开全保真，跳位看得见、可理解，不是静默损坏；符合「内容保真优先于排版美观」。
- ~~**改实现**：寻找「不跳位」的落点~~（❌ 已排除）：段落插在**祖先项正下方**会把**后面兄弟的层级**拖乱——
  文档级段落插入即断开列表，后续嵌套项失去父容器、被解析成顶层（撞公理 1/3）。此路不通。
- ~~**降级**：嵌套项不接管~~（❌ 已排除）：缩进残留 🔴B 会回来，拿真 bug 换小别扭，不划算。

**✅ 方法论欠账已还（2026-10-11，与本拍板同批）**：
`list-demote.spec.ts` 的 `[...textSeq(editor)].sort()` 多重集比对**已全部移除**（5 处），
换成**按拍板契约独立推导的精确顺序断言**；§7 三个场景全部入锁（场景一 = B1、场景二 = B2、场景三 = 矩阵新行），
现 **26 条**。反向校准：`hasOuter` 改 `false`（撤嵌套脱出）⇒ **恰好 5 条转红**（嵌套叶子 / 矩阵深层 / §7场景三 / B1 / B2），
顺序从拍板值退回未脱出值（如 B2：`B,D,E,C,A` → `B,D,C,E,A`），证明顺序锁真承重——
`.sort()` 时代这一回归**完全不可见**。

判据（长期有效）：**每条断言必须能红**。三查 —— ① 是否用了排序/去重等弱化断言
② 期望值是独立推导的还是抄实测的 ③ 撤掉修复该列是否真的转红。

## 8. 已知取舍 · 顶层项「转普通段落」会切断列表（⚖️ 已拍板：接受，2026-10-11）

**形状**：对**顶层中间项**执行「转普通段落」（Ctrl+0 / 命令面板「普通段落」/ 斜杠「正文」），产出
`- 甲` ＋ `乙`（普通段落）＋ `- 丙` —— 列表从中间断成两张、中间夹一行 doc 层文字。

**连带代价**：`Alt+↑/↓` 换位只认同一父容器（[`list-move.ts`](../src/components/Editor/tiptap/list-move.ts):41）⇒ **跨过中间那行的两项再也挪不动**（`甲` 与 `丙` 已在两张表里）。

**为什么不是 bug、也躲不开**：Markdown 里「两张列表中间插一行普通文字」**只有这一种写法**；契约 §2 已经批准「转普通段落」在顶层项上就是「原地退出列表，前后兄弟拆成两张列表」。要让列表不断开只有两种代价更大的办法——把目标项**先挪到列表末尾再转**（用户的行会跳位置），或**对中间项不提供该命令**（砍功能）——**都是拿更别扭的行为换一个不影响内容的结果**，故不取。

**已拍板（2026-10-11，方案 A「接受现状」）**：

| 这个形状从哪来 | 判词 |
|---|---|
| 用户主动按「转普通段落」 | **批准产物**（本就是契约 §2 承诺的形态），不修、不许改 |
| 误操作 / `Shift+Tab` / 行首退格 | **缺陷**（台账 `§二 #26`、`#55`；那几条已修） |

**判据公式（后人的第一句话）**：

> 看到「列表被切成两张 + 中间夹一段」先问一句：**这是用户按「转普通段落」得来的吗？**
> 是 ⇒ 契约批准的产物，别改；否 ⇒ 走台账 `#26` / `#55` 的缺陷路径。

**残余诉求（若将来有人嫌换位挪不过去）**：正解在**换位本身**（让 `Alt+↑/↓` 能跨过非列表块，或给真·拖拽换位兜底，见 [`PROPOSAL-list-row-drag.md`](./PROPOSAL-list-row-drag.md)），**不是**去拦住「转普通段落」。属**独立议题，勿顺手改**。

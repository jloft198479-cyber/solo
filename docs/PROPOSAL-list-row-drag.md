# 列表行拖拽换位（同层）· 提案

> 一句话：给列表的每一行配一个**抓得住的把手**，鼠标按住上下拖，就能把这一行挪到别的位置。
> **本提案只做「同层换位」**（兄弟行之间上下换位置）；**跨层**（左右拖改变缩进层级）本次**不做**。
> 相关前作见 [`PROPOSAL-list-outline-experience.md`](./PROPOSAL-list-outline-experience.md)（折叠 / 引导线已落地）。

> ## ⚠️ 方案变更（2026-10-09）：先做键盘，鼠标拖拽暂缓
>
> 简乐拍板：**换成 `Alt+↑/↓` 实现，已实施**（落地记录见 **§十**）。
> 原因：§三 与 §六 讨论下来，「把手与折叠箭头抢同一格留白」是这个功能唯一的高风险源；
> 键盘触发**零 CSS、零装饰、零左侧留白** ⇒ 该风险整体消失，难度从「中等偏难」降到「偏易」。
> **§〇 ~ §九 保留为鼠标拖拽方案的完整分析**（结论仍有效，只是不再先行）；**§十** 是本轮真实落地。

## 〇、先说人话（30 秒版）

**这是什么**：现在你的列表要挪一行，只能剪切再粘贴。做完这个，鼠标悬到某一行左边，会出现一个「把手」，按住它上下拖，这一行（连同它的子项）就跟着走，松手落位。

**难在哪**：难点**不是**「换位置」——那部分是成熟技术，几十行代码的事。
难点在**「把手放哪」**：列表前面那个圆点，是**浏览器用 CSS 画出来的装饰**（不是真元素，鼠标摸不到它）。你看到它、但它接不住鼠标。要让它能抓，就得「自己再画一个圆点」把它顶替掉——可那会连带把有序列表的数字、缩进对齐、任务列表的勾选框都拽进来，等于**把列表排版的底座重做一遍**。这是整件事里唯一的硬骨头。

**我的建议**：**不做「圆点本身当把手」，改做「左侧独立把手」**（鼠标悬停时在空白处冒出，像 Notion 那样）。效果一样——都能拖着整行走——但**一个字节都不碰原生圆点**，风险小一个数量级。理由见 §三。

**结论**：能做，工作量与风险都**中等**（不是小活，但可控）。不确定性就集中在一处——「把手形态」这个决策；其余部分都有现成范本可抄。

## 一、目标与非目标

### 目标

| # | 目标 |
|---|---|
| G1 | 鼠标悬停列表行 → 该行左侧出现**把手**（可抓取的视觉提示） |
| G2 | 按住把手上下拖 → 该行实时跟随鼠标，并显示**落点指示线** |
| G3 | 松手 → 该行落到目标位置；**一次 Ctrl+Z 即可还原** |
| G4 | 拖动的行**连同它的子项一起移动**（幕布/Notion 一致行为） |
| G5 | 普通列表 / 有序列表 / 待办列表**都支持**；**文件格式零改动** |
| G6 | 拖到「非同一层」的位置 → **不生效**（退回原位），不猜用户意图 |

### 明确的非目标（越界即返工）

| 不做 | 原因 |
|---|---|
| ❌ **跨层**（左右拖改变缩进/层级） | 简乐 2026-10-09 明确：先做同层 |
| ❌ 不改 markdown 语法 / schema / parser / serializer | 换位只是把行换个顺序，格式一字未动（§四.1） |
| ❌ 不引第三方拖拽库（dnd-kit / sortablejs / prosemirror-* 插件） | 会引入第二套数据结构，撞保真红线；且拖拽库不认识「同层」概念 |
| ❌ 不做多选批量拖拽 | YAGNI；单行先跑通 |
| ❌ 不做跨文档/跨列表拖拽 | 本次范围外 |
| ❌ 不碰标题 / 段落 / 代码块 / 表格 / Callout | 只作用于列表区（沿用前作口径） |

## 二、难易度拆解（你问的核心）

把这件事拆成 5 块，逐块给难度和风险：

| 模块 | 难度 | 风险 | 说明 |
|---|---|---|---|
| **① 换位逻辑**（把第 2 行挪到第 4 行） | 🟢 简单 | 低 | ProseMirror 成熟配方：一个事务里「删掉再插回」。约 30~50 行 |
| **② 鼠标拖拽手势**（按下 → 移动 → 松开） | 🟡 中等 | 中 | 要自己管鼠标事件、把鼠标坐标换算成文档位置、算插入点 |
| **③ 落点指示线** | 🟢 简单 | 低 | 自绘一条绝对定位的细线即可（§四.4） |
| **④ 把手放哪**（独立把手 vs 圆点本身） | 🔴 **偏难** | **高** | **本功能的真正难点**。见 §三 决策 1 |
| **⑤ IME 组字安全**（把手会不会搅乱输入法） | 🟡 中等 | 中 | 有成熟范本（`list-fold` 的折叠箭头），照抄即可；但**必须**照抄 |

**一句话结论**：**中等偏难**。①③④之外的都顺，④是「一票定生死」的决策——选独立把手，整体降到**中等**；选圆点本身当把手，整体抬到**偏难**且要多花一倍功夫。

## 三、四个关键决策（我给建议 + 理由）

> ⚠️ **本节按「鼠标拖拽」方案写的，已被 §十 的方案变更取代**（改为键盘 `Alt+↑/↓`）。以下四条决策
> 仍是将来真要做鼠标拖拽时的前置分析，**不要照着它直接动手**。

> 这四处只要有一处选错，后面的活就白干。逐条给建议，理由用大白话。

| # | 决策点 | **我的建议** | 理由（大白话） | 备选代价 |
|---|---|---|---|---|
| **1** | **把手放哪** | **独立把手**：鼠标悬停时，在行的**左侧空白处**冒出一个 `⋮⋮`（六点）把手，**不动原生圆点** | 原生圆点是 CSS 画的假装饰，鼠标摸不到；要在它上面做文章，就得自己重画圆点、数字、对齐，牵一发动全身。独立把手等价但**零触碰**原生排版 | 「圆点本身当把手」= 幕布原味，但要把 `ul/ol` 的 `list-style` 关掉、自绘 widget 复刻圆点与序号 → 工作量翻倍 + 对齐/序号出错风险（列入阶段 4，暂不做） |
| **2** | **拖动怎么实现** | **自己写鼠标事件**（`mousedown`/`mousemove`/`mouseup`） | 浏览器原生 HTML5 拖拽在 contenteditable 里脾气古怪（WebView2 尤甚）、拖影是浏览器截的图不受控、`dragover` 落点太粗。自己写才能精确控制「同层」判定 | 用原生拖拽能白捡 `Dropcursor` 落点线，但换来一堆不可控行为 |
| **3** | **落点线怎么画** | **自绘一个单例细线元素**（不注册 decoration） | 拖拽是一瞬间的事，线是临时的；做成 decoration 反而要经过 IME 那套契约。自绘 = 零 schema、零 decoration、零 IME 风险 | 复用 `Dropcursor`（Tiptap 默认已开）——但它只跟原生拖拽联动，且落点由 PM 自己算，我们**管不了「只许同层」** |
| **4** | **把手要不要逐行做成 decoration** | **不要**。做成**单例浮层**（像现有浮动菜单），鼠标在哪个列表行就摆到哪一行 | 折叠箭头（decoration widget）就落在**紧贴光标**的位置，`KNOWN-ISSUES §二 #23` 正是这里踩过「widget 无稳定 key ⇒ 每次按键重建 DOM ⇒ 打标点出选中态」。**多一个常驻 widget = 在同一高危点再多一份扰动**。单例浮层不随文档变化重建 → 从源头绕开 | 逐行 decoration 实现更直观（照抄 `list-fold`），但把风险搬进了输入法热点区 |

**决策 1 的补充**：如果你的心里话是「我就是要圆点本身能抓」（幕布原味），也做得到——但请**放到平台跑通之后再单独做**（§八 阶段 4）。理由：到那时「换位 + 拖拽」机制已被真机验证可靠，圆点替换就只剩纯视觉活，出错也好回滚。

## 四、技术方案（怎么实现）

### 4.1 换位怎么做 —— 一个事务、一次撤销、格式零改动

**核心事实**：列表的层级与顺序**本来就是标准 Markdown**。把「第 3 行挪到第 1 行」在文件里就是**两行文本换个位置**，不产生任何新语法。

```
操作前              操作后
- 甲                - 丙
- 乙        →       - 甲
- 丙                - 乙
```

做法：定位被拖的行所属的**父列表节点**，在该**父列表内部**把子节点数组重排，然后：

```ts
// 删掉原位置 + 在目标位置插回，同一个 transaction（tr），因此一次 Ctrl+Z 即还原
const tr = view.state.tr;
tr.delete(itemFrom, itemTo);
tr.insert(targetPos, itemNode);   // targetPos 为删除后经 tr.mapping 映射的坐标
view.dispatch(tr);
```

- 整行（`listItem` / `taskItem` 节点）是**带子树的**——连同它的嵌套子列表一起搬走（G4）。
- **单事务 = 单次撤销**。若拆成两个事务，用户要按两次 Ctrl+Z，是体验缺陷。
- 备选（更简单但 DOM 重建面更大）：整块替换父列表 `tr.replaceWith(parentStart, parentStart + parent.nodeSize, 新父列表)`。列表特别长时更慢，故列为备选。

### 4.2 同层怎么判（G6 的关键）

- 鼠标坐标 → `view.posAtCoords({left, top})` → 沿 doc 向上找到最近的 `listItem` / `taskItem`。
- **同层成立的条件**：目标行的**父列表节点**与拖动行的父列表节点是**同一个**。
- 若鼠标落在**子列表**（更深一层）里 → 视为「非同一层」，**在父列表范围内就近吸附**（夹到上下最近的兄弟槽位），而不是拒绝或乱插。
- 插入序号：拿每行的 DOM 矩形（`getBoundingClientRect`）比鼠标 Y 与各行的垂直中点。
- 边界：父列表只有 1 项时无事可做，直接不启动拖拽。

> 注：solo 的 schema 允许同一列表里**混排**普通项与待办项（`(listItem | taskItem)+`，见 `editor-extensions.ts:246`）。因此「同层」只看**父列表是不是同一个**，不限制项的子类型——把普通项拖进一堆待办项里，schema 是允许的（视觉上少见，但不是错误）。

### 4.3 把手怎么出现 / 消失

- 监听编辑器容器的 `mousemove`（rAF 节流），命中某个 `li p` 时，把一个**单例** `.list-drag-handle` 元素绝对定位到该行圆点的左侧。
- `mouseleave` / 滚轮 / 窗口失焦 / 文档变化 → 隐藏。
- **不做逐行 decoration**（见 §三 决策 4）。
- 位置：现有折叠箭头 `.list-fold-toggle` 在 `left: -2.5em`（`editor.css:447`，鼠标悬停 `li p:hover` 才现，`:466`）。把手放到**更靠左**（约 `-3.6em`），与箭头**错开横向位置**，二者同现不打架（最终间距以真机视觉验收为准）。

### 4.4 落点线怎么画

- 一个 `position: absolute` 的单例 `.list-drop-indicator` 细线元素，追加在编辑器容器内。
- 每次 `mousemove` 用目标行的 `getBoundingClientRect()` 设 `top` / `left` / `width`。
- 拖拽结束即移除。**不注册 decoration、不碰 schema**。

### 4.5 拖起来的「跟手感」

- 被拖的行加一个 `.is-dragging` class（略降透明度 / 轻微高亮），提示「正在移动这一行」。
- 可选（YAGNI，可后置）：拖到编辑器上下边缘时**自动滚动**。
- 不搬真实 DOM 做浮动幽灵（复杂度换来的收益小，且真实 DOM 一旦脱离 PM 管辖容易出事）。

### 4.6 取消与退场

| 情形 | 行为 |
|---|---|
| `mouseup` 落在合法同层槽位 | 执行换位 |
| `mouseup` 落在非法位置（不同层 / 列表外 / 没动） | **不生效**，清掉指示线 |
| 拖拽中按 `Esc` | 取消 |
| 拖拽中窗口失焦 | 取消 |
| 拖拽中切文件 / 文档被整体替换 | 取消（位置已失效） |

## 五、红线自检（对照 AGENTS.md §1 禁令）

| 禁令 | 本方案如何遵守 |
|---|---|
| **#3 不许硬编码颜色** | 把手 / 指示线颜色全走 `--*` 主题 token |
| **#8 组字态不许绕开 composition-freeze** | 把手做成**单例浮层、不逐行建 decoration**（从源头减少进入该区的扰动）；若实现中确需 decoration，**必须**走 `mapFrozenDecorations` + 稳定 `key`（照 `list-fold.ts:191-195 / 337`） |
| **#5 / 5b schema / mark 契约** | **完全不动** schema / parser / serializer / mark，无需跑契约锁；但**要补一条换位后的 roundtrip 保真测试**（§八） |
| **#10 不许猜失败原因** | 落点判定失败先看真实坐标/DOM，不猜 |
| **#11 不许加守卫掩盖根因** | 非法落点**不生效**（用户可预期的行为），不是「塞个 if 兜住」 |
| **#12 不许手抄库函数重写** | 不重写 ProseMirror 的 `delete`/`insert`，只做坐标计算 |
| **#13 时序 / UI / IME 必须真机验证** | 收尾必做真机手感验收（人工），不靠单测交差 |
| **#14 不许文档硬编码计数** | 本文不写精确行数 |

**改动后必跑**：`vue-tsc --noEmit` + `bun run test` + `bun run build`，**外加真机手感验收**。

## 六、衍生风险清单（逐条预判 + 对策）

| 风险 | 触发条件 | 对策 |
|---|---|---|
| **与折叠箭头抢地盘** | 把手与 `.list-fold-toggle`（`left: -2.5em`）都想占圆点左边 | 把手放更左（`-3.6em`），二者错开；真机看是否拥挤 |
| **IME 候选窗扰动**（`KNOWN-ISSUES §二 #23` 同款） | 把手若逐行建 decoration 且无稳定 key，会在光标旁反复重建 DOM | 走 §三 决策 4：单例浮层；如退化为 decoration，必须带 key + 走 freeze |
| **换位后折叠态错位** | 折叠某行再拖动它 | 折叠位置集合随事务 `map` 平移（`list-fold.ts::mapFolded`）；**加测试**验证「折叠的行被拖动后仍折叠」 |
| **撤销要按两次** | 删除、插入分成两个事务 | 强制**单事务**（§4.1）；加测试断言 undo 一步还原 |
| **大文档卡顿** | 50 万字文档里拖行 | 沿用 `isHeavyDocument()`（`document-scale.ts:39`）降级：大文档**不启用**拖拽与把手（同折叠/焦点模式的既有降级口径） |
| **拖拽把文字拖成选区** | 没拦住浏览器默认行为 | 把手 `mousedown` 里 `preventDefault()` + `stopPropagation()`（照 `list-fold.ts:158-161` 的先例） |
| **有序列表序号乱掉** | 拖动 `1. 2. 3.` 的行 | 换位后序号**本应**重排（这是功能本身）；只需保证序列化输出合法 markdown（roundtrip 测试兜底） |
| **换位引入多余空行 / 松紧列表变化** | 项与项之间原本有空行（loose list） | 换位只搬节点、不改编排；roundtrip 测试覆盖「loose list 换位后仍是 loose」 |

## 七、会不会影响 IME 那个修复（你担心的）

**结论：不影响。** 二者在代码上是**两套互不相干的东西**：

| | IME 重锚护栏 | 本次拖拽 |
|---|---|---|
| 位置 | `src/components/Editor/tiptap/ime-anchor.ts` | 编辑器 CSS + 一个新的交互模块 |
| 触发 | **窗口移动 / 缩放** | **鼠标在列表行上按下拖动** |
| 作用对象 | 编辑器的 `blur()` / `focus()` | 文档节点的顺序 |
| 共享状态 | 无 | 无 |

**唯一的交集**是「都在编辑器左侧、都靠近光标」这个**物理位置**——而对策就是 §三 决策 4（把手不逐行建 decoration）与 §五 的 #8 条：**不往 IME 热点区塞常驻 widget**。

**为了让你手上的测试版不受影响**：新功能**从当前修复分支切出去**（`fix/ime-anchor-guard` → `feat/list-row-drag`），内容一模一样，**你正在跑的 dev 版仍是带护栏的那版**，护栏照常生效。等两边都稳了再谈合并。

## 八、分阶段与验收标准（冻结）

| 阶段 | 内容 | 风险 | 独立可回滚 |
|---|---|---|---|
| **1** | **换位机制 + 独立把手鼠标拖拽（同层）** ← 本提案核心 | 中 | ✅ |
| **2**（可选，近乎白送） | 键盘 `Alt+↑/↓` 触发**同一套**换位命令 | 低 | ✅ |
| **3**（暂不做） | 跨层（左右拖改变缩进） | 高 | ✅ |
| **4**（暂不做） | 原生圆点换成自绘 widget，**圆点本身即把手**（幕布原味） | 高 | ✅ |

> 阶段 2 之所以「白送」：换位命令一旦写好，键盘触发只是再接一个入口，几乎不新增加风险；而它能在**不动鼠标、不动 CSS** 的前提下先把「换位逻辑」验穿。这也是前作 `PROPOSAL-list-outline-experience.md` 阶段 4 未做的那一项，可与本次合并推进。

### 阶段 1 验收标准（冻结，逐条真机确认）

1. 悬停任意列表行 → 左侧出现把手；移开 → 消失。
2. 按住把手上下拖 → 出现落点指示线；被拖行有「正在移动」的视觉状态。
3. 松手落在同层槽位 → 行落到该位置，**连同子项**。
4. **Ctrl+Z 一次**即回到原顺序。
5. 拖到**子列表 / 列表外 / 不同层级** → **不生效**，行退回原位。
6. **普通 / 有序 / 待办**三种列表都能拖。
7. 拖完后**存的还是标准 Markdown**，用别的编辑器打开顺序正确（roundtrip 保真）。
8. 在列表里正常打字（含中文组字 + 紧随标点）→ **无新增输入法异常**。
9. 大文档（`isHeavyDocument`）→ 不启用拖拽，行为退回现状，不卡顿。

## 十、落地记录：键盘 `Alt+↑/↓`（已实施）

> 本节是**真实落地**，即 §八 的**阶段 2**。§四 的鼠标拖拽把手方案**顺延**为后续，不删除。
> 分支：`feat/list-row-drag`（自 `fix/ime-anchor-guard` 切出，IME 护栏不受影响）。

### 做了什么

光标落在任意列表项内，按 **`Alt+↑` / `Alt+↓`**，该项在**同层兄弟之间**上下换位，**连同子项整体移动**，缩进层级不变。跨层**不做**。

| 边界 | 行为 |
|---|---|
| 首项按 `Alt+↑` / 末项按 `Alt+↓` | 认领按键但**不动**（不穿透成其他行为） |
| 光标不在列表项内 | **不认领**（按键照常走原有逻辑） |
| 中文组字中（`view.composing`） | **不认领**（不打断输入法） |
| 撤销 | 单事务 ⇒ **一次 `Ctrl+Z`** 还原 |

### 落地文件

| 文件 | 角色 |
|---|---|
| `src/components/Editor/tiptap/list-move.ts` | **唯一实现**：`moveListItem(view, direction)`，单事务（delete → map → insert），光标跟走 |
| `src/components/Editor/tiptap/__tests__/list-move.spec.ts` | 15 条单测（含撤销、组字、边界、嵌套、待办/有序/混排） |
| `src/commands/registry.ts` | 注册 `list.moveItemUp` / `list.moveItemDown` |
| `src/composables/useCommandDispatcher.ts` | 转发（仅编辑器视图；快捷键需编辑器有焦点） |
| `src/components/Editor/tiptap/editor-commands.ts` | 执行分支（**刻意不走** `chain().focus()`） |
| `src/composables/useFloatingListMenu.ts` | 浮动列表菜单**让路**（Alt 键不参与菜单导航） |
| `src/components/Editor/tiptap/extensions/list-fold.ts` | 复用 `list-move` 导出的节点类型集合，删掉本地重复定义 |
| `wiki/快捷键速查.md` | 登记两条快捷键 |

### 三个「必须这样写」的决策

1. **命令 `scope: 'app'`，不是 `'editor'`**：`useAppDomEvents` 对「编辑器内 + scope=editor + 用户未自定义」的按键**直接放手**给 ProseMirror 内置 keymap；而 PM **没有**「整项移动」内置命令 ⇒ 标 `editor` 会变成**死键**。
2. **不给 `menuSection`**：快捷键要转 Tauri accelerator 进原生菜单，而别名表**没有方向键** ⇒ `ArrowUp` 原样透传，Tauri 不认（它用 `Up`/`Down`）。给了会**注册失败**。
3. **浮动列表菜单必须让路**：它只判 `event.key === 'ArrowUp'`、**不判修饰键**，而按住 Alt 时 `event.key` 仍是 `'ArrowUp'` ⇒ 不让路就会**同一次按键既动菜单又动列表项**。

### 已知行为（非缺陷）

移动一个**已折叠**的项，会使其**展开**——折叠态按位置标记，位置被删除后无处可依。**只丢视图态，不动内容**。

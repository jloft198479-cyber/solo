# 列表结构与回退行为修复方案

> **状态：方案未执行；已完成第二轮独立复审（2026-10-10，见 §十）**。本文只做审查与方案，未改动任何产品代码。
> **复审一句话**：病看对了（§2.1 / §三 全部实测复现、file:line 准确），药有三处核心假设错或不完整（F-1 / F-3 / F-4）⇒ **不建议按原文直接进入阶段 2**；另牵出比本案更常踩的 #25（列表项内敲 `# 标题` 吞标记）。
> 触发背景：用户报「列表里母主题无法用 `Alt+↑/↓` 换位」，追查发现**根因不在换位功能本身，而在列表结构与回退（Backspace）行为**。

## 二、实测事实

### 2.1 现象二确认：Backspace 会把列表劈成两段（🔴 P0）

输入 `- 甲 / - 乙 / - 丙` 三行列表，光标置「乙」行首，按一次 Backspace：

```
【前】doc
        bulletList
          listItem → paragraph "甲"
          listItem → paragraph "乙"       ← 光标在此行首
          listItem → paragraph "丙"

【后】doc
        bulletList   → listItem → paragraph "甲"
        paragraph    → "乙"                    ← 变成孤立段落
        bulletList   → listItem → paragraph "丙"
```

**列表被切成两个独立 `bulletList`，中间夹一个 `doc` 层段落。** 对照实验：

| 光标位置 | 结果 | 是否劈开列表 |
|---|---|---|
| 中间项（乙）行首 | 甲 ｜ **乙（段落）** ｜ 丙 | ❌ **劈成两段** |
| 首项（甲）行首 | 甲（段落）｜ 乙 丙 | ✅ 不劈 |
| 末项（丙）行首 | 甲 乙 ｜ 丙（段落） | ✅ 不劈 |
| 嵌套子项（甲1）行首 | 甲 ／ 甲1 ／ 乙（三项平级） | ✅ 不劈（只提升一级） |

**这是上一轮「母主题 `Alt+↑` 挪不动」的直接成因**——`moveListItem` 硬约束「只在同一容器内挪兄弟」（`list-move.ts:10`），列表被劈开后母主题已不是兄弟。

**代码路径**（逐段已读源码）：

```
按键 Backspace
  → StarterKit 默认启用的 ListKeymap（starter-kit/dist/index.js:12,42-44；生产未禁用）
  → handleBackspace（@tiptap/extension-list/dist/index.js:538-565）
      第 560 行 命中条件：光标在列表项「第一个子块」开头
      第 564 行 return liftListItem(name)
  → liftListItem（prosemirror-schema-list/dist/index.js:206-219）
      父是 listItem ⇒ liftToOuterList（220-237，末尾有 join ⇒ 不劈）
      父是 list ⇒ liftOutOfList（238-260）
  → liftOutOfList 第 256 行 ReplaceAroundStep：在被提内容**两侧各塞一个空 list 壳**
    装剩余兄弟，**且不做 join** ⇒ 列表劈成两个
```

对比 `liftToOuterList` 末尾第 233-234 行的 `canJoin + join`——**同一个库里的两条路径，一条收尾合并、一条不收**，这就是劈开的全部原因。

### 2.2 现象一确认：列表项内可藏段落，视觉上无法分辨（🟡 P1）

```
【输入】- 甲
        ␣␣- 1
        （空行）
        - 乙

【结构】bulletList → listItem → [ paragraph "甲", bulletList → listItem → paragraph "1" ]
                    listItem → paragraph "乙"
```

而**带空行缩进的续行**会变成**列表项内的第二个段落**：

```
【输入】- 甲
        （空行）
        ␣␣续行
        （空行）
        - 乙

【结构】bulletList
          listItem → [ paragraph "甲", paragraph "续行" ]   ← 项内两段
          listItem → paragraph "乙"
```

**视觉为何分不出**（`editor.css` 实测取值）：

| 相邻关系 | 间距 | 出处 |
|---|---|---|
| 列表项 ↔ 列表项 | `0.2 × 段距` = 0.15~0.2em ≈ **2~3px** | `editor.css:410-412` |
| 列表项内段落 ↔ 上一行 | **0** | `editor.css:423-426` |
| 正文段落 ↔ 列表 | `1 × 段距` = 0.75~1em | `editor.css:152-154` / `401` |

⇒ **「项内续段」与「下一个列表项」的间距只差 2~3px**，且它**没有圆点但缩进与项内容齐平**——肉眼确实无法判断它是不是独立段落。用户判断成立。

**三个来源**（`listItem.content = 'paragraph block*'`，`extension-list/dist/index.js:424`）：

1. **导入/粘贴**：别处复制来的宽松列表带缩进续段 ⇒ 直接解析成项内第二段；
2. **schema 补位**：内容不以段落开头（如 `- # 标题`）时模型补空段落——`serializer.ts:508-512` 的 `skipLeadingEmpty` 就是为此打的补丁，**佐证该现象真实且已被撞过**；
3. **Tab/Backspace 提升后的产物**（2.1 的兄弟现象）。

**保真结论**（〔复审修订〕项内段落**并非只能「读进来」**，见 §十 F-6）：项内多段**往返稳定**（序列化为 `- 甲\n\n  续段\n- 乙`，二次收敛 ✅）⇒ **不是数据风险**，是"用户看不出结构"的**感知风险**。

### 2.3 连带发现（同批实测）

| 发现 | 详情 | 严重度 |
|---|---|---|
| Enter 在**末位空项** | 空项被提出列表 → 变空段落，且文档末尾再多一个空段落（TrailingNode） | 🟢 低（"退出列表"是期望行为） |
| Enter 在**中间空项** | 列表里多出一个空项（不退出） | 🟢 低 |
| `Tab` / `Shift+Tab` | **〔复审修订：原文「正常、不需要动」不成立〕** `Tab` 缩进正常；但 `Shift-Tab` 绑的就是 `liftListItem`（`@tiptap/extension-list:492`，taskItem 同款在 `:1253`），实测**顶层中间项行首按 Shift+Tab 与 Backspace 结果完全相同**（列表劈成两段、中间夹孤立段落）。方案 A 只关 Backspace 这一扇门，用户换键照样劈。详见 §十 F-3 | 🔴 **P0 同罪** |
| `Delete`（向后删） | 正常（合并到下一项） | — |
| `Mod-Backspace`（Ctrl+Backspace） | **〔复审新发现〕同一扇门的第二条路**：`@tiptap/extension-list:716` 把 `Mod-Backspace` 也接到同一个 `handleBackspace`，实测顶层中间项行首按它 ⇒ 与 Backspace 一样劈开。且 solo 自己规定 `Mod+Backspace` 删块（`mermaid-block.ts:474` / `math-block.ts:203`），**同键已叠两套语义**，方案 A 未列入 | 🔴 **P0（与 #1 同罪）** |
| `TrailingNode` | StarterKit 默认启用（`@tiptap/extensions/dist/index.js:609-653`，补段落的 `tr.insert` 在 `:631`、判据 `:635-639`）⇒ **文档以列表结尾时，列表后永远跟一个空段落**；**〔复审修订〕**该空段落序列化时会写出一个 **U+00A0（NBSP）行**（`serializer.ts:567-571`，写入在 `:569`，实测 codepoints 含 `U+a0`）——这是「往用户文件里写不可见字符」，不是「看着多一段」 | 🟡 中（复审上调，原判 🟢 低） |
| 宽松列表归一 | `- 甲\n  - 1\n\n- 乙`（loose）保存后空行被去掉（tight）。**已登记** `KNOWN_FIDELITY_GAPS['lists.md']`，FORMAT 级、有意为之 | 🟡 已知 |

## 三、根因：三处规划不合理

| # | 根因 | 性质 | 说明 |
|---|---|---|---|
| 1 | `liftOutOfList` **只管把项提出列表、不管列表被劈开** | 上游库行为（solo 直接继承） | 对幕布式大纲而言，「把节点摘下来」正确语义应是「变成上一层的兄弟」，而不是「往树中间插一个孤立段落把树劈开」 |
| 2 | **Backspace 语义错配** | solo 未做约束 | 用户按 Backspace 想的是「删除 / 回退」，系统给的是「取消这一项的列表身份」；且**没有组字态门控**（`handleBackspace` 不检查 `view.composing`） |
| 3 | `listItem.content = 'paragraph block*'` **太松 + 静默补位** | schema 设计 | 列表项内可藏任意块，视觉上又无从分辨；契约锁 `schema-contract.spec.ts:67` 已把这个约束**锁死**，改动须走有意变更流程。**〔2026-10-10 补〕** 该约束已被 F-8 的修法**绕过而非推翻**——把「手打」对齐到「读盘」的既有表示（列表项首格只收 paragraph ⇒ 标题经补位空段落落在第二块），**未动 schema**，故不触发有意变更流程 |

**用户的判断（"根因在删除/回退的操作逻辑与段落划分规则本身"）成立。** 补充一条修正：现象一（项内段落）与现象二（劈开列表）**不是同一个东西**——前者不切断列表、往返稳定；切断列表并导致 `Alt+↑` 失效的是后者。修复优先级应压在现象二上。

## 四、修复方案

### 方案 A（推荐）：重设 Backspace 语义 —— 永不劈开列表

新增一个键位扩展，**优先于 ListKeymap 接管列表项开头的 Backspace**（`priority` 高于 StarterKit；不修改上游包）：

| 光标所在 | 列表项数 / 层级 | 新行为 |
|---|---|---|
| 列表项首块开头 | **有缩进**（嵌套项） | 保持现状：提升一级（反缩进）——`liftToOuterList` 本来就安全 |
| 列表项首块开头 | 顶层，列表 **> 1 项** | **与上一项合并**（内容并入上一项末尾），**不再 lift** |
| 列表项首块开头 | 顶层，列表 **= 1 项** | 保持现状：退出列表变普通段落（无副作用） |
| 列表项**非首块**开头 | — | 不接管，交给默认（合并段落，安全） |

**为什么选「合并到上一项」**：这是幕布 / Workflowy / Word 的通行语义——"行首退格＝把这一行并回上一行"，既不凭空造段落、也不切断列表，还符合"回退"的直觉。

**实现可行性预判**：PM 自带的 `joinBackward` 在列表项首块开头天然会**合并相邻两个 listItem**（走 `findCutBefore` + `canJoin` + `join`）。若成立，实现量极小（新增扩展 + 一次 `joinBackward`），**但必须先实测确认**（阶段 1）。

> **〔复审实测已证，本条预判不成立 —— 见 §十 F-1〕** 在生产扩展集（`createEditorExtensions`，含 ListKeymap）里对 `- 甲 / - 乙 / - 丙` 中间项行首跑 `joinBackward()`：命令返回 `true`，但产出的是
> `bulletList → listItem → [ paragraph "甲", paragraph "乙" ]`，存盘 `- 甲\n\n  乙\n- 丙`。
> 即它把「劈开列表」换成了**本文 §2.2 自己判定为「肉眼无法分辨」的项内隐藏第二段**，与上表承诺的「内容并入上一项末尾」不是同一个语义。要拿到承诺语义，须**再并一次段落**（连跑两次 `joinBackward` 实测得 `paragraph "甲乙"`）。
> 另一条更省力的事实：tiptap 核心 Keymap 的 Backspace 链本身就含 `joinBackward`（`@tiptap/core/dist/index.js:5689-5705`），实测**同位置按 Shift+Backspace 走的就是这条路**（结果即上面的项内两段）。所以方案 A 的准确表述应是「**别让纯 Backspace 被 ListKeymap 抢去 lift**」，而不是「新增扩展自己实现合并」——后者要重新处理 `undoInputRule`、组字期、空项、混排等一整圈语义，前者只是让路。

### 方案 B（不推荐，仅记录）：约束列表项内容

- **收紧 schema**（如 `paragraph+`）：`paragraph block*` 已经是最松形态，收紧会**丢内容**（撞保真红线）⇒ ❌ 不可行；
- **粘贴/导入时规范化**（把项内续段拆成独立列表项）：会**改写用户文件语义**，且覆盖不到"打开已有多段的文件"⇒ ❌ 代价大于收益；
- **视觉区分**（加大间距 / 加标识）：**用户明确否决** ⇒ ❌ 不做。

⇒ **现象一（项内段落）判定为「登记 + 不动」**：它往返稳定、~~无法从 UI 打出（实测：Enter 各位置都不产生项内第二段）~~ **〔复审修订：这条理由作废〕键盘就能打出来，实测三条路**——① 列表后紧跟的段落，在其行首按 `Tab` ⇒ 该项变成两段（`extension-list:598-623` 的 `handleTab`，存盘 `- 甲\n\n  段落`）；② 方案 A 拟用的 `joinBackward`（见上）；③ **混排列表**（`- [ ] 甲` / `- 乙`）中间普通项行首 Backspace ⇒ 乙被并进 taskItem 成为第二段，且**乙的「普通项」身份被吞成待办项内容**（Enter 在各位置确实不产生第二段，原文这半句没错）。
> ⇒ 「只登记不处置」的**结论仍可接受**，但依据必须换成「往返稳定 + 改 schema 会丢内容 + 粘贴规范化会改写用户语义」，**不能再用「UI 打不出来」**——否则将来任何人拿这条理由去否决新提案，就建在假前提上。更要紧的是：方案 A 若落地，它会**主动制造**项内第二段（F-1），届时现象一就从「读进来的存量」升级成「高频按键的日常产物」，「不动」这个结论需要重新评估。
>
> 原文这句判断保留：**真正的风险是用户不知道自己在哪一层**——需要的是结构提示，不是间距，另案讨论（与 `KNOWN-ISSUES` §二 #24「聚焦模式粒度只到顶层块」同题，且 #24 已拍板「先让列表换位跑几天再动」，本案排期必须与它对表）。

### 方案 C（可顺带）：修掉 `Alt+↑/↓` 的静默失败

**〔复审修订：本方案把两种情况混成一种了〕**
- **列表已劈开**这一场景（也就是用户真正报障的场景）：实测光标放回孤立的「乙」时 `moveListItem` 返回 **`false`**——此刻那块是 `doc` 层段落，函数在 `list-move.ts:56` 就拒收了，按键会**继续往下穿透**，不是「认领但不动」。这一类**修好 A 就自然消失**，不需要单独加反馈。
- 「已在首位 / 已在末位」才是**返回 `true` 但不动**（`list-move.ts:66-67`），而这是 `PROPOSAL-list-row-drag.md` §十 **已拍板记录的有意行为**（原文：首项按 `Alt+↑` / 末项按 `Alt+↓`「认领按键但不动（不穿透成其他行为）」）。**方案 C 若要改掉它，属于推翻既有拍板，必须先单独征求简乐同意，不能挂在「顺带（可选）」里。**

建议保留的部分：给「跨容器 / 到边界」加**轻量反馈**（状态栏闪一句），以及在劈开结构里允许「跨相邻同层容器」移动——但要先确认它改的是哪一种，见 §七 第 4 条订正。

### 推荐组合

**方案 A 为主 + 方案 C 顺带**，方案 B 只登记不执行。

## 七、决定（2026-10-10 简乐一次同意）

> 本节**前身是「开放问题（待拍板）」**——把九条技术选择题打包甩给用户是错的：他无法从零拍板。现改为「决定 + 一句理由」，用户只回答「同意 / 不同意」。

| # | 决定 | 理由（一句话） |
|---|---|---|
| 1 | **顶层首项行首 Backspace**：前面是段落 / 标题 ⇒ 并进那个块；前面是列表 ⇒ 并进上一列表的末项；**文档第一块 ⇒ 不响应**（保持不动、不产生段落） | 这是 Word / 幕布 / Typora 的通行行为，「够不着就不动」 |

| 3 | **不做**显式「合并相邻列表」命令 | 批量改写用户既有文件风险大于收益；Ctrl+Z 就能救 |

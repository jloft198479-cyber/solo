## 3. 新发现

### M-1（必修）验收 #3「唯一例外是 callout」不成立 —— 真实例外 4 类，后 3 类未声明

**取证**：忠实模拟 rev5 全部 10 条规则（含规则 5 的内联样式、规则 6 的拆壳与 `colspan/rowspan` 清理），归一前 doc 与回读 doc 各取**带深度前缀的完整类型路径签名**，再用 LCS 差分对齐（纯位移不计入）：

```
删除 5 条：
  - frontmatter|[]
  - text:"title: T"
  - text:"、与 "                                    ← 文本内 U+200C 被剥
  - image|[…["alt","**甲，**乙"]…]                   ← alt 值内 U+200C 被剥
  - callout|[["calloutType","note"],["title","有标题"]]
新增 5 条：
  + text:"、与 "
  + image|[…["alt","**甲，**乙"]…]
  + callout|[["calloutType","note"]]
  + text:"有标题"
  + paragraph|[]                                    ← callout 注入的标题段
```

⇒ 前 4 组删除中，**只有最后一组是 rev5 声明的 callout 例外**；另 3 组全是 rev5 **未声明**的期望差异：

| 未声明的期望差异 | 来自哪条规则 | 为什么必然发生 |
|---|---|---|
| `frontmatter` 节点 + 其文本消失 | 规则 1（删 frontmatter） | 归一**有意**删除 ⇒ 回读 doc 必然少一个 `frontmatter` 节点 |
| 文本节点里 U+200C 消失 | 规则 8（剥文本 ZWNJ） | ZWNJ 由 **markdown 解析器**（`parser.ts:726-736`）插入，**HTML 解析不会重新插回** ⇒ 源 doc 有、回读 doc 无 |
| 属性值里 U+200C 消失（实测 `image.alt`） | 规则 8（剥属性 ZWNJ） | 同上；且属性 ZWNJ 本来就存在（`serializer.ts:721-730` 注释「属性通道不经过 `escapeInline`」） |

**为什么是必修而不是措辞问题**：
- 这三个差异**都是归一层的设计目的**（就是要删 frontmatter、就是要剥 ZWNJ），所以它们**必须**被声明为期望差异；rev5 却说"唯一例外是 callout"，照字面写测试 ⇒ 必红。
- 更危险的是**红得没有信息量**：实现者会以为是"归一破坏了结构"，而实际只是"计划漏写了三个已知副产物"。最坏结果是整条 #3 判据被删 —— 而 #3 是**唯一**能抓住"PM 静默变形"的锁（rev3 必修③ 的成果），删掉等于把最贵的防线拆了。

**建议修法（二选一，都很小）**：
- **A（推荐）**：把比对做成**对称清洗** —— 在比签名**之前**，对源 doc 与回读 doc **都**施加同一套清洗（去 frontmatter 节点、剥文本/属性 ZWNJ），于是这 3 类差异被消掉，剩下的真结构差异**就只有 callout**，「唯一例外是 callout」这句话才真正成立。
- **B**：保持单侧比对，但把期望差异写成**声明式集合** `{frontmatter, 文本ZWNJ, 属性ZWNJ, callout标题}`，并明确"集合之外的任何增删一律判红"。

> 语义提醒：本方案在**外部路径上有意破坏 frontmatter**，所以严格意义上的"往返逐字保真"**不可能**达成。验收 #3 的措辞应从「签名逐字相等」改为「签名相等，除**有意破坏集**」。

### S-1（建议）幂等标记 `data-solo-externalized` 会随产出一起出站，且 1-A 清单漏了它

- 依据：规则 ① 末尾"函数末尾置该属性"（`:125`）+ ② 直接取 `div.innerHTML`（`:151`）⇒ 标记**必然出现在对外 HTML 里**。
- rev5 的 1-A「失真消失（不含）」清单（`:202`）列了 11 项，**没有** `data-solo-externalized` ⇒ 凭空多一个私有属性出站，无人看管。
- 影响小（solo 忽略未知属性、Word 忽略），但属"新引入的对外噪声"应显式登记。建议：在 1-A 清单补上 `data-solo-externalized`，并要求 `serializeDocumentHtml` 返回前**摘掉该标记**（幂等只在 `externalizeHtml` 单次调用内需要，跨调用因每次新建 detached div 而是天然幂等的）。

## 4. 替 rev5 实测的「唯一结构可疑动作」

rev5 6 条自己标了 ⚠️：「`<thead>` 提升是本方案唯一在结构上的可疑动作……由验收 #3 的类型路径签名判定；一旦签名出现变形，**撤掉 `<thead>` 这一条**。」（`:140`）

**实测结论：对 PM 签名完全透明，不必撤。**

```
输入: <table class="mk-table"><tbody><tr><th>A</th><th>B</th></tr><tr><td>1</td><td>2</td></tr></tbody></table>
提升后: …<thead><tr><th>A</th><th>B</th></tr></thead><tbody><tr><td>1</td><td>2</td></tr></tbody>
签名差分: 删除 0 / 新增 0
```

PM 解析器遇到 `thead`/`tbody` 这类无规则元素会**透明下钻**，`tableRow+` 的 content 规格不受 row group 影响 ⇒ rev5 准备的 fallback（撤 thead）用不上，可放心保留。

> 附（上轮已测，此处仅确认 rev5 撤销正确）：`<ol><li><div data-footnote-def>>` ⇒ 签名变形为 `footnoteSection > footnoteDef > orderedList > listItem > footnoteDef`（**def 变 2 个**）；`<hr>` ⇒ `footnoteSection > footnoteDef > horizontalRule > footnoteDef`。rev5 撤掉这两条是对的。

## 7. 更正附注（2026-10-11 晚 · 见 qoder 对 rev6 的回执）

**S-1（幂等标记随产出出站）—— 本报告判错，已被证伪，撤回。**

- qoder 的反驳：标记 `data-solo-externalized` 只打在**临时承载 `div` 自身**（方案 ① 的 `externalizeHtml(root)`，② 传入的正是那个 `div`），而 `serializeDocumentHtml` 取的是 `div.innerHTML` —— **`innerHTML` 只序列化子节点，不含宿主自身的标签与属性**（宿主归 `outerHTML`）。
- 我的独立验证（happy-dom）：

  ```
  宿主属性     : 已设置            // div 上确实有 data-solo-externalized
  innerHTML   : "<p>x</p>"        // 不含该属性
  outerHTML   : "<div data-solo-externalized=\"\"><p>x</p></div>"
  ⇒ 标记出现在 innerHTML 里？ false
  ```

- **⇒ qoder 对，我错。** 错因：我把"设置在容器上"与"取 innerHTML"两个事实各自记住了，却没把它们联起来——属性挂在宿主上，而 innerHTML 的语义边界正好把宿主排除在外。这与 **2026-09-16「模型看不到图」判例同型**：单点事实都拿到手了，缺的是把两点接起来的推理，然后凭"感觉"下了结论。
- **边界说明**：证伪的是"会出站"这一断言；**rev6 在 1-A 补的兜底断言「出站 HTML 不许出现该标记」仍然值得保留**，但性质变了——它不再是"修一处真实泄漏"，而是**锁住不变量**："标记必须待在承载 div 自身"（若将来有人改实现，把标记打到每个被改写的子元素上，就会真出站，这条断言会立刻抓住）。这是一个恰当的防呆设计，不是冗余。rev6 把这条写清（`:127`）比 rev5 只写"函数末尾置该属性"更稳。

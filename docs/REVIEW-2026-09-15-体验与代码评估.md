## 0. 一句话结论

**工程质量 TOP 级，但有一个能毁掉大文档体验的低级性能 bug。**

护城河（测试换真身、敏感区台账、防抖分层、IME 组字冻结）做得比多数商业编辑器扎实；
但序列化器一处 **`output +=` 字符串累加** 让大文档序列化变成 O(n²)——
**24 万字、60 个块 27ms，24000 个块 14 秒**，差 520 倍。

| 维度 | 评分 | 判定 |
|---|---|---|
| 格式准确性 · 输出（落盘） | 6.5 / 10 | 41 例 18 例偏差、2 例**二次不收敛** |

| 代码简洁优雅 | 8 / 10 | 禁令零违规，残余 4 项结构债（已自查登记） |

## 1. 🔴 头号问题：序列化 O(n²)

> ### ✅ 已修复（2026-09-15）
>
> 改动落在 [`serializer.ts`](../src/components/Editor/tiptap/markdown/serializer.ts)：字符串累加 → 分片数组，
> 并把四处「需读真实字符」的判定改为 O(1) 尾部取值（`escapeInline` / `ensureNewline` / `blankLine` / `heading`）。
>
> **等价性（逐字节）**：19 份 fixture + 19 份剪贴板 + 62 项合成场景（31 场景 × 文件/剪贴板）= **100 项，
> 改前改后 hash 与长度**全部一致，0 差异**。
>
> **回归**：`bun run test` 1452 通过 / 47 文件；`vue-tsc --noEmit` 零错误；`vite build` 通过。
>
> | 块数 | 改前 | 改后 | 提速 |
> |---|---|---|---|
> | 1,000 | 56.1ms | 34.6ms | 2× |
> | 5,000 | 3,390.8ms | 105.6ms | 32× |
> | 10,000 | 13,632.8ms | 173.6ms | 79× |
> | 20,000 | 53,384.4ms | 364.5ms | **146×** |
>
> 复杂度曲线：改前 1,000→20,000 块（20 倍）耗时 **953 倍**（≈n^2.3）；
> 改后同样 20 倍块数耗时 **10.5 倍**（≈n^1.08，线性）。**小文档亦快约 2 倍**（无退化）。

### 实测数据（Node 环境；WebView2 实际约 ×2~3）

| 字符数 | 块数 | 解析 | 序列化 |
|---|---|---|---|
| 4,300 | ~350 | 8ms | 4ms |
| 17,200 | ~1,400 | 30ms | 20ms |
| 68,800 | ~5,600 | 70ms | **217ms** |
| 258,000 | ~21,000 | 185ms | **9,525ms** |

### 归因实验（同量级字符，只改块数）

| 样本 | 字符 | 块数 | 序列化 |
|---|---|---|---|
| 少数巨块 | 240,348 | 60 | **27ms** |
| 多数小块 | 348,889 | 24,000 | **14,052ms** |

字符量差 1.45 倍，**耗时差 520 倍** ⇒ 复杂度由**块数**驱动，非字符数。

### 根因（微基准复现，128,000 块）

```
现状（output += ... + endsWith('\n')）  56,510ms
数组 push + join                            12ms      ← 4,709 倍，输出逐字节相同
```

代码位置：[`serializer.ts`](../src/components/Editor/tiptap/markdown/serializer.ts)

| 行 | 代码 | 问题 |
|---|---|---|
| 31 | `output = ''` | 累加式输出 |
| 45 | `write()` → `this.output += text` | 每写一次产生新的 V8 ConsString（绳结） |
| 56 | `ensureNewline()` → `this.output.length` + `this.output.endsWith('\n')` | **读取字符即强制扁平化绳结 → 单次 O(n)** |
| 70 | `blankLine()` → `this.output.endsWith('\n\n')` | 同上 |

每个块都要 `flushClose → ensureNewline`，于是「每块 O(已输出长度)」⇒ 总计 O(n²)。
25.8 万字 ≈ 21,000 块 × 平均 12.9 万字拷贝 ≈ 2.7 GB memcpy ≈ 9.5s —— 与实测吻合。

### 修法（约 15 行，零行为变化）

```ts
// 1) output: string  →  private out: string[] = []
// 2) write(text)     →  this.out.push(text)
// 3) ensureNewline() →  只看 this.out 最后一个元素（不再触碰整串）
// 4) 出口统一 this.out.join('')
```
`endsWith` 三处全部改成对数组末元素的判定即可，`flushClose`/`blankLine` 语义不变。
**验收**：改动前后对 19 份 fixture 做全量序列化快照、逐字节 diff 必须为空。

## 1.5 🔍 溯源：为什么「以前解决过」又出现

**结论：没有复现，也没有回退——是这个根因从来没有被修过，只是被掩盖了。**

### 证据链

| 环节 | 事实 | 出处 |
|---|---|---|
| 历史诊断 | 全量序列化被列为热点 **H9**，定性为 **「O(n)，500ms 防抖」** | [`large-document-performance.md`](./archive/large-document-performance.md):69 |
| 定性错误 | 实为 **O(n²)**。同一份文档里 H15（搜索替换）被正确标为 O(n²)，**唯独 H9 判成 O(n)** | 同上:88 vs :69 |
| 对策选择 | 因为判成 O(n)，对策走 **「降频」**：`P0-1` 关闭路径免序列化 + `P6-03` 序列化缓存复用 | 同上:29 / commit `929f770` |
| 拼接本身 | `this.output +=` 与 `ensureNewline()` 的 `endsWith` **自 v1.1.6 起一次未改** | `git log -S` 仅命中 `b72d6d2`（v1.1.6）与 `ffa2d2a` |
| 结构性方案 | **P2 分块装载 / 虚拟滚动被明确砍掉**（「与不追超长文档的定位冲突」） | 同上:34 |

### 为什么「感觉被解决了」

降频手段对**能感知的症状**是有效的，且都命中了：

| 上次动作 | 用户感知 | 是否治本 |
|---|---|---|
| P0-1 关闭路径免序列化（`editGeneration` 代际闸口） | **「关不掉了」消失** ← 这是最刺眼的症状 | ❌ 只是不跑，没让它变快 |
| P0-2 关窗逃生舱（3s 强制关） | 再不济也能关 | ❌ 逃生舱 |
| P0-3 阈值分层（50万/200万） | 「大文档有预案了」 | ❌ 门槛远高于性能拐点 |
| P6-03 序列化缓存复用 | 重复序列化少了，**症状变轻** | ❌ 减少**次数**，不降**单次成本** |
| P2 砍掉 | 「不做超长文档」——预期管理 | ❌ 主动放弃 |

⇒ **降频 = 减少 O(n²) 的执行次数。** 只要块数不多，次数一少就感知不到；
但块数过万后，**单次执行本身**就足以吃满整个空闲窗口 —— 此时防抖、缓存、idle 调度全部失效。
这就是「优化过很多次、每次都有效、但问题还在」的机制。

### 附带发现：档案文档存在「✅ 已实施」高报

`large-document-performance.md` 的 P1 行标「✅ 已实施」，逐项核对实际状态：

| P1 子项 | 档案标注 | 代码实际 |
|---|---|---|
| paragraph-focus 只维护 2 条装饰 | ✅ | ✅ 属实（`DecorationSet.empty` + `isHeavyDocument` 守卫） |
| 大纲面板关闭时跳过提取 | ✅ | ✅ 属实（`useEditorSync.skipOutline`） |
| 序列化缓存复用 | ✅ | ✅ 属实（`MarkdownEditor.vue` `cachedSerialize`） |
| **code-block 高亮按需化** | ✅ | ⚠️ **只做了 heavy 档降级，`IntersectionObserver` 视口触发的「按需化」未实现**（[`code-block.ts:137`](../src/components/Editor/tiptap/extensions/code-block.ts) 仍直接 `highlightAuto`） |

⇒ 档案文档的完成度标注有 **1/4 高报**，建议按代码校正，避免后续再按它做判断。

### 一句话结论

> **不是「又复现了」，是「从来没修根因」。**
> 上次诊断时把 O(n²) 看成 O(n)，于是选择了「少跑几次」而不是「让它变快」。
> 症状被掩盖了一年（v1.1.6 至今），直到块数涨过万级门槛才重新浮出水面。

## 1.6 🌍 同行对标：同类问题业界怎么处理

> 先给结论：**A/B 类同行不是「解决了 O(n²)」，而是架构上根本没有这道工序。**
> solo 必须整篇序列化，这是 WYSIWYG + 纯 Markdown 落盘的产品代价，**不该妄想消除，但可以用 O(n) 支付**。

### 三类架构的分野

| 类别 | 代表 | 编辑期真相源 | 是否存在「整篇序列化」 | 大文档手段 |
|---|---|---|---|---|
| **A · 单真相源** | VS Code / CodeMirror 6 / Obsidian / Monaco | 纯文本 buffer | ❌ **不存在**（源码即文档） | piece tree / rope + viewport 虚拟渲染 |
| **B · 块级存储** | Notion / Logseq / 飞书文档 | block 数组，每块独立 | ⚠️ 仅 per-block | 块级独立渲染 + 虚拟化 |
| **C · 双真相源** | **solo** / Typora(WYSIWYG 模式) / Marktext / 一切 TipTap+Markdown 编辑器 | 富文本树（Markdown 只是持久化格式） | ✅ **必须整篇反向转换** | 降频 / 缓存 / 降级 / 逃逸 |

### A 类的真实手段（它们处理的是"编辑"和"渲染"，不是"整篇导出"）

1. **VS Code — Piece Tree**：双 buffer（原始只读 + 追加只写）+ 红黑树索引。
   起因是用户报「打不开 35 MB 文件」（1370 万行，旧行数组实现分配 **600 MB** 后 OOM）。
   重写后 184 MB / 310 万行：内存≈原文件大小，打开从数秒降到几百毫秒。
   团队博客原话：「**编辑巨型文件最快的方式，就是永远不要编辑文本本身**」——所有输入 append 到 add buffer，原文一个字节都不搬。
   【高】来源：[Text Buffer Reimplementation](https://code.visualstudio.com/blogs/2018/03/23/text-buffer-reimplementation)
2. **CodeMirror 6 — Rope**：不可变平衡 B-tree（分支因子 32），结构共享；`replace` 走 decompose/recompose，只重建路径上的节点。定位第 N 行 O(log N)。
   【高】来源：[Text Structure](https://deepwiki.com/codemirror/state/3.1-text-structure)
3. **渲染侧一致用 viewport 虚拟化**：Obsidian 官方文档直言「编辑器支持百万行文档，原因之一是**只渲染可见内容**（略超出）」。
   【高】来源：[Viewport](https://docs.obsidian.md/Plugins/Editor/Viewport)

> ⚠️ **别误读**：以上解决的是「字符级编辑是 O(log n)」和「渲染只做可视区」。
> **整篇导出在任何编辑器里都是 O(n)**——VS Code 选中 184 MB 全选复制同样要遍历全文，只是常数小。
> solo 的目标不是「消除整篇序列化」（做不到，也不该做），而是**让它退回 O(n)**。

### C 类同行在这一层的惯用法

| 惯用法 | 说明 |
|---|---|
| **不累加字符串** | 累积到数组 `push`，末尾 `join` 一次；或分块 chunk 数组，最后拼一次 |
| **输出 DOM 而非字符串** | ProseMirror 官方 `DOMSerializer` 产出 `DocumentFragment`，拼接交给浏览器引擎（原生 C++ 层，天然 O(n)） |
| **增量序列化** | 只对脏区间重算——但 ProseMirror 无内建 dirty-range API，需自上而下比对，复杂度高，**不建议现在做** |
| **必须整篇时，缓存结果** | 相同文档树复用上次输出（solo 已做，见 `MarkdownEditor.vue` 的 `cachedSerialize`） |

### 一个反常识点（值得进 LESSONS）

`+=` 在 V8 里被 **ConsString（惰性绳结）** 优化过——写的时候确实接近 O(1)，不立即拷贝。
**但只要对累积结果做任何需要真实字符的读操作**（`endsWith` / 正则 / `slice` / 模板插值比较），V8 必须把整条绳结**摊平**一次，代价 O(当前长度)。

solo 的路径恰好是：每块 → `write()` 拼一段 → `ensureNewline()` 对**整个 output** 调 `endsWith('\n')` → 摊平。
⇒ 块数 n 次摊平，每次 O(n) ⇒ **O(n²)**。

上游 `prosemirror-markdown` 并未安装在 node_modules（solo 的 serializer 是[全自研](../src/components/Editor/tiptap/markdown/serializer.ts)），
故这不是「照抄上游带来的问题」，而是自研时对 V8 字符串行为的一次误判。

### 对 solo 的结论

- **不需要**上 piece tree / rope：那是为「百万行纯文本」设计的，与 solo 不追超长文档的定位不符。
- **必须**修的是「单次序列化的复杂度」：**15 行改动、零行为变化、4700× 收益**，属于单点修复，不是架构重构。
- 修完再重新标定 `HEAVY_DOC_CHARS`，让降级档位落在真实拐点上。

## 2. 格式准确性 · 输出（落盘保真）

探针：41 条真实场景（`md → doc → md`，判据「首轮输出 === 输入」+「二次收敛」）。
结果：**偏差 18 例 / 不收敛 2 例**。

### A 级 — 语义或数据风险，必修

| # | 现象 | 输入 → 输出 | 危害 |
|---|---|---|---|
| A1 | **列表内含代码块/引用：缩进拍平 + 二次不收敛** | `- 项一\n\n  ```\n  代码\n  ```\n\n- 项二` → `- 项一\n\n\`\`\`\n代码\n\`\`\`\n- 项二` → 二轮又多一空行 | 代码块**跑出列表**（语义变了），且**每次保存文件都在变**，diff 永不干净 |
| A2 | **嵌套列表：父项与子项间插空行 + 缩进 2→3 空格** | `- 父项\n  - 子项 A\n- 父项2` → `- 父项\n\n   - 子项 A\n- 父项2` | AI 输出 / 手写大纲全是紧凑嵌套；每存一次被撑开一次，编辑时视觉跳动 |
| A3 | **表格对齐丢失** | `\| :-- \| :-: \| --: \|` → `\| --- \| --- \| --- \|` | 用户设的对齐被抹平（已登记 #11） |

## 5. 响应速度：防抖分层（这块设计质量很高）

[`useEditorSync.ts`](../src/composables/useEditorSync.ts) 的四层防抖 + 空闲调度，是本项目最值得骄傲的工程细节：

| 通道 | 防抖 | 说明 |
|---|---|---|
| 光标信息 | 100ms | 拖选时避免全量遍历 doc |
| 字数统计 | 150ms | heavy 档直接停掉实时统计 |
| 大纲提取 | 500ms | heavy 档 + 面板关闭 ⇒ 跳过全文遍历 |
| 序列化 | 500ms | **再交 `requestIdleCallback`**，2000ms 超时兜底 |

外加**代际闸门**（`editGeneration` vs `syncedGeneration`）：关窗/切文档时若基线已同步就跳过全量序列化 ——
这正是 4MB 文档「关窗不卡死」的关键。

⇒ **结论**：中等文档（≤2 万字）的响应设计已经到位；问题全在 §1 的 O(n²)。

### 9.3 一项**实测后决定不改**：打开即全量序列化

`MarkdownEditor.vue:372` 建基线时无条件跑 `serializeMarkdown(initialDoc)`。

- **报告的前提已失效**：原文写「同样吃 O(n²)」——§1 修复后实测是**线性**的（见 §9.2 第 2 表），
  8k 文档只有 **7.5ms**，85k 才 28.6ms。
- **这笔序列化是承重的**：基线必须等于「载入文档的序列化产物」而非磁盘原文，
  否则 parse→serialize 的非字节等价（CRLF→LF、mark 顺序）会让「打开即显示未保存」。
- **推后会有代价**：把它挪到空闲时段，会让「打开→立刻输入→撤销回原文」这条
  极窄路径出现误标脏；而这正是敏感区第 1 条（脏态/保存冲突）反复踩过的地方，
  项目契约明写「偏保守只浪费一次序列化；偏乐观会丢编辑」。
- **结论**：用 7.5ms 的典型收益换脏态管线的时序风险，不划算；
  ≥400k 文档才值 130ms，而产品定位明确不追超长文档。**保留现状，不做门控。**

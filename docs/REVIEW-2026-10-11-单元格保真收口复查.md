## 1. 决策一（#61）：一行守卫——方向对，但只修了「第一行」

**证实的部分**：`atBlockStart()` 首行 `if (this.inTableCell) return false;`（`serializer.ts:152`）准确掐掉了 `:157` 的 `prefix === '' ⇒ true` 这条误判路径，被它管住的正是 `:566-569` 的 `^([#+\->])` 与 `^(\d{1,9})([.)])`。探针六形态（`- 甲` `+ 乙` `> 丙` `# 丁` `1. 戊` + 对照）全部逐字原样；`*` 仍转义（`:541` 行内恒需）——**与 §6「明确不改什么」一致，没有过度修**。

**证伪的部分（同一病灶的第二行）**：

```
serializer.ts:570   result.replace(/\n([#+\->])/g, '\n\\$1')
serializer.ts:571   result.replace(/\n(\d{1,9})([.)])(?=\s|$)/g, '\n$1\\$2')
```

这两条是**正则按 `\n` 判行首**，**不经过 `atBlockStart()`** ⇒ `inTableCell` 守卫对它们无效。而 `cellToText`（`:883`）是在**转义之后**才把 `\n` 换成 `<br>`。于是：

| 实测（格内 `codeBlock`，文字 `a * b\n- 行二\n# 行三`） | |
|---|---|
| R1（首存落盘） | `\| a \* b<br>\- 行二<br>\# 行三 \|` |
| R2（重开再存） | `\| a \* b<br>- 行二<br># 行三 \|` |
| 判定 | **R1 ≠ R2 ⇒ 首存即改文件**，且**多余那一层反斜杠正是 #61 要清的东西** |

**可达性（这是关键，决定它不是理论问题）**：格内 `toggleCodeBlock` 实测返回 `接管=true` 且 `codeBlock` 落在格内（探针 dump：`table,tableRow,tableHeader,codeBlock,text,paragraph`）⇒ 斜杠菜单「代码块」+ 两行代码 = 中招。`codeBlock` / `mermaidBlock` / `mathBlock` 的 content 是 `text*`，**多行文字本来就是一个含 `\n` 的文本节点**（围栏代码读进来就这么存）。

所以台账 §二 #61 行里那句「只有『文本节点里含裸 `\n`』这一**合成形态**才现不对称，而**解析与键入都产不出它** ⇒ 不为它单列现状登记锁」**判定错误**：它不是合成形态，它是这三个节点的正常形态。

**锁为什么看不见自己的洞**（这是本轮最该记住的一条）：

- `roundtrip.spec.ts:1948-1953`「边界：多行格子（行内 `<br>`）仍原样，不因换行触发块首转义」——喂的是 markdown 串 `| 甲<br>- 乙 |`。因 `html:false`（`parser.ts:113`），`<br>` 在这里是**字面文本**、整格只有**一个文本节点、零个 `\n`** ⇒ 这条锁**按构造恒真**，它没有测「多行」，它测的是「一行里有两个尖括号」。撤掉 `:570` 也不会红。

**这一条的修法（一句话，留给拍板后执行）**：`:570-571` 与 `:566` 同族（都在回答「这行是不是块内容起点」），应在单元格语境一并关闭——把两条规则包进 `if (!this.inTableCell) { … }`。门控安全性等价于决策一：格内的 `\n` 马上会被 `:883` 换成 `<br>`，那点转义**永远不会被需要**。

## 2. 决策二 B1（拍平）：块语法确实挡住了，但只挡到第 1 层

**证实有效的部分**（不该被下面的问题淹掉）：`:283-297` 的递归规则——「textblock 直接取行内内容、容器继续下钻」——按节点 `content` 表达式一刀切，**新增块类型默认被拍平**，不会因为忘登记而漏（这条设计判断我认同，比我上轮提的「列一张白名单」更稳）。探针 9 型逐条：`$$` / ` ``` ` / `> ` / `- ` / `[!NOTE]` **一个都没进单元格**，`mathBlock` 落 `| x=1 |`、`codeBlock` 落 `| x = 1 |` 且**语言名不再混进正文**（这正是它 §1.3 表里最脏的那格，确实收住了）。

### 2.1 🔴 黏连只修到第 1 层：`<br>` 只插在格的直接子块之间

```
serializer.ts:883   return parts.join('<br>')…          ← 只有这一处插分隔
serializer.ts:296   node.forEach((child) => this.renderFlattenedInline(child));
                                                       ← 递归下钻：兄弟之间什么都不插
```

唯一例外是 `:292-293` 给 `callout` 标题手工补的 `<br>`。于是「多个块黏成一坨」这个他自己写进注释的病灶（`:870-872`），**在深一层原样保留**。实测四条：

| 怎么造出来 | doc 形状 | 屏幕上 | 落盘 R1 | R1===R2 |
|---|---|---|---|---|
| 斜杠「待办」勾第一项 | `cell[taskList[taskItem(买奶,✓), taskItem(写码)]]` | 两个待办项 | `\| 买奶写码 \|` | **true** |
| 斜杠「有序列表」两项 | `cell[orderedList(li(五), li(六))]` | 五 / 六 | `\| 五六 \|` | **true** |
| **HTML 粘贴** `<ul><li>第一项</li><li>第二项</li></ul>` | `cell[bulletList[li(第一项), li(第二项)]]`（实测节点链为真） | 两项 | `\| 甲<br>第一项第二项 \|` | **true** |
| **纯键入**：格内 `toggleBulletList` + `Enter` | `cell[bulletList[li[para(丙), para(丁)]]]` | 两项 | `\| 丙丁 \|` | **true** |

**「文字全部保住」在这个形状上不成立**：字符一个没少，但**用户写的两项变成了一项**，中间连个空格都没有（中文场景下连分词的边界都被抹掉）。这不是「排版损失」，这是**内容变形**——而 B1 的取舍恰恰写着「内容保真 > 排版保真」。

**锁为什么看不见**：`roundtrip.spec.ts:2018-2022` 那条「多块格子：块与块之间用 `<br>` 分隔，不首尾黏连」搭的是 `cellDoc([P('甲'), P('乙')])`＝**两个直接子块**；Phase O 的 `BLOCKS` 表 `:1984-1990` 每种列表**只放一个项**、`codeBlock` 只放一行。⇒ 同一条断言在「深一层」**从未被跑过**，不是跑绿了，是没跑。

### 2.2 🔴 attrs 通道里的用户输入整体消失

`:283-297` 对 attrs 只补写了 `callout.title` 一处（`:288-294`）。实测：

- `taskItem{checked: true}` → `| 买奶写码 |`，**`[x]` 痕迹为零** ⇒ 用户勾的框没了，且重开后连「这里曾经是个待办」都看不出来；
- `orderedList{start: 5}` → `| 五六 |` ⇒ 编号起点没了；
- `heading{level: 3}` → `| 三级 |`、`codeBlock{language: 'js'}` → `| x = 1 |` ⇒ 这两条**是设计**（GFM 格子存不下级别和语言），认。

前两条与后两条的区别：`level` / `language` 是**排版**，`checked` / `start` 是**用户敲进去的数据**。他 §3 的 B1 定义说保「文字」，那 `checked` 算不算文字，需要**明写进取舍**，不能靠「它落在 attrs 不在 content」自动豁免。

### 2.3 🔴 选定的分隔符，solo 读不回来（这条是产品级，不是实现级）

`cellToText` 用 `<br>` 分隔（`:883`、`:293`），`:883` 还把 `hardBreak` 写出的 `'  \n'`（`:765-767`）一并转成 `<br>`。但**打开文件这一路**：

- `parser.ts:113` = `new MarkdownIt('commonmark', { html: false, … })`；`:133` 的注释自己写明「`html:false` 下 `html_inline` rule 被禁用（整段标签被当纯 text）」；
- ⇒ `parser.ts:683-684` 那条「`<br>` → `hardBreak`」**在文件打开路径上是死代码**（只有别的入站路径能碰到它）；
- ⇒ 既有锁 `roundtrip.spec.ts:413-417` **明确断言** `| line1<br>line2 |` 重开就是字面文本 `line1<br>line2`。

实测：`parseMarkdown('| 甲<br>乙 |')` → 单个文本节点 `"甲<br>乙"`；`serialize(段落[甲, hardBreak, 乙])` → `| 甲<br>乙 |`，重开 → 字面 `甲<br>乙`。

**所以 B1 的落盘形态，重开后屏幕上是一串 `<br>` 标签字符。** 这不是本次引入的（Shift+Enter 早就这样），但 B1 把它从「少见的 hardBreak 路径」**升级成了每一个多块格子的默认形态**——可见面扩大了。`serializer.ts:870` 那句「与『格内换行 → `<br>`』的既有写法一致」成立，但那个「既有写法」是**只写不读**的单向约定，注释里没写这一半。

### 2.4 顺带：#60 的入口一个都没堵

`table.ts` **不在** `536fd07` 改动清单（10 个文件）⇒ `tableCell.content` 仍是 TipTap 默认 `block+` ⇒ 探针实测格内 `toggleBulletList` / `toggleCodeBlock` / `toggleBlockquote` / `insertContent(mathBlock)` **四条全部 `接管=true` 且块落在格内**。⇒ PROPOSAL §2 自己写的「点了有效、存了没保住」**仍然存在**，只是「没保住」的样子从「变味」变成了「变字 + 挂 `<br>`」。B1 是事后兜底，不是入口拦截，台账里「已消除全部用户可见危害」这句要按 §2.1–2.4 改口。

## 3. 「不要轻信锁」——本轮的锁体检结果

`536fd07` 新增 24 条锁、反向校准自述 6 红 + 9 红 + 1 红。**我没有重跑撤代码校准**（本轮不改码），但换了另一把尺子：**逐条问「这条锁搭的 doc 形状，覆盖了病灶的哪一角」**。结果：

| 锁 | 自述锁的是 | 实际 doc 形状 | 看不见什么 |
|---|---|---|---|
| `:1926-1935` 格首五形态 | 不加反斜杠 | markdown 串，格首单个标记 | 第二行以后的 `\n` 规则（§1） |
| `:1948-1953` 多行格子仍原样 | 换行不触发块首转义 | **一行**含字面 `<br>`，零 `\n` | 同上——按构造恒真 |
| `:1993-2001` 七型逐条 | 文字不丢、语法不进、收敛 | 每种列表**一项**、代码块**一行** | 兄弟块黏连（§2.1）、`\n` 转义（§1） |
| `:2018-2022` 多块用 `<br>` 分隔 | 不首尾黏连 | 两个**直接**子段 | 深一层的黏连（§2.1） |
| 全局 `out2 === out1` 判据 | 保真 | — | **收敛 ≠ 保真**：`买奶写码` 完美收敛 |

**判据要换**：这族的锁应当断言 **重开后的屏幕文本**（`parseMarkdown(R1).textContent`）里「两项之间确有分隔」，而不是只断言 `R1 === R2`。前者会因黏连立刻红，后者永远不会。

## 4. §7 五条挑战，逐条回话

1. **§7.1「`inTableCell ⇒ atBlockStart()=false` 是否漏掉了某个真需要块首转义的场景？请在『一个格子塞多个块』与『格内含 hardBreak / `<br>`』两条路径上挑战」** → **击中，但方向反了**：不是「漏掉了该转义的场景」，而是**漏掉了同族但没被这条守卫管的另两条规则**（`:570-571`）。两个被点名的路径我实测完：真 `hardBreak` 形态**收敛但换行丢失**（`:765` → `<br>` → `html:false` 读不回，§2.3）；多块形态**收敛但兄弟黏连**（§2.1）。他在台账里对这两条的自评（「对称」「压根没有 `\n`」）**都只在「收敛」这一个维度上成立**。
2. **§7.2「B2 收紧 `content` 后 `canReplaceWith`/`canJoin`/`lift`/`setBlockType` 有无连带」** → **仍是悬空问题**：B2 没做（`table.ts` 未改），所以这条**没有被验证，也没有被需要**。真要动 schema 时才必须答。
3. **§7.3「HTML 粘贴 `<td><ul>` / `<td><h1>` 会不会静默丢内容」** → **我实测代答了**：粘贴/`insertContent` 的 `<ul>` 两项**能落进格子**（schema 允许），B1 下**字不丢、边界丢**（`第一项第二项`，§2.1）。⇒ 对 B2 的含义是**正面的**：收紧 schema 不会因「读不进去」而丢字，但**当前 B1 兜底本身有洞**，所以「先 B1 再 B2」的顺序判断成立、B1 完成度不成立。
4. **§7.4「`taskList` 的 `[` 残留漂移值不值得再收一档」** → **同意接受**，实测 `- [ ] 项` → `- \[ ] 项` 仍存在，`[` 属行内恒需转义（`:541` 的 `[`），放宽会把真链接打断。但他 §6 说「#61 修完后这一型的漂移仍存在（一次收敛）」——现在这条在格内**变成「拍平后连 `[ ]` 都没有」**（§2.2），所以 `[` 的讨论在格子里已经**降级**，只在普通列表里还活着。
5. **§7.5「列宽补空格算不算『打开即改文件』」** → **接受他的判定**（属 B5 设计，`visualWidth`/`WIDE_CHAR_RE` `:886-895` 是刻意的对齐机制，不是漂移）。补一句：现在文件里多出来的可见变化不是列宽，是 `<br>`（§2.3）——那条**该算**。

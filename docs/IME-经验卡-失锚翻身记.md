# IME 经验卡 · 失锚翻身记

> **一句话**：solo 历史上最贵的输入法候选框失锚问题，第一回合三个补丁全败、当晚用户叫停；一个多月后**换了一条机制**、从同栈外部项目抄来解法，10-12 定案转正。
>
> **为什么单独一张卡**：结案经验卡（[`docs/archive/IME-结案经验卡-2026-10-12.md`](./archive/IME-结案经验卡-2026-10-12.md)）回答「**复发时怎么排查**」；本卡回答「**我们是怎么赢的、下次怎么复制这场胜利**」——**全过程细节都在这里，千万不能丢**。
>
> ⚠️ **这个错犯过两次**：10-12 施工方发现自己的记忆写着「未解决、等上游」，查证才推翻；10-14 我写项目大事记，又照记忆把这一仗记成「负」，被简乐当场纠正。**根因相同：只读了记忆索引条目就下结论，没读完主题档案。** 本卡 + 编年史就是补这个洞。

## 二、全过程编年史（本卡主体，细节都在这一节）

### 2.1 前史：这病有多难缠（09-13 之前）

- 候选窗由系统进程 `TextInputHost.exe` 的 UWP 合成层绘制、**无独立 HWND**（Win32 枚举 / UIA 都拿不到）⇒ **只能屏幕像素取证**（判据 = 选中项高亮色 + 形状约束）。
- 相关旧账：`KNOWN-ISSUES §一 #4`「IME 候选栏变箭头」= `editor.css` 的 `ime-mode: active`（IE 遗留），已删；`§一 #15` 三层修复与组字守卫保留（它们正是组字期 DOM 保持干净的原因）。
- 2026-09-05 组字期诊断证明**应用层干净**：光标矩形从未退化、DOM 仅组字文本自身、无装饰重建、无 refocus ⇒ 残差在 WebView2/TSF 可见层之下。
- 发作规律：约 16% 会话命中；「**进入 solo / 切文档 / 移窗口**」后第一次组字失锚、第二次自愈。
- ⭐ **关键怪癖（决定了后来所有的验证方法）**：**任何鼠标移动/点击即清除**。一次解释三件事 —— ① 我们看到的「第二次组字自愈」；② 用户报的「偶发」；③ **35 次自动对照实验零复现**：自动化里先点/动鼠标 = **自己把 bug 擦了**。⇒ **复现必须全程零鼠标事件**；⇒ 自动化测试这条路对这个问题先天失效。

### 2.3 ⭐ 转折：那一轮「去外面找解法、逐条核实、组合定案」（10-07 → 10-09）

> 这一节就是用户说的「**参考最佳实践、结合别人的方法才成功**」的那一轮。它不是一次灵光乍现，而是一段**有来有回的讨论 + 逐条取证**。原始记录见 `.workbuddy/memory/2026-10-09.md`（「发现外部首个带 A/B 验证的社区解法」+「同族线索核实」两段）。

**① 起点：用户的一句追问**
- 第一回合三版补丁全败、当晚叫停后，问题在 09-24 被「封存」。一个多月后，**简乐追问：「GitHub 上大量类似项目难道也没解决吗？」**
- 这句话把方向从「自己造」掰回了「先搜别人怎么解的」—— 正是后来沉淀成打法①（见 §四·1）的那一下。

**② 挖到同栈「双胞胎病友」Lanmark（核心借力点）**
- 顺着上游 `#5675` 活动区，找到 `observer130/lanmark` 的 commit `ba451f0`「fix(ui): Windows 缩放窗口后输入法候选框跑到屏幕左上角」，**引用的就是同一个 issue**。
- **技术栈逐字相同**：Tauri 2.11.5 / wry 0.55.1 / webview2-com 0.38.2，且同为「所见即所得 Markdown 编辑器」⇒ 不是「类似」，是「同一个坑的同款受害者」。
- **症状逐字吻合**：拖窗缩放后打字 → 候选框浮屏幕角 → 不自愈 → 需真实焦点转移才恢复；Edge/Chrome 不复现。
- **它给的解法（我们最后抄的就是这个）**：窗口几何稳定后（防抖 120ms）`blur()` → **等 60ms** → `focus()` + 还原选区与滚动；只在 Windows/WebView2 启用；组字中不打断（pending → 等 `compositionend` 补做）。
- **它最有价值的一份遗产 ——「无效手段实测表」**：

| 手段 | Lanmark 实测 |
|---|---|
| `blur()` → 等 60ms → `focus()` | ✅ 修复 |
| `blur()` → `setTimeout(0)` → `focus()` | ProseMirror 够用 / CodeMirror 6 无效 |
| 同步 `blur+focus` | ❌ |
| 只 `focus()` | ❌ |
| 只挪 DOM 选区 | ❌ |
| `NotifyParentWindowPositionChanged` | ❌ |

⇒ 必须**真实焦点转移** + 两次变化**拉开间隔**才重发 `TextInputState`。
⇒ **这表反过来解释了「我们第一回合为什么全败」**：我们设想过的「延迟 300ms 只 `focus()`」正属「只 focus」一档，注定无效；v1/v2/v3 鼠标注入走的是「刷新触发器」另一条机制，失败也不冤。**外部一份实测表，同时给出了「抄什么」和「为什么自己造的不行」。**

**③ 用户带来第三方调研 4 条线索，逐条回第一现场核实**
- 简乐另带来一份第三方 AI 生成的调研（含 4 条链接），要求送检。**逐条核实，发现真伪混杂** —— 这轮的核心纪律是「同栈 + 同病 ≠ 可以照抄」：

| 线索 | 核实结论 | 能不能抄 |
|---|---|---|
| **Blender PR `#132102`**（原生 C++ 走 IMM，`GHOST_ImeWin32` 源自旧 Chromium） | ✅ 真实 | ❌ **不可搬**：Blender 是原生应用、自控候选窗，能直接调 `ImmSetCandidateWindow`；solo 走 WebView2 托管，**IMM 上下文在 WebView2 子窗口（Chrome_WidgetWin_1）**，顶层调 `ImmSetCandidateWindow` **够不着**——正撞文档已列的死路 |
| **xterm.js `#5839`**（Tauri 2.0+WebView2+Win11，候选窗右下角） | ✅ 真实 | ⚠️ 仅旁证：根因在 xterm 自身（buffer cursor 停输出区），其重定位 textarea 的解法对 solo 无效 |
| **paseo `#3511`**（Electron+xterm.js） | ✅ 真实 | ❌ 情形相反：它说「普通 textarea 不受影响」，而 solo 裸 input 也复现 |
| **VSCode `#259380`** | ✅ 真实但**转述两处有误** | ❌ 不可抄：① 症状是「候选窗不出现」非位置错乱；② 缓解是**关掉**旧版微软拼音兼容开关（非打开）；③ 出自用户评论非官方 |

**④ ⭐ 这一轮最关键的两次「辨析」（决定了我们没把唯一有效的方案自己否掉）**
1. **Blender 经验不可搬** —— 上面已说（架构层够不着）。若照「原生应用能调 IMM」去给 solo 加 `ImmSetCandidateWindow` 预定位，是撞死路。
2. **「事后重锚无效」被过度推广，差点误杀我们的方案**：第三方把 Blender 的「给**已存在的候选窗**发移动请求（组字中被忽略）」推广成「任何事后操作都无效」。但二者解决的是**不同环节** —— Blender 是「挪已有的框」；Lanmark / 我们的做法是从头**重建渲染进程文本输入状态**（blur→focus 重发 `TextInputState`），pending 到 `compositionend` 之后、作用于**下一次**组字。**若照第三方的推广采信，会误杀当前唯一有 A/B 验证的解法。**

**⑤ 组合定案：别人方法怎么「合」成我们的方案**
- 主线 **直接采用 Lanmark 护栏**（blur→60ms→focus + 防抖 120ms + 组字 pending），这是「参考最佳实践」的本体。
- **Blender 式 `ImmSetCandidateWindow` 预定位 —— 明确不做**（架构够不着）。
- 「验证 TSFImeSupport flag 是否生效」—— 思路有价值但更廉价替代判据已够（文档 O9 已确认候选窗由 `TextInputHost.exe` 画，flag 生效后可重采现场侧证），列为可选诊断，不阻塞主线。
- 给用户的「兼容模式」自救指引 —— **暂缓**（第三方方向说反，须先自证）。
- ⚠️ **诚实标注**：Lanmark 的 A/B 样本仅「护栏关 2 轮 / 开 2 轮」，n 很小；落地后仍需本项目自己的统计判定（后来用被动探针 + 日常观察补足，见 §2.6 / §2.7）。

**⑥ 顺带回答「GitHub 上大量类似项目为什么没事」**
- 主流 Markdown 编辑器（Typora/Obsidian/MarkText/Notion）多为 **Electron**（自带完整 Chromium），不走 WebView2 这条特定链路 ⇒ 根本不踩这个坑。**Tauri 系才踩**。
- 且触发条件苛刻（拖窗后立刻打字 + 全程不碰鼠标），多数项目没发现或用户忍了；微软对该族 0 回复。

**⑦ 这轮留下的纪律（后来写进打法①）**
- 动手造之前先问「同栈项目有没有解过这道题」；判断「现成的为什么不行」的成本，远低于造一个。
- 每条外部解法都**回第一现场核实**后才采信 —— **同栈 + 同病 ≠ 可以照抄**（4 条线索里就有 1 条转述两处有误、1 条情形相反、1 条仅旁证）。

### 2.4 落地：第一版护栏，以及它为什么没生效（10-09 上午）

- **阶段 0**：证据进 master；开分支 `fix/ime-anchor-guard`（基线 `55bbbc1`）；建修复档案；**验收判据提前定死**（「护栏关时必须能测出 HIT」是有效性前提，否则数据作废）。
- **阶段 1**：新建 `src/components/Editor/tiptap/ime-anchor.ts`，`installImeAnchorGuard(opts) → dispose()`；
  - 组字态走 `composition-freeze.ts`（唯一真相源，**不另造第 5 份 `let liveView`**）；
  - 挂 DOM `resize` 防抖 **120ms**；`blur→60ms→focus`；
  - 带**临时 A/B 开关**（`localStorage['solo:imeAnchorGuard']==='off'` 即时停用，Console 一行即可，**验证完必须删**）。
- **阶段 2**：闸门全绿（全量 1521 例 / `vue-tsc` 0 错 / `eslint` 0 错 / 沙盒 build 32.62s）。
- **08:12~08:25 首轮真机**：简乐启动 dev 构建后**直接测了一轮**，报「候选框飞到屏幕角」。
  - 只读核验（方法可复用）：进程路径 = `src-tauri/target/debug/solo.exe`；Vite `1420` LISTENING；`curl http://localhost:1420/…/ime-anchor.ts` 能取到本模块源码 ⇒ **确系 dev 构建、护栏确已加载**（排除「测的是旧版」）。
  - ⚠️ 但该轮**混杂**：他自述「拖边框缩放，**也移动了**」⇒ 无法区分「护栏没触发」与「触发了但无效」。

### 2.5 ⭐ 关键修正：用户一句话推翻代码假设（10-09 08:18）

- **简乐两条关键纠正**（本人长期经验）：
  1. 该问题**概率性出现、无法按需复现**（原话：「你专门测，它不一定能暴露出来」）⇒ **人工刻意 A/B 本身不成立**；
  2. 失锚**多数发生在「移动窗口」时**。
- **技术后果（推翻现护栏触发面）**：Windows **纯移动窗口不发 `resize`/`Resized`，只发 `Moved`**（源码事实：`tao` 的 `event_loop.rs:1210/1227`，本项目记忆与 `RELEASE_PROCESS` 均已载）⇒ 首版只挂 DOM `resize`，对「移动」**完全无感** ⇒ **一直在治非主因**。这与「首轮开着护栏仍 HIT」互相印证。
- **处置（当天完成，分支 `75c49e1`）**：
  1. 触发面：只缩放 → **移动 + 缩放**（订阅 Tauri `onMoved`/`onResized`，异步建立 + dispose 退订防泄漏；保留 DOM `resize` 兜底给非 Tauri / 测试场景）；
  2. 判据：人工 A/B → **被动探针对账**（见 2.6）；
  3. 探针写盘留痕。
- **⭐ 打法沉淀**：**用户的一手经验就是第一现场，应直接据此改方案，而不是再设计实验让他去跑。** 这次靠他这句话才找到真错处。

### 2.6 被动探针：概率性问题的验证办法（10-09 设计，10-12 删除）

- 新增临时 `ime-anchor-probe.ts`：把护栏每次**触发 / 跳过**写盘到 `%APPDATA%\com.solomarkdown\ime-anchor-probe.json`；仅 dev + Tauri 生效；异常全吞。
- **零人工负担用法**：简乐**照常使用**；若再见候选窗飞角，读该文件最近记录：

| 失锚前探针里有什么 | 结论 |
|---|---|
| **有** `reanchor / blur+focus` | 护栏跑了但没用 ⇒ 该机制对本机无效，需换招 |
| **只有** `skip`（`not-focused` / `ab-off` / `no-view`） | 护栏被跳过了 ⇒ 看 reason 定位 |
| **什么都没有** | 护栏没跑 ⇒ 触发面仍不够，继续扩 |

- **已知局限**：`MAX_EVENTS = 400` ⇒ 重负载下只保留最近约十几分钟；**再遇失锚须尽快读盘**，否则证据被覆盖。

### 2.7 观察期读数（10-09 08:31~08:38）

| 取样 | 跨度 | compositionstart | reanchor `blur+focus` | skip | 失锚 |
|---|---|---|---|---|---|
| ① 重启后首次（简乐报「**好像解决了**」） | 138 秒 | 62 | **22**（move 20 / resize 1 / dom-resize 1） | 2（均 `not-focused`） | **0** |
| ② 同一会话累计 | 425 秒 | 80 | **33**（move 30 / dom-resize 2 / resize 1） | 3 | **0** |

- 判读：✅ **护栏确在「移动窗口」时触发** —— 正是首版全缺、也是简乐指出的主触发 ⇒ **方向修对了**；✅ `skip:not-focused` 说明焦点不在编辑器时正确空操作（退化安全有效）。
- ⚠️ **不可据此宣布治愈**：① 仅单一会话；② 该 bug 状态**会话内恒定** ⇒ **重启本身可能使它暂不出现**（重启混杂，无法排除）；③ 无 `pending` 样本（未覆盖「移动恰好发生在组字中」）。

### 2.8 定案与清场（10-12）

## 三、最终是怎么解决的（机制原理 · 一步一步）

> ⭐ **本节能直接回答「最后到底怎么解决的」**—— 不靠表格、不靠比喻一带而过，把每一刀为什么这么切讲透。代码见 `src/components/Editor/tiptap/ime-anchor.ts`。

### 3.1 先定位：失锚发生在哪一层

- 候选框**不是 solo 画的**，是系统输入法进程（`TextInputHost.exe` 的 UWP 合成层）画的。
- 输入法要把候选框画在哪儿，得问浏览器：「光标（caret）现在的坐标矩形在哪？」→ 浏览器通过 **TSF（Text Services Framework）** 的 `GetTextExt` 把 caret 矩形交给输入法。
- solo 用 WebView2（Chromium 内核）。**窗口几何一变（拖动 / 缩放）**，Chromium 进程侧的 TSF 文本库**没有用新窗口坐标及时刷新 caret 矩形**——它还记着旧坐标，甚至认为「没有有效锚点」。
- 输入法拿不到有效 caret 矩形时，**回退到默认位置 = 屏幕角**，这就是「飞角 / 失锚」。
- **关键判据**：角是**恒定**的（韩文报左上、我们报右下，同一机制），不是随窗口「偏移一个量」。凡是「坐标缓存过期 / 算错偏移」类假说都解释不了角位恒定 ⇒ 已排除，根因锁定为「无锚点回退」。

### 3.2 关键认识：要让浏览器「重新喂一次坐标」

- 病根不在「候选框画歪了」，而在「浏览器手里那份 caret 坐标**过期**了」。
- 所以修法**不是去挪候选框**，而是**逼浏览器用新窗口位置重算 caret 矩形，并重新上报给 TSF**。
- 在 Chromium 里，浏览器进程侧的 TSF 文本库，是靠**渲染进程重发一次 `TextInputState`（文本输入状态）**来刷新的；而**焦点状态的变化**会触发这次重发。→ 这就是整个解法的支点。

### 3.3 重锚护栏实际做的动作（一步一步，对应代码 `reanchor()`）

1. **窗口停稳**：拖 / 缩会连发一串事件，先用 `IME_ANCHOR_DEBOUNCE_MS = 120` 防抖等它安静。
2. **确认焦点在编辑器**：取 `view.dom` 元素 `el`，校验 `document.activeElement === el`；不在就空操作（护的是输入焦点，别的地方不碰）。
3. **组字中不打断**：若 `isFrozen(view)`（组字态唯一真相源 `composition-freeze.ts`）为真，置 `pending = true` 先返回，等 `compositionend` 再补（见 3.5）。
4. **存滚动位置**：`saveScroll()` 自 `el` 向上逐层记下非零 `scrollTop/Left`。
5. **`el.blur()`** —— 让编辑器**失去焦点**。这一步把浏览器进程侧的焦点状态变成「离开」。
6. **等 `IME_ANCHOR_FOCUS_DELAY_MS = 60` ms**（关键，见 3.4）。
7. **`view.focus()`** —— 用 TipTap/PM 的 focus 让编辑器**重新获得焦点**（会按 `state.selection` 还原光标）。这一步把焦点状态变回「进入」，触发渲染进程**重发 `TextInputState`**，caret 矩形按**新窗口坐标**重新上报 TSF。
8. **`restoreScroll()`** 还原滚动位置（防焦点转移引发跳动）。

→ **结果**：输入法再问「光标在哪」，浏览器这次给的是**移动后的正确坐标**，候选框就贴回光标了。

### 3.4 为什么必须隔 60ms，不能紧挨着

- Chromium 会把「同一轮渲染任务内」的焦点变化**批处理 / 合并**：如果 `blur` 和 `focus` 发生在同一个 task（甚至 `setTimeout(0)` 的延迟太短），浏览器进程侧看到的是「焦点没变过」，于是**不会重发 `TextInputState`**，TSF 布局也就不刷新 —— 等于白做。
- 必须让两次状态变化落在**不同的任务 / 帧**里，形成一次「真实可见的焦点转移」。60ms 是外部同栈项目（Lanmark）实测出来的最小有效间隔（更短在 CodeMirror 6 上无效），本项目沿用同一保守值。
- 这也顺带解释了死路清单：只 `focus()`（没先 blur，没有转移）、同步 `blur+focus`（合并）、`setTimeout(0)`（太近，合并）、只挪 DOM 选区（没动焦点）—— 全部无效，因为它们都没能触发那次「重发」。

### 3.5 为什么组字中不能动：pending 兜底

- 组字中（拼音候选还挂着）`blur()` 会**吞掉预编辑**（半截拼音被提交或取消），所以不能打断用户打字。
- 护栏检测到组字（`isFrozen`）就置 `pending`，先不 `blur`；等 `compositionend`（这串拼音输完）再 `schedule()` 补做一次重锚。
- 既修了锚点，又从没打断过一次输入。

### 3.6 为什么必须订阅 `onMoved`（不是只挂 `resize`）—— 最易漏的一处

- 失锚**多数发生在「移动窗口」时**（简乐一手经验）。
- Windows 规则：**纯拖动窗口只发 `WM_MOVE` / `Moved`，不发 `WM_SIZE` / `resize` / `Resized`**。DOM 的 `resize` 事件纯移动时**根本不触发**。
- 首版护栏（10-09 上午）**只挂了 DOM `resize`** → 对「移动」完全无感 → 等于一直在治非主因（首轮真机「开着护栏仍失锚」就是这个原因）。
- 修正（10-09 当天靠用户一句话改对）：订阅 **Tauri 原生 `onMoved` + `onResized`**（移动和缩放都抓），并保留 DOM `resize` 兜底（非 Tauri / 测试场景）。这一条是整场翻身里「从负到胜」的转折点。

### 3.7 一句话回顾（快递员比喻）

候选框 = 系统派的快递员，他需要「包裹地址」（光标坐标）。窗口一搬家，浏览器手里地址簿旧了，快递员只能按默认地址（屏幕角）送。护栏做的事 = 让浏览器把「我搬家了、这是新地址」**重新上报一次**（`blur → focus` 制造一次真实的地址簿刷新）；而 60ms 是「确保这次上报不是被系统当成废话合并掉」的间隔。

### 3.8 还有哪些约束（勿违）

- **只在 Windows 生效**：`isWindows` 门控，其它平台整段空操作（连监听都不挂）。
- **退化安全**：无 view / 已销毁 / 焦点不在编辑器（`document.activeElement !== el`）→ 空操作。
- **组字态走唯一真相源** `composition-freeze.ts` 的 `isFrozen`，不另造判断。

## 四、三条可迁移打法（从全过程提炼）

### 1️⃣ 同技术栈的项目，先搜一遍别人怎么解的

- 第一回合的思路是「**自己造**」：观察到「手动晃鼠标能好」，就做了三个版本的「自动抖鼠标」—— 全部失败。
- 第二回合的转折是「**先搜**」：在 GitHub 找到 `observer130/lanmark`，**内核版本一样、踩的是同一个上游 issue**，它已给出解法并实测有效。
- **教训**：动手造之前先问「同栈项目有没有解过这道题」。**判断「现成的为什么不行」的成本，远低于造一个的成本** —— 尤其当问题是**宿主 / 内核缺陷**（我们自己修不了的那一层）时，外部同栈项目几乎是唯一信息源。
- ⚠️ 但**不能照抄**：同期还核了 4 条外部线索，其中 2 条引述未能核实、1 条（Blender 的 `ImmSetCandidateWindow`）在架构上不成立。**每条外部解法都要回第一现场核实**，见 [`IME-ANCHOR-GUARD-2026-10-09.md`](./archive/IME-ANCHOR-GUARD-2026-10-09.md) §8。
- 🔗 **那一轮的完整过程（用户追问 → Lanmark 借力 → 4 条线索逐条核实 → 组合定案）见 [§2.3](#23-转折那一轮去外面找解法逐条核实组合定案10-07--10-09)。**

### 2️⃣ 补丁无效时，换机制，而不是加第四个补丁

- 第一回合三版补丁**死在同一个机制上**（合成鼠标输入）：v1 触发器没接 `Moved` 从未开火 → v2 接上但「事前注入防不住」→ v3 改成组字后注入仍钉死。**同一机制上的参数级修补，修不出机制级的问题。**
- 第二回合**换了一条完全不同的机制**：不再请求输入法移动候选窗，而是让浏览器**重发一次文本输入布局**（`blur → 隔 60ms → focus`，制造一次真实焦点转移）。**解的是另一个环节。**
- **教训**：当第 2、3 个补丁都在同一个假设上失败时，**停下来质疑机制本身**，别去调第 4 组参数。（与 [`LESSONS.md`](./LESSONS.md) D2「单向棘轮」同源。）

### 3️⃣ 阶段性的「认输」必须标注时效，不能写成终局

- 09-24 的结论是「**输入注入通道穷尽，此路封死**」—— **这句话本身是对的，但它只对「鼠标注入」这一条机制成立。**
- 它被（包括我自己）误读成「**这个问题没救了**」，于是写进了项目记忆、对外报告、乃至大事记初稿。**一个正确的局部结论，被放大成了错误的全局结论。**
- **教训**：封存 / 认输类结论必须写清**边界** —— 写「哪条路封死」，不写「此问题封死」；并显式标注「**此为阶段性结论**」，给未来的自己留一个复查钩子。

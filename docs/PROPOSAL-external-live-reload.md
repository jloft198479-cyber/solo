# 方案：外部改文件实时跟随

> **状态：`parked` —— 2026-10-21 决定搁置，未动一行业代码。** 重启时先读 **§十**（含与历史方案的关系、从哪继续）。

## 一句话结论

**别开接口，让 Agent 直接写文件；solo 补一个「盯着这一篇文件、变了就跟上」的能力。**
性能负担 ≈ 0（每 2 秒一次读文件时间戳，微秒级）。真正要设计的是**跟上的时候别打断正在读的人**。

## §二 做什么 / 不做什么

**做**
- 只盯**当前打开的这一篇**文件（单文件，不是整个目录）。
- 磁盘内容变了 → 按既有四道闸决定「静默跟上」还是「提示用户」。

**不做**（明确划界，防止范围膨胀）
- ❌ 不做 AI 侧边栏 / 不接大模型。
- ❌ **不开 API / MCP / HTTP 端口**。理由：① 开端口 = 本机任意程序可改你的文档，跟「本地优先·极简」反着来；② 有端口就要处理光标/组字态/并发合并，等于把单人笔记本改造成协作编辑器，工作量和回归风险都不成比例；③ **Markdown 本身就是接口**——纯文本，任何 Agent 用最笨的方式（直接读写文件）就能改，根本不需要 solo 开门。
- ❌ 不做目录监听 / 新文件自动进侧边栏（另一个需求，另开方案）。
- ❌ 不做冲突合并。脏着就一律交给用户裁决，程序绝不替他选。

## §三 两档方案

### 档 A · 提示档（最小改动，零新风险）

1. 新增一个轮询：每 `EXTERNAL_FILE_POLL_MS`（建议 2000）调一次 `getFileMtime(path)`。
2. mtime 与基线不一致 → 走**现有**的 `promptExternalModified()`，状态栏出提示，用户点一下才重载。

- **改动面**：1 个 composable/函数 + `useDocumentSession` 内一处接线（注册/注销）。
- **用户体感**：Agent 改完 → 状态栏冒出「文件已在外部修改」→ 点一下看到新内容。**跟现在唯一的区别是不用先切走再切回来。**
- **风险**：几乎为零（复用现有提示路径，不做任何自动重载）。

### 档 B · 跟随档（推荐）

在 A 之上加两件事：

1. **干净态 + 非大文档 → 静默重载**（复用 §一 那套决策，**抽成公共函数**，不抄第二遍）。
2. **重载前后保持阅读位置**：DOM 替换前记 `scrollRatio`，替换后按同一比例写回（复用 `currentScrollRatio()` / `:523` 的现成算法，**内存态**，不落盘）。

- **用户体感**：Agent 改完 → 内容自己变，**眼睛停留的位置不动**。
- **为什么位置保持是必选项不是加分项**：不做的话，每次重载都把人甩回文档开头。AI 改文档常常改的是后半段，读者正在那儿看——一甩就废，这功能等于没做。

### ~~推荐 B，理由~~

> ⚠️ **本节结论已被 §九 推翻（2026-10-21 重审）**：改为**先做 A**，B 作为 A 之后的第二阶段按真实体感再定。原文保留以留痕。

A 只解决了「不用切窗口」，B 才解决「实时可见」。而 B 相对 A 多出来的成本主要是**位置保持**这一处，其余全是复用。

## §四 关键设计点

### 1. 先抽公共函数，再接线（真理源唯一）

`handleWikilinksSynced`（`:495-520`）里那套「脏态双查 + 大文档闸 + 路径比对」是**全仓唯一一份**正确实现。
⚠️ **绝不能在轮询分支里抄一遍** —— 两处真相源，改一处漏一处就是静默丢内容（本项目最贵的事故类型）。

做法：抽 `reloadFromDiskIfSafe(path): Promise<void>`，两个调用点（wikilink 同步 / 外部轮询）共用。
注意：现有 `wikilink-sync-refresh-lock.spec.ts` 是按**函数体文本**做断言的（第 105-121 条），抽取后该锁的 `bodyOf(session, 'handleWikilinksSynced')` 会失配 ⇒ **抽函数这一步要同步改这条锁**，别让它变假绿。

### 2. 写入稳态判定（防抖）

Agent 写文件可能是分块的（流式写 / 分多次 write），mtime 会在很短时间内连变多次。
⇒ 检测到变化后**不立刻重载**，再等一个短窗口（建议 300ms）复查 mtime 是否还在变，稳定了才动手。否则一次写入会触发 N 次全量重解析。

### 3. 四道闸（全部已有，列出来只为确认不被绕过）

| 闸 | 作用 |
|---|---|
| `isSaving \|\| isOpeningFile` | 自己保存引起的 mtime 变化不误判 |
| `isSamePath` | 读盘这几百毫秒里用户换了文档 → 放弃，绝不把别篇内容写进这篇 |
| `evaluateDirtyFromEditor()` **await 前后各一次** | 用户在读盘期间开始打字 → 改走提示，绝不静默覆盖 |
| `isHeavyDocument()` | 大文档重载 = 一次全量重解析的顿挫，挡在自动路径外，只提示 |

### 4. 一个漂亮的推论：只保滚动，不必保光标

**重载发生的必要条件是「干净态」**——用户没在编辑。没在编辑 ⇒ 光标位置没有意义。
⇒ 首版**只保滚动比例**，不碰选区/光标。**这个分支天然成立，不需要额外论证。**

## §五 性能量化

| 项 | 开销 |
|---|---|
| 轮询本身 | 每 2s 一次 `getFileMtime` = 一次异步 invoke + 一次 `metadata()` 系统调用。**微秒级**，比自动保存（默认间隔 ≥5s，且要全量序列化 + 写盘）轻一个数量级以上 |
| 稳态判定 | 只在真变化时才多跑一次，平时不触发 |
| 重载（仅档 B） | 一次 `openDocument` + 全量重解析。被 `isHeavyDocument()` 挡住；普通文档量级下就是「打开一个文件」的时间 |
| 常驻内存 | 一个 timer + 一个闭包。**没有常驻服务、没有端口、没有后台线程** |

**结论：性能负担可以忽略。** 真正的成本不在性能，在**行为正确性**（别打断阅读、别覆盖未保存内容）。

### 为什么选轮询而不是 fs 事件监听

| | 轮询（本方案） | 装 `notify` 做真监听 |
|---|---|---|
| 新依赖 | **无** | 需新增 crate（AGENTS.md §1.5：不许擅自装依赖） |
| 新 Rust 命令 | **无** | 至少 2 个（watch/unwatch）+ 四处注册 + `ARCHITECTURE.md` 命令表同步（有机器锁 `arch-drift.spec.ts`） |
| 事件风暴 | 天然免疫 | Windows 上原子写（tmp+rename）连发多次事件，仍要自己做稳态判定 |
| 适用性 | 只盯 **1 个**文件，绰绰有余 | 为监听整个工作区而生（VS Code / Obsidian 场景） |

**1 个文件用不上一个 crate。** 轮询就是这里的最佳实践。

## §六 风险与防误伤

| 风险 | 兜底 |
|---|---|
| 覆盖用户未保存的编辑 | 脏态双查（已有闸）。**这是铁律，任何档位都不许绕过** |
| 重载把读者甩回顶部 | 档 B 的位置保持；做不到就退回档 A |
| 大文档卡顿 | `isHeavyDocument()` 挡自动重载，只提示 |
| 自己保存误触发 | 保存后基线已对齐 + `isSaving` 跳过 |
| 定时器泄漏 | 随 `onUnmounted` 注销，与现有 `unlistenWikilinksSynced` 同一套兜法（含异步注册的竞态处理） |
| 文件被删除/移动 | `getFileMtime` 失败 → 跳过本次并留痕（现有兜法，`:590`） |

## §七 验收口径（写用户动作，不写「N 条锁转绿」）

1. 打开一篇文档，**不切走窗口**，用外部编辑器（或命令行）改它并保存 → solo 里内容自己变，滚动位置基本不动。
2. 在 solo 里打几个字（制造脏态），再从外部改并保存 → **内容不变、不闪、不丢字**，状态栏出提示；点提示才重载。
3. 打开一篇超大文档，外部改 → 只提示，不自动重载，界面不卡。
4. 外部连续快速写多次（模拟流式写）→ 只重载一次，不抖。
5. 在 solo 里保存 → 不触发外部修改提示。

> 方法：把原方案的每条断言拉回代码核对一遍。**本节的"已核"= 读代码推断，未真机验证**（按 §七 的验收口径，最终仍以真机操作为准）。

### 9.1 结论翻转：**先做档 A**，B 降级为"看体感再定"

**原方案 §三 的推荐是错的，错在没先问一句：「实时可见」本身是不是伪需求。**

外部 Agent 改文档，只有两种真实姿势：

| 姿势 | 人的行为 | 需要什么 |
|---|---|---|
| **异步（主流）** | 发指令 → 去干别的 → 回来检查 | 回来时能看见变化 ⇒ **获焦检查已经够用**，档 A 只是省掉「切走再切回」 |
| 同步 | 盯着屏幕看 Agent 一个字一个字改 | 才需要真正实时 + 不打断阅读 ⇒ 只有档 B 能满足 |

异步姿势下，「静默重载 + 位置保持」这套复杂度（见 9.2 #1，比原方案估的贵得多）**买不到东西**。

⇒ **档 A 是档 B 的严格子集，也就是它的第一阶段**：轮询骨架、抽公共函数、提示去重，B 全都要用。先做 A，跑一两周；真觉得"还得点一下太烦"，再上 B —— 那时只加 `MarkdownEditor.vue` 那一处。

**附带的好处（原方案没意识到）**：档 A **不碰编辑器内核**，而档 B 要动 `MarkdownEditor.vue` 的文档替换 watch——那属于 `ARCHITECTURE.md §11` 的敏感区。少碰一次就少一次保真回归的机会。

### 9.2 原方案漏掉的三处实质缺口（按严重度）

| # | 缺口 | 代码事实 | 不修的后果 |
|---|---|---|---|
| **1** | **「复用现成的位置恢复」是错的** —— 现有逻辑对**同路径重载天然失效** | `MarkdownEditor.vue:593` 恢复只在 `path !== prevPath` 时调用；`:508` 还有 `if (path === restoredPath) return;` 守卫；更关键的是 `:590` `editor.value.commands.focus('start')` **每次替换文档都执行** ⇒ 滚到顶 | 档 B 每次重载**仍会甩回顶部**，功能白做。必须在编辑器内**新增内存态 ratio 路径**（替换前记 `currentScrollRatio()`，替换后写回），不能走 `restoreReadingPosition` |
| **2** | **提示会赖着不走** | `promptExternalModified`（`:474-480`）每次都 `clearTimeout` 再重设 30s；轮询每 2s 跑一次、基线在用户点重载前不变 ⇒ 每 2s 重置一次 | 与 `:473` 注释「30s 自动消失，避免常驻挡视野」直接冲突。修法：记「已提示过的 mtime」，同一 mtime 只提示一次 |
| **3** | **抽函数会让既有锁变成假绿** | `wikilink-sync-refresh-lock.spec.ts:105-121` 用 `bodyOf('handleWikilinksSynced')` 断言 4 个关键调用；抽成 `reloadFromDiskIfSafe` 后函数体只剩一行调用 ⇒ 4 条全红 | 原方案写「同步改这条锁」**太轻**：只把断言目标换成新函数 = 丢掉了「handleWikilinksSynced 真的调了它」这条接线断言，将来调用点被删依然全绿。**必须一分为二**：决策断言搬到新函数 + 新增一条接线断言 |

### 9.3 原方案担心过头、已核安全的两条（写下来，免得下次重复担心）

| 疑点 | 结论 | 依据 |
|---|---|---|
| 静默重载会不会把用户**改了一半的标题**抹掉？ | **不会** | `setFile` 确实会把 `displayName` 重置回 baseName（`file.ts:86-87`），但 `setDisplayName` 会置 `isDirty=true`（`:97`）；而 `syncEditedContent` 在内容未变时**只 `return false`、不重置 isDirty**（`:69-71`）⇒ 标题脏洗不白 ⇒ 脏态闸挡住自动重载 |
| 轮询会不会撞上自己保存、误报"外部修改"？ | **当前代码顺序下无窗口** | `isSaving=true`（`:266`）→ 写盘 → `markSaved`（`:278`，含基线）→ `isSaving=false`（`:328`）。基线更新**早于** isSaving 复位 |

⚠️ 第二条是**隐式契约**：谁将来把 `:328` 挪到 `markSaved` 之前，竞态就回来了，而所有测试都不会红。⇒ 建议在 `:328` 旁写一行注释钉住，或补一条锁。

### 9.4 原方案需要更正的事实与措辞

| 原文 | 更正 |
|---|---|
| `handleWikilinksSynced` 在 `:495-520` | 函数实际从 **`:491`** 起，四道闸在 `:493-513` |
| 「比自动保存轻**一个数量级**」 | 拍脑袋的倍数，撤掉。可核事实：轮询 = 一次 `metadata()` 系统调用（微秒级）；保存 = 全量序列化 + 写盘；重载 = 解析 + 全量序列化（50 万字档：解析 88ms / 序列化 35ms，Node 口径，WebView2 ×2~3，见 `document-scale.ts` 注释）。**真正贵的是重载，不是轮询** —— 这句才是重点 |
| 「1 个文件用不上一个 crate」 | 结论对、理由要更准：监听不是「加个 API」，而是 `@tauri-apps/plugin-fs` / `notify` + 新命令 + 四处注册 + 权限配置 + `arch-drift` 文档同步。为 1 个文件付这套成本不划算 |
| 档 B 「多出来的成本主要是位置保持这一处」 | 实际动 **3 个文件**：`useDocumentSession.ts` + `MarkdownEditor.vue` + 锁文件。原估过于乐观 |

### 9.5 原方案没提、需要补的两条

- **窗口最小化/隐藏时刻意不暂停轮询**：开销可忽略，且切回来时状态已是最新；加暂停反而要另做「恢复时补查」分支，得不偿失。
- **多窗口开同一篇天然受益**：各自轮询，脏的走提示、干净的静静跟上（内容不同才替换），与 v1.2.63/64 的互链跨窗口同步是同一套语义，**不需要额外设计**。

### 9.6 修正后的执行顺序

| 阶段 | 内容 | 碰敏感区？ | 验收 |
|---|---|---|---|
| **1（建议现在做）** | 抽 `reloadFromDiskIfSafe` + 锁一分为二 + 轮询骨架 + 提示去重 | 否 | §七 第 1、2、4、5 条 + 「提示 30s 后自己消失」 |
| 2（看体感再定） | `MarkdownEditor.vue` 同路径重载位置保持 | **是**（文档替换 watch） | §七 第 1、3 条 |

阶段 1 单独就有用户价值（不用切窗口），且完全不碰编辑器内核。

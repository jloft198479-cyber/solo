# ADR-0001 列表「转普通段落」产出的夹心形状是批准产物

- Status: Accepted
- Date: 2026-10-11（简乐拍板 A）

## Context

台账 `§二 #26` 曾认定「一张列表被切成两个容器 + 中间留 doc 层孤立段落」是 `Alt+↑/↓` 跨段挪不动的**真因**；但契约 `PROPOSAL-list-semantics.md:48` 批准「转普通段落」在顶层项产出的**正是同一个形状**（落盘串逐字相同）。同一形状、两处判据相反，必须定一个。

## Decision

这是**产品立场**问题，不是代码 bug：Markdown 里「两张列表中间插一行普通文字」只有这一种写法，「转普通段落」必然会切一下列表。

- 由**用户主动按「转普通段落」**产生的这个形状 = **契约批准的正确产物，不修、不许改**
- 由**误操作 / Shift+Tab / 行首退格**产生的 = **缺陷**，那几条已修（见 §二 #26、#55）

判据公式：先问「这是不是用户按转段落得来的」。

## Consequences

- 正面：判据冲突消灭，不必为消除该形状而砍功能
- 负面：`Alt+↑/↓` 跨段落换位移不动，成为**格式硬限制的已知代价**
- 残余诉求的正解在**换位本身**（跨非列表块换位 / 拖拽换位，见 `docs/PROPOSAL-list-row-drag.md`），**不靠拦住「转普通段落」**
- 被否的两个备选（记录以免重提）：B 先挪到列表末尾再转 —— 用户的行会跳位置；C 中间项按住不响应 —— 砍功能，用户会以为坏了

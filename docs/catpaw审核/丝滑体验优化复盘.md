## 一、背景与目标

### 1.1 前置条件

Phase 1-6 性能优化已全部完成并通过第三方审查（tag `phase-1-5-complete` + Phase 6 commit `929f770`），覆盖：

- 图片尺寸占位 / 序列化缓存 / 外部文件监听

三件套全绿：1119 tests passed + `vue-tsc --noEmit` + `bun run build`。

### 1.2 问题定义

用户反馈：**"快但不丝滑"**。

具体表现（1-5 万字区间）：

- 滚动时有偶发的 layout hitch（布局跳变导致的"咯噔"感）
- ProseMirror 偶发长帧（diff 计算或 decoration 重建）
- IME 合成阶段有轻微延迟

### 1.3 目标

从"快"（计算层已优化到位）到"丝滑"（感知层优化），参考标杆产品 Linear / Raycast / iA Writer / Notion 的动效一致性。

## 二、方案设计（6 维度）

| 维度                    | 优先级 | 核心思路                                                          | 参考产品         |
| ----------------------- | ------ | ----------------------------------------------------------------- | ---------------- |
| 动效 token 统一         | P0     | 收敛散落的 `0.15s ease` / `0.2s ease` / `0.25s ease` 为统一 token | Linear / Raycast |
| 滚动惯性感              | P1     | RAF + lerp 插值替代原生 wheel 滚动，产生 iOS 式滑行               | iOS / Notion     |
| content-visibility 估值 | P1     | 段落/标题分级估值，减少首次滚动跳变                               | —                |
| 视图切换过渡            | P2     | 编辑器↔图片预览 crossfade                                         | Notion           |
| 微交互触感              | P2     | 按钮按压 scale + 弹簧曲线回弹                                     | Raycast          |
| 入场编排                | P3     | 窗口显示后编辑器和状态栏分层淡入                                  | Linear           |

### 2.1 P0：动效 token 统一

**设计意图**：丝滑的核心不是"动效多"而是"一致"。Linear / Raycast 全局用同一时长、同一曲线，比"这儿弹那儿滑"的不一致感更跟手。

**新增 token**：

```css
--motion-fast: 120ms;
--motion-base: 200ms;
--motion-deliberate: 350ms; /* 新增：慢动效（入场编排） */
--ease-out: cubic-bezier(0.2, 0.8, 0.2, 1);
--ease-spring: cubic-bezier(0.34, 1.56, 0.64, 1); /* 新增：弹簧回弹 */
```

**改动范围**：18+ 文件，35+ 处硬编码 `transition` / `animation` 值替换为 `var(--motion-*) var(--ease-out)`。

### 2.2 P1a：滚动惯性感

**设计意图**：用 JS 拦截 `wheel` 事件，通过 RAF + lerp 插值平滑滚动位置，模拟 iOS 的惯性感。

**核心实现**（`useSmoothScroll.ts`，93 行）：

- 监听 `wheel` 事件，`preventDefault` 阻止原生滚动
- 记录目标位置，RAF 循环中用 lerp 系数（0.12→0.15）逐帧逼近
- 尊重 `prefers-reduced-motion`（降级为原生滚动）
- 不影响程序化滚动（`scrollTo`）和代码块横向滚动

> **这是整个优化方案中最大的失败点。详见第六节根因分析。**

### 2.3 P1b：content-visibility 估值优化

**设计意图**：`content-visibility: auto` 让屏幕外内容跳过渲染，但浏览器需要预估高度（contain-intrinsic-size）。估值偏差导致首次滚动时滚动条跳变。

**改动**：

- 段落默认估值 2rem → 4rem（审查后修正为 3rem）
- 新增标题 h1-h6 / 引用块分级估值
- 减少首次滚动时滚动条跳变幅度

### 2.4 P2a：视图切换过渡

**设计意图**：编辑器↔图片预览切换时加入 `view-switch` 淡入淡出，避免硬切。

### 2.5 P2b：微交互触感

**设计意图**：

- 按钮按压 `scale(0.97)` + `--ease-spring` 弹回
- 滚动条 thumb hover 过渡

### 2.6 P3：入场编排

**设计意图**：窗口显示后，编辑器和状态栏分层依次淡入（80ms 间隔），用 `:not(.app-entered)` 控制初始态。

## 四、第三方审查（5 个问题）

由 workbuddy 审查，逐条代码验证全部属实：

### 4.1 useSmoothScroll 程序化滚动竞争（严重）

**问题**：lerp 动画通过 `element.scrollTo(targetY)` 更新位置，这会触发 `scroll` 事件。但外部代码（大纲跳转、搜索高亮）也会调用 `scrollTo`，同样触发 `scroll` 事件。lerp 的 scroll 事件处理器会把位置"拉回"旧的 target，覆盖外部跳转。

**修复**：引入 `isLerpScroll` 标志区分 lerp 自身赋值与外部 scrollTo 触发的 scroll 事件。外部 scroll 抢入时取消 lerp 动画，避免拉回旧 target。

**教训**：拦截原生行为时，必须考虑与所有其他调用者的交互——scroll 事件是广播的，不区分来源。

### 4.2 lerp 系数注释数学错误（轻微）

**问题**：注释声称 lerp 系数 0.12 时"~20 帧（~300ms）到 95%"，但 `0.88^20 ≈ 0.088`，实际需要 ~23 帧才到 95%。

**修复**：系数改为 0.15（`0.85^18 ≈ 0.054`，~18 帧 ≈ 300ms 到 95%），注释同步修正。

### 4.3 Token 遗漏 5 文件 21 处（中等）

**问题**：P0 全量替换时遗漏了 5 个文件共 21 处硬编码值：SearchPanel / SettingsModal / SettingsSwitch / ShortcutSettingsPanel / StatusbarQuickActions。

**修复**：全部替换为 `var(--motion-fast) var(--ease-out)`。

**教训**：全量替换必须 grep 验证覆盖率，不能凭印象认为"改完了"。

### 4.4 打印入场态覆盖缺失（严重）

**问题**：P3 入场编排用 `opacity: 0` + `transform` 控制初始态，但 `@media print` 没有覆盖这些状态——打印时内容是透明的。

**修复**：`@media print` 加 `.editor-area/.statusbar-container { opacity: 1; transform: none; }`。

**教训**：`@media print` 必须显式覆盖所有运行时视觉状态类（与 v1.2.30 打印时 focus-mode 丢段落 bug 同类）。

### 4.5 段落占位值偏高（轻微）

**问题**：P1b 把段落 `content-visibility` 估值从 2rem 改为 4rem，但实际平均段落高度约 3rem，估值偏高导致滚动条偏短。

**修复**：4rem → 3rem。

## 六、失败根因分析

### 6.1 根因一：JS 拦截原生滚动是根本性方向错误

**这是最核心的失败原因。**

原生浏览器滚动是高度优化的：

- 滚动计算在 **compositor 线程**执行，不占用主线程
- 硬件加速合成，60fps 稳定
- 原生支持 momentum scrolling、overscroll behavior、scroll snap

useSmoothScroll 的做法：

1. `wheel` 事件 → `preventDefault` 阻止原生滚动
2. JS 计算目标位置
3. RAF 循环中 lerp 插值 → `element.scrollTo()` 更新位置

这引入了：

- **输入延迟**：wheel → JS handler → RAF → scrollTo，比原生 wheel → compositor → scroll 多了一层 JS 往返
- **主线程竞争**：lerp 循环占用主线程，与 ProseMirror 的 diff/decoration 争抢
- **丢帧**：主线程繁忙时 RAF 被延迟，lerp 步进不均匀 → "一格一格挪动"
- **功能丢失**：原生 momentum、overscroll 弹性效果全部消失

**类比**：像是把高速公路（compositor 原生滚动）改成了收费站（JS 拦截 + 逐帧放行），即使每个收费员都很高效，总吞吐量也必然下降。

### 6.2 根因二：全量 token 替换的批量风险

P0 一次性替换了 18+ 文件 35+ 处硬编码值。问题：

- **无法隔离问题**：用户感觉"不如以前"时，无法确定是哪个替换导致的
- **有些 transition 可能故意不同**：不同交互的动效参数可能有合理差异，统一不一定正确
- **格式兼容性风险**：transition 属性的变化可能影响 CSS 解析顺序或触发重排

### 6.3 根因三：缺乏用户实测前置验证

优化方案基于行业最佳实践（Linear / Raycast / Notion）设计，但：

- DevTools Performance 面板能测帧率，但测不了"感觉"
- 只在代码层面验证（三件套全绿），没有在真实使用场景中验证体感
- 用户实测发生在审查修复之后，此时已经是"完整方案"，回退成本高

## 七、经验教训

### 7.1 绝对不要用 JS 拦截原生滚动

> **铁律**：原生滚动跑在 compositor 线程，JS 拦截跑在主线程。前者永远比后者快。

任何试图用 `wheel` + `preventDefault` + RAF 替代原生滚动的方案，都会引入输入延迟和主线程竞争。lerp 插值看似平滑，实际在主线程繁忙时会产生不均匀步进，比原生滚动更卡。

**正确方向**：CSS-only 滚动优化（`scroll-behavior`、`overscroll-behavior`、`scroll-snap-type`）。

### 7.2 小步快跑，一次一改

> **铁律**：一次只改一个维度，用户实测通过后再改下一个。

6 个维度一次性提交，导致：

- 无法定位哪个改动导致了回退感
- 回退时只能全删，好的改动（如 content-visibility 估值优化）也一起丢了

**正确做法**：每个维度独立 commit，用户实测确认"不比以前差"后再叠加下一个。

### 7.3 用户实测前置

> **铁律**：DevTools 测不了"感觉"，体感优化必须用户实测。

性能优化的"快"可以用数字衡量（帧率、耗时），但丝滑的"感觉"只能靠人判断。应该在第一个维度（P0 token 统一）完成后就让用户试，而不是等 6 个维度全做完才测。

### 7.4 保留独立回退能力

> **铁律**：每个优化维度应独立可回退。

本次回退用的是 `git reset --hard`，把所有改动一起丢了。如果每个维度是独立 commit，可以只 revert 导致问题的那个，保留有效的改动。

### 7.5 content-visibility 估值优化本身是好的

> **注意**：P1b content-visibility 估值优化（段落分级估值）是有效改进，但因与失败的 P1a 滚动拦截打包在同一批 commit 中，回退时一起丢了。下次可以单独再做。

## 八、未来优化方向建议

### 8.1 CSS-only 滚动优化（推荐首选）

不拦截原生滚动，只用 CSS 增强：

```css
/* 平滑滚动（程序化 scrollTo 生效，wheel 保持原生） */
html {
  scroll-behavior: smooth;
}

/* overscroll 弹性效果 */
.mk-editor-scroll {
  overscroll-behavior: contain;
}
```

优势：零 JS 开销，compositor 线程执行，不与主线程竞争。

### 8.2 compositor-friendly 动画

只使用 `transform` 和 `opacity` 做动画（compositor 线程合成，不触发 layout/paint）。避免：

- `width` / `height` / `margin` / `padding` 动画（触发 layout）
- `background-color` / `box-shadow` 动画（触发 paint）
- `border-radius` 动画（触发 paint）

### 8.3 动效 token 统一（可单独再做）

P0 token 统一的方向是对的（Linear / Raycast 的做法），失败在于和滚动拦截打包在一起。可以单独做：

1. 只统一 token，不改任何交互逻辑
2. 小批量替换，每批 3-5 个文件
3. 每批替换后用户实测确认无回退

### 8.4 content-visibility 估值优化（可单独再做）

P1b 的分级估值方案是合理的，可以单独再做：

1. 段落估值用 3rem（审查修正后的值）
2. 标题 h1-h6 分级估值
3. 引用块估值

### 8.5 性能打点先行

在优化前先加 `performance.mark` / `performance.measure` 打点，量化各环节耗时。这样：

- 优化前有基线数据
- 优化后可以对比
- "感觉变差"时可以定位是哪个环节退步了

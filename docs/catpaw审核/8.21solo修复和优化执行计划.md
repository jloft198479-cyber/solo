#### ⚠️ P1-01 · setContent 事务污染撤销栈

| 字段         | 值                                                                       |
| ------------ | ------------------------------------------------------------------------ |
| **合并编号** | M-01                                                                     |
| **来源**     | S4 P0-A, S3 P0-2, S6 P3-A                                                |
| **级别**     | P0 · 数据安全                                                            |
| **风险**     | **高** — Ctrl+Z 退回旧文档内容，保存即覆盖文件                           |
| **难度**     | 低（核心修复几行代码），但需复杂推理确保不破坏现有切换流程               |
| **文件**     | `src/components/Editor/MarkdownEditor.vue`（watch handler，约 L217-238） |

**问题描述**：切换文档时，`setContent()` 创建的事务被推入 PM history 栈。用户切到文档 B 后按 Ctrl+Z，会一步退回文档 A 的内容。若此时触发自动保存（500ms 防抖），A 的内容会被写入 B 的文件——**静默数据损坏**。

**修复方向**：`setContent` 时给事务附加 `addToHistory: false` filter，或用 `view.dispatch(view.state.tr.setMeta('addToHistory', false).replaceWith(...))`。需确认 TipTap 的 `editor.commands.setContent()` 是否透传此 meta——实测代码中 `setContent` 已传 `{ emitUpdate: false }` 但未处理 history。

**复杂推理点**：

1. `emitUpdate: false` 只是抑制 `onUpdate` 回调，不影响 history
2. 需确认 PM 的 `history` 插件是否尊重 `addToHistory: false` 事务 meta
3. 修复后需验证：切换→Ctrl+Z 不会退回旧文档；切换→编辑→Ctrl+Z 正常回退编辑步骤
4. 需同时检查 `file.ts` 的 `syncEditedContent()` 在切换时的脏态判定是否受影响

**验证方法**：

- 打开文档 A（有内容），切换到文档 B，按 Ctrl+Z → 应停留在 B，不退回 A
- 打开文档 A，编辑后切换到 B，按 Ctrl+Z → 应回退 B 的编辑（不影响 A）
- `bun run test` roundtrip 测试全通过

#### ⚠️ P1-02 · exit_app 只检查焦点窗口脏态，其他窗口数据丢失

| 字段         | 值                                                                                                                                                                            |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **合并编号** | M-10                                                                                                                                                                          |
| **来源**     | S8 P1-S8-1, S8 P3-S8-1                                                                                                                                                        |
| **级别**     | P0 · 数据安全（多窗口场景）                                                                                                                                                   |
| **风险**     | **高** — 多窗口场景下应用级退出只检查焦点窗口                                                                                                                                 |
| **难度**     | 中 — 需遍历所有窗口状态并设计跨窗口保存确认流程                                                                                                                               |
| **文件**     | `src/composables/useAppWindowSession.ts`（exit handler，约 L229-235），`src-tauri/src/commands/window.rs`（exit_app，约 L162-166），`src-tauri/src/state.rs`（LoadedWindows） |

**问题描述**：用户在 A 窗口编辑（未保存），在 B 窗口按 Cmd+Q。`exit_app` 只检查 B 窗口的 `isDirty`，A 窗口的修改被直接丢弃。`state.rs` 的 `LoadedWindows` 只在创建窗口时写入，退出时从未被读取遍历。

**修复方向**：

1. 前端 `exit_app` handler 遍历所有已打开窗口的脏态（需跨窗口状态共享——可通过 Rust 侧 `LoadedWindows` + IPC 查询每个窗口的 `isDirty`）
2. 若任一窗口有未保存内容，弹出确认对话框（列出窗口标题）
3. 用户确认后逐窗口保存再退出

**复杂推理点**：

1. 跨窗口脏态获取：前端无直接访问其他窗口 Vue store 的能力，需通过 Rust IPC 中转或全局事件广播
2. `LoadedWindows` 当前只存 `{ label, url }`，需扩展存储 `isDirty` 状态或增加查询命令
3. 确认对话框的交互设计：是列出所有脏窗口让用户批量选择保存，还是逐个弹窗？
4. macOS 的 `Cmd+Q` 与 Windows 的关闭按钮行为差异需分别处理
5. 与 P1-01 的依赖关系：如果 P1-01 未修复，切换后的脏态判定本身就有问题

**验证方法**：

- 开两个窗口各编辑不同文件（不保存），在其中一个按 Cmd+Q → 应提示两个文件都有未保存内容
- 开两个窗口，一个干净一个脏，按 Cmd+Q → 应只提示脏窗口
- 单窗口场景回归测试：正常退出流程不受影响

#### ⚠️ P1-03 · rename 成功 + 写内容失败导致保存死锁

| 字段     | 值                                                                          |
| -------- | --------------------------------------------------------------------------- |
| **来源** | S7 P1-S7-1                                                                  |
| **级别** | P1 · 流程死锁                                                               |
| **风险** | **中** — 文件名改了但内容没写进去，后续保存永久卡死                         |
| **难度** | 低-中                                                                       |
| **文件** | `src/composables/useDocumentSession.ts`（saveCurrentDocument，约 L267-292） |

**问题描述**：保存流程中先 `rename` 后 `persist_content`。若 rename 成功但写内容失败（如磁盘满/权限变更），`store.path` 已更新为新路径但内容未写入。下次保存时再次 rename（旧路径→新路径），但旧路径已不存在 → 永久失败。

**修复方向**：将 rename 和 persist 拆为两阶段——先 persist 到新路径成功后再 rename，或失败时回滚 `store.path` 到旧值。

**复杂推理点**：

1. persist-then-rename 的原子性：先写新文件再删旧文件更安全，但需处理临时文件命名
2. 回滚路径需考虑 `store.savedContent` 和 `store.originalContent` 的同步更新
3. 需确认 Rust 侧 `rename_file` 是否幂等（同路径 rename 是否报错）

**验证方法**：

- 模拟 persist 失败（如目标路径设为只读目录）→ 确认 `store.path` 不变，可重试保存
- 正常 rename + persist 成功 → 确认旧文件被正确重命名

#### ⚠️ P3-02 · 搜索高亮缓存缺 doc 检查

| 字段         | 值                                                                                                                            |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| **合并编号** | M-08                                                                                                                          |
| **来源**     | S5 P1-A, S6 P2-E                                                                                                              |
| **级别**     | P1 · 正确性                                                                                                                   |
| **风险**     | 中                                                                                                                            |
| **难度**     | 中 — 需同时更新高亮位置和 currentMatches 的 pos                                                                               |
| **文件**     | `src/components/Editor/tiptap/extensions/search-highlight.ts`（约 L46-52），`src/components/Editor/tiptap/useEditorSearch.ts` |

**问题**：搜索高亮的 DecorationSet 缓存以 `state` 对象为 key，但未检查 doc 是否变化。用户在搜索高亮期间编辑文档，高亮位置会错位（decoration 的 pos 仍指向旧位置）。

**修复方向**：

1. 在 `decorations(props)` 中增加 `props.doc === cachedDoc` 检查
2. doc 变化时需通过 PM 的 mapping 机制更新高亮 decoration 的 pos（`DecorationSet.map()`）
3. 同步更新 `useEditorSearch.ts` 中的 `currentMatches` 数组的 pos

**复杂推理点**：

1. PM 的 `DecorationSet.map(mapping)` 可自动更新 pos，但需确认在 `appendTransaction` 还是 `decorations` 阶段调用
2. `currentMatches` 是 Vue ref，非 PM state——更新它需要找到正确的触发时机
3. 需区分"用户编辑导致 doc 变化"和"setContent 导致 doc 变化"：前者需 map 高亮，后者应清除高亮

**验证**：

#### ⚠️ P4-01 · code-block-lowlight 每事务 2× 全文档遍历

| 字段         | 值                                                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **合并编号** | M-02                                                                                                                                        |
| **来源**     | S2 P0-1, S6 P1-B                                                                                                                            |
| **级别**     | P0 · 编辑期性能                                                                                                                             |
| **风险**     | 中 — 需 fork 或 wrap 第三方插件，可能影响后续升级                                                                                           |
| **难度**     | **高** — 需深入理解 lowlight + ProseMirror 事务管线                                                                                         |
| **文件**     | `node_modules/@tiptap/extension-code-block-lowlight`（第三方源码），`src/components/Editor/tiptap/extensions/code-block.ts`（本项目包装层） |

**问题描述**：每次按键产生事务后，`code-block-lowlight` 的 `appendTransaction` 对 oldDoc 和 newDoc 各跑一次 `findChildren` 全文档遍历（找 code-block 节点），判断是否需要重新高亮。大文档（1000+ 代码块）下，每次按键 4 次 O(n) 遍历中有 2 次来自这个插件。

**根因**：第三方插件源码中无"光标不在 code-block 内则短路"的前置检查。它无法知道哪个 code-block 被修改了，只能全量扫描比较。

**修复方向**（按侵入性从低到高）：

1. **Wrap 方案（推荐先试）**：在本项目的 `code-block.ts` 包装层中，覆写 `appendTransaction`——先用 PM 的 `transaction.steps` + `mapping` 判断是否有 step 影响了 code-block 节点的文本内容，没有则返回 null 短路
2. **Patch 方案**：直接 patch `node_modules` 中的 `appendTransaction`，增加 `oldDoc === newDoc` 或 `transaction.docChanged === false` 短路（但每次 `bun install` 后会被覆盖）
3. **Fork 方案**：fork `@tiptap/extension-code-block-lowlight`，在 fork 中增加增量高亮逻辑（只对受影响步的 code-block 重新高亮）

**复杂推理点**：

1. PM 的 `transaction.steps` 可以判断修改范围，但 code-block 内编辑的 step 类型（ReplaceStep）与块外编辑相同，需通过 `mapping.map(oldPos)` 判断受影响区间是否落在 code-block 节点内
2. `appendTransaction` 返回 null 表示"不需要追加事务"——短路返回 null 是安全的
3. `oldDoc.findChildren` 和 `newDoc.findChildren` 的比较目的是检测 code-block 内容是否变化——如果用 step 判断已知无 code-block 变化，可安全跳过
4. Wrap 方案需确认 TipTap 的扩展合并机制是否允许覆写 `appendTransaction`（需检查 `Extension.extend()` 的行为）
5. 如果选择 Fork 方案，需在 `package.json` 中用 `resolutions` 或 `overrides` 字段指向 fork 版本

**验证方法**：

- 大文档（500+ code-block）连续打字，DevTools Performance 录制确认 `appendTransaction` 耗时显著下降
- 代码块内编辑→语法高亮正常更新
- 代码块外编辑→代码块高亮不变
- `bun run test` roundtrip 测试通过

#### ⚠️ P4-02 · markdown-input scanHeadings + decorations 全文档遍历

| 字段         | 值                                                          |
| ------------ | ----------------------------------------------------------- |
| **合并编号** | M-03                                                        |
| **来源**     | S2 P0-2, S2 P0-3, S6 P1-C                                   |
| **级别**     | P0 · 编辑期性能                                             |
| **风险**     | 中 — 修改自定义插件内部逻辑                                 |
| **难度**     | **中-高** — 需设计增量扫描策略                              |
| **文件**     | `src/components/Editor/tiptap/extensions/markdown-input.ts` |

**问题描述**：每次按键产生事务后，`markdown-input` 插件在两个阶段各跑一次 `scanHeadings(newDoc)` 全文档遍历：

- `appendTransaction` 阶段：找第一个 pending heading（找到即返回，但遍历到找到为止）
- `decorations(props)` 阶段：遍历到底，构建 pending heading 的 decorations

WeakMap 缓存以 doc 引用为 key，但 PM 不可变模型保证每次事务都生成新 doc 引用 → 缓存对每次按键必然 miss。

**修复方向**：

1. **增量扫描**：利用 `transaction.steps` + `mapping` 判断受影响区间，只扫描受影响区间附近的 heading 节点，而非全文档
2. **两阶段共享结果**：`appendTransaction` 阶段已扫描过的结果可通过 PM plugin state 传递给 `decorations` 阶段，避免重复扫描
3. **降级方案**：如果增量扫描实现复杂度过高，可先实现"两阶段共享"消除一次遍历（2× → 1×），再考虑增量

**复杂推理点**：

1. heading 节点的 `attrs.level` 变化（如 `#` → `##`）会改变节点类型，PM 的 `ReplaceStep` 不直接反映节点类型变化——需检查 `transaction.steps` 中的 `SetNodeStep` 或 `AttrStep`
2. `scanHeadings` 的目的是找 "pending heading"（带特定 attrs 的 heading 节点），增量扫描需确保不漏掉远处的 pending heading 变化
3. `appendTransaction` 返回新事务会再次触发 `decorations`——需避免无限循环（PM 内置防循环机制，但需理解其工作原理确保不误触）
4. 两阶段共享结果不能用模块级变量（多 editor 实例会串），需通过 PM plugin state 传递

**验证方法**：

- 大文档（1000+ heading）连续打字，DevTools Performance 录制确认 `scanHeadings` 调用次数和耗时下降
- 在文档不同位置编辑→大纲面板正确更新
- `bun run test` roundtrip 测试通过

#### ⚠️ P5-01 · 无虚拟化 + 无 content-visibility

| 字段         | 值                                                                                                                                                                                                               |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **合并编号** | M-05                                                                                                                                                                                                             |
| **来源**     | S3 P0-1, S6 P0-A                                                                                                                                                                                                 |
| **级别**     | P0 · 结构性性能                                                                                                                                                                                                  |
| **风险**     | **高** — content-visibility 可能破坏 scroll-spy、搜索高亮、focus mode                                                                                                                                            |
| **难度**     | **高** — 需大量实测验证兼容性                                                                                                                                                                                    |
| **文件**     | `src/components/Editor/tiptap/editor.css`，`src/components/Editor/OutlinePanel.vue`，`src/components/Editor/tiptap/extensions/search-highlight.ts`，`src/components/Editor/tiptap/extensions/paragraph-focus.ts` |

**问题描述**：ProseMirror 不虚拟化（全文档节点常驻 DOM），`editor.css` 全篇无 `content-visibility` / `contain` 属性。大文档（10000+ 字）滚动时浏览器无法跳过离屏内容的布局和绘制，每帧全量 rasterize。

**修复方向**：

1. **content-visibility: auto（推荐先试）**：给 `.ProseMirror > *`（顶层块节点）加 `content-visibility: auto` + `contain-intrinsic-size: auto 2em`，让浏览器跳过离屏块的渲染
2. **真正的虚拟化**：改 ProseMirror 的 DOM 渲染层，只渲染视口内的节点——侵入性极大，需 fork PM，不推荐

**复杂推理点**：

1. **scroll-spy 破坏**：`content-visibility: auto` 会使离屏元素的 `getBoundingClientRect()` 返回估算值（基于 `contain-intrinsic-size`），OutlinePanel 的二分查找 scroll-spy 依赖精确的 `top` 值 → 需改用 IntersectionObserver 替代 getBoundingClientRect
2. **搜索高亮跳转破坏**：`scrollIntoView()` 到一个 `content-visibility: auto` 的元素时，浏览器会先渲染该元素再滚动，可能导致跳转延迟或闪烁 → 需测试确认
3. **focus mode decoration 破坏**：离屏块的 `.dimmed` decoration 在 `content-visibility: auto` 下不渲染，滚动到视口时才渲染 → 视觉上可能出现"淡化效果闪烁"
4. **`contain-intrinsic-size` 的值**：设太小→滚动条跳变；设太大→空白区域过多。需按平均段落高度估算
5. **打印破坏**：`content-visibility: auto` 在 `@media print` 下的行为需测试（参考 v1.2.30 的打印 focus mode 教训）
6. **浏览器兼容性**：Tauri 用 WebView2（Chromium），`content-visibility` 从 Chrome 85 起支持，需确认 WebView2 版本

**验证方法**：

- 大文档（20000+ 字）滚动 FPS 显著提升（DevTools Performance 录制对比）
- scroll-spy 大纲高亮在快速滚动时仍正确跟随
- 搜索高亮跳转目标位置准确
- focus mode 开启滚动时淡化效果无明显闪烁
- 打印输出完整（不丢段落）
- `bun run test` 通过

#### ⚠️ P5-02 · 打开即全量加载图片/mermaid/math

| 字段         | 值                                                                                                                                                                      |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **合并编号** | M-06                                                                                                                                                                    |
| **来源**     | S3 P0-3, S6 P2-C                                                                                                                                                        |
| **级别**     | P0 · 加载期性能                                                                                                                                                         |
| **风险**     | 中 — 改动面涉及 3 种 NodeView                                                                                                                                           |
| **难度**     | **高** — 需设计 IntersectionObserver 延迟渲染策略                                                                                                                       |
| **文件**     | `src/components/Editor/tiptap/extensions/image.ts`，`src/components/Editor/tiptap/extensions/mermaid-block.ts`，`src/components/Editor/tiptap/extensions/math-block.ts` |

**问题描述**：文档打开时，所有 image/mermaid/math NodeView 同步创建并触发渲染：

- image：每个 NodeView 创建时同步调 `resolveImageDisplay` IPC（路径解析+授权），N 张图=N 次 IPC
- mermaid：每个 NodeView 创建时同步调 `mermaid.render()`（CPU 密集）
- math：每个 NodeView 创建时同步调 `katex.render()`（CPU 密集）

大文档（50+ mermaid 块）打开时主线程被阻塞数秒。

**修复方向**：

1. **IntersectionObserver 延迟渲染**：NodeView 创建时只渲染占位符（skeleton），用 IntersectionObserver 监听进入视口后再触发实际渲染

3. **mermaid/math 分帧渲染**：用 `requestIdleCallback` 或 `requestAnimationFrame` 分批渲染，每帧只渲染 1-2 个块

**复杂推理点**：

1. **ProseMirror NodeView 生命周期**：NodeView 在 `update()` 被调用时可能已离开视口（PM 不销毁离屏 NodeView）→ IntersectionObserver 的 `unobserve` 时机需精确
2. **mermaid NodeView 的 `contentDOM: undefined`**：当前设计为 `isolating: true` + `contentDOM: undefined`（支持点击进入 textarea 编辑），延迟渲染需确保 textarea 在用户点击时已准备好
3. **搜索跳转到未渲染的块**：搜索结果在 mermaid/math 块内时，该块可能尚未渲染 → 需在跳转前手动触发渲染
4. **打印时未渲染的块**：与 P5-01 的打印问题类似，`@media print` 需确保所有块已渲染
5. **IntersectionObserver 的 root**：需设为 editor 的滚动容器（不是 window），否则在 editor 局部滚动时无法正确检测
6. **已有的性能优化记录**：AGENTS.md 记录了 mermaid CSP nonce 问题（v1.2.36→v1.2.38）和字体加载问题（v1.2.29→v1.2.33），mermaid 渲染链路已有复杂历史，延迟渲染不能破坏现有 CSP 兼容

**验证方法**：

- 大文档（50+ mermaid 块）打开时间显著缩短（DevTools Performance 录制对比）
- 滚动到 mermaid 块时正常渲染（有短暂加载动画可接受）
- 搜索跳转到 mermaid 块内的文本→块已渲染
- 打印输出包含所有 mermaid 图
- `bun run test` 通过

| **风险**     | 中                                                                                                                       |
| **难度**     | 中                                                                                                                       |
| **文件**     | `src/assets/styles/main.css`（`*` 过渡），`src/themes/manager.ts`，`src/components/Editor/tiptap/useEditorAppearance.ts` |

**问题描述**：主题切换时发生三层连锁：

1. CSS `* { transition: ... }` 导致全文档元素触发过渡动画 → 每帧全量 recalc style + paint
2. CSS 变量变化触发 ProseMirror decorations 全量重建
3. MutationObserver 监听到 CSS 变量变化 → 所有 Mermaid NodeView 重新渲染

**修复方向**：

1. **缩小过渡范围**：将 `* { transition: ... }` 改为只对特定属性/元素应用过渡（如 `body, .mk-editor, .ProseMirror`），而非全局 `*`
2. **Mermaid 重渲节流**：MutationObserver 回调中用 `requestAnimationFrame` + 去重，只重渲一次而非每个 NodeView 各渲一次
3. **过渡期间冻结 decorations**：主题切换期间临时禁用 decorations 重建（设置 flag，切换完成后清除）

**复杂推理点**：

1. `*` 过渡的设计意图是让所有颜色变化平滑过渡——缩小范围后部分元素会"突变"，需评估视觉可接受度
2. AGENTS.md 记录了 v1.2.30 的 crossfade 方案（`triggerContentCrossfade`，200ms opacity 0.6→1）——需确认缩小过渡范围后 crossfade 仍有效
3. Mermaid NodeView 重渲的 MutationObserver 监听的是 CSS 变量变化还是 DOM 属性变化？需读源码确认
4. 主题切换是低频操作（用户不会每秒切主题），但连锁重渲在大文档下可能卡 2-3 秒

**验证方法**：

- 大文档（10000+ 字 + 10+ mermaid 块）切换主题，DevTools Performance 录制确认主线程阻塞时间下降
- 主题切换视觉过渡仍然平滑
- mermaid 图在主题切换后正确使用新主题色
- `bun run test` 通过

#### ⚠️ P5-04 · scroll-spy 改用 IntersectionObserver

| 字段     | 值                                                    |
| -------- | ----------------------------------------------------- |
| **来源** | S3 P1-1, S6 P2-G                                      |
| **级别** | P1 · 滚动性能                                         |
| **风险** | 中 — 与 P5-01 的 content-visibility 有强依赖          |
| **难度** | 中                                                    |
| **文件** | `src/components/Editor/OutlinePanel.vue`（约 L34-70） |

**问题描述**：当前 scroll-spy 在每次滚动帧通过 `getBoundingClientRect()` 获取标题位置做二分查找。虽然已优化为二分（O(log n)），但 `getBoundingClientRect()` 仍触发一次强制布局。如果 P5-01 实施了 `content-visibility: auto`，`getBoundingClientRect()` 返回的是估算值，scroll-spy 会失准。

**修复方向**：改用 `IntersectionObserver` 监听标题元素进入/离开视口，完全消除滚动帧中的布局查询。

**复杂推理点**：

1. IntersectionObserver 的回调是异步的（在滚动之后触发），scroll-spy 的高亮会有延迟——需评估可接受度
2. 需确定"当前活跃标题"的定义：是视口顶部碰到的最后一个标题？还是视口中心的标题？当前二分查找用的是 `top <= 0`（标题在视口顶部以上），IntersectionObserver 需用 `rootMargin` 模拟此逻辑
3. 与 P5-01 的依赖：如果 P5-01 先实施，本项必须跟进；如果 P5-01 不实施，本项为可选优化

**验证方法**：

- 滚动时大纲高亮正确跟随，无明显延迟
- 快速滚动时不高亮闪烁
- 与 P5-01 同时开启时 scroll-spy 仍准确

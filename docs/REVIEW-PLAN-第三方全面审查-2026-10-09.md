# 第三方全面审查方案（2026-10-09）

> **这不是审查报告，是「作业书」。** 本文只回答一件事：**第三方要按什么口径、查哪些层、交什么货、守什么红线**。
> 执行由第三方审查者（人 或 AI Agent）完成，**本方案不含任何审查结论**。
> 基准：`master @ 6513a86` · `v1.2.57` · 2026-10-09。

---

## 0. 一句话目标

**在 solo 现有功能范围内，从产品定位一路查到代码细节，回答三个问题：① 做得对不对（是否符合自身定位）② 做得好不好（对比优秀 Markdown 软件）③ 哪里会塌（风险与债）。**

三条硬约束（越界即偏离）：

| # | 约束 | 含义 |
|---|---|---|
| 1 | **现有功能下** | 不评判「该加什么功能」的可行性，只查现有能力「真实可用度 / 保真度 / 体验度」。加功能属产品决策，不在审查范围 |
| 2 | **向优秀 Markdown 软件看齐** | 主基准 **Typora**，辅 **Obsidian / 幕布 / iA Writer**（见 §5） |
| 3 | **宏观 → 微观** | 三层递进（§4），每层产出可独立交付 |

**成功标准（可验收）**：产出一份报告 + 分级问题清单，其中**零无证据断言**——每条发现必须附「文件:行号 / 可复现输入 / 实测输出」三件套（纪律来源：`docs/project_rules：工作原则和纪律.md`）。

## 3. 审查分层总览

```
宏观 ── 产品与信息架构      ← 定位一致性 / 功能覆盖 / 入口可发现性
  │
中观 ── 模块与系统行为      ← 架构 / 性能 / 保真 / 稳定安全 / 兼容性
  │
微观 ── 代码与文档          ← 代码质量 / 文档漂移 / 测试质量
```

每层规定四件事：**审什么 · 判据 · 方法 · 产出**。

---

## 4. 分层详解

### 4.1 宏观层 —— 产品与信息架构

**审什么**

| 子项 | 具体问题 |
|---|---|
| 定位一致性 | 每个现有功能是否服务「个人化阅读 + 写作体验」？（判据 = [`solo产品精神.md`](./solo产品精神.md)）有没有功能「越界」进协作/知识库/长文档处理器？ |
| 功能覆盖度 | 对照 §5 基准，solo 在「写作器高频刚需」上有无硬缺口？（如最近文件、阅读位置记忆） |
| 入口可发现性 | 同一能力能否从多条路到达、四源是否一致：**命令面板 / 菜单 / Slash / 快捷键**（真理源 [`registry.ts`](../src/commands/registry.ts)）？有无「有实现但没有入口」的僵尸功能（先例：拖拽手柄样式类无生产者）？ |
| 减法正确性 | 已删功能（导出系统、文件树、源码模式）的**替代路径是否真的够用**？用户有感知落差吗？ |

**判据**：`solo产品精神.md` 的取舍准绳 > 「优秀软件都有」。（本项目明确反对「为对齐而加功能」，见 `archive/solo互链方案-2026-09-11.md:33`。）

**方法**：读 FEATURE-MATRIX 附 A「未实现/已删清单」；起真机（`bun run dev:tauri`）走一遍主路径。

**产出**：定位一致性结论 + 功能差距决策单（每条给「建议做/不做 + 理由」）。

---

### 4.2 中观层 —— 模块与系统行为

**审什么**

| 子项 | 具体问题 | 关键锚点 |
|---|---|---|
| 架构健康度 | 分层是否单向 DAG？旧的层级环 / 上帝文件 / 跨层单例 / 耦合热点**现状如何** | 承接 `AUDIT-REPORT-2026-09-14 §4`；查 `composables/`→`components/` 是否仍反向 import |
| 性能 | 大文档（10 万字级）输入/打开/序列化是否线性？**O(n²) 修复后新基线是多少** | `serializer.ts`、`document-scale.ts`、`code-block.ts` 分批高亮 |
| 保真 | parser/serializer/schema 三道防线是否真能抓 bug？测试网有无「假绿」 | 四张网 `roundtrip` / `fixtures` / `fuzz` / `schema-contract` + `mark-delimiter-coverage` |
| 稳定与安全 | 原子写 / 保存冲突 / 路径·URL 信任边界 / IME / 崩溃恢复 | `document.rs`、`image.rs`、`composition-freeze.ts` |
| **来源兼容性**（产品靶子） | 「别处复制来的内容能否正确显示」——粘贴 HTML/Markdown/Word/网页 的覆盖度 | `markdown-paste.ts`、`suggestion-guard.ts` |

> ⭐ **保真审查要用专门方法**：重点查三件事——**① 内容是否被静默丢弃 ② 往返是否真保真 ③ 多套 schema 是否漂移**。**核心红线**：`fixtures` 只断「两轮一致」对「稳定地丢内容」免疫 ⇒ 必须查「**首轮输出 === 输入**」这类硬判据。

**判据**：① 性能用**同口径实测**（区分纯计算 vs 含前置；同结构数据）；② 保真须参照**第三方标准实现**（markdown-it/CommonMark spec），**不能用 solo 自己当参照**（会对称复制缺陷）。

**方法**：`bun run test` 全量 + 单跑四张网；大文档用可复现输入；**若声称性能数字，必须留下生成脚本**（纪律：无可复现输入的旧基线只能定性）。

**产出**：架构现状图 + 性能实测表（新基线）+ 保真缺口清单（区分「已登记」与「新发现」）。

---

### 4.3 微观层 —— 代码与文档

**审什么**

| 子项 | 具体问题 |
|---|---|
| 代码质量 | 硬编码（尤其颜色/计数）· 死代码 · 僵尸文件 · 重复实现 · 注释掉的代码 · TODO |
| 文档漂移 | 文档描述 ⟷ 代码实际是否一致（先例：`FEATURE-MATRIX` 附录 B 6 条，如 wiki 写「2 秒自动保存」实为默认关闭） |
| 测试质量 | 断言强度 / 覆盖缺口 / 假绿风险 / 是否有「测了但测不到」的用例 |
| 一致性 | 数量类事实是否硬编码进文档（禁令 14）；命名/风格是否统一 |

**方法（⚠️ 本节可直接套用技能模板）**：本方案挂载的 `easy-code-review` 技能提供四类检查模板 —— **① 需求符合性 ② 非必要文件修改 ③ 代码质量 ④ 变更影响分析**。其中「**非必要修改检查**」对本项目价值最高（solo 改动常「牵一发而动全身」，敏感区/联动矩阵就是为此存在）。

> ⚠️ **技能适用范围声明**：`easy-code-review` 面向「**审核一次具体代码修改（diff）**」，是**微观层的一个子集工具**，**不能覆盖**宏观/中观。第三方应把它当**微观层的检查清单**用，而非本次审查的全部方法。用于 diff 审核时，先取 `git diff` / `git show`。

**判据**：文档与代码不符时**以代码为准**（但结论要指出「是文档错还是代码错」）。

**产出**：问题清单（按 §6 分级）+ 文档漂移表（文档写什么 / 代码是什么 / 影响）。

## 5. 对标基准 —— 优秀 Markdown 软件

**基准清单**（按权重）：**Typora**（主基准）> Obsidian / 幕布 > iA Writer / Ulysses / Craft（专项参考）。

**对照维度表**（每维给「solo 现状 / 基准现状 / 差距 / 是否值得追」）：

| 维度 | 对照要点 |
|---|---|
| 写作体验 | WYSIWYG 手感、焦点/打字机模式、段落间距、光标行为 |
| 结构导航 | 大纲、跳转历史、标题折叠、阅读位置记忆 |
| 输入体验 | **输入法（中文！）、粘贴保真、Slash 命令、自动补全** |
| 编辑能力 | 表格、数学、图表、脚注、Callout |
| 文件与组织 | 最近文件、多窗口、文件关联 |
| 输出 | 复制/导出/打印 |
| 性能 | 大文档打开与输入延迟 |
| 可拓展 | 主题、字体、自定义 |

**🔴 对标口径约束（三条红线）**

1. **对标 ≠ 照抄**：每条差距都要过 `solo产品精神.md` 筛。solo 是「个人化阅读+写作工具」，不是知识库/协作平台。
2. **不得翻案已拍板的「不做」**：源码模式、文件树/工作区、TOC、版本历史、打字机模式待定 —— 这些在 `AUDIT-REPORT-2026-09-14 §6.2` 已有决策，**除非第三方给出新证据，否则不重开**。
3. **「反超项」也要记**：solo 的 WikiLink 全家桶、Callout 12 色、多进程多窗口、脚注/Frontmatter 节点是对标优势，报告应如实记录，避免只呈现差距。

## 6. 交付物与格式

**必交**：

1. **一份审查报告**（Markdown）：按 §4 三层组织，每层「结论 + 证据 + 建议」。
2. **分级问题清单**：`P0`（数据丢失/安全/崩溃）· `P1`（功能性缺陷）· `P2`（体验/结构债）· `P3`（打磨）。
3. **差距决策单**：对标 §5 的每条差距，给「建议做/不做 + 理由 + 成本估计」。

**每条发现的强制格式**（缺一即不合格）：

```
【P?】一句话现象
证据：<文件>:<行号>  ·  <可复现输入/命令>  ·  <实测输出>
影响：谁会遇到 / 后果多严重
建议：怎么改（不改也行，说明理由）
```

**禁止**：
- ❌ 无证据的确定性断言（「可能是…」要显式标注为推测）
- ❌ 报「数量」不给清单（写「共 N 处」必须把 N 处列出来）
- ❌ 引路径/行号不回查（引之前先确认存在）

## 7. 第三方须知（红线与工具）

**🔴 只读审查**：**不改代码、不 git commit、不 git push**。**如需「改代码做反向校准实验」（临时改坏验证防线能抓），必须先在沙盒内进行并获用户同意**（临时产物归口与清理纪律见 [`AGENTS.md`](../AGENTS.md) §1）——**默认交由 owner 执行**。

**不得执行的操作**：
- 🚫 删文件 / 装依赖（`AGENTS.md` §1 禁令 15）
- 🚫 把 `docs/archive/`、`.trae/`、`.opencode/` 当规则来源
- 🚫 绕过安全闸门（不得设 `CODEBUDDY_SAFE_DELETE_ENABLED=0`）

**验证命令（三闸门 + Rust）**：

```bash
bun run test                 # 全量测试（含 markdown 保真四网）
npx vue-tsc --noEmit         # 类型闸门
bun run build                # 前端构建闸门（注意 dist 清理会被安全闸门拦，见 RELEASE_PROCESS §11）
bun run dev:tauri            # 行为层真机核查（时序/UI/IME 类问题必须走这步）
# Rust：cargo check（本机需 MSVC 环境；agent 托管 shell 的坑见 BUILD_GUIDE §4.3）
```

**运行时注意**：
- **dev ≠ release**：CSP / prod-only 问题必须在 `tauri build` 后的 release 二进制上验（禁令 9）。
- **单测 ≠ 通行证**：时序/UI/IME/异步类结论，**必须有真机手感证据**（人工或 CDP 探针），单测只是入场券（禁令 13）。

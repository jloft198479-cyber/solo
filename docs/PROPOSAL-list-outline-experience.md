# 列表区幕布式大纲体验（执行分案）

> **落地情况（2026-10-08）**：**阶段 1、2 已实现**并本地提交（`0e534ba` → `fa133f9` → `17b5037` → `37f6aee`），等真机手感验收；**阶段 3、4 经简乐决定不做**（本文档后续只作设计记录）。
> 下表"改动清单"是当时的**设想**，实际落点与出入见 §九「落地记录」——阶段 1 的顶层导轨做出来后已按审美移除。

## 一、目标与非目标

### 目标

把**文档中的列表内容**呈现为幕布（Workflowy / 幕布）式的**可折叠、可聚焦的层级树**：

- 层级一眼看清（树状视觉）
- 能折叠/展开某个节点及其全部子孙
- 能"聚焦"某个节点——只显示它这一支，其余淡出
- 树状手感（键盘缩进/反缩进/整项挪动）

### 明确的非目标（越界即返工）

| 不做                                     | 原因                             |
| -------------------------------------- | ------------------------------ |
| ❌ 不把整篇文档转成幕布大纲                         | 用户 2026-10-08 明确：只动列表，其余原样     |
| ❌ 不改标题 / 段落 / 代码块 / 表格 / Callout 的任何渲染 | 非列表区"保持不变"是硬要求                 |
| ❌ 不做 markdown 语法变更                     | 列表嵌套本就是标准 markdown，**文件格式零改动** |
| ❌ 不做思维导图 / 节点连线图                       | 已评估并由用户否决（次要需求）                |
| ❌ 不引第三方 outliner / 思维导图库               | 会引入第二套数据结构，撞保真红线（见 §五）         |
| ❌ 不改 schema / parser / serializer      | 本方案不产生新语法，无触碰必要                |

---

## 二、关键前提：这个功能**不会改动文件格式**

这是本方案最重要的安全论点，必须先讲清。

**事实**：列表的层级缩进**本来就是标准 Markdown**。用户文档里已存在的嵌套列表：

```markdown
- 父节点 A
  - 子节点 A1
    - 孙节点 A1a
- 父节点 B
```

存盘就是这段文字，别的 Markdown 阅读器打开显示的就是这个层级。**我们不需要为此发明任何语法。**

**所以本方案做的是**：给这套已有的"子抽屉套娃"加一层**显示 + 交互**的外壳（连线、折叠箭头、聚焦淡出）。

比喻：抽屉本来就是套娃结构。幕布只是给套娃加了**可推拉的隔板（折叠）**&#x548C;**只开一支看（聚焦）**&#x7684;便利，**箱子本身（文件内容）一点没动**。

推论（决定了本方案的风险等级）：

- ✅ round-trip 保真**零风险**——不碰 parser/serializer/schema，不需要跑保真三道防线
- ✅ 脏态判定（`syncEditedContent` 语义比对）**零影响**——折叠/聚焦是纯视图层
- ✅ 「打开即显示未保存」不可能发生——文档内容逐字节未变
- ✅ 老用户单文件升级**零感知**——默认全展开，行为与现在完全一致

## 三、改动清单（全部基于已核实的代码事实）

### 阶段 1：树状视觉（纯 CSS，零 JS）

**唯一改动文件**：`src/components/Editor/tiptap/editor.css`（现有列表样式在 397–455 行）

**现状核实**：

```css
.tiptap-editor ul { list-style-type: disc; padding-left: 1.5em; }
.tiptap-editor li { margin: calc(var(--mk-paragraph-spacing) * 0.2) 0; }
.tiptap-editor li::marker { color: var(--text-secondary); }
```

现状是**普通无序列表**：只有 `disc` 圆点 + 缩进，**没有任何"这是一棵树"的视觉连接**。

**改什么**：

1. 加层级引导线（`border-left` + 逐级递进的浅色），让父子关系一眼可辨
2. 列表容器左侧加一条**淡色导轨**（"这是大纲区"的视觉边界，满足"明确区分列表/非列表"）——**已实现后又移除**，原因见 §九
3. 缩进节奏微调，让层级递进更清晰

**风险**：极低。纯装饰，不碰 DOM 结构、不碰逻辑。  
**回滚**：删掉这段 CSS 即可，零副作用。

---

### 阶段 2：折叠 / 展开（1 个 PM 插件）

**新增文件**：`src/components/Editor/tiptap/extensions/list-fold.ts`（**唯一新增文件**）

**做法**：

- 插件 state 存"哪些 listItem 被折叠"（位置集合），随事务 `map` 平移
- 装饰层给**有子项的 listItem** 挂一个折叠箭头（widget）
- 折叠时给被隐藏的子孙节点挂 `display: none` 装饰

**必须遵守的两条铁律**（否则会有衍生 bug）：

| 铁律                                                                  | 依据                                                                                                                              |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **装饰必须走 `composition-freeze`**——组字期只 `mapFrozenDecorations` 平移，绝不重建 | `composition-freeze.ts:9` 明写"新增任何 decoration 必须遵守"；重建会换掉正在组字段落的 DOM → **IME 候选窗失锚**（本项目已有血泪案例，`topics/ime-candidate-window.md`） |
| **大文档自动降级**——`isHeavyDocument()` 为真时不建装饰                            | 照抄 `paragraph-focus.ts:112` 现成先例；`document-scale.ts` 定义 heavy=50 万字符，且 `doc-heavy` 档会开 `content-visibility`，与折叠装饰叠加有风险          |

**范本**：`paragraph-focus.ts` 已经把这件事做了一遍——它就是用装饰层做"聚焦淡出"、走组字总闸、heavy 降级。**折叠是同一个模式的另一个应用**，照抄结构即可，不是新发明。

**为什么不用第三方 outliner**：那会引入独立于 PM 文档的第二套树数据结构，两份数据要双向同步——这是保真地狱（AGENTS 敏感区第 15/16 条正是防这个）。

---

### 阶段 3：聚焦子树（复用现成零件）——**未做（简乐 2026-10-08 决定不做）**

**做法**：点一个列表项 → 只显示它这一支，其余淡出；顶部显示面包屑逐层跳出。

**复用**：`par`<u>`agraph-`</u>`focus.ts` 的淡出机制（装饰 class + swapActiveBlock 增量更新）**已经存在且已验证**，只需把粒度从"顶层块"扩展到"列表子树"。

**风险**：中。低——因为是既有机制的参数化扩展，不是新机制。

---

### 阶段 4：键盘树操作（增量最小）——**未做（简乐 2026-10-08 决定不做）**

| 键                   | 动作       | 现状                     |
| ------------------- | -------- | ---------------------- |
| `Tab` / `Shift+Tab` | 缩进 / 反缩进 | ✅ **已有**，不需新增          |
| `Enter`             | 新建同级项    | ✅ **已有**，不需新增          |
| `Alt+↑/↓`           | 整项上下移动   | ❌ 需新增（约 30 行，一个 PM 命令） |

**极简原则**：只补唯一缺失的那一个（`Alt+↑/↓`），已有的绝不重写。

## 六、衍生 bug 风险清单（逐条预判 + 对策）

| 风险                  | 触发条件                                             | 对策                                                          |
| ------------------- | ------------------------------------------------ | ----------------------------------------------------------- |
| **IME 候选窗失锚**       | 折叠装饰在组字期重建 DOM                                   | 走 `mapFrozenDecorations`，组字期只平移（照 `paragraph-focus.ts:126`） |
| **大文档卡顿**           | 50 万字文档开折叠                                       | `isHeavyDocument()` 降级，不建装饰（同 `paragraph-focus.ts:112`）     |
| **折叠状态错位**          | 折叠后编辑上方内容，位置偏移                                   | 位置集合随事务 `map` 平移；折叠态**只存视图层不进文档**                           |
| **与任务列表 flex 布局打架** | 箭头 widget 塞进 `li` 影响 checkbox 对齐                 | 阶段 2 单独验收任务列表；箭头用绝对定位，不改 `display:flex`                     |
| **折叠状态影响复制/查找**     | 折叠后全选复制                                          | 装饰不改文档 ⇒ 复制内容不变（天然安全，需验证）                                   |
| **单文件升级错乱**         | 打开旧文件残留折叠态                                       | 插件 state 随文件重建；切文件时重置（同 `isWholeDocReplace` 判定）             |

**最大风险源是阶段 2**（折叠装饰碰组字态）。因此建议阶段拆分独立验收，阶段 1 先行。

```
阶段 1  树状视觉（纯 CSS）              → 独立验收
阶段 2  折叠/展开（唯一新插件）         → 独立验收（重点验 IME + 任务列表）

```

每阶段独立可回滚、独立提交、独立验收。任一阶段有衍生 bug 就地停下，不带病进下一阶段。

## 八、待简乐拍板的开放问题

1. **是否需要"大纲模式开关"**？（默认全展开 + 随时可折叠 vs 整个列表区切成节点视图）
   - 我的建议：**不需要**。默认全展开、每项带折叠箭头，即是幕布手感本身，不加模式开关（少一个状态、少一处分支 = 少一处 bug）。
2. **折叠状态要不要跨会话记住**（下次打开还保持折叠）？
   - 我的建议：**不记**。属视图态，持久化会引"文档内容变了但折叠态没变"的错位问题，不值得。

---

### 与原设想的出入

1. **顶层淡色导轨已移除**：它与箭头的正确水平位置落在同一列，会撞车。简乐明确"线不重要"，故去掉。保留下来的是**嵌套列表的竖引导线**（`li > ul/ol` 的 `border-left`，挂在子列表左沿、不切圆点）。
2. **箭头改为"悬停该行才浮现"，判定挂在该行的段落上而非整个 `li` 上**：对齐幕布"鼠标悬浮在主题上时圆点前面出现展开/收起图标"。挂 `li` 会导致悬停子行时父行箭头一并点亮（`li` 是子行的祖先）。
3. **垂直对齐改用「整行高盒居中」而非写死 em 偏移**：`top: 0` + `height: calc(var(--mk-line-height) * 1em)` + `align-items: center`，与项目符号同一水平线。靠 em 猜 marker 位置不可靠（浏览器 marker 定位不定）。

### ⚠️ 必须记住的 DOM 事实（改这两个选择器前先看这里）

**待办项的正文不在 `li` 的直接子级。** `@tiptap/extension-list` 的 `TaskItem.renderHTML` 产出的是 `li > label + div`，正文段落与嵌套列表都在那个 `div` 里；且 `editor-extensions.ts` 配了 `nested: true`，**待办项是可以挂子列表的**。

⇒ CSS 里这两个选择器**必须用后代选择器**，否则只对无序/有序列表生效、待办列表**静默失效**：

- `.tiptap-editor li p`（箭头 `position: relative` 锚点）——写成 `li > p` 会让待办项箭头丢掉锚点、跑到容器外
- `.tiptap-editor li ul` / `.tiptap-editor li ol`（嵌套引导线）——写成 `li > ul` 会让待办项漏画线

该约束已由 `extensions/__tests__/list-fold.spec.ts` 的 DOM 契约用例锁住（TipTap 若改 `renderHTML` 会立刻转红）。

### 一处主动补的行为：光标落进隐藏区自动展开

折叠之后，方向键下移 / 大纲面板跳转 / 查找命中都可能把光标送进 `display: none` 的区域，出现"光标在哪看不见"。故 `apply` 里加了 `revealFoldedAtCursor`：光标落在已折叠项的隐藏子树内就展开该项（纯视图态操作，不回写文档；组字期不执行，避免重建装饰扰动 IME）。

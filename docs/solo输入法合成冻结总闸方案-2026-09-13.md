# solo 输入法「合成冻结总闸」执行方案

> 状态：**提案，待用户拍板**。本文只做方案，不含任何已落地代码改动。
> 方向已定：保持 Typora 式纯所见即所得（不换引擎），用**一道总闸**根治，不再渐进打补丁。

---

## 0. 一句话（给非代码读者）

打中文时，输入法需要"你正在打字的那块屏幕区域纹丝不动"，它才能把候选小窗贴准。
solo 的卖点是"边打边把 `#`、`*`、`/` 实时变成标题、加粗、菜单"——等于在输入法最需要静止的时候一直动它，小窗就跟丢、飘走、塌成小块。
**本方案：拼字期间让编辑区整体"定格"，等你把字上屏后再一次性补做所有变化。** 用一道总闸管住所有会动屏幕的地方，而不是像现在这样哪儿漏堵哪儿。

---

## 1. 根因（第一性原理）

不是 WebView2 / 系统缺陷——否则所有用 WebView2 的软件（VS Code、Slack、Teams、无数 Tauri/Electron 应用）打中文都会飘，而它们不飘。

真正根因是**架构性的**：solo 让**同一个 contenteditable 同时承担两个角色**——
1. 输入法拼字的"落笔面"（composition surface）；
2. markdown 实时渲染的"重画面"（render surface）。

输入法（经 TSF/IMM）靠浏览器报告的**光标矩形**决定候选窗贴哪儿；浏览器又靠 DOM 算这个矩形。拼字期间只要 DOM 被改、版式被重排，光标矩形就失真，候选窗即失锚。solo 的整个设计就是在拼字期间不停改这块 DOM。

**外部佐证（真实根治案例）**：Markra 2.0.0《为了修好中文输入法，我重写了编辑器内核》给出同一条铁律——
> 「输入法合成期间，视觉层应该尽量保持安静。」
并点名两类肇事者：① 合成期重新解析 / 折叠语法 / 重建预览；② **浮动工具条抢焦点**。它自己选择换引擎（CodeMirror 6）实现该原则；本方案在**不换引擎**的前提下，用同一原则落地。

> 注：Markra 还指出另一类症状——mark 边界处上屏文字落错位置/继承错格式（多层位置映射歧义）。本方案的"合成期定格"同样覆盖该类，因为定格期间不做任何 mark 折叠/结构变身。

## 3. 关键设计约束（实现前必须钉死，否则会做错）

1. **🚫 不能用全局 `dispatchTransaction` / 包裹 `view.dispatch` 来"一律挡掉合成期事务"。**
   ProseMirror 内部的合成事务（浏览器落的拼字文字）与应用发起的事务走**同一条通道**，无可靠公开标记区分。全局拦截会**连用户打的字一起挡掉**，输入直接坏。
   → 总闸**不是"一个拦截点"**，而是**"一份共享契约 + 各变更入口主动接入"**。这是 PM 分布式架构决定的，必须如实接受，别幻想一个魔法开关。

2. **composing 权威信号 = `view.composing`（浏览器）。** 插件 `state.apply` / `appendTransaction` 拿不到 view → 沿用现有"工厂闭包登记 `liveView`"套路，但**统一到共享模块**，不再每插件各存一份。

3. **"定格"的准确定义**：合成期间只允许**浏览器自己的合成文字**落地；其余一切（结构变身、装饰重画、菜单定位/重渲、nodeview 重建）**暂停**，推迟到 `compositionend` + settle 之后**统一补做**，且补做**绝不落在下一次合成进行中**。

4. **退化安全**：freeze 逻辑任何异常都不得卡死输入——宁可"少冻结"（退回当前行为）也不能"挡掉合成文字"。共享模块对 `liveView` 缺失/销毁要有兜底。

## 4. 方案架构：`composition-freeze` 共享总闸

新增单一模块（建议 `src/components/Editor/tiptap/composition-freeze.ts`），作为**唯一真相源**：

**职责**
- **权威 composing 状态**：由 `compositionstart/update/end` + `view.composing` 共同维护，对外只暴露 `isFrozen()`。
- **集中 settle 调度**：统一管理"上屏后延迟补做"，**新合成一开始即取消所有未决 flush**（根治漏洞 B 的连打竞态——现在这个判断散在 markdown-input 两处定时器里，收敛到一处）。
- **延迟队列 `defer(fn)`**：合成期被暂停的动作入队，`compositionend`+settle 后按序 flush；保证**不丢、不重、时机对**。
- **`frozenDecorations(oldSet, tr, newDoc)` helper**：合成期"只 map 平移、不重建"的统一实现（替代 4 份内联副本）。

**各入口接入（把散守卫收敛 + 堵漏洞）**
- `markdown-input.ts`：
  - `appendTransaction` 改查共享 `isFrozen()`（行为等价，去重）。
  - **`state.apply()` 的 pending-heading 装饰改走 `frozenDecorations`**（堵漏洞 A）。
  - 两处 settle 定时器交给共享 scheduler（堵漏洞 B）。
- `paragraph-focus.ts` / `search-highlight.ts` / `code-block.ts`：内联 `liveView?.composing` → 共享 `isFrozen()` + `frozenDecorations`（**纯收敛，行为不变**，4 份→1 份）。
- `editor-extensions.ts` 三个浮动菜单：`onStart/onUpdate` 加 `isFrozen()` 守卫——**合成期不 `clientRect()`、不重 show、不抢焦点**，推迟到 flush（堵漏洞 C，对齐 Markra"浮动工具条不抢焦点"）。
- nodeview（验证项 D）：确认 `update()` 在节点未变时复用 DOM；合成期不重建 block widget。
- `MarkdownEditor.vue`：注册 freeze 插件（置于插件序列**最前**，先于一切装饰/变身插件建立 composing 状态）。

**完整性保障（治"尚未暴露、终将出现"）**
- 每个变更入口配**回归锁**（现有 `markdown-input-ime.spec.ts` / `paragraph-focus.spec.ts` / `code-block.spec.ts` 为模板；补 suggestion 菜单 + markdown-input apply 装饰两把新锁）。
- 文档化铁律 +（可选）lint：**新增任何 decoration / appendTransaction / nodeview / 浮动菜单，必须走 `composition-freeze`**。这样未来功能自动被总闸管住，不会再漏。

## 5. 边界与风险（逐项处理/验证）

- **连打多词竞态**：flush 只能落在"上一词上屏、下一词未起"的缝里；新合成开始即取消未决 flush（集中调度保证）。
- **叠加场景各验一遍**：焦点模式开 / 搜索框开 / 大文档（content-visibility 开）/ 代码块内，四种叠加下总闸都须正确定格+正确放行。
- **nodeview 稳定性（D）**：公式/图表/图片/callout 在相邻段落拼字时不得重建。
- **大文档叠加（E）**：content-visibility 的 containment 本身会干扰光标矩形；普通文档已关闭，大文档场景需真机确认是否仍失锚，必要时合成期临时降级。
- **退化安全**：见 §3.4。

## 8. 影响面评估（性能/功能）

- **性能**：合成期做**更少** DOM 工作（暂停重画）；非合成路径（英文、滚动、保存、渲染）**零影响**（总闸休眠）；排队补做的开销可忽略、拼完即清。
- **功能**：拼字窗口内本就不该有功能抢动界面，暂停不误伤任何即时反馈；**顺手修掉** `/中文粘屏`（漏洞 C）与连打竞态（漏洞 B）。
- **唯一可感知点**：上屏后"变身/重画"延后一小拍补做——**这就是现状行为**（标题本就停顿后才变），非新增延迟。
- **代价**：闸门开合时机必须分毫不差（§5），靠"先原型验证再推全量"兜底。

## 11. Buddy 评审（2026-09-13，HEAD=b9ab2f4）

### 已核对属实的部分（可执行）

- §2 现状清单逐条在代码里对上：4 份 `let liveView` 内联副本、`markdown-input.ts:160` 的 apply 装饰无 composing 判断、`editor-extensions.ts` 三个 suggestion 的 `onStart/onUpdate` 零守卫。
- §3 的约束是对的且必须遵守：**不能**在 `view.dispatch` 上全局拦截（合成事务与应用事务同通道，会连用户打的字一起挡）。
- §6 的**分阶段 + 回滚锚点**思路正确。**P0 已于 21a028b 落地**（纯重构、行为等价）：新增 `src/components/Editor/tiptap/composition-freeze.ts`，4 处守卫迁入，新增模块契约测试 9 例；vitest 1322 全绿 / `vue-tsc` 干净 / eslint 干净 / build 通过。

### ⚠️ 被证据推翻的部分（不要再照做）

1. **漏洞 A 的因果链不成立。** 方案称「apply 里每个 docChanged 都 remove+add 装饰 ⇒ 合成期改 DOM」。实证：`prosemirror-view/dist/index.js:4000-4004` 的 `InlineType.eq` 是 `compareObjs(attrs) && compareObjs(spec)`——**值比较，不是引用比较**；`sameOuterDeco`（同文件 :1756）据此判定是否复用 DOM。⇒ **spec/attrs 相同的装饰「移除后原样加回」不会重建 DOM**，该处只是白做 CPU 活，**不是 DOM churn 源**。P1-A 不建议做。
2. **漏洞 B 已被现有守卫覆盖。** DOM 事件处理器与 `setTimeout` 回调不会交叠，`compositionstart` 同步置 `view.composing` 后定时器到点必然读到 true。P2-B 收益存疑、暂缓。
3. **漏洞 C 单独也不足以造成失锚。** `onStart/onUpdate` 是只读 `clientRect()`（`coordsAtPos`）+ Vue 组件在 contenteditable **之外**重渲，不移动编辑区布局。
4. **§1「不是 WebView2 / 系统缺陷」是逻辑捷径。** 「所有 WebView2 软件都该飘」这个反证不成立——本项目已有**源码级**机制证据：`RenderWidgetHostViewAura::GetCaretBounds()` 在 `!text_input_manager_->GetActiveWidget()` 时返回**空矩形**；空矩形 = TSF 无位置 ⇒ 系统把候选窗夹到屏幕右下角（实测 21 帧坐标一字不差全为 `(1340,996)`，且**只有 solo 中招**，WorkBuddy 756 帧零异常）。这与「solo 在合成期动 DOM」**不互斥也不互相印证**，不能据此排除**透明无边框窗口**与 **WebView2 运行时 152.0.4191.66** 这两个 solo 独有变量。

### 结论与建议路线

- 方案的**架构（共享契约 + 各入口接入）值得保留**，P0 已按此落地，作为后续任何守卫的唯一接入点。
- 但方案的**根因判断缺证据**：真正触发条件经 35 次自动对照实验仍**零复现**，属偶发（约 16% 会话命中）。
- 建议：**先取证再改行为**——用 §7.2 的思路做**静默度量**（合成期采样非合成 DOM 变更 + 各入口动因 + 光标矩形），跑在真实使用里，而不是先把三处守卫全加上。否则很可能又是「打地鼠」。
- §7.2 里「全量重写探针」不必重写：`.sandbox-ime/` 已有可复用的像素取证与 CDP 通路（见 `.workbuddy/memory/topics/ime-candidate-window.md`）。

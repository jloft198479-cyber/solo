## 二、Mermaid 专题：文档误标「未保存」（问题 #1 深挖）

> 这是用户报告、KNOWN-ISSUES 已记录（§二 #4）、两轮排查都确认的 bug。因为它最典型、也最容易被修错，单独成节讲透。

### 2.1 现象

打开一个含 Mermaid 图表的文档，**什么都没改**，状态栏却显示「未保存」。副作用：自动保存空转、关闭时弹无谓的「是否保存」确认框。

### 2.2 触发链（已核实的部分）

标脏的唯一入口是 `onUpdate` 里这句无条件调用：

```typescript
// src/components/Editor/MarkdownEditor.vue:257-264
onUpdate: ({ editor: ed }) => {
  const t = ed as unknown as TiptapEditor;
  fileStore.markUserEdit();   // ← 无条件标脏，问题就在这
  debouncedWordCount(t);
  debouncedOutline(t);
  debouncedSerialize(t);
},
```

那 `onUpdate` 到底什么时候被 TipTap 触发？查 `node_modules/@tiptap/core/dist/index.js:6103` 的源码：

```javascript
// 只有「非 preventUpdate」且「有 docChanged 事务」且「doc 真的变了」才 emit update
if (transaction.getMeta("preventUpdate")
    || !transactions.some((tr) => tr.docChanged)
    || prevState.doc.eq(state.doc)) {
  return;
}
this.emit("update", { ... });
```

再看加载文档用的 `setContent`（index.js:1218）：

```javascript
tr.replaceWith(0, doc.content.size, document2).setMeta("preventUpdate", !emitUpdate);
```

本项目加载时传的是 `setContent(doc, { emitUpdate: false })`（[MarkdownEditor.vue:274](../src/components/Editor/MarkdownEditor.vue#L274)），所以这次事务**带了 preventUpdate，本身不会触发 onUpdate**。但它**仍是 docChanged 事务**，会被别的插件看到。

接着 `markdown-input` 插件的 `view.update` 会响应**任何** docChanged（[markdown-input.ts:185-206](../src/components/Editor/tiptap/extensions/markdown-input.ts#L185-L206)），若检测到 pending heading 就排一个 300ms 后的 `forceCheck`（[markdown-input.ts:169-180](../src/components/Editor/tiptap/extensions/markdown-input.ts#L169-L180)）。`forceCheck` 通过 `setMarkdownInputState` dispatch 一个 meta 事务（[markdown-input.ts:308-310](../src/components/Editor/tiptap/extensions/markdown-input.ts#L308-L310)），再进 `appendTransaction` 全文档扫描（[markdown-input.ts:254-304](../src/components/Editor/tiptap/extensions/markdown-input.ts#L254-L304)）。

### 2.3 尚未完全定位的部分（如实标注）

「那个最终触发 onUpdate 的**非 preventUpdate 的 docChanged 事务**具体从哪来」还没 100% 抓到现行。已排除的：Mermaid NodeView 的 `renderMermaid` 只操作 DOM、**不 dispatch 事务**（[mermaid-block.ts:454/460](../src/components/Editor/tiptap/extensions/mermaid-block.ts#L454)）。可疑方向是 `forceCheck` 时机与 Mermaid 异步渲染叠加后，`appendTransaction` 链路里某个转换产出了 docChanged 事务。**这一环需要在落地时用 DevTools 打断点确认。**

### 2.4 关键纠错：KNOWN-ISSUES 给的修法①是无效的

[KNOWN-ISSUES.md §二 #4](./KNOWN-ISSUES.md) 提了两个修法，其中修法①「在 onUpdate 里判断 transaction 的 preventUpdate meta，是 true 就跳过」**不成立**——因为上面 2.2 的源码证明：TipTap 在 emit update **之前**就已经把带 preventUpdate 的事务过滤掉了，`onUpdate` 回调里拿到的事务**必然不带** preventUpdate。判断它永远是 false，等于没判断。

> 教训：照搬文档里的修法前，先读一遍框架源码确认前提是否成立。

### 2.5 修复方案：交互门控（对触发源免疫）

**核心思路**：不去纠结那个后台事务从哪来，而是换个判定标准——**只有用户真的碰过编辑器，才允许标脏**。文档加载后立一道「门」，直到收到第一个真实用户事件（键盘 / 指针 / 输入法）才放行。这样无论 Mermaid 异步渲染、`forceCheck`、还是任何未知的插件后台事务，只要发生在用户动手之前，统统被门挡住；而用户任何真实编辑（打字、点工具栏、快捷键）都必然先产生一个用户事件把门打开，不会漏标。

**这个方案的最大优点：不依赖定位触发源。** 就算那个后台事务的来源永远查不清，门控也照样有效。

```typescript
// src/components/Editor/MarkdownEditor.vue
// ── 加载门控：文档加载后暂停标脏，直到首个真实用户交互 ──
// 免疫一切插件后台事务（Mermaid 异步渲染 / forceCheck 等），不依赖定位触发源。
let userInteracted = false;

/** 文档加载 / 切换文件时重新武装门控 */
function armInteractionGate() {
  userInteracted = false;
}

/** 任一真实用户事件 → 放行 */
function releaseInteractionGate() {
  userInteracted = true;
}

// onMounted 里挂监听（capture 阶段，确保最先拿到事件）
onMounted(() => {
  const el = editorWrapRef.value;
  el?.addEventListener('keydown', releaseInteractionGate, true);
  el?.addEventListener('pointerdown', releaseInteractionGate, true);
  el?.addEventListener('beforeinput', releaseInteractionGate, true);
  el?.addEventListener('compositionstart', releaseInteractionGate, true);
  // ...其余原有逻辑
});

// onBeforeUnmount 里对应 removeEventListener（略，与上四个一一对应）

// createEditor 开头武装门控
function createEditor(content: string) {
  armInteractionGate();
  // ...原有逻辑
}

// 文件切换的 watch 里也要重新武装
watch(() => fileStore.currentFile.path, () => {
  armInteractionGate();
  // ...原有逻辑
});

// onUpdate 改为 gated
onUpdate: ({ editor: ed }) => {
  const t = ed as unknown as TiptapEditor;
  if (userInteracted) fileStore.markUserEdit();   // ← 只有用户交互过才标脏
  debouncedWordCount(t);
  debouncedOutline(t);
  debouncedSerialize(t);
},
```

**边界自检**（四层自检里的「异常级」）：
- 打开文档不动 → 后台事务触发 onUpdate，门未开 → 不标脏 ✅
- 打开就打字 → `beforeinput` 先开门 → onUpdate 标脏 ✅
- 打开就点工具栏加粗 → `pointerdown` 先开门 → 命令事务标脏 ✅
- 切文件 → watch 里重新武装 → 新文件不会被旧交互状态误标 ✅

**提速说明**：本条主要是**正确性修复**，顺带消除「误标脏 → 自动保存空转 → 无谓序列化 + IPC 写盘」的隐性开销。

## 三、高优先级问题

### 3.1 问题 #2：Rust 同步命令阻塞主线程

**现状证据**：[document.rs:19](../src-tauri/src/commands/document.rs#L19) `open_document`、[:31](../src-tauri/src/commands/document.rs#L31) `save_document`、[:60](../src-tauri/src/commands/document.rs#L60) `rename_file` 全是**同步** `fn`。

**根因（大白话）**：Tauri 里**同步命令跑在主线程**上，异步命令才跑在 tokio 线程池。主线程就像一条单车道，大文件读写是辆横在路中间的大卡车——它不动，后面所有 UI 操作（点击、滚动、打字、动画）全堵死。打开 / 保存一个几 MB 的文档，磁盘 IO 几十到几百毫秒，这段时间整个窗口是僵的。

**修复方案**：改成 `async fn`，把阻塞 IO 丢进 `tokio::task::spawn_blocking`（Cargo.toml:29 已有 `tokio rt-multi-thread`，条件满足）。

```rust
// src-tauri/src/commands/document.rs
#[tauri::command]
pub async fn open_document(path: String) -> Result<DocumentOpenResult, AppError> {
    let path_for_io = path.clone();
    let (content, last_modified_ms) = tokio::task::spawn_blocking(move || {
        let content = fs::read_to_string(&path_for_io)?;
        let last_modified_ms = read_modified_time_ms(Path::new(&path_for_io))?;
        Ok::<_, AppError>((content, last_modified_ms))
    })
    .await
    .map_err(|e| AppError::Native(format!("任务调度失败: {}", e)))??;

    Ok(DocumentOpenResult { path, content, last_modified_ms })
}

#[tauri::command]
pub async fn save_document(
    path: String,
    content: String,
    expected_last_modified_ms: Option<u64>,
    force: bool,
) -> Result<DocumentSaveResult, AppError> {
    // 冲突检查也涉及 metadata IO，一并放进 spawn_blocking
    let path_for_io = path.clone();
    let last_modified_ms = tokio::task::spawn_blocking(move || {
        let path_ref = Path::new(&path_for_io);
        if !force {
            if let Some(expected) = expected_last_modified_ms {
                if let Ok(current_modified) = read_modified_time_ms(path_ref) {
                    if current_modified != expected {
                        return Err(AppError::conflict(
                            "文件已被外部修改，请重新加载或选择强制覆盖",
                        ));
                    }
                }
            }
        }
        atomic_write(path_ref, content.as_bytes())?;
        read_modified_time_ms(path_ref)
    })
    .await
    .map_err(|e| AppError::Native(format!("任务调度失败: {}", e)))??;

    Ok(DocumentSaveResult { path, last_modified_ms })
}
// rename_file 同理：校验逻辑留在外面，fs::rename / canonicalize 进 spawn_blocking
```

**注意点**：
- `generate_handler!` 注册和 `commands/mod.rs` re-export **都不用改**（函数名不变，Tauri 自动识别 async）。
- 前端 [document.ts:29](../src/services/tauri/document.ts#L29) 本来就是 `await invokeCommand`，**前端零改动**。
- `AppError` 须是 `Send`——现有 async 命令（`fetch_font_data` 等）已编译通过，说明满足。
- `import_document_image` / `save_clipboard_image` / `authorize_image_asset` / `resolve_image_display` 也是同步 fn，含 `fs::copy` / `canonicalize`，建议一并异步化（其中 `resolve_image_display` 与问题 #6 联动）。

**提速说明**：大文件打开 / 保存从「卡死主线程几百毫秒」变为「主线程零阻塞，IO 在后台线程跑」，窗口始终可交互。这是「大文档卡顿」的头号根因。

### 3.2 问题 #3：markdown-input 每次变更两次全树扫描

**现状证据**：[markdown-input.ts:194](../src/components/Editor/tiptap/extensions/markdown-input.ts#L194) `view.update` 里 `findPendingHeading`（内部就是 `scanHeadings` 全树 `descendants`，[:466](../src/components/Editor/tiptap/extensions/markdown-input.ts#L466)）扫一遍；[:265](../src/components/Editor/tiptap/extensions/markdown-input.ts#L265) `appendTransaction` 里 `scanHeadings` 再扫一遍。

**根因（大白话）**：每敲一个键，文档变一次，这个插件就把整棵文档树**从头到尾犁两遍**——一遍在 `view.update`，一遍在 `appendTransaction`。文档越大，每键代价越高，纯属重复劳动。

**修复方案**：加 doc 级缓存。ProseMirror 的 doc 是**不可变**的，doc 引用没变 = 内容没变，缓存绝对安全。这跟 [editor-metadata.ts:22](../src/components/Editor/tiptap/editor-metadata.ts#L22) 大纲用 `WeakMap<EditorState, ...>` 缓存是同一个成熟套路。

```typescript
// src/components/Editor/tiptap/extensions/markdown-input.ts
// doc 级扫描缓存：doc 引用不变即内容不变，WeakMap 不阻止 doc 被 GC
const _scanCache = new WeakMap<PMNode, {
  emptyHeading: { pos: number; level: number } | null;
  pendingHeading: PendingHeading | null;
}>();

function scanHeadings(doc: PMNode): {
  emptyHeading: { pos: number; level: number } | null;
  pendingHeading: PendingHeading | null;
} {
  const cached = _scanCache.get(doc);
  if (cached) return cached;

  // ...原有 descendants 扫描逻辑保持不变...

  const result = { emptyHeading, pendingHeading };
  _scanCache.set(doc, result);
  return result;
}
```

**提速说明**：同一 doc 的两次扫描合并为一次，每次按键的全文档遍历从 2×O(n) 降到 1×O(n)，大文档打字跟手度直接受益。改动极小、有现成测试保护（markdown-input 有大量 IME 回归测试），风险低。

### 3.3 问题 #4：远程图片 base64 往返

**现状证据**：Rust 侧 [image.rs:28](../src-tauri/src/commands/image.rs#L28) `fetch_remote_image` 下载后把字节 **base64 编码成字符串**走 IPC（[:78-79](../src-tauri/src/commands/image.rs#L78-L79)）；前端 [image.ts:86](../src/components/Editor/tiptap/extensions/image.ts#L86) 用 `atob` + 逐字符 `charCodeAt` 循环转回 `Uint8Array` 建 Blob。

**根因（大白话）**：本来搬一张 10MB 的图就够了，结果 base64 先把它**吹大到 13.3MB**，塞过 IPC 这道窄门；前端收到后还得**一个字符一个字符地翻译回二进制**（`atob` + for 循环）。等于来回搬两趟大件，还把翻译官（主线程）累趴下——这几百毫秒里 UI 是卡的。

**修复方案**：Rust 下载后**落盘缓存 + 授权 asset 协议**，只回传一个文件路径；前端转成 asset URL 直接显示。**IPC 不再传任何图片字节，主线程不再 atob。**

```rust
// src-tauri/src/commands/image.rs
#[tauri::command]
pub async fn fetch_remote_image(app: AppHandle, url: String) -> Result<String, AppError> {
    // ...原有下载 bytes 逻辑保留（含 10MB 上限、UA、超时）...

    // 落盘缓存：以 URL 哈希命名，已存在则跳过写盘
    let cache_dir = app
        .path()
        .app_local_data_dir()
        .map_err(|e| AppError::Native(e.to_string()))?
        .join("remote-image-cache");
    fs::create_dir_all(&cache_dir)?;
    let ext = mime_to_extension(&content_type);
    let file_name = format!("{:x}.{}", url_hash(&url), ext); // url_hash: 简单稳定哈希
    let cached = cache_dir.join(&file_name);
    if !cached.exists() {
        fs::write(&cached, &bytes)?;
    }

    // 授权 asset 协议作用域
    app.asset_protocol_scope().allow_file(&cached)?;

    // 只回传路径（几十字节），不再回传 base64（十几 MB）
    Ok(cached.to_string_lossy().to_string())
}
```

```typescript
// 前端 image.ts：getRemoteImageDisplaySrc 拿到路径后转 asset URL，删掉 atob 链路
import { toAssetUrl } from '../../../../services/tauri/asset';
// fetcher 返回值从 base64 dataURL 改为文件路径
// dataUrlToBlobUrl() 整个函数可删除
```

**注意点**：
- 缓存目录建议加 LRU / 上限清理（可复用现有 50MB 预算思路），避免无限膨胀。
- `mime_to_extension` 已存在（[document.rs:164](../src-tauri/src/commands/document.rs#L164)），可复用或下沉为公共函数。
- 本条是 Rust + 前端联动改动，改动面较大，建议放在前面几项稳定后再做。

**提速说明**：以 10MB 图片为例——IPC 数据量从 ~13.3MB 字符串降到几十字节路径；主线程 `atob` 循环（百万次级）彻底消失；图片改由浏览器内核从磁盘流式加载。打开多远程图的文档提速最明显。

## 四、中优先级问题

### 4.1 问题 #5：字体启动 IPC 传数 MB 字节

**现状证据**：[fontLoader.ts:69](../src/services/fontLoader.ts#L69) `readFontBytes` 走 IPC 取字体字节 → [:45](../src/services/fontLoader.ts#L45) `new FontFace(family, bytes)`。CJK 字体动辄 8-15MB，每次启动 / 切字体都要 IPC 搬一遍。

**根因（大白话）**：字体文件明明已经躺在本地磁盘上了，却还要先通过 IPC 把几个 MB 的字节**整个搬进前端内存**，再交给浏览器。等于「东西就在仓库里，却非要先扛到办公室再用」。

**修复方案**：改用 **CSS `@font-face` 注入 + asset URL**，让浏览器内核自己从磁盘读字体，IPC 只传一个路径。

```typescript
// src/services/fontLoader.ts
import { convertFileSrc } from '@tauri-apps/api/core';

async function registerFontViaCss(family: string, cachedPath: string): Promise<boolean> {
  const assetUrl = convertFileSrc(cachedPath);
  const style = document.createElement('style');
  style.textContent = `@font-face {
    font-family: "${family}";
    src: url("${assetUrl}");
    font-display: swap;
  }`;
  document.head.appendChild(style);
  try {
    await document.fonts.load(`16px "${family}"`);
    return document.fonts.check(`16px "${family}"`);
  } catch {
    return false;
  }
}
// readCache 里优先 registerFontViaCss，失败再回退现有 registerFontFromBytes
```

**前置条件（已核实，全部满足）**：
- font-cache 目录已在 `assetProtocol.scope`（v1.2.13 加）
- CSP `font-src` 已含 `asset:`（v1.2.30 加）
- CSS `@font-face` 的 `url()` **不走 CORS**（v1.2.33 血泪教训，W3C 标准行为）

> ⚠️ **高风险提示**：字体加载在本项目有「连修四版才修对」的历史（见 AGENTS.md 经验沉淀）。此项**必须在 `tauri build` 的 prod 二进制里验证**（dev 不附加 CSP，验证不了），并**保留 `read_font_bytes` 作为 fallback**。若 prod 验证不顺，宁可维持现状，不硬上。

**提速说明**：IPC 从传数 MB 字节降到传一个路径字符串；字体由内核流式读盘，启动与切字体的首屏渲染更快。前提是 prod 验证通过。

### 4.2 问题 #6：`resolve_image_display` 无缓存

**现状证据**：[document.rs:300](../src-tauri/src/commands/document.rs#L300) 每张本地图片每次渲染都重新 `canonicalize` + `metadata` + `allow_file`；前端调用点在 [MarkdownEditor.vue:451-460](../src/components/Editor/MarkdownEditor.vue#L451-L460) 的 `setLocalSrcResolver`。[image.ts:367-384](../src/components/Editor/tiptap/extensions/image.ts#L367-L384) 的 `dataset.prevLocalSrc` 只能防**同一个 img 元素**重复解析，文件切换 / 编辑器重建后全部重来。

**根因（大白话）**：同一张图的路径解析结果明明不会变，却每开一次文档、每渲染一次都重新走一遍 IPC + 磁盘校验。图文档里有 N 张图，就是 N 次往返。

**修复方案**：前端加**会话级 Map 缓存**，key 用 `src|docPath|storagePath`，文件切换时清空。

```typescript
// src/components/Editor/MarkdownEditor.vue
const resolvedImageCache = new Map<string, string>();

setLocalSrcResolver(async (src: string) => {
  const storagePath = settingsStore.settings.imageStoragePath;
  const docPath = fileStore.currentFile.path;
  const cacheKey = `${src}|${docPath ?? ''}|${storagePath ?? ''}`;
  const hit = resolvedImageCache.get(cacheKey);
  if (hit) return hit;
  try {
    const resolved = await resolveImageDisplay(src, docPath, storagePath);
    const url = toAssetUrl(resolved.path);
    resolvedImageCache.set(cacheKey, url);
    return url;
  } catch {
    return null;
  }
});

// 文件切换 / 存储路径变化时清空缓存
watch(
  () => [fileStore.currentFile.path, settingsStore.settings.imageStoragePath],
  () => resolvedImageCache.clear(),
);
```

**说明**：Rust 侧 `allow_file` 幂等，重复授权无害；缓存只是省掉重复的 IPC 往返与磁盘校验。若与问题 #2 的 `resolve_image_display` 异步化叠加，效果更佳。

**提速说明**：多图文档首次打开仍需 N 次 IPC，但**之后每次切回 / 重渲都是零 IPC**。图文档越多、切换越频繁，收益越大。

### 4.3 问题 #7：字数统计全文拷贝

**现状证据**：[editor-metadata.ts:15-18](../src/components/Editor/tiptap/editor-metadata.ts#L15-L18)

```typescript
export function getEditorWordCount(editor: TiptapEditor): number {
  const text = editor.state.doc.textContent;   // 全文拼一个大字符串
  return text.replace(/\s+/g, '').length;      // 再正则生成一个新字符串
}
```

**根因（大白话）**：为了数有几个字，先把**整篇文章复印成一张超长纸条**（`textContent`），再把纸条上所有空格剪掉、**重新拼一张**（`replace`）。两次全文拷贝，大文档每次防抖触发都来一遍，内存和 CPU 都花在复印上。

**修复方案**：遍历文本节点逐段计数，**不产生全文大字符串**（每段文本节点都很小）。

```typescript
// src/components/Editor/tiptap/editor-metadata.ts
export function getEditorWordCount(editor: TiptapEditor): number {
  let count = 0;
  editor.state.doc.descendants((node) => {
    if (node.isText) {
      // 只在单个文本节点（小字符串）上去空白计数，避免全文拷贝
      count += (node.text ?? '').replace(/\s+/g, '').length;
      return false;
    }
    return true;
  });
  return count;
}
```

**提速说明**：内存峰值从 O(全文长度 × 2) 降到 O(最长单个文本节点)；大文档字数统计的 GC 压力显著下降。已有 150ms 防抖兜底，二者叠加更稳。

### 4.4 问题 #8：OutlinePanel scroll-spy O(n)

**现状证据**：[OutlinePanel.vue:22-38](../src/components/Editor/OutlinePanel.vue#L22-L38) `updateActive` 每帧 `for` 循环遍历**所有标题**，每个都 `view.domAtPos` + `getBoundingClientRect`。已有 rAF 节流（[:40-46](../src/components/Editor/OutlinePanel.vue#L40-L46)），但一帧之内仍是 O(n) 次 DOM 查询。

**根因（大白话）**：滚动时每帧都把**全部标题挨个量一遍身高**，就为了找「视口顶部之上最后一个」。标题越多，每帧量得越久。而其实标题位置是有序的，完全可以**二分**，不用挨个量。

**修复方案**：二分查找激活项（标题按文档序排列，`top` 单调），把每帧 O(n) 次 `getBoundingClientRect` 降到 O(log n) 次。

```typescript
// src/components/Editor/OutlinePanel.vue
function updateActive() {
  const view = props.editorRef?.getEditorView?.();
  if (!view || !scrollContainer || props.items.length === 0) {
    activePos.value = null;
    return;
  }
  const top = scrollContainer.getBoundingClientRect().top + 88;

  // 二分：找「top <= 阈值」的最后一个标题（位置随文档序单调）
  let lo = 0;
  let hi = props.items.length - 1;
  let current: number | null = null;
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;
    const dom = view.domAtPos(props.items[mid].pos);
    const el = dom.node instanceof HTMLElement ? dom.node : dom.node.parentElement;
    if (!el) { lo = mid + 1; continue; }
    if (el.getBoundingClientRect().top <= top) {
      current = props.items[mid].pos;
      lo = mid + 1;
    } else {
      hi = mid - 1;
    }
  }
  activePos.value = current;
}
```

**提速说明**：`getBoundingClientRect` 会触发样式计算，调用次数从每帧 n 次降到 log n 次。标题几十上百个的长文档，滚动帧率更稳。标题少的文档收益有限，故列中优先级。

### 5.3 问题 #11：焦点模式每次按键重建 decoration

**现状证据**：[paragraph-focus.ts:31-65](../src/components/Editor/tiptap/extensions/paragraph-focus.ts#L31-L65) 缓存命中条件是 `activeBlock + docSize` 都不变；**每次按键 docSize 都变** → 缓存必失效 → `state.doc.forEach` 重建全部顶层块 decoration（[:49](../src/components/Editor/tiptap/extensions/paragraph-focus.ts#L49)）。
